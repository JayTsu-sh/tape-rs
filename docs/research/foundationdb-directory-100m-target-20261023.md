# 亿级文件目录的目标设计（2026-10-23）

2026-10-23 三节点隔离验收：在 207–209 的独立数据目录和端口 `45150` 运行 FDB 7.3.78，3 个协调者、`double` 复制、每进程 4 GiB 内存；`status details` 报告 3 台机器、复制 Healthy、容忍 1 台故障。写入合成受管命名空间、池、卷放置、已验证空卷扫描和未决请求后，停止 207 的 FDB 进程；在 208/209 上读回元数据，旧 owner 发布被拒，新 owner 发布一次且重试幂等。逐台恢复并调高内存后复制重回 Healthy；目录原语测试在三节点运行通过。该集群的文件备份恢复至独立本机 FDB 实例后，终态校验通过。测试仅涉及合成元数据，未连接生产 `ltfsd` 或磁带；没有亿级容量、网络分区、备份自动化和真实介质提交证据的验收，不能据此切换生产权威。

2026-10-23 当前代码切片：可选 `fdb` feature 下的 [`managed_catalog`](../../src/managed_catalog.rs) 提供稳定文件 ID、目录 inode、按父目录/名称排序的目录项、当前版本、物理副本、按卷反向索引、owner epoch 和幂等提交。新命名空间以 `Building` 状态导入，冻结后核对独立源摘要和结构关系，通过后才能用 `seal_import` 开放查询；未完成时返回 `Incomplete`。普通提交须先持久登记请求，发布时在短事务内检查请求代次、命名空间、物理库 serial、owner、卷代数及扫描 ID、父目录、预期版本和同名冲突，再原子更新索引与操作标记。目录及按卷枚举使用上限 1000 的 keyset 分页。

[`control`](../../src/managed_catalog/control.rs) 以 `U/<ns>/<真实物理带库序列号>`、`T/<ns>/<pool UUID>` 和 `X/<ns>/<pool 名称>` 记录逻辑命名空间的带库成员及池基础配置（名称、单带文件数软上限）。`update_pool` 要求 revision 逐次加一，并在事务内比较上次读到的完整记录；池记录与名称索引一同更新，旧名称可重新使用，重复请求识别为已完成，真正过期的更新和改走又改回的 ABA 请求被拒绝。新增的受管命名空间用 `a/<ns>` 不可变标记区别于旧实验命名空间；`b/<卷 UUID>` 记录 `(ns,pool UUID,真实 serial,条码)`，`c/<真实 serial>/<条码>` 在全局唯一地反查卷。放置登记在单事务中检查库/池归属、卷和条码唯一性及卷尚未开始扫描，重复登记幂等；相同真实 serial 可参与多个逻辑命名空间，但同一物理库的同一条码不能被两个命名空间或卷认领。`CommitReceipt` 现有可选 `pool_id`，受管命名空间准入与发布在各自事务内校验 pool、namespace、卷和 serial 一致；旧实验命名空间也不能对已绑定卷准入或发布。已绑定的卷不能由另一 serial 开始扫描。pool/库列表保持有界 keyset 分页。pool 与条码归属按卷记录，不在每个文件或副本行重复存放；每次准入/发布增加少量点查，不产生随文件数增长的额外控制索引。

`VolumeExtentCache::file_by_path` 使用本地 SQLite 路径唯一索引定位 UID，再复核该文件的不可变证明；`resolve_data_file` 与 LTFS 读路径一致，只跟随一层卷内相对符号链接，拒绝越根、断链、链式链接和非空但无 extent 的文件。`ManagedCatalog::resolve_read` 先取得 FDB 已就绪的逻辑文件、副本及放置，再用同一卷扫描来源打开本地缓存，核对实际数据文件 UID/长度后返回物理读取计划。真实 EE 索引夹具的用户别名→`.LTFSEE_DATA` 文件已通过测试；这不涵盖 EE 保存目录/符号链接对象的 `gpfs.*` 元数据语义。返回计划后执行器仍必须持有 Raft owner/PR、重新确认介质身份和扫描资格；当前生产 `ltfsd` 尚未调用该计划。

`resolve_path(namespace, byte_path)` 现在在同一 FDB 读事务中解析目录项、inode、文件 head、当前物理副本、Ready 扫描来源及磁带放置/条码归属。受管卷从登记放置起持有 `W/<ns>/<卷 UUID>` 不可用标记；重扫及取消期间保留，验证并原子切换 Ready 后清除。缺失目录项只在该命名空间没有不可用卷时返回 None，避免把尚未完成的扫描误报成 404；已有其他卷的可读文件仍可读取。这个标记是每卷一条控制记录，不随文件量增长；旧 `catalog/18/` 隔离数据不迁移。该 API 尚未接入生产 HTTP/FUSE，也没有为符号链接、删除墓碑与完整文件属性建立运行时映射。

上述记录仍属隔离原型。当前键前缀为 `tape-rs/catalog/22/`，pool 记录有单调 revision、完整池策略及节点组引用索引，准入和物理副本显式记录内容摘要算法；旧 `catalog/21/` 实验数据不迁移；inode 格式新增属性，head 和卷扫描主记录格式未改。**生产 `ltfsd`、HTTP/FUSE、Raft/SQLite 管理归属和执行器尚未切换到这套权威**，也尚未将实际库存、真实 LTFS 索引证据和 owner/PR 执行资格接入生产登记入口。旧实验命名空间仍走旧放置规则，不能和新受管命名空间混用同一批真实介质；全面迁移需盘点并导入全部介质归属，再原子切走现有池/磁带权威。

`catalog/22/` 的 `NodeAttributes` 版本化编码精确保留 LTFS 只读位、五个时间字段、fileuid、原顺序 xattr 和符号链接目标。文件收据携带属性摘要，准入指纹绑定该摘要，发布时属性随 inode、head、副本和操作标记在同一事务落库；普通文件还核对 LTFS fileuid 与索引哈希属性，符号链接的摘要可来自目标数据文件。目录与根目录有属性导入入口，命名空间摘要覆盖完整 inode，`resolve_path`/`resolve_read` 返回属性。编码属性不超过 64,000 字节时内联于 inode；超过后以 64,000 字节为一块存于同一命名空间，inode 保留长度、块数及 SHA-256 摘要，写入和更新与 inode 在同一事务完成，读取与校验须核对完整块序和摘要。当前单节点属性上限为 4,000,000 字节；超限会拒绝而不会截断。207 历史 `directory.db` 的只读抽样中，最大 metadata 为 590,725 字节，故采用分块；生产导入前仍须扫描所有真实 LTFS 索引，确认该上限足够。隔离单节点故障重启已覆盖大属性读回；三节点新分块布局的故障切换仍待最终复验。现有生产 HTTP/FUSE 尚未使用它。

`catalog/13/` 原型新增 `(serial,barcode)` 全局磁带分配键：先事务性保留 namespace/pool，不需要预先知道卷 UUID；核对介质后须以当前 owner epoch 将卷 UUID 同时写入分配记录、卷主记录和条码反向索引。已绑定分配即使反向索引缺失也禁止直接解绑；未绑定分配可解绑，未绑定卷不能准入文件提交。相同请求可幂等重试，跨命名空间/池争夺同一条码拒绝。此原型尚未核对真实带上 UID 和 LTFS 源证据，也尚未接入现有 `tape assign`；**生产解除未绑定预留也必须先证明该带从未开始媒体写入或已完成结果未定对账**，生产解绑还必须核对未决写入、扫描和活副本。直接让 Raft 和 FDB 同时接受 `tape assign` 会形成双权威，不能作为生产接线方式。

`catalog/14/` 允许 `begin_managed_import` 创建不可见的受管候选，并在 Building 阶段登记真实带库、池、条码预留与经 owner 栅栏的卷绑定；文件和控制查询在 seal 前仍返回未就绪。新 `e/<ns>/<serial>/<barcode>` 索引使废弃候选可有界定位其全局条码声明；普通清理遇到归属时停下。必须在当前 owner 栅栏、候选副本清空、卷扫描全部退役且卷反向索引清空后，显式 `release_discarded_tape` 才能释放全局分配和放置键；随后可续清其 namespace 控制记录。候选导入的介质写入是否发生仍由调用方独立核对，不能凭 FDB 空记录推断安全。此流程已在隔离 FDB 用文件候选导入和废弃路径测试，尚未连接生产媒体扫描器或 ltfsd。

卷重扫现在使用独立 `VolumeScan { generation, id }`，**同一 LTFS 代数可有不同扫描 ID**。就绪记录、物理副本、提交指纹和反向索引均绑定扫描 ID，当前键前缀为 `tape-rs/catalog/22/`；早期隔离原型格式没有迁移。扫描状态持久化为 `Building→Verifying→Verified→Ready→Retired`；不匹配时进入 `Rejected`，候选也可取消为 `Retired`。相同 token 可在客户端重开或 owner 接管后续扫；另一候选不能覆盖当前扫描。就绪切换原子退役旧扫描，旧副本及旧游标失效；取消只作用于匹配的候选，并保留未就绪屏障和已观察代数；不能据此恢复旧索引可读性。新的扫描须验证完成后才能重新开放，且不得退回较早代数。写入同时检查扫描状态，状态、就绪/取消与 owner epoch 检查使用事务冲突范围，阻止旧 owner 和在途旧扫描继续发布。操作去重指纹不包含执行凭据 owner epoch，新 owner 重放同一操作时可识别已应用结果；尚未应用的操作仍必须通过当前 owner 栅栏。每次最多 1000 条的 `purge_retired_volume_index` 只清理退役扫描的反向索引，保留小型状态墓碑，阻止清理后复用扫描 ID。

隔离单节点 FDB 7.3.78 测试覆盖重复提交、同代数替换、客户端重开/owner 接管、取消与在途事务冲突、旧游标/旧副本失效、分批清理及 1001 项分页；三节点验证了单进程退出期间的元数据读写和独立备份恢复。**这仍不是生产目录切换**：模块未接入 `ltfsd`、HTTP/FUSE，现有 Raft/SQLite 仍在用；现有逻辑目录尚不能原地流式对账，重扫测试在新命名空间导入候选。卷扫描清单和当前原语模型的命名空间结构已由模块校验；独立源扫描真实性及真实 LTFS 凭据仍由调用方保证，废弃导入候选已有下述有界清理；在用命名空间的过期物理描述已有下述有界压缩，副本 ID 墓碑和操作标记已可按显式请求水位清理，自动轮换/保留预算已有下述独立维护驱动，生产任务联动仍未实现。池的完整策略及生产归属迁移、带上 UID、墓碑、目录重命名、批次发布、任务、备份自动化、迁移及亿级/物理验收仍未完成。

## 已实现的卷扫描完整性校验

[`verification`](../../src/managed_catalog/verification.rs) 的 `ScanDigest` 接受独立源扫描的提交记录，按 `(namespace UUID, file UUID, copy UUID)` 的字节顺序流式计算计数和 SHA-256 摘要链，只持有上一个键、计数及 32 字节摘要。源扫描可在节点 SQLite 暂存后按此顺序外排序；**不能把 FDB 已导入数据反读出来充当期望清单**，否则会掩盖漏导入。摘要绑定卷 UUID、代数、扫描 ID 和每项不可变元数据（包括名称/父 inode、版本、大小和内容哈希），不包含执行凭据 owner epoch/操作 ID。它是元数据清单摘要，不是磁带文件内容读回。

`freeze_volume_scan(expected)` 冻结候选并固定期望值，与在途导入冲突；重复调用不能更换期望或重置进度。`verify_volume_scan_page` 每事务最多检查 100 个副本，批量发出点查后按键顺序汇总，原子持久化已核对计数、摘要和游标；不在每次导入时更新同一个全局计数键。进度属于每卷扫描，重新打开客户端或 owner 接管后从已提交游标继续。反向索引存入导入时的 32 字节指纹，校验同时读取并核对其不可变物理副本记录，避免可变逻辑 head/路径影响清单校验；新增空间为每副本 32 字节，假设 1 亿文件各两份副本则增加约 6.4 GB 逻辑数据，尚未计复制和引擎开销。

扫描全部核对且计数/摘要均匹配才进入 `Verified`，`mark_volume_ready` 只接受此状态。计数或摘要错误进入 `Rejected` 并保持读写禁用；物理副本缺失/结构不一致返回错误，进度不前进；修正期望须取消后启动新扫描 ID。隔离测试已覆盖 1001 条实际导入记录的多页核对、重开客户端/owner 接管后续验、期望不可变、冻结与取消事务冲突、计数/摘要错误及缺失副本。下述两阶段测试只覆盖单节点 FDB 重启后的受管放置和请求恢复；尚未测量亿级吞吐、长距离 FDB 时延或扫描中途的服务重启恢复，命名空间中不属于卷副本清单的空目录和额外条目由下节的独立校验处理。

## 已实现的命名空间封口校验

[`namespace_verification`](../../src/managed_catalog/namespace_verification.rs) 通过 `NamespaceDigest` 流式生成按 inode UUID 排序的源摘要，包含规范根、空目录、所有文件的父/名称及 head（当前版本、大小、当前副本 ID）。`freeze_namespace` 固定期望并阻止整个候选命名空间的逻辑写入；`verify_namespace_page` 以每事务最多 100 项/父链步数持久化校验进度。验证顺序为 inode、目录项、head、副本和根连通性：双向核对父子关系，检查 head 的当前副本存在且版本一致，检查额外 head/副本不存在孤立逻辑引用，并验证未退役扫描的卷反向索引。计数/摘要不符进入 Rejected；结构错误保持未就绪，进度不前进；完整通过后进入 Verified，`seal_import` 才允许切换 Ready。

连通性阶段不用 inode 永久缓存深度，也不为目录改名更新后代。它在临时键空间按需记录已证明到达根的节点，父链栈与游标可跨事务恢复，最多保留 1024 层栈；超深父链和环被拒绝。批量预取当前节点及父节点的证明，避免逐节点范围读取。证明只用于被冻结的候选验证；终态后可通过 `purge_namespace_proofs` 每事务最多 1000 项清理，正在验证时禁止清理。临时证明约占每 inode 55 字节逻辑键值，1 亿 inode 约需额外 5.5 GB 临时逻辑空间，尚未计复制、引擎和进度记录；无需在进程内装入全树。

文件 head 增加当前副本 ID，记录由 16 字节增至 32 字节，1 亿文件增加约 1.6 GB 逻辑数据；这样每文件可在有界读取中验证当前副本，无须枚举该文件全部历史副本。该阶段原型键格式曾升级到 `catalog/10/`，目前已为 `catalog/21/`；旧隔离格式未迁移。源摘要与上述索引校验针对当前目录模型，已包含 LTFS fileuid 和首选内容摘要类型，仍缺完整 xattrs、符号链接及删除/墓碑导入。

逻辑完整性和介质可用性分别判断：退役扫描的旧卷反向索引可已被清理，已知文件的 inode/head/物理描述仍可保留，读取时继续检查卷状态，返回暂不可用；不能因带不在线而把已知文件当作不存在。隔离测试覆盖 1103 个 inode（含 1001 个空目录）跨页核对、客户端重开续验、150 层父链栈恢复、超过 1024 层拒绝、目录环、15 类缺失/额外/不一致记录或错误摘要、证明分批清理及退役卷不可读时仍保留逻辑文件。该测试仍不是亿级吞吐、真实 LTFS 扫描导入或生产权威迁移验收。

## 已实现的废弃候选清理

[`cleanup`](../../src/managed_catalog/cleanup.rs) 提供显式 `discard_import` 和 `purge_discarded_namespace`。仅 Building、Verifying、Verified、Rejected 可以转为永久 Discarded；Ready 即使为空也禁止废弃，未知命名空间不会自动创建墓碑。待处理请求或保留引用存在时，废弃和清理均拒绝；登记/引用新增与废弃通过非 snapshot 状态键及范围读取形成冲突。冻结/验证失败的命名空间仍可查询待处理请求并在确认执行器已停止后取消，避免冻结后无法清除阻塞；请求窗口不能在冻结期改变。废弃不自动取消卷扫描、不修改卷就绪指针，也不触及磁带。

副本清理须先经 owner 栅栏流程显式退役候选引用的卷扫描。每次最多删除 100 条命名空间记录，另可删除至多 100 条对应卷反向索引；先完整校验副本页，再安排删除，避免错误返回时提交半页删除。按副本、inode、目录项、head、操作结果、临时证明、校验进度、准入、保留引用、维护策略/配额/代次/进度和请求窗口十四类前缀处理，保留永久 S 废弃墓碑。无 offset、全局操作扫描或全量内存清单。`complete` 只说明这些命名空间前缀已清空；若人为损坏造成 V 存在而 R 缺失，仍须单独退役该扫描并运行卷反向索引清理，不能声称全库无孤立记录。

操作身份现在是 `(namespace,request_epoch,operation_id)`，不是全局任务 ID。P 按此顺序组织，可以随废弃候选或按过期水位有界清理，无需再增亿级反查索引。相比早期全局 UUID 操作键，命名空间和代次增加 24 字节，终态标签再增加 1 字节；假设同时保留 1 亿条操作结果，增加约 2.5 GB 逻辑数据，未计复制/引擎。保留永久废弃墓碑，废弃检查先于终态命中，确保旧重放不能复活；namespace ID 禁止复用。

Ready 命名空间临时证明删空后清其续验进度；退役卷 V 删空后清卷续验进度，G/S 墓碑及未就绪屏障保留。测试覆盖 1105 个 inode、2521 条原有候选记录及新增维护控制/分片计数记录和 103 条卷反向索引、97 项批次及重开续清、损坏不提交前项删除、跨命名空间同操作 UUID 保护、待处理请求/保留引用阻止废弃及终态临时数据清理。

## 已实现的在用命名空间历史描述回收

[`history`](../../src/managed_catalog/history.rs) 的 `compact_superseded_copies(namespace,after,limit)` 只对 Ready 命名空间执行，每事务最多检查 100 条副本记录。只有版本严格低于当前 head、卷扫描身份匹配且已 Retired、并未被当前就绪指针引用的描述可以回收。当前版本主副本及所有同版本备用副本保留；最新已知文件即使只在退役扫描上，也保留 inode、目录项、head 和完整物理描述，继续区分“已知但暂不可用”和“不存在”。当前主副本必须存在、请求代次已开放且与 head 版本一致，否则整页拒绝回收。

R 的完整描述按摘要类型分别为 SHA-256 105、MD5 89、未知 73 字节，均包含 8 字节请求代次、8 字节 LTFS fileuid 和 8 字节文件长度；1 亿个当前副本因此比不存长度增加约 0.8 GB 逻辑数据，用于独立核对索引文件长度。未过期旧版本压成 17 字节墓碑（`0xff`、8 字节版本、8 字节请求代次），并清对应 V；水位推进后，过期旧版本可直接删除完整描述，已压缩墓碑也可删除。当前版本即使来自已过期请求，仍完整保留。副本 ID 由请求身份确定，且旧请求在终态查询前就被窗口拒绝，因此删标记不会开放旧身份复用。`physical_copy` 对合法旧版本墓碑返回 None，若墓碑指向当前副本/当前版本则报损坏；命名空间副本验证接受合法旧版本墓碑，活动卷扫描验证仍要求完整描述。该阶段格式为 `catalog/10/`，当前使用 `catalog/21/`；未迁移旧隔离数据，生产未接入。

回收在非 snapshot 事务内批量读取并对同文件/扫描点查去重，全部检查通过后才写或删；head、窗口、保留引用及就绪指针变化会与在途回收冲突。初版只要该命名空间存在任何保留引用就暂停历史描述回收，避免把引用保护误作“仍可删历史”；这不是文件系统快照，不能固定可变 head/目录视图。采用 keyset 游标，零回收页仍可能有下一页；客户端重开可继续。`next=None` 是本轮到末尾，不是所有并发更新的快照；新插到游标之前的记录下一轮处理。`compacted/forgotten` 是最终成功尝试的统计，未知提交后重试可能少计，不能作持久审计计数。

以 SHA-256 副本为例，105 字节描述压成 17 字节减少 88 字节，每条 R 逻辑键值从 174 降为 86 字节；假设 1 亿条未过期历史描述均为 SHA-256，减少约 8.8 GB，仍留约 8.6 GB 墓碑；请求过期后这些历史 R 可删除。V 若尚未先行清理，每条另减少 141 字节，1 亿条最多再减约 14.1 GB。均不含复制、引擎、日志，也不是实测空间收益。当前版本 R 不因请求过期删除。

测试保留了 1007 条副本中 1001 条未过期描述压缩、跨页/重开续扫、零回收页、重复扫描、当前/备用副本及退役介质最新文件保护、活动扫描旧版本不压缩、head/就绪指针并发冲突和 11 类结构损坏整页拒绝；新请求测试另覆盖过期完整描述及既有墓碑删除。备用副本是有效记录形态夹具，生产 add-replica API 尚未实现。

## 已实现的请求准入、过期水位与历史引用

[`requests`](../../src/managed_catalog/requests.rs) 为每个命名空间初始化 `RequestWindow { first_retained:1, accepting:1 }`，请求代次独立于设备 owner epoch。前者决定逻辑重放保留范围，后者仍必须来自真实 Raft/PR fencing；owner 接管可换执行凭据继续相同请求。每文件提交只读取窗口；准入/完成更新所选分片的计数，不逐文件改写同一窗口或全局计数键。

| 键 | 当前用途 |
| --- | --- |
| `E/<namespace>` | 16 字节窗口，只在创建、轮换/过期时修改。 |
| `I/<namespace>/<epoch>/<operation_id>` | 32 字节准入摘要加完整准入参数 JSON（含分片许可），解码上限 8192 字节；保存计划路径、文件、预期版本、目标卷/扫描、大小和哈希及原执行凭据，支持脱离节点 SQLite 恢复。 |
| `P/<namespace>/<epoch>/<operation_id>` | 41 字节终态：Applied/Cancelled 标签、指纹、已应用版本；已取消请求不会返回成功写入。 |
| `F/<namespace>/<epoch>/<reference_id>` | 显式历史引用，阻止对应代次过期，并暂时阻止该命名空间历史描述回收；没有自动 TTL。 |

请求代次为每条完整副本描述和压缩墓碑各增加 8 字节；若有 1 亿当前文件各两份副本，完整描述约增加 1.6 GB 逻辑 value。I 只应覆盖尚未解决的执行工作，而非全库文件目录；已有下述原语层的准入预算，长期未决的媒体对账仍须接入生产任务服务。

使用流程如下：

1. 读取当前准入代次，持久保存稳定 operation ID、预期文件版本与计划参数；通过 `derive_copy_id` 生成副本 ID。它使用带域分隔的 SHA-256 前 128 位绑定命名空间、文件 ID、请求代次、operation ID 和预期版本，owner 凭据不参与。不同请求/代次不能把已回收的旧副本 ID 作为可自由复用参数；安全性依赖该摘要的抗碰撞性。
2. **实际介质操作前**调用 `register_request`。同请求同参数幂等，变造参数拒绝；生产 `publish/publish_imported` 不会自动补准入。`pending_requests` 每页最多 100 个，校验完整参数、指纹及键身份后返回；别的客户端/新 owner 可从 FDB 恢复，须完成真实接管 fencing 并重新核对媒体证据后继续，不能直接使用记录中的旧 owner 凭据。
3. 验证介质提交后才发布，原子写 head/副本/V/终态并清 I。结果未定时保留 I 对账；只有执行器已停止或 fenced、且证明未发生介质提交后，才能 `cancel_request`；已提交工作必须完成发布，再由后续显式业务操作处理，不能用取消遗忘提交。取消还检查当前 owner，原子记录 Cancelled 并清 I，阻止与发布竞争产生两个终态。FDB 内部栅栏不能替代外部机械/写入停止证明。
4. `rotate_request_epoch(expected)` 以 CAS 开启下一代并关闭旧代的新准入；旧代已登记请求仍可完成/取消，同请求重试可识别已登记/已完成结果。读取者/导出任务如要保留现有历史，先登记稳定引用 ID，再访问描述，结束后显式释放；引用不能恢复登记前就已回收的数据。
5. 达到业务响应查询保留期后，显式调用 `advance_request_floor(expected,before)`。水位单调前进且不能越过当前准入代次；跨旧代次范围中只要还有 I 或 F 就拒绝。登记/引用与轮换/过期发生竞争时，通过窗口键和范围冲突重试，不维护单键全局逐请求计数；人工推进是管理覆盖，可早于自动保留期限，不能把它当作自动保留期保证。
6. 过期检查先于 P 终态查询。无论 P/R 是否已清理，旧请求统一返回 RequestExpired；客户端不得把同一不明结果请求自动换代重发。`purge_expired_requests` 每事务最多清 1000 条过期终态；历史副本回收按前节规则删过期旧 R。过期代次的“查不到终态”不能解释为“从未执行过”。

隔离 FDB 测试覆盖 1001 个完整待处理请求的 97 项分页/客户端重开恢复和发布、1002 条过期终态的分批清理；未准入拒绝、未完成请求/历史引用阻止过期、轮换与在途登记冲突、引用与水位推进冲突、取消/发布竞争、旧 owner 取消拒绝、冻结候选仍能恢复/取消待处理请求、未解决引用阻止废弃、清理前后重放均过期、已回收 ID 复用拒绝、过期描述/墓碑删除且当前文件保留。

## 已实现的自动维护驱动与准入背压

[`maintenance`](../../src/managed_catalog/maintenance.rs) 增加可单独运行的 `MaintenanceDriver`。`maintenance(namespace)` 显式认领维护者，返回的驱动支持 `poll` 和 `run_until(stop)`；新认领者在 FDB 原子更新 owner token，旧驱动被 fenced。token 只管理目录维护，不能替代设备的 Raft/PR owner。驱动尚未由 ltfsd 任务 leader 启动。

默认每命名空间策略如下，仅允许在尚无请求/副本/引用的初始窗口配置，运行中不静默改变保留协议：

| 约束 | 默认值 | 达限行为 |
| --- | --- | --- |
| 代次时间 | 1 小时 | 封口并尝试开启下一代 |
| 终态自动保留期 | 代次封口且排空后 24 小时 | I 未决或 F 引用存在时不推进水位 |
| 待处理准入总量 | 4096 | `AdmissionLimited`，不登记新 I |
| 每代次累计准入 | 100 万 | 已完成/取消也不返还本代次预算；等待轮换 |
| 同时占用预算的代次数 | 128（可配置 2..4096） | 暂停新准入，已准入工作仍可完成 |

预算最多拆成 64 个分片，精确分摊总额度；每次准入按 operation ID 选择起点，最多探测 8 个分片。先 snapshot 探测，再对选中分片非 snapshot 校验和增计数。局部热点或分片额度组合可能在全局仍有余量时保守背压；`accepting_requests` 是窗口/总量诊断，不承诺某个请求必能获得许可。I 的准入摘要绑定分片许可和逻辑参数。发布和取消在完成所有校验后，与 P/I 更新原子释放待处理额度；相同终态重试不会重复释放。累计额度只在该代次过期且控制记录回收后删除。

新增 `A/<ns>` 存 40 字节策略，`K/<ns>` 存 84 字节固定进度及至多一条 R 游标，`D/<ns>/<epoch>` 存 32 字节代次时间，`B/<ns>/<epoch>/<shard>` 存 8 字节累计数（epoch=0 为待处理数）。没有按亿级当前文件复制控制计数；I 最多解码 8192 字节，默认 4096 个待处理请求的 value 上限约 33.6 MB，P 每条逻辑键值 102 字节。128 代、每代 100 万准入的 P 理论上界约 13.056 GB，未计引擎/复制/其他目录记录；这是保守预算上界，不是实测容量或吞吐保证。

维护按五阶段循环：代次生命周期、过期 P 清理、历史 R 压缩/清理、过期 B/D 清理、封口代次排空观察。每个数据页最多 100 项，历史回收规则沿用前节；排空观察分别检查每个封口代次，避免旧代次逐个串行累加 24 小时。过期但未清完 P/B 的 D 仍占代次预算，先清 P，再清 B，最后清 D，防止清理停摆时仅推进水位就绕开容量约束。维护只改元数据，不自动取消请求、释放引用、退役卷扫描、丢弃导入或格式化磁带。

维护时钟由驱动已确认步骤间的单调 elapsed 累加，时钟、阶段、R 游标、排空游标、步序和上一报告与该步修改在同一事务持久化。未知提交重试同一序号返回原报告，不再重复加时间；跨客户端接管继承进度。节点墙钟跳变不触发过期，停机或失败造成的时间少计会延后清理。保留期从维护确认封口且无 I 时开始，因此只提供保守的最短自动保留时间。`run_until` 有工作时以短间隔推进，每五个无进展步骤后降低频率；没有测得亿级清理吞吐。

`maintenance_status` 返回策略、当前窗口、待处理数、本代累计准入、是否开放及最近一步报告；`pending_requests` 可有界定位未决请求。新增 `maintenance_diagnosis` 在一个 FDB 读取事务内检查占预算最久的代次，区分已过期 P 结果积压、B 计数积压、D 描述待清、未决 I（返回并校验一个 operation ID）、代次尚未观察排空、F 历史引用（返回并校验一个引用 ID）、剩余保留时间、可过期及当前准入暂停。诊断只做有限点查/首项范围读取，不逐文件扫描；它是某一时刻的观察，显示的请求/引用 ID 不构成取消或释放的证明。`history_references(namespace,after,limit)` 每页最多 100 个引用 ID，校验键、空 value 和请求代次，可跨客户端用独占游标续读；水位越过游标代次时拒绝旧游标。

最近一步报告不是完整历史审计。原型 F 只保存引用 ID 和代次，**尚不能从引用自身查到任务所有者、创建时间或证明其已退出**；孤立引用的任务归属对账、告警及人工处置仍未完成。F 引用数量及 G/S 墓碑没有纳入请求预算；活动扫描上的旧物理描述也不会自动退役，因此不能据此声称所有目录历史总空间都已硬限额。

隔离测试覆盖并发准入、累计额度不返还、损坏许可拒绝且无半提交、幂等完成/取消、封口背压、排空后保留、长期 I/F 保护、多个代次独立排空、201 条终态积压的有界续清、未知提交重试不重复计时、维护者接管、101 条当前文件的跨页游标恢复及保护。另有 `tests/fdb_restart.rs` 的分阶段忽略测试：单节点 FDB 的正常停服和 SIGKILL 重启各通过一次；三节点集群在停止一台协调者/数据节点时，剩余两台核对未决请求并完成新 owner 发布。`audit` 阶段在独立恢复实例核对终态。此测试不模拟媒体提交证明，也不覆盖数据损坏或网络分区。生产 ltfsd/HTTP/FUSE、真实执行器的准入/对账/取消、任务 leader 生命周期和策略权威迁移仍未接入，不能宣称生产写入已有这些保护。生产备份恢复必须冻结写入、核对设备 fencing 与磁带内容，旧窗口恢复不能直接开放重放；备份自动化、亿级吞吐和物理验收仍待完成。

## 设计要求与权威

1. 一个逻辑文件只有一个当前身份和版本；文件、目录、墓碑、副本及库/池放置关系可跨节点、跨物理库查询。`lookup` 的“不存在”必须有完整索引水位支持；索引重建或滞后时返回“暂不可判定”，不能返回假 404。
2. 一盘磁带上的 LTFS 索引是介质内容的最终证据，但不能独自恢复全局逻辑库、池政策、跨库副本意图和已删除关系。**FDB 是共享管理元数据的唯一写入权威**；它要独立备份，不能把“可从磁带重扫”当成完整灾备方案。
3. Raft 仅保留小规模、设备所有权相关的状态：节点/库配置、owner 轮次、PR/fencing 进度和控制日志。池政策、磁带管理归属、文件、副本、文件任务及其索引不再以 Raft 日志逐条复制，也不在每个节点复制一份完整 SQLite 目录。把现有这些字段迁走时，必须切换所有管理/调度读写点，禁止双权威。
4. 本机 SQLite 只保存节点独有且有界的状态：执行步骤日志、尚未上传的扫描/发布暂存、幂等 outbox、可丢弃的热缓存及其水位。它不是全局文件目录的恢复来源，也不应随集群文件总数线性增长。
5. FDB 失联时，停止新的写入、删除、迁移、回收与管理归属变更的准入；已解析到明确 `(file_id,version,replica,hash)` 的在途读取可按设备 owner 和介质校验规则完成。不能使用无水位本地缓存接受新变更。

物理带库始终用真实 changer serial 标识和选择；覆盖多个物理库的逻辑库/命名空间另有稳定 ID，不能把显示名或某个物理序列号当作逻辑库的永久主键。

以上是目标决策，不是对当前实现的描述。FDB 的有序键范围与同事务多索引更新适合目录，然而它不提供 SQL/全文检索或跨磁带写入原子事务。[数据建模](https://apple.github.io/foundationdb/data-modeling.html)、[Anti-Features](https://apple.github.io/foundationdb/anti-features.html)

| `files`、`files_by_tape` | FDB 权威的逻辑 inode、目录项、版本、墓碑、物理副本及按卷反向索引。 | 路径解析、目录分页、副本放置和按卷枚举走不同键前缀；更新当前版本及二级索引在同一短事务内完成。 |
| `staging`、`staging_by_batch` | 本地 SQLite/分段文件保留执行器暂存和上传 outbox；FDB 保存全局操作意图、批次状态及已完成介质提交凭据。大批次先写不可见候选，再以小事务发布批次标记。 | 不把百万条目录项塞进 Raft 或一个 FDB 事务；失败后根据操作 ID、带上索引和 FDB 标记恢复，未发布部分不可见。 |

## FDB 键布局与查询接口

下列前缀是逻辑示意，不是已定的二进制编码：

| 访问方式 | 记录/索引示意 | 设计理由 |
| --- | --- | --- |
| 库、池、卷政策 | `policy/library/<id>`、`policy/pool/<id>`、`media/volume/<uuid>`，以及按物理库/池枚举的索引 | 控制规模随库、带、池数增长。更新政策要 CAS 版本，并核对执行器 owner 轮次。 |
| 命名空间与目录 | `node/<namespace>/<inode_id>`、`child/<namespace>/<parent_inode>/<name>` → inode ID | 稳定 inode 避免在亿级目录树上因目录重命名改写所有后代的完整路径键；路径按分量解析，`readdir` 按父 inode 范围分页。必要时使用有水位的路径热缓存。 |
| 当前版本与墓碑 | `head/<namespace>/<inode_id>` → 文件版本/墓碑/操作 ID；大批次另有 `candidate/<batch_id>/...` | 普通版本切换与目录项和副本引用一起提交；大批次先保留旧 head、再按发布标记解析候选。墓碑保留足够长以阻止旧卷扫描“复活”文件。 |
| 物理副本 | `copy/<file_id>/<copy_id>` → 卷 UUID、索引代数、扫描 ID、带上 UID/路径、哈希及真实 `(round,seq)`；`by_volume/<uuid>/<scan_id>/<file_id>/<copy_id>` → 引用；卷放置记录提供库序列号、池 ID 和条码 | 通过 `by_volume` 有界枚举回收/迁移候选；未移除全部反向引用前禁止解除卷放置，避免亿级副本重复存储库、池和条码。副本必须指向已验证卷代数。 |
| 操作与导入 | `op/<operation_id>`、`batch/<batch_id>`、`volume_scan/<uuid>/<scan_id>` | 意图、介质凭据和发布标记分开；重复请求用稳定 ID 去重。导入中的记录不参与正常查询。 |

公开的目录模块接口应表达领域操作，例如 `resolve(path)`、`list_children(parent,cursor,limit)`、`publish_tape_commit(receipt)`、`replicas_on_volume(volume,cursor,limit)`、`set_policy(expected_version,change)` 和 `task(id)`；FDB 键、重试、分页及水位隐藏在模块内。目录重命名使用稳定 inode 和父子关系，需在事务内检查目标冲突与祖先环；超深目录要有明确深度/路径长度限制。没有理由把完整路径复制到每一个副本键中。[FDB 范围与索引建模](https://apple.github.io/foundationdb/data-modeling.html)

## 磁带提交、结果未定与大卷对账

正常写入先在 FDB 用短事务登记稳定操作 ID、预期旧版本和目标卷；执行器经 Raft owner/PR fencing 后写磁带。只有读到可验证的 LTFS 提交证据，才用短 FDB 事务检查 owner 轮次和预期版本，原子发布 `head`、副本、反向索引与任务终态。owner 接管时应先把新 Raft 轮次写入 FDB 的该库 fencing 键；旧轮次的发布事务必须失败。FDB 与磁带没有跨系统原子提交：磁带已提交而 FDB 发布失败时，任务保持结果未定，重新读取磁带索引和操作 ID 后幂等发布；绝不盲目重写或把源副本删除。[FDB 未知提交结果](https://apple.github.io/foundationdb/developer-guide.html)

单次 FDB 事务不能承载百万文件变更：当前官方上限是受影响数据 10 MB、值 100 KB、约 5 秒；官方还建议超过 1 MB 的事务重新设计。普通文件提交保持小事务；大批次在版本化候选键空间按有界块写入，完整校验后仅切换小型发布标记，读取路径对 `head`/目录项选择已发布版本，不能直接从尚未更新完的单值 `head` 读“当前”。批次预留受影响路径，阻止并发版本更新越过批次标记；后台分批清理旧候选。[FDB 已知限制](https://apple.github.io/foundationdb/known-limitations.html)、[子空间间接引用模式](https://apple.github.io/foundationdb/subspace-indirection.html)

首次导入可在新命名空间代数的独立键前缀下分片建立记录及索引、核对计数/摘要后切换 `active_namespace_generation` 入口指针；读取模块先解析入口指针再访问 `node/child/head`，旧代数待游标和读取引用失效后分批清理。这需要预留旧、新两代的临时容量。日常整卷重扫先把扫描结果流式落入本地暂存并计算差异，再分批更新 FDB：卷状态为 `reconciling` 时，其副本不用于新的写入、删除或回收判定；读查询如依赖该卷要返回暂不可用或改选已确认副本，未知路径不能被断言为不存在。所有差异、墓碑和反向索引完成后再标为 `ready`。这牺牲重扫期间该卷的可用性，换取明确的一致性语义；要用现场规模测量窗口长度。扫描过程必须避免把全部 LTFS 索引和结果一次载入内存。

迁移先发布并验证目标副本，再改变源副本的逻辑状态；对本次允许压测的高文件量带，保留源介质数据，**不运行格式化或会自动格式化的回收路径**。即使全局反向索引显示零引用，也须与当前卷索引/版本对账后才能作破坏性回收；受本次用户限制的介质没有格式化许可。

## 亿级容量、热点与恢复验收

以 `N=1 亿` 个当前文件、平均 `r=2` 份副本作**假设**，仅 inode、目录项、head、副本主记录和按卷反向索引就至少约 `3N + 2rN = 7 亿` 个逻辑键；尚未计池/任务、墓碑、旧代数、额外索引及离线观察。若假设每键值对平均 200 字节，仅这五类记录便约 140 GB 逻辑数据，三副本的原始数据至少约 420 GB，实际磁盘还要计存储引擎、日志、临时代数和备份。这不是现场测量，必须先采样真实路径、元数据长度、目录深度、副本数和更新率。官方报告的是特定硬件/工作负载的性能，不能作为本项目亿级文件吞吐承诺。[FDB 数据建模](https://apple.github.io/foundationdb/data-modeling.html)、[性能说明](https://apple.github.io/foundationdb/performance.html)

- `readdir` 和按卷枚举只提供带大小上限的 keyset cursor，不用 offset，也不跨页维持超过 FDB 事务寿命的读取事务。普通目录遍历在并发修改下允许重新开始或弱一致；审计/导出使用固定已发布代数。极热的单目录、单卷和全局计数不能依赖每文件更新一个共享键；需根据压测再划分前缀或分片聚合。[分段范围读取](https://apple.github.io/foundationdb/segmented-range-reads.html)、[热点建议](https://apple.github.io/foundationdb/data-modeling.html)
- 若一文件对应一任务，任务历史也可能达到亿级。FDB 保留正在执行及约定查询期内的终态；完成后的详细步骤按可查询要求归档/压缩并分批清理，不能让本地执行日志或 FDB 热任务前缀无限增长。保留期限与历史查询合同需在实施前确定。
- 目录数据库只是瓶颈之一：现有 `LtfsVolume::mount` 和 `VolumeState` 会持有大索引/目录树，`catalog sync` 也以完整卷索引遍历。[卷挂载](../../src/ltfs/volume.rs)、[状态模型](../../src/core/volume_state.rs)、[离线同步](../../src/catalog/sync.rs) 亿级方案必须另做每卷索引流式解析、按需装载或外存结构，并测内存峰值；仅迁到 FDB 不构成亿级验收。
- `LtfsIndex::scan_full_reader` 已提供完整索引的逐条回调：文件 UID、时间、扩展属性、符号链接及 extent 保留，目录按子节点之后输出，返回值只保留头部和根目录属性；增量索引及未知元素明确拒绝。合成百万文件解析单独运行 12.52 秒、峰值 RSS 9616 KiB（单机测试进程，非现场/端到端指标）。回调可能先于后续 XML 错误发生，消费者必须写入不可见候选并在整个扫描、计数及介质证据校验成功后才发布。当前 `LtfsVolume::mount`/恢复、`catalog sync`、执行器与 FDB 导入尚未使用此入口，增量链重放、完整元数据映射和海量文件按需读取仍待实现；不能据此宣称亿级卷已可挂载。
- `VolumeExtentCache` 新增可重建的节点本地物理位置缓存：恢复候选记录索引构造原文 SHA-256，缓存构建只读重定位同一构造，核对结束文件标记、卷 UUID/代数/自指针/原文摘要，逐文件分批写临时 SQLite，成功后以硬链接无覆盖地发布单文件；文件 UID 和所有 extent 数值以无损十进制保存，并按文件证明核对读取结果。缓存不保存或代替 FDB 逻辑目录、LTFS 全部元数据，也不参与当前 `ltfsd` 读写；增量链与非完整索引不能直接建立它。构建会改变驱动器读位置，生产调用须在 owner/PR 资格与设备操作串行化之下。合成 100 万空文件/零 extent、本机 `/work/tmp` 单进程实测：XML 75,778,683 字节、SQLite 92,291,072 字节，缓存构建 56.42 秒、包含生成 XML 的测试总耗时 61.46 秒、峰值 RSS 14,800 KiB；该分布远轻于真实大文件多 extent/xattr，不能外推为亿级或物理带速率。崩溃遗留临时文件清理、真实介质重读及生产接线仍未验收。[源码](../../src/catalog/volume_extents.rs)
- `catalog/15/` 的物理副本加入 8 字节 LTFS `fileuid`（1 亿当前副本约增加 0.8 GB 原始 value，未计 FDB 索引/副本/存储开销）。准入记录、重试指纹和已发布副本都携带同一 UID；0 拒绝，u64 范围无损。它把 FDB 的逻辑文件身份与本地 extent 缓存的卷内 UID 接起来，但目前还没有生产调用者，也未验证卷内 UID 唯一性或把扫描摘要和缓存 manifest 绑定。下一版模型已提供显式哈希算法/未知状态；完整 LTFS 元数据映射和读时验证仍待完成，不能给只有 MD5 或未记录哈希的 EE 文件伪造 SHA-256。旧 `catalog/14/` 隔离数据不迁移。
- `catalog/16/` 进一步将内容摘要设为 `Sha256`、`Md5`、`Unknown` 三态。LTFS xattr 提取会校验长度/十六进制/重复属性，双哈希优先选 SHA-256，未知状态明确不构成内容校验证据；副本值按类型分别占 97、81、65 字节，避免在亿级 MD5/无哈希副本上填充无意义的零字节。准入 JSON、操作指纹和副本值均绑定算法，旧 `catalog/15/` 隔离数据不迁移。当前只有目录原语和提取函数，`ltfsd` 未调用，尚不能声称 EE 文件已导入或已按 MD5 完成读时验证。
- `catalog/17/` 对每个受管卷扫描保存不可变 `K/<volume UUID>/<scan ID>` 索引证明：格式版本、LTFS 分区/起始块、索引构造原文 SHA-256；卷 UUID 和代数由键及扫描记录约束。登记前须用同一证据打开由完整索引构建的本地 extent 缓存，owner epoch 和待扫描指针在同一 FDB 事务中核对；相同证明可幂等重试，冲突证明拒绝。受管卷缺失/损坏证明时冻结、就绪、物理副本读取和按卷枚举都拒绝；旧就绪结果重试也不会把缺失证明当成功。读路径可从 FDB 查询证明，再以该证明打开节点缓存，缓存中的 UID、路径、长度、extent 逐条校验。隔离 FDB 服务停服重启后已验证该链路；真实生产执行器尚未调用 `build_confirmed`→登记，FDB 收据与索引中的每个 UID/路径/长度也尚未逐条独立对账。K 与 G 扫描墓碑暂一同保留，长期清理策略待设计。旧 `catalog/16/` 隔离实验数据不迁移。
- `catalog/18/` 在每条 R 物理副本值中持久化 8 字节文件长度。受管卷逐页验证必须提供同一索引证明对应的本地缓存，并在推进 FDB 游标前逐项核对 fileuid 是否存在、索引长度是否等于 R 长度；缺缓存不能退化成仅比较 FDB 自身摘要。普通实验命名空间仍可使用原分页接口。此阶段没有证明逻辑路径等于 LTFS 物理路径：EE 的用户路径可能是指向 `.LTFSEE_DATA` 的符号链接；导入该映射和完整属性仍是生产切换前的必做项。旧 `catalog/17/` 隔离实验数据不迁移。
- `catalog/20/` 的池记录增加介质限制、挂载上限、节点组、低空间和无空间告警开关与阈值，连同名称、文件数上限和 revision 一起接受 CAS 更新。取值约束对齐现有管理命令；编码带版本和精确长度校验。旧 `catalog/19/` 只包含名称/文件数上限，实验数据不迁移。此模型仍缺生产运行时调用及节点组、驱动资源的 FDB 权威迁移，不能据此改变实际调度。
- `catalog/21/` 在每个命名空间登记默认 `G0` 和可创建的节点组，并给每个池维护一条按节点组反查的引用索引。创建/更新池必须先确认目标组存在；更换组、池记录和引用索引在同一事务中完成。删除节点组会以非快照范围读检查仍有无池引用，默认组不得删除；废弃候选清理包括两类新键。旧 `catalog/20/` 实验数据缺引用索引，不迁移。节点成员与驱动资源实际分配仍缺 FDB 权威和运行时接线。
- 以真实路径长度分布建立 1 亿文件合成数据，测点查、深目录解析、千万子项目录分页、按卷枚举、并发写入、重命名、百万文件带扫描、重复/中断导入、FDB 恢复及备份恢复；验收指标包括 p95/p99、导入速率、冲突/重试率、空间峰值、恢复时间和“查询暂不可判定”比例。目标数值须依据业务 SLA 与实测确定，不凭空规定。
- FDB 连续备份和恢复演练是上线门槛；FDB 备份与 Raft 小控制快照不是一个原子快照。恢复后暂停设备变更，核对 Raft owner/fencing、FDB 元数据与磁带索引，再开放服务。不能指望从亿级本地 `directory.snap.db` 拉一份文件恢复。[FDB 备份文档](https://apple.github.io/foundationdb/backups.html)

此设计的直接迁移顺序是：先补齐领域目录模块与 FDB 模型并以合成亿级数据压测；再迁移池/磁带政策的写入权威；随后双读核对文件、副本、任务与介质凭据；最后切断文件级 Raft 投影和整库 SQLite 快照。每一步都要证明结果未定恢复、旧 owner 拒绝发布、无假阴性查询和跨库副本安全，再把相应旧路径删除。当前第一切片仅在可选 feature 下提供未接入运行时的 FDB 原语，未触及现场设备。

## 已确认完整索引的本地导入清单

可选 FDB 模块的 `ImportSpool` 把恢复协议已经确认的完整 LTFS XML 逐条写入节点本地 SQLite，保存根、目录和文件的完整 `NodeAttributes`、文件长度及 UID。它用唯一约束拒绝重复路径/UID，拒绝不安全路径、截断 XML、增量索引、超出属性上限以及原文 UUID/代数/自指针/SHA-256 不符。只有全部解析完成并按路径重新计算行摘要后，才以硬链接无覆盖方式发布权限 `0600` 的清单文件；重新打开时再次全量校验行摘要和计数。最多 1000 项一页的路径游标可供后续 FDB 导入从断点续读，父目录在路径顺序中先于子项。`build_confirmed` 可在 owner/PR 和设备串行化保障下，从已确认的物理索引只读构建；调用会移动驱动器读位置。清单是可重建的导入证据，不是用户查询权威或卷 extent 缓存。

本机合成 100 万空文件/1 根目录实测：XML 75,778,684 字节、清单 SQLite 83,156,992 字节；构建、重新打开并完整校验用时 91.44 秒，测试进程总 96.44 秒，峰值 RSS 61,540 KiB。IBM EE 完整索引夹具和约 590 KB 属性样本通过分页、重开及损坏拒绝测试。这个结果没有覆盖 FDB 网络导入、多个卷合并、真实 AA00 索引或生产查询。最初把本机 glibc 2.39 测试程序送到 207 时因 207 的 glibc 2.34 在加载阶段失败；随后用 Zig 按 glibc 2.34 交叉编译，测试产物最高只需 `GLIBC_2.34`，在 207/208/209 三节点各以 EE XML 夹具通过 1/1。三机程序哈希相同（`f3da97b50157c98fc31e1455b8a5cd7939bc899e9b25a9c1f498c854845f09e8`），测试程序及临时 SQLite 已清理，正式服务未改。这是现场软件验收，不是物理磁带扫描。下一步需要读取真实高文件量卷的索引，再由独立来源摘要验证 FDB 候选并做唯一权威切换；高文件量磁带不得格式化。

一盘带的清单不能直接变成用户目录：同一路径可能留有多盘旧副本，当前目录按 `tapers.version` 的 `(round,seq)` 以及墓碑选择可见版本；IBM EE 的用户路径还可能只是指向 `.LTFSEE_DATA` 的符号链接。跨卷归并必须先独立确认每盘身份、版本/墓碑次序、别名目标与既有 `directory.db` 的当前记录，再生成唯一逻辑 inode 和物理副本关系。存在并列、缺证或来源不完整时保持候选不可见，不能按扫描顺序覆盖 FDB 当前 head，也不能把单卷清单的成功当作整库迁移完成。

### 本地双投影绑定门槛

`record_volume_source` 登记受管卷扫描来源之前，必须同时打开与同一个 UUID、代数、索引位置及原文 SHA-256 绑定的 `ImportSpool` 和 `VolumeExtentCache`。清单重新按路径流式校验全部行摘要；随后逐文件按 UID 查询 extent 缓存并校验文件证明、路径、长度和符号链接，最后要求两边文件总数相等。逐行处理的内存上限取决于单个文件的属性和 extent 数，不会把一页最多 1000 个大属性对象同时放进内存。任一文件缺失、多出或不一致都拒绝在 FDB 写入来源记录。新参数 `LocalVolumeSources` 明确提供两个本地路径。

这一步只证明同一卷的两个本地投影一致；它仍不能证明现有 `directory.db` 的当前逻辑版本、跨卷墓碑、EE 用户别名与物理对象的全局归并。实际运行时也还没有调用这个登记入口，不能因此开放生产 FDB 目录。真实高文件量磁带仍不得格式化。

本机 100 万空文件的双投影基准通过：清单构建加重新校验 95.60 秒，extent 缓存构建及逐文件对账后总计 260.83 秒；源 XML 75,778,684 字节、清单 83,156,992 字节、缓存 92,291,072 字节。`/usr/bin/time` 包裹 `cargo test` 记录的峰值 RSS 820,828 KiB 包括编译子进程，不能当作测试程序本身的峰值。直接运行已编译测试程序复测，清单阶段 89.90 秒、双投影总计 252.55 秒，**测试进程峰值 RSS 29,764 KiB**。此结果仅是单机百万条、无真实数据 extent 的合成负载，不能据此推算现场磁带读取或 1 亿文件端到端性能。

### 跨卷逻辑候选与离线目录对账

本地导入清单版本 2 额外建立按用户逻辑路径排序的紧凑 `catalog_candidates`。普通文件、目录从完整 LTFS 节点投影，`.tapers/deleted/<hash>` 墓碑根据已核对的 `tapers.deletedPath` 投影到被删路径；内部 `.tapers` 节点不作为用户候选。清单在发布前计算候选总数和独立摘要，重新打开时验证节点和候选两套摘要。版本与墓碑属性格式不合法或同一逻辑路径来源冲突时拒绝构建。旧版本 1 清单需从已确认索引重建；这只是节点本地可重建文件，不涉及生产目录格式。

`ImportReconciler` 对所有已确认卷按 `(pool UUID, 用户路径)` 做有界多路归并，每卷只缓存 8 个紧凑候选。最高 `(round,seq)` 唯一者成为当前版本；最高版本在不同卷并列时，缺独立副本意图证明，拒绝自动选择。按条码、池、卷 UUID 和代数先核对离线 `directory.snap.db` 的全部磁带，再逐行核对当前文件/目录/墓碑的条码、代数、长度、SHA-256、版本、删除位和完整 LTFS 可见属性。目录快照多行、缺行、属性不符或来源未覆盖都拒绝；审计产出应用水位、路径数、墓碑数与摘要，摘要同时绑定所有磁带的清单原文和候选摘要。整个审计使用一个 SQLite 读事务。运行中 WAL 库不是稳定审计输入；生产切换还须冻结相应写入并确认快照水位与当时 Raft/FDB 状态一致。这个对账入口仍只读，不会自动向 FDB 发布候选。

合成百万空文件直接运行测试程序：XML 75,778,684 字节、版本 2 清单 134,897,664 字节、extent 缓存 92,291,072 字节，清单构建/重开 125.82 秒、两个本地投影与逐文件对账后总 288.69 秒、单卷百万候选逐路径归并 13.91 秒，整个测试 307.64 秒，进程峰值 RSS 30,296 KiB。增加约 51.7 MB 本地清单空间换取跨卷路径归并时不反复解码百万条完整属性。该样本仍无真实大属性分布，且尚未测量多卷对账与 FDB 网络导入吞吐；不能外推至亿级生产 SLA。

### 审计后不可见 FDB 候选暂存

`ManagedCatalog::stage_audited_reconcile` 先要求目标命名空间处于受管 Building 状态、所有本地清单重新验摘要，然后将跨卷合并结果与离线 `directory.snap.db` 全量对账。审计水位、磁带来源及逐路径摘要作为不可变 FDB 暂存清单身份；相同证据重试逐字节核对已写候选，变化的来源或快照拒绝复用。全部候选写完后再次核对本地清单和离线目录，再写完成标记。中断时只留下不可见的部分记录，重新调用同一入口可续验；`seal_import` 遇到任何暂存清单都拒绝开放命名空间，必须由后续物化与独立验证流程显式解除。

暂存键按命名空间和连续序号排列，记录保留赢家和全部旧副本、墓碑的池/卷/代数/版本/物理路径。常见不超过 64,000 字节的候选使用一个 FDB value（含长度与 SHA-256）；更大的候选拆成最多 64,000 字节的 value，最后一块与行头原子提交，重读时逐块验长度与摘要。键不携带完整路径，避免 LTFS 最长路径超出 FDB 键长度。显式废弃候选时，既有有界清理流程先移除暂存分块与行，再清理暂存清单；永久废弃标记仍保留，防止旧请求复活。这个阶段只是来源证据的持久化工作集，不是用户可查的 FDB 目录：尚未建立稳定 inode、当前墓碑 head、完整属性、读路径与任务/池唯一权威，也没有声称亿级 FDB 写入性能已达标。后续物化不能把这些原始暂存键直接当成公开文件查询结果。

2026-10-24 验证：本机隔离 FDB 完成合成目录暂存、超 100 KiB 单路径分块重读和服务重启后续读；正式 207–209 FDB 集群的每个节点各自完成合成目录暂存/清理，另由 207 写入、208 重读、209 废弃并有界清理同一暂存行。三节点测试后均显示数据库可用且健康、数据 healthy、3 进程、容忍 1 台机器故障。现场测试只用随机合成命名空间，没有导入真实介质、接线到生产 `ltfsd` 或操作 `/dev/sg*`。目前常见候选虽只占一个 FDB 键，写入仍是逐路径事务；亿级规模必须测网络吞吐并设计有界批量写入，不能由百万本地清单结果外推。

发布前增加 `verify_staged_import`：要求已完成清单和 Building 状态，从 FDB 按最多 64 行一页重读候选，核对连续行号、池/路径严格排序、每行内容或分块摘要、墓碑数和全局行摘要；最后再次核对清单与状态。缺行、多行、坏分块或乱序都拒绝。这为后续物化提供独立重读门槛，但当前不调用物化/发布；每个大行需另行读取分块，亿级目录仍需测实际网络吞吐。207 暂停 FDB 时，208 在两节点可用状态完成同一候选的重读，209 完成清理；207 恢复后集群重回 3 进程、healthy、Fault Tolerance 1。故障窗口内 `healthy=false`、数据暂为 initializing、Fault Tolerance 0，故不能把“可用”报告成“健康”。

新写入的暂存行使用版本 2：在当前赢家的来源列表后，附上从已核对本地 `ImportSpool` 逐路径读取的完整 `NodeAttributes` 原始编码（五个时间、fileuid、原顺序 xattr、符号链接等）。写入前重建候选并与紧凑索引逐字段比较，重读时再次从属性重建并比较；属性字节参与行摘要和全局摘要。行仍按 64,000 字节切块，不把大属性塞入单个 FDB value。版本 1 的候选行仍可读路径和重试清理，但 `staged_entry` 对其返回未完成，后续物化不能无属性发布。这个改动使后续物化不依赖运行时留存节点 SQLite 清单；目录快照与带上来源的审计仍是独立前置条件。合成 80 KiB xattr、目录墓碑的逻辑/物理类型差异，以及 207 写入后停服、208 重读全部属性、209 清理均已通过；正式 `ltfsd` 尚未接线，也未在真实高文件量磁带上验证属性分布和 FDB 容量预算。

### 经证明的 Building 目录物化

`confirm_staged_import` 在 Building 状态下重新按页读取全部暂存行、校验全局摘要，并要求每一行都有可重建介质候选的完整属性；同一事务核对受管标记、状态和未变化的完成清单，写入私有证明键。旧版本 1 行即使摘要正确也不能取得该证明。证明与暂存清单不一致时拒绝物化，废弃命名空间的有界清理会删除证明键。

`materialize_staged_directory` 只投影当前未删除的目录，先确认池已在受管命名空间登记，再将池 UUID 作为命名空间内的虚拟根目录名称。目录 inode 由命名空间、池 UUID 与完整逻辑路径的域分离 SHA-256 确定；重试得到同一个 inode，父目录缺失或身份冲突时拒绝。目录使用赢家的完整 LTFS 属性，按暂存路径顺序处理时父目录先于子目录。此阶段文件、旧副本和墓碑仍仅在私有暂存键里，`seal_import` 仍由暂存清单阻止，Building 命名空间的普通查询不可见。

这只是可重试的单目录写入原语，不是亿级目录导入吞吐的证明。后续必须建立有界批量/游标执行、保留 `(round, seq)` 和墓碑语义的文件 head 与物理副本模型、完整物化进度及扫描证明，并将池/任务/读写入口迁为 FDB 唯一权威；在这些工作完成且现场验收前，不得切换生产 `ltfsd`。

### 全部来源的 LTFS fileuid

版本 2 暂存行只保存当前赢家的完整属性，因此只有赢家的 LTFS fileuid；同一路径的旧副本缺少 fileuid，不能安全关联到各卷的本地 extent 缓存。新写入的版本 3 行对每个来源按条码重新查询已核对的 `ImportSpool`，从原始完整节点重建候选并逐字段比较，再将该来源的 fileuid 与候选一起写入 FDB。UID 与候选顺序对齐，当前赢家的 UID 还要与完整属性中的 fileuid 一致。格式继续使用现有分块与行/全局摘要，重试逐字节校验；旧版本 1/2 行可读路径并清理，但不能取得版本 3 所需的物化证明。

这使多卷副本具有后续读定位所需的介质节点身份，尚不证明这些来源已登记为 FDB 卷放置/扫描、也没有把旧副本发布为可读取 copy。下一步需将每个来源与 FDB 中已核验的卷索引身份及 owner/PR 证据绑定，再设计含真实 `(round, seq)`、墓碑与全部副本的目标 head；不能把 fileuid 当成卷归属或内容校验的替代品。单卷仍按版本 2 的方式查询赢家完整节点，多卷每条旧来源增加一次查询；必须重新测量多卷场景与 FDB 写入吞吐，不能引用版本 2 的百万文件计时作为新流程性能。

### 暂存来源与受管卷身份的只读核对

`verify_import_source_binding` 在一个 FDB 读版本中核对 Building 命名空间的受管标记、卷放置及条码反向索引、磁带分配和池归属、真实带库序列号、精确的已就绪扫描以及该扫描不可变的 LTFS 索引位置与 SHA-256。任一身份不一致、扫描正在重建或命名空间已封口均拒绝。它不改变 FDB 键格式，也不授予 owner/PR 执行许可；调用者仍须从恢复确认的带上索引和本地 `ImportSpool`/extent 缓存提供可信来源。隔离 FDB 和 207–209 正式 FDB 的合成数据只证明元数据核对逻辑，不代表真实高文件量卷已接入。

此原语目前按单卷调用，版本 3 暂存行尚未持久记录其扫描 ID 和索引摘要，也没有整批来源证明或最终封口门槛。下一步应为每个卷保存经核对的来源绑定，流式确认全部暂存候选只引用这些卷，在物化与封口时重新验证扫描未变化；必须避免亿级路径流程持有一个长事务或把所有文件读入内存。正式 `ltfsd` 继续使用现有 Raft/SQLite 权威，直到源绑定、文件 head/全部副本、任务、备份恢复及物理验收形成完整切换路径。

`stage_audited_reconcile` 现要求调用者提供与离线 `ImportVolume` 完全一一对应的 `ImportSourceBinding`：按条码、卷 UUID、池、代数和原始索引身份逐项核对，拒绝缺项、重复项与跨命名空间项，并在 FDB 中确认每卷仍处于相同的就绪扫描。进入流式目录审计前、审计完成后且写完成清单前各做一次核对；扫描变为 reconciling 后旧绑定不能重试。此核对不会把卷集合或扫描 ID 持久化为封口证明，因此 `confirm_staged_import` 仍不能凭当前暂存结果发布文件；后续必须补有界的卷绑定记录与独立重验。

废弃候选已有明确的元数据退役路径 `retire_discarded_volume_scan`：仅 Discarded 命名空间且 owner epoch 匹配时，把精确的 Ready 扫描退役并清除 ready 指针；活跃的新扫描必须先按原有取消流程退役。随后才能显式释放条码归属并分页清除候选。它不执行装带、格式化或介质写入，调用方仍须先确认旧 owner/PR 的物理执行许可已撤销。合成双卷测试覆盖缺/重复/错误绑定、扫描变化拒绝、退役权限、重试和完整清理；还需在生产切换流程中接入并验收。

### 可重启的来源绑定证明

流式暂存现在为每个来源卷写入一条私有 `k/<namespace>/<volume UUID>` 记录，包含池、真实带库序列号、条码、扫描 UUID/代数及不可变 LTFS 索引位置和 SHA-256。相同证据可重试，任何字节变化都拒绝复用该候选。完成暂存后，`l/<namespace>` 存储精确暂存清单、卷数及按卷 UUID 排序的来源记录摘要；写入前分页核对 FDB 中没有缺卷、多卷或不同记录。`verify_staged_source_bindings` 可在进程重启后分页重读，逐卷复核当前 FDB 放置/分配/ready 扫描与索引身份，末尾再次核对清单、摘要和 Building 状态。内存与卷数成正比，单次 FDB 事务按页或单卷界定，不与亿级文件数成正比。

`confirm_bound_staged_import` 先独立复核全部来源和版本 3 暂存行，逐候选检查条码、池、卷 UUID 与代数确实属于已绑定来源；随后在一个事务中读取并核对已有目录证明和来源证明，两者均无冲突才写入缺失的证明，避免冲突返回时只提交一半证明。`bound_staged_import_summary` 只读取历史证明，不能替代读时对当前扫描及 owner/PR 许可的重新检查。废弃候选的分页清理包含新 `k/l/n/o` 键。持久化变化仅涉及仍不可见的 `catalog/22` 实验导入候选；旧候选缺少这些键时必须废弃后重新导入，生产 Raft/SQLite 目录和磁带格式均不变。

受管批量导入在写第一条候选前还会落下 `o/<namespace>` 来源绑定要求标记。旧的独立目录确认只接受非受管命名空间；任何受管目录物化都必须在同一 FDB 读版本看到此标记、`j` 目录证明和与 `l` 完成摘要一致的 `n` 来源证明，缺标记的旧受管候选也不能绕过门槛。标记写入前若已有目录证明则拒绝把旧候选补标。`o` 同样随废弃候选分页清理。此门槛没有重新验证当前 ready scan 或赋予介质许可，封口前仍须做独立来源重验和文件/墓碑/全部副本的完整物化证明。

这填补了“重启后无法重建来源集合”的缺口，但尚无文件 head/墓碑/全部物理副本的可恢复物化，也没有把生产 `ltfsd` 的读写和管理权威迁至 FDB。证明写入时与以后介质操作之间还需再次核对 ready scan 和 owner/PR；源变化后的旧证明不应赋予读写许可。亿级导入仍需对当前逐路径事务、属性分块、卷数与 FDB 容量进行正式压力测量。

### IBM EE 别名与物理数据对象

真实 EE 索引夹具表明，用户文件可能是长度为 0 的 LTFS 符号链接，目标位于卷根 `.LTFSEE_DATA/`；别名的 fileuid 与目标的 fileuid 不同，目标才持有实际长度和 extent。`ImportSpool::resolve_file_data` 现在在同一份已确认完整索引内解析该相对路径，拒绝越过卷根、指向其他目录、缺失目标和链式链接，并返回逻辑/数据 UID、数据路径、长度及目标索引中的内容摘要。暂存候选遇到 EE 别名会先验证目标存在。原来暂存版本 3 的 `source_file_uids` 仍是**别名** UID，不能作为读取数据 extent 的 UID；文件副本物化必须另存并验证目标数据 UID/长度/摘要，不能直接复用该字段。

离线清单在流式扫描时保留所有物理 `nodes` 供源校验与定位，但不把 `.LTFSEE_DATA` 及其子路径写入逻辑 `catalog_candidates`；这些对象不能与用户别名同时作为文件发布。索引必须同时有该目录及指向它的 EE 别名，否则因布局不明而拒绝导入，避免误吞同名用户目录。跳过候选在逐节点扫描中完成，不产生最后一次删除海量行的大事务。离线 `ImportSpool` 的 `user_version` 从 2 升至 3，旧清单需由同一已确认的只读 LTFS 索引重建；FDB 键和带上格式均未改变。若目录快照仍按旧口径包含内部数据路径，审计会明确不匹配，必须先核实该快照的真实用户目录语义。此处只用 IBM EE XML 夹具和三节点只读软件测试验证，尚未在真实高文件量带上验收。

受管暂存行现写版本 4：原逐来源逻辑 fileuid 后新增数据类别。直接文件存数据 UID/长度/摘要，EE 别名存不同的数据 UID 与目标真实长度/摘要，普通非 EE 符号链接显式标为尚未可物化，目录及删除标记不产生数据副本。赢家完整 LTFS 属性仍另存。行摘要与分块摘要覆盖这些字段，按页重读时校验来源种类、UID、长度与候选哈希；`confirm_bound_staged_import` 要求每行都具备版本 4 数据身份。私有 `o/<namespace>` 来源绑定门槛现在值为版本 `4`，旧空值门槛不能通过受管确认或物化；旧候选须废弃后从已确认索引重建。普通非 EE 符号链接保留在候选中，但其后续读语义仍需单独物化设计，不能当作普通数据文件副本发布。

这一步仍只是不可见暂存，不等于用户可读文件：`source_file_uids` 保留逻辑节点 UID，新的 `source_data` 才提供数据 extent UID。下一步须将这两种身份、真实 `(round, seq)`、墓碑和全部物理副本映射进 FDB 的 head/R/V 与独立封口证明，并在查询时依次检查就绪扫描和执行者 owner/PR；不能仅凭已确认的暂存行开放生产读写。

后续复核发现版本 4 的 EE 数据来源虽有真实 UID，却未持久保存 `.LTFSEE_DATA` 的目标路径；仅凭 UID 无法在尚未加载完整卷索引的节点上解释别名。因此受管暂存改为版本 5：仅 EE 别名追加真实数据相对路径，直接文件复用候选路径，不为海量普通文件重复存储路径。写入前和重读时校验路径分量、数据目录边界，并用赢家的完整符号链接属性核对目标路径；行摘要覆盖新增字段。旧版本 4 行仍可解码用于检查或废弃，但受管 `o` 门槛升为 `[5]`，旧候选不得授权新物化，需从已核对索引重建。生产 Raft/SQLite 和带上格式未变；这仍未完成文件/墓碑/副本的目标物化。

物理副本值现在可选保存 `MediaProvenance{version:(round,seq),logical_file_uid,physical_path,ee_alias}`。旧副本值仍按原格式解码；扩展格式在固定摘要标志位标记，故尾段缺失不能被误读为无来源的旧副本。副本主体的 `ltfs_file_uid` 始终是真实数据对象 UID；EE 别名逻辑 UID 和 `.LTFSEE_DATA` 路径在扩展尾段，直接文件的逻辑/数据 UID 必须相等。卷放置记录在其反向副本索引非空时不可解除，故库序列号、池和条码由卷放置归一化提供，避免每个亿级副本重复字段。已确认的 extent 缓存核对副本路径、UID 和长度。旧记录缺扩展字段只用于兼容读取，正式切换前仍须逐步补齐运行时新提交的介质来源；当前尚未把暂存来源物化到副本键。

现有 `publish_imported` 仍走普通写入的请求 admission、当前 owner epoch、卷 Reconciling 状态和逐次 head 版本递增路径，且 `encode_copy` 只写旧副本格式。它不能直接承担受管 v5 暂存的离线分页物化：一个逻辑文件可能有跨卷的多个历史物理来源，赢家由介质 `(round,seq)` 决定；墓碑及原生符号链接也不能伪装成数据副本。应提供独立的 Building 导入事务，按稳定 `(namespace,pool,path,source)` 身份幂等写入 node/child、head 或墓碑、全部 R/V 反向记录和介质来源，并仅在卷扫描及来源绑定证明已就绪时接受。每页的完整性还须独立核对，不能因目录已创建或单个副本写入成功就清除暂存封口闸门。

当前已实现一个限定范围的原子文件物化：`staged_data_file_plan` 从已确认的 v5 行和当前就绪卷绑定构造稳定 inode、赢家 head 及全部数据来源的稳定副本 ID；FDB head 的单调序号来自已排序的 `(round,seq)`，原始介质版本保留在每个副本的 `MediaProvenance` 中。`materialize_staged_data_file` 在单个 FDB 事务中重新核对 Building 状态、暂存清单与证明、每个来源的卷放置、分配和就绪扫描，再写 child/node/head、完整属性块和所有 R/V；相同重试逐键核对，部分或冲突写入拒绝。单次最多 32 个数据来源、512,000 字节属性，以约束事务大小；超限候选仍留在私有暂存区。赢家为墓碑/目录时不写文件，任一来源为原生符号链接或删除标记时保守拒绝。EE 别名保留逻辑 UID 和真实 `.LTFSEE_DATA` 数据 UID/路径，按普通数据文件投影。

这一原语只证明单路径原子性，**没有全命名空间完成证明**。暂存清单仍阻止 `seal_import`，Building 目录不可供普通查询使用。正式切换前仍需分页处理高副本数、墓碑及原生符号链接，独立核对每个暂存路径与目标 head/R/V/属性、卷扫描和反向索引总量，再设计可恢复的封口协议；还需迁移生产 `ltfsd` 唯一权威及验证亿级吞吐、备份恢复和真实介质故障流程。不得把单文件物化测试当成生产可切换证据。

已增加只读的 `verify_materialized_data_file`，对单个已确认数据文件重建预期投影，在同一 FDB 读事务核对头、子项、inode、完整属性块、每个 R/V 值以及该 inode 下的**精确 R 键集合**。缺失、部分写入或多出 R 均拒绝；副本 ID 重复在计划阶段拒绝。该检查不会修补缺口，也不会写“已完成”标记。它是逐路径诊断与后续分页核验的构件，尚未枚举整个暂存清单或全局 V 索引，且当前只在 Building 状态运行；跨页冻结、孤儿 V 检查和基于独立来源摘要的封口仍待实现。

受管暂存目前还可接收一个显式的节点本地 SQLite 工作目录：同一轮已审计的完整来源逐路径建立稳定 inode、head 和全部预期 R 值，SQLite 以 BLOB 主键在磁盘上排序，进程只保留一条记录和少量卷/池身份。工作文件以 0600 创建，属于可重建离线观察工作集，完成或普通失败后删除；崩溃可能遗留随机命名的文件，需由运维按任务清理。仅当**全部**路径都是当前存活目录或有界全数据文件、没有墓碑/原生符号链接/无法表达的旧来源时，才把命名空间摘要和副本数量/摘要与原暂存清单一起写入私有 `q/<namespace>` 版本 2 证明。旧候选没有该证明或证明版本不同，必须废弃重建；无生产 Raft/SQLite 或带上格式变更。

`freeze_bound_staged_import` 在来源绑定确认后用 `q` 的独立 inode 摘要冻结 Building，再由现有逐页命名空间验证检查 N/C/H/R 的结构、反向 V 对应关系和连通性。冻结后 `verify_bound_import_copies` 以有界 FDB 页重读所有 R 键/值，对照来自离线工作区的有序副本摘要；缺少非当前旧副本也会失败。它还逐个扫描已绑定卷/扫描下的 V 键，核对每条 V 的命名空间、版本、R 值摘要和对应 R 记录，并要求总数与 R 一致；缺失或孤儿 V 均拒绝。通过时私有 `s/<namespace>` 绑定同一 `q` 证明。验证失败不写成功标记，受管暂存清单仍阻止 `seal_import`。当前 R/V 扫描在进程故障后从头重做，跨页使用多个读版本；仍缺持久分页游标、冻结期间的来源扫描再验证和墓碑/符号链接模型。该检查只覆盖绑定卷的指定扫描，不能证明其他卷/旧扫描的全局 V 空间无异常；它是正式封口的必要构件，**还不是可发布证明**。亿级正式切换前须完成持久化批次证明和源扫描变更栅栏，并通过备份/恢复、容量和真实磁带验收。

后续已补墓碑私有投影：由审计过的删除候选与已绑定卷身份生成 `t/<namespace>/<pool UUID>/<SHA-256(逻辑路径)>`，值包含完整逻辑路径、介质 `(round,seq)`、卷/扫描/代数及逻辑 UID。写入前核对 `.tapers/deleted` 物理路径与删除属性；同一事务重验暂存和就绪扫描，拒绝相同路径下的可见 N/H。离线 SQLite 额外对预期墓碑键和值磁盘排序，`q` 证明升为版本 3 并绑定墓碑计数及独立 SHA-256；计数还必须等于旧目录审计值。`verify_materialized_tombstone` 做逐条只读核验，`verify_bound_import_copies` 在写 `s` 前分页扫描全部私有 `t`，缺失、多出或值变化都拒绝。删除路径只建立必要池根，不创建可见文件；Building 阶段依旧不可查询。旧版本 2 的实验性 `q` 须废弃重建，生产目录与磁带格式均未改变。

这仍不构成生产删除语义：运行时尚无墓碑值解码、删除顺序栅栏和可见 head 更新，跨多个 FDB 读版本的完整扫描也不能替代封口时的单一来源快照。`seal_import` 继续拒绝受管暂存；正式 `ltfsd` 仍以 Raft/SQLite 为共享权威。原生符号链接、高副本数、可恢复分页封口、亿级压力、持续备份/恢复及真实高文件量介质验收尚未完成。

### 受管导入的可重启物化游标

为避免亿级导入在进程重启后重扫已经完成的全部路径，`materialize_bound_import_page(namespace, limit)` 按已确认暂存序号每次处理最多 1000 条，仅分发到已验证的目录、数据文件或墓碑物化原语。私有 `u/<namespace>` 游标记录版本、下一条序号和完整 `q` 投影证明的 SHA-256；每一页所有路径成功后才在单个 FDB 事务中推进，同时核对 Building、暂存清单/确认和 `q` 未变化。页内中断最多重放本页，物化写入必须幂等；冲突、缺行或不支持的来源形状不推进游标。`freeze_bound_staged_import` 现在要求游标等于暂存总行数。旧版本 3 的实验性 `q` 候选若没有 `u`，可用相同确认来源从序号零重放；这不会修改磁带或生产 Raft/SQLite。

该游标只是物化进度，不是可发布证明。冻结后仍需独立核对 N/C/H/R/V/T，源扫描变化和多版本跨页读取仍须由最终封口栅栏处理；`seal_import` 继续拒绝受管暂存。当前逐行调用还会重复读取暂存行与来源绑定，亿级吞吐须实测并优化为有界批量读取，不能从游标正确性推断性能达标。

### 跨页副本核验的来源扫描修订号

受管命名空间创建时初始化私有 `v/<namespace>` 为零。已绑定受管卷的扫描真正进入 Begin、Ready 或 Cancel 时，在同一 FDB 事务内递增该修订号；幂等返回和拒绝不递增。`verify_bound_import_copies` 开始前读取修订号，跨页核对 R、绑定扫描的 V 和 T 后，在写 `s` 前的事务内重读它；变化即拒绝本次核验。新的 `s` 为版本 1、八字节修订号及 `q` 的 SHA-256。`inspect_bound_import_copy_fence` 在同一只读事务核对 Verified 状态、暂存及来源确认、`q`、已完成的 `u`、当前 `v` 与 `s`，供诊断。将来的发布事务必须在**自身事务内**重复该栅栏；独立诊断结果随时会过期。废弃候选清理也覆盖 `v`。旧受管实验候选没有 `v` 或仍保留旧 `s` 时不能直接封口，应废弃重建。

这个修订号只覆盖已绑定卷的扫描状态变化；完整核验仍在不同 FDB 读版本上进行，直接越过受管 API 篡改键、未纳入修订号的未来写路径和目标记录并发变化仍需封口事务及写路径审计解决。当前 `seal_import` 继续拒绝暂存候选，不能据此切换生产 `ltfsd`。

封口前置栅栏现还在同一事务读取 `Z/<namespace>` 命名空间验证进度，要求它的期望摘要和最终实际摘要都等于 `q` 中的命名空间摘要，且已经完成连通性阶段；否则单靠 `Verified` 状态与 `s` 不能证明 `q` 就是被冻结核验的目标。事务也检查没有未完成请求或文件引用（`I/F` 前缀），避免把旧导入请求带入可写的 Ready 状态。受管物化本身只在 Building 写目标记录，Verified 阶段通过公开写路径冻结；仍需完成正式封口与暂存行后续清理协议，不能用只读 `inspect_bound_import_copy_fence` 的单次结果授予运行时访问权。

### 受管候选的受限原子发布与暂存回收

`seal_bound_staged_import` 现于**同一 FDB 事务**重验上述 Verified 状态、`Z/q/u/s/v`、来源确认和未完成请求，要求 `q` 的墓碑数为零，才写入持久私有 `w/<namespace>` 封口证明并把状态改为 Sealed。重复发布只接受已有 Sealed 与匹配的 `w/s`，返回未发生新发布。它不会调用非受管 `seal_import`，后者仍拒绝带暂存清单的候选。原生符号链接及超出单文件副本/属性上限的来源在生成 `q` 前已被拒绝，因此不能由此路径发布。保守拒绝墓碑的原因是运行时还不能按介质版本阻止旧扫描复活被删除的路径；不能用只读 T 摘要代替这一语义。

发布成功后，`purge_sealed_import_staging(namespace, limit)` 可在 Sealed 与 `w` 闸门下每事务清理最多 100 条 `g/h` 逐路径暂存行，支持中断后重试。`f/j` 清单与确认、`k/l/n/o` 来源、`q/s/u/v/w` 证明和私有 T、可见 N/C/H/R/V 都保留；这使已发布目录无需永久重复保存每路径的原始暂存值。仍须设计长期证据保留/压缩与正式运行时使用此目录的唯一权威、后续源扫描与删除顺序、生产切换/回退。当前 FDB API 的 Sealed 不等于生产 `ltfsd` 已接入；正式服务依然以 Raft/SQLite 为权威，不能因单独的发布单测切换。

### 物理带库预备路由

`z/<真实带库序列号>` 保存候选 namespace 和单调修订号，仅供切换前发现；它**不授予** `ltfsd` 读写 FDB 目录的权限。预备事务要求候选已受管、Sealed，且 `q/s/v/w` 封口证明与当前来源修订号一致，并确认 `U/<namespace>/<serial>` 成员关系；发现时在同一读事务重复这些检查，来源变化会拒绝返回旧候选。重试同一候选幂等；换候选须对当前修订号做 CAS。删除时保留递增修订号的空路由墓碑，防止旧节点持有的修订号在新候选重建后再次命中。无路由与墓碑对发现 API 均表现为空。这个小键空间按物理库数量增长，不按文件数增长。

预备路由不是活动指针。当前 `ltfsd` 的 Raft 日志仍写每库 SQLite，文件查询仍从 SQLite 构造目录列表。正式迁移需先冻结旧写入与任务执行、证明导入快照覆盖冻结点，再以共同 epoch/owner 屏障原子决定唯一权威；活动 FDB 文件读写还需分页接口和介质提交次序。未完成这些条件前不得用预备路由替换生产服务或声称已切换。持续备份、亿级性能容量、真实高文件量介质端到端验收仍是生产闸门。

### 旧目录权威的两阶段屏障

每个真实带库作用域的 Raft 控制状态保存 `catalog_quiesce_index` 和 `catalog_frozen_index`，并随控制快照恢复。`POST /libraries/<serial>/admin/catalog/current/quiesce` 需要 `confirm=true`，且要求管理任务和回收已结束，返回该库第一次暂停的日志索引；所有文件服务 lane 在应用该条目后停止新的上传、删除、改名及原生元数据变更。已准入的上传仍可完成并由当前 owner 落带；在途执行报告、目录片和提交仍按旧协议复制。暂停后拒绝新的池/磁带管理、回收与设备接管。`resume` 必须带完全相同的暂停索引且尚未冻结；这只恢复旧 Raft/SQLite 权威，不涉及 FDB。

内部 `CatalogFreeze` 命令要求暂停索引匹配、设备 owner 已退出、管理任务与回收均结束。冻结后任何迟到的旧目录变更在控制状态机被拒绝，SQLite 投影只推进日志索引，不写入文件、暂存、任务或池；候选设备能力报告与 VIP 撤址仍可推进。快照目录的历史重放不会修改实时文件服务的暂停门槛。该冻结命令尚未开放 HTTP：必须先补目录/任务债务检查、全节点应用确认、来源扫描与 FDB 候选覆盖冻结点的证明，才可将其纳入生产切换编排。没有这些证明，冻结索引只是旧写入停止的屏障，**不是** FDB 激活许可；生产 `ltfsd` 仍以 Raft/SQLite 为权威。

### 冻结前后的本节点目录审计

`GET /libraries/<serial>/admin/catalog/current/audit` 在所请求的**本节点**打开只读 `directory.db`，用同一 SQLite 语句的读快照取得目录应用索引、是否仍有 `staging` 分片、是否仍有非 `committed`/`failed` 的文件任务。`indeterminate` 也算未决，必须对照介质和目录确认，不能因 owner 退出而静默视为成功。响应还给出本节点 Raft 应用索引、暂停/冻结索引、owner 与目录合并状态；目录不存在、索引缺失或为负时返回错误，不产生空目录或伪造“已排空”。多库网关的管理 GET 在本地回答，因此编排者可以分别向每个物理节点取证，不能只查询 VIP 一次便声称全节点确认。

这项审计不改变持久格式，也不授予 FDB 权威。检查未决任务在最坏情况下扫描本节点全部任务行，内存有界但耗时与历史任务量相关；亿级切换必须在冻结窗口测量，若反复轮询成本不可接受，应在显式迁移阶段建立可验证的部分索引或增量计数，不能在生产启动时隐式构建大索引。三个节点均显示 `frozen_projection_caught_up=true` 且债务为空，只证明各自旧目录投影到了冻结点。现有 `stage_audited_reconcile` 已能读取**符合 `directory.db` 结构的离线快照**，并与带上扫描结果逐路径核对；但还没有证明传入的快照确实出自生产库的冻结点，也没有将全节点排空证据与受管 FDB `q/s/w` 证明绑定。因此不能用此次 HTTP 结果或现有 FDB 封口结果直接切换运行时。

离线导入的 `audit_directory_snapshot` 现于读取应用索引和介质候选的**同一 SQLite 读事务**内拒绝残留 `staging` 分片或状态不为 `committed`/`failed` 的文件任务；缺少任一债务表也失败关闭。`stage_audited_reconcile` 在写任何候选清单前先执行该审计，完成逐路径暂存后又完整重读快照并比较摘要，因此不能从有债务的快照建立新的受管导入证明。此约束仍只针对提供的离线文件，不能证实文件来自生产库冻结点；快照来源与所有节点水位的绑定仍是下一道闸门。

### 冻结投影标记与离线快照文件身份

成功的 `CatalogFreeze` 现在在本节点 SQLite 投影的**同一事务**写入 `meta.catalog_frozen_index` 与 `meta.applied_index`。被控制状态机拒绝的冻结不写该标记；重复冻结只接受与已保存索引一致的标记，发现冲突则拒绝投影。原有 Raft 控制快照仍保存冻结索引。每节点的目录审计在同一查询中取两种索引，并新增 `projected_frozen_index`；只有它等于本节点控制状态的冻结索引、目录应用索引已追平时才报告 `frozen_projection_caught_up=true`。

FDB 离线导入现要求快照中有非零且不超过应用索引的冻结标记，并在只读事务持有期间逐路径核对介质来源、债务为空，随后流式计算所提供的独立 SQLite 文件 SHA-256。`DirectoryAudit` 同时保存冻结索引、逻辑行摘要和文件字节摘要；受管暂存清单升级为 v2，来源汇总随之升级为 v2，`q` 投影证明及后续 `s/w` 通过清单字节绑定这两个值。旧实验性暂存候选不能升级使用，应按既有废弃路径清理后重建。快照文件摘要允许识别扫描间被替换或改写的文件，内存使用固定 1 MiB；每次完整审计额外顺序读取一次 SQLite 文件，亿级目录需在现场测量时长与磁盘负载。

这个标记证明**所提供文件内部**来自执行过冻结投影的目录格式，不能单靠元数据防止离线伪造，也未证明所有 Raft 节点在同一冻结索引排空。生产编排仍需由服务从已冻结节点导出独立文件、记录其 SHA-256 和节点身份，并把 207–209 各节点的控制索引、投影索引和债务证明绑定到 FDB 激活事务。即使 `w` 已 Ready，也不能在完成该步骤及运行时单权威接线前切换正式 `ltfsd`。

### 运行节点导出冻结快照

`POST /libraries/<真实序列号>/admin/catalog/current/export` 在请求命中的**本节点**核对控制冻结状态、本地 SQLite 冻结投影和零暂存/零未决任务，再以 SQLite `VACUUM INTO` 生成一致的离线文件。响应为 `application/octet-stream`，以 `x-tapers-source-node`、`x-tapers-freeze-index`、`x-tapers-directory-index` 和 `x-tapers-snapshot-sha256` 头给出来源及字节摘要。服务在发流前重新核对控制冻结状态，打开文件后立即 unlink 临时路径，单库同时只允许一次导出；失败时不保留中间快照。接收方必须把字节保存为独立文件，核对 SHA-256 后再做离线导入，不能直接指向在线 WAL 数据库。该端点需要已冻结状态；它不会自行暂停、冻结或接管设备。

操作时应分别访问每个节点的客户端监听地址，保留各自的响应头和文件，例如 `curl --fail --request POST --dump-header node207.headers --output node207.db http://<节点地址>/libraries/<序列号>/admin/catalog/current/export`；用 `sha256sum node207.db` 与该响应的 `x-tapers-snapshot-sha256` 核对。不能用 VIP 的单次结果代替三个节点，也不能把下载成功当作 FDB 激活许可。

这使快照字节与一个具体运行节点的冻结投影可直接核对，但 HTTP 头不是密码学签名，调用方仍须信任所连接的节点和管理网络。它也尚未将 207–209 的所有节点证明及这份文件的 hash 写入同一 FDB 激活事务。`VACUUM INTO` 需要可容纳完整目录副本的本地空间，亿级目录必须在正式冻结前测量磁盘余量、耗时和下载吞吐。当前导出与受管 FDB 导入可独立使用于验收，不能据此宣称生产 `ltfsd` 已改用 FDB。

### 三节点快照与预备路由的来源证明

`inspect_frozen_snapshot` 对下载后的离线 SQLite 文件核对冻结标记、应用水位及零暂存/未决任务，在一个读事务中按主键顺序流式散列池、磁带、文件和任务的全部投影列，并另外散列整个快照文件。内容摘要包含冻结索引而排除继续前进的 Raft 应用水位：冻结后的拒绝命令可以令三个节点的文件字节和应用索引不同，但不能令目录内容不同。`verify_node_export` 还要求本地文件的索引和文件 SHA-256 与该节点导出响应头一致；节点 ID 由调用方提供，须由可信的节点连接确定，不能从未经认证的响应头直接采信。此扫描内存有界，但对亿级文件需要每节点一次表扫描和一次整文件读取，冻结窗口及磁盘带宽仍须实测。

受管 FDB 私有 `x/<真实带库序列号>` 现在保存三个不同节点的快照文件摘要、各自应用索引、共同冻结索引与目录内容摘要，并绑定选定导入来源的文件摘要、当前 `z` 预备路由修订号、`q` 导入清单字节摘要及 `s/w` 封口证明。`certify_prepared_cutover` 在**一个 FDB 事务**中重验路由、Sealed 封口和带库成员关系，再写证明；重复提交幂等，旧路由修订号不能覆盖新证明。读取时重新核对路由与封口，废弃路由或来源变化不会返回可用证明。三节点内容分歧、选错导入文件、响应头与文件不符都拒绝。该键按物理库数增长，不按文件数增长。

`x` 仍是**预备来源证据**，不是活动目录指针或租约。当前尚无负责从三个可信节点取得响应、核对控制冻结状态及发起这一 API 的生产编排器；没有签名或可信管理通道时，调用方可伪造节点归属。更关键的是，现有 `ltfsd` 仍以 Raft/SQLite 服务所有读写：必须先建立跨旧权威冻结和 FDB owner epoch 的唯一活动状态，再实现运行时分页查询、任务及介质提交语义，验证回退与故障恢复，才能让此证明成为正式切换的输入。合成 FDB 测试不能替代真实高文件量带验收，高文件量磁带不得格式化。

### 预备候选在激活前保持只读

受管 `seal_bound_staged_import` 现在把已核验候选从 `Verified` 原子推进到独立的 `Sealed` 状态（持久编码 `6`），同时写 `w`。`Sealed` 允许分页读取和核对导入结果，也允许在 `w/s` 匹配时分批清理重复的暂存行；普通目录创建、池/带库控制变更、文件请求准入与发布、卷扫描变更均须拒绝。卷扫描入口特别需要在同一 FDB 事务重读状态，因为它原来只凭 owner epoch 与卷放置即可启动新扫描，封口后还能使来源修订号失效。预备 `z` 路由和 `x` 来源证明现在只接受 `Sealed`，不接受旧版本留下的 `Ready+w` 候选；后者必须在确认未服务、无外部路由后废弃并重建，不能自动升级。

真正激活时，必须在一个受单权威屏障保护的 FDB 事务中核对 `x/z/q/s/w` 和旧 Raft 冻结证据，然后建立唯一活动指针及 owner epoch，并且仅在这些条件成立后让运行时写入。单纯把 `Sealed` 改为 `Ready` 会重新开放普通 FDB 写路径，却仍没有 ltfsd 运行时数据与 PR 许可的单权威。当前显式激活 API 只完成 FDB 内的原子转换；正式服务保持 Raft/SQLite 路径。

### 按物理带库序列号激活 FDB 候选

`A/<真实带库序列号>` 是新增的活动记录，保存 namespace、预备路由修订号、冻结索引、完整 `x` 证明的 SHA-256 和激活时的 owner epoch。`activate_prepared_cutover` 是显式 API：单个 FDB 事务核对当前 `x/z/q/s/w`、已封口 `Sealed` 状态和带库成员关系，把该库 owner epoch 提高一代，转候选为 `Active` 并写 `A`。因此旧 FDB owner epoch 不能在激活后发布，同一证明的请求幂等；不同证明被拒绝。激活后预备路由和证明不能改写；活动发现每次重验路由、完整证明摘要、导入基线及 epoch 下限。该键空间按带库数增长，与文件数量无关。此次在私有 catalog/22 格式内增加 `A`，没有迁移已有生产目录；旧实验性候选不能自动激活。

**这个事务只能原子化 FDB 内的状态**。调用方必须先从可信的三个运行节点确认旧 Raft 已不可恢复写入、冻结投影及任务债务排空，并确认独立导入快照和 `x` 是这些节点的证明。现有 API 的证据结构可由调用者构造，没有管理通道身份验证；现有生产 `ltfsd` 也尚未消费 `A`，没有把文件/池/任务读写改路由到 FDB 或将设备 PR 接管与新 epoch 相联。因此即使 `A` 存在，也**不能**仅凭它切换正式服务。实现接线前不得对正式带库调用激活 API。合成测试只对独立随机序列号激活，随后在测试专属 FDB 键上做精确补偿并清理候选；补偿代码不能作为生产回退操作。

### 旧目录服务的启动闸门

FDB 特性构建的 `ltfsd` 新增 `--fdb-cluster-file <PATH>`。配置此参数时，启动进程在创建网络、执行线程和文件暂存区之前，逐个按真实带库序列号查询 FDB 的 `A`。任一库已有活动记录、活动证明损坏或 FDB 不可达，进程都拒绝以 Raft/SQLite 旧文件服务启动；多库配置的全部带库均需核对。这个参数应在正式切换前部署至 207–209 的每个 `ltfsd` 启动配置，不能只给切换操作者本地进程使用。旧版或未配置该参数的守护进程仍不知道 FDB 活动记录，因此目前不能启用正式带库的 `A`。

该闸门只阻止**重启后的旧路径**。运行中的旧实例要先通过不可恢复的 Raft 冻结与设备 owner 退出，才可激活；服务运行时切换到 FDB 的文件、管理、任务、分页查询和 PR/owner 接线仍待实现。配置 `--fdb-cluster-file` 时未发现活动记录，守护进程仍走原 Raft/SQLite 路径，不把预备路由或 FDB 可达误当成生产切换完成。

### 激活后禁止普通 FDB 写入

激活事务现把候选从 `Sealed` 转为独立的 `Active` 状态（持久编码 `7`），同时写 `A` 并推进 owner epoch。活动路由发现要求 `Active`，普通 FDB 目录、池、请求和文件发布入口仍只接受各自原有的 `Ready` 或 `Building` 状态。已绑定受管卷的扫描变更在同一事务拒绝 `Sealed` 与 `Active`；活动命名空间也不能走废弃导入入口。节点、路径、文件 head 和卷放置的只读查询仍可读取 `Active`。验证、证明清理入口不能把 `Active` 改回其他状态。

上文较早章节所述“封口转为 Ready”“预备路由接受 Ready”“激活转为 Ready”记录了先前设计，均由后续独立 `Sealed`/`Active` 状态替代。旧试验数据不能自动转换。`Active` 目前没有可用于生产文件写入的 API；后续必须另建要求活动路由、当前 owner epoch、物理 PR 许可及介质提交证据的运行时事务路径。正式 `ltfsd` 仍未接入这些路径，不能把合成激活测试当成生产切换验收。

### 活动目录的同版本路径读取与 owner 准入

`resolve_active_path(serial, path)` 以真实带库序列号在一个 FDB 读事务中获取 `A`，重验 `x/z/q/s/w`、Active 状态和 owner 下限，再在同一读版本解析目录 inode、head、当前副本和卷放置。缺活动路由、证明损坏或 FDB 不可达返回错误，不把它们解释为 404。既有 `resolve_path(namespace, path)` 仍供导入诊断；未来运行时服务必须从 `serial` 入口读取，不能仅凭曾缓存的 namespace ID 访问活动目录。返回的卷放置和本地 LTFS extent cache 仍需在装带后按当前 PR/介质身份复核，FDB 查询本身不授权设备 I/O。

`register_active_request` 在单个 FDB 写事务中要求 namespace 为 Active，读取当前 `A`、完整来源证明及精确 owner epoch，再预留请求许可和写入 intent；活动路由或证明缺失时失败关闭，旧 epoch 返回 `StaleOwner`。`cancel_request` 遇到 Active 也先核对相同路由和 epoch，只有已确认未提交介质数据时才能释放准入。合成测试覆盖当前 owner 登记/取消、旧 owner 拒绝、FDB owner 换代后旧请求拒绝、当前 owner 继续登记以及证明损坏拒绝。这个 API 只是**发出介质 I/O 之前**的元数据准入；调用方还必须在设备 PR 栅栏下执行磁带操作。尚未建立将 LTFS 实际提交证据绑定到 Active head/copy 发布的运行时事务，也未把 `ltfsd` 文件服务接到这些 API，因此不能据此切换生产。

### 活动请求窗口与卷代数边界

2026-10-24 已为 Active 增加 owner 栅栏下的请求代次轮换、过期水位推进及有界终态清理。三者在写事务里重验活动证明和精确 owner epoch；普通 Ready/Building 维护入口仍拒绝 Active。推进水位前逐范围确认没有未决请求或历史引用，清理终态后仍以水位拒绝旧重试。207–209 三节点随机合成候选及停一节点窗口均已验证，未操作介质。

**介质提交代数不能复用导入扫描代数。** 当前 `VolumeScan {generation,id}` 与 `Ready` 清单指针共同证明导入时完整来源扫描。真实 LTFS 追加提交会增加 generation；如果新副本继续声称旧 generation，FDB 与磁带索引不一致；如果每次提交把整个 Ready 扫描换代，旧副本会因扫描退役而失去可读资格，亿级文件也不能每批重扫。后续应保留不可变的已验证导入基线，另以单调提交序列记录当前卷索引代数、索引位置/摘要和已提交的变更批次；读取时以当前已确认索引核对所选副本的 UID/extent，旧文件仍可读，当前 head 指向的新副本由同批 FDB 事务发布。执行器只有在持有设备 PR、`LtfsVolume` 提交成功并重验 owner 后才能提交该事务；结果未定需先恢复磁带再对账，不能提前发布或取消请求。具体键编码、容量预算和故障重放规则仍待实现和压力验收。

第一片卷代数结构已落地为每卷一个 `r/<volume UUID>`，仅 Active 命名空间可在完整路由证明和精确 owner epoch 下更新。值保存紧邻的前驱与当前索引构造身份：卷 UUID 由键限定，值含 generation、分区、起始块、SHA-256 和 Full/Incremental 标志。每次更新要求前驱**完整等于**当前观察身份、generation 恰好加一；相同前驱/结果重试幂等，另一候选或旧 owner 拒绝。没有 `r` 时以不可变的已验证导入 `S/M/G` 来源为基线，更新不改变它，也不改变文件 head、副本或旧缓存。记录只陈述执行器观察到的磁带提交，**不是**介质真实性证明，也不授予文件可读或可见权限；增量索引的 SHA 属于磁带上的增量构造，不能拿来直接打开仅接受完整 XML 的 `VolumeExtentCache`。接线时必须从当前磁带索引链构建可重建本地 extent 视图，并在 FDB 的同一最终发布事务中核对已观察索引、活动 owner、请求许可及整个批次的文件变更。当前仍无此发布/恢复事务，正式 `ltfsd` 不能切换。

`LtfsVolume::committed_index_construct()` 现从成功写入的实际 XML 计算构造 SHA-256，只在 S4 屏障与 VCI 全部成功后随已提交视图一起推进；失败后保留旧身份，重新挂载则使用恢复协议确认的物理构造摘要。卷会话复用也保留该身份。`ActiveIndexIdentity::from(CommittedIndexConstruct)` 提供向 FDB 观察记录的显式转换。模拟磁带验证 DP Full 与 Incremental 两条路径在断电重挂载后身份一致，屏障失败不提前推进。此值仍须由持有 PR 和当前 owner 的 `ltfsd` 执行器取得并与 FDB 提交事务连接；目录自身不能凭一份调用者提交的值证明物理介质真实性。

活动卷观察现在在推进 `r/<volume UUID>` 游标的同一 FDB 事务中，为每个新代数写入 `r/<volume UUID><generation>` 的不可变批次 ID 和索引身份；导入基线仍从原始 `S/M/G` 来源读取。`observed_active_volume_generation` 按真实带库序列号和活动路由在一个读版本中查询历史代数，缺失或损坏已经观察到的身份时失败关闭，未来代数返回空。这样旧副本不会因为 `r` 游标继续前进就失去其物理索引代数证据。每次介质提交增加一条 67 字节值的 FDB 记录，增长按提交次数而非文件数；保留期和安全清理由后续副本引用与恢复窗口协议确定，不能按时间盲删。该记录仍只是恢复证据，未把旧副本变成可读的 Active 计划，也不能代替本地增量索引链的 extent 视图。

活动卷顶层前缀从原实验性 `B` 改为 `r`：`B/<namespace><request epoch><shard>` 已被请求配额占用，命名空间清理会对它做前缀扫描；混用可能错误清理卷证据。`r` 在 catalog/22 内独立，当前没有正式 Active 带库或旧格式迁移。本次合成夹具按确切 `r` 键清场；若将来发现遗留实验性 `B` 卷键，必须先核对 UUID 和完整记录格式再单独清理，不能把配额键当卷游标。

Active 请求准入现在在同一 owner-fenced FDB 事务读取已验证的导入 scan 和最新 `r` 游标：收据必须绑定原 scan ID，目标代数必须恰好为当前代数加一；已观察代数返回 `GenerationConflict`，更远的未来代数或旧 scan 返回 `VolumeNotReady`。已登记但未发布的请求在其目标代数被观察到以后不能由 `cancel_request` 释放许可或写入“已取消”终态，同样返回 `GenerationConflict`，供接管者恢复对账。合成测试在第二个 catalog 连接上核对未决 intent 仍在；只在撤销**测试专属合成索引**后取消并清场。这个检查能阻止把已观察介质提交误判为完全未写带，但还不能保证取消发生在介质提交**之前**时不会与后续带写入竞速。正式执行器必须以批次清单、PR/owner 栅栏和单事务发布协议消除该窗口，不能把请求准入当作最终落带许可。

### Active 批次的分页准入屏障

`stage_active_batch` 在介质 I/O 前把同卷、同下一代、同扫描、同 owner 的已准入收据规范排序，写入私有 `p/b/<volume><generation>` 头、`p/g/<volume><generation><page>` 清单页，并以 `p/i/<namespace><request epoch><operation>` 占用每个请求。每页最多 128 项，页内请求占用与清单在同一 FDB 事务提交；封口事务重新读取所有页、核对全批摘要，最后把头转为 `Sealed`。单次 API 最多 65,536 项；执行器未来必须在介质 I/O 前拆分更大的队列。这个上限约束 FDB 事务尺寸，不是整个带库的文件容量上限。请求取消和重复准入在同一事务读取占用键，因此与分页占用的并发写入产生冲突并重试；被占用时返回 `BatchClaimed`，不能取消后继续写带。

接管者可查询 `active_batch_status`。未封口的 `Open` 头表示按协议尚未开始介质 I/O；`abort_open_active_batch` 先把它标为 `Aborting`，再逐页原子删除页与请求占用，最后删除头，支持切主后重试。`Sealed` 不允许走这条清理路径：它仅证明元数据准入完成，**不证明磁带成功提交**，必须先读取介质和设备 PR 证据再决定发布或保留待对账。最终发布协议还必须按页清理 `p/i` 与 `p/g`，仅在引用与恢复窗口允许时回收批次头；否则这些键会随文件数无限增长，不满足亿级目录。正式执行器尚未调用本 API；整批文件 head/copy/任务终态原子发布与结果未定恢复仍需实现。故不能把此屏障当成生产切换许可。

`record_active_volume_index` 现在在推进 `r` 游标的同一事务要求对应卷代数的 Sealed 批次头，核对批次 ID、命名空间、导入扫描和不高于当前 owner 的封口 epoch。每代不可变历史值包含版本、批次 ID 与索引构造身份；重复观察必须给出同一批次 ID，不能把另一批误认作同一次提交。旧 50 字节实验性历史值不会被猜测升级；现场没有正式 Active 卷，合成候选按精确身份清场。此操作仍只记录调用者已经通过介质回读与 PR 验证的结果，FDB 自身无法证明磁带物理提交。接任 owner 可以在重新验证介质后记录前任封口的批次；结果未定时不得凭 Sealed 状态推进 `r`。

`recover_observed_active_batch_page` 是接任者的有界读取入口。它在一个 FDB 读版本中核对当前 owner、活动路由和卷放置、Sealed 头、该代 `r` 历史中相同的 batch ID，并按最多 128 项读取清单、占用键及原准入 intent；每项收据的完整指纹、卷代数、扫描和原 owner 必须匹配。尚未观察到目标索引时返回空，而不是把 Sealed 误判为落带成功；清单或 intent 损坏、旧 owner 和批次不匹配时失败关闭。继任 owner 可读取前任封口的页，不得因此跳过设备 PR、实际索引链和介质回读。合成测试覆盖 129 项两页、跨 owner 读取、旧 owner 拒绝及被篡改页拒绝。

观察到索引后，可用 `prepare_observed_active_file` 将单个文件的完整 LTFS 属性写入私有 `p/v/<卷><代数><请求>` 记录及 `p/a/<卷><代数><请求><分块>`。写入事务核对活动 owner、卷放置、Sealed 批次、`r` 中相同 batch ID、原请求 intent 与占用；属性 digest、普通文件 fileuid 与内容摘要必须对应收据。完整属性最大沿用 4 MB 限制，每块 64 KB，文件的分块和标记同事务写入，避免 128 个大属性压进一个 FDB 事务。`recover_observed_active_prepared_file` 在同一读版本重新核对身份并复原所有分块，任何缺失、顺序或摘要损坏均拒绝。上述键完全不可见于活动目录读取，也不结束请求。

每页准备完后，`mark_observed_active_batch_page_prepared` 核对该页全部原清单请求、占用和逐文件准备标记，写 `p/y/<卷><代数><页>`。`seal_observed_active_preparation` 再一次读取至多 512 个连续页标记，核对页数、顺序、batch ID 与当前 `r` 索引，在同一事务写小的 `p/z/<卷><代数>` 总准备证明；缺一页返回未完成。接任 owner 可幂等重做文件、页和总证明。该结构的最终封口成本随批次数量的页数增长，而不读取亿级目录或整批属性。现场合成覆盖 129 文件两页、80 KB 分块属性、缺页拒绝和 owner 接任。

`p/z` 仍**不是文件发布**。它只证明所有受信任的准备 API 已将属性与请求身份持久绑定；没有改变 `C/N/H/R/V/P`，读取继续看到导入基线。后续必须做版本化的不可见目录变更及单事务可见性标记，并让路径、目录分页、head、副本、任务结果在同一 FDB 读版本解释该标记；还必须在发布后按引用与重放窗口分批清理 `p/a,p/v,p/y,p/z`。不清理会按文件数持续增长，违背亿级规格。属性必须由持 PR 的执行器从成功提交或恢复回读的真实 LTFS 索引提供；纯 FDB 证明不能鉴别调用者伪造的物理提交。

批次准入的原始清单页 `p/g` 与新页摘要 `p/h/<卷><代数><页>` 现在同一事务写入、重试时成对核对。批次头格式升至版本 2，头中的总摘要由最多 512 个有序页摘要计算；最终 Sealed 事务一次范围读取至多 512×32 B 的摘要并核对键顺序、数量和总摘要，不再顺序读取最多约 3.6 MB 的原始清单。恢复页、准备页和中止页都重新核对 `p/g` 与 `p/h`，缺失或不匹配失败关闭；未封口中止逐页清理两者。旧版实验性批次头不能用新程序继续封口，须依其原版本先完成中止/精确清理；正式 Active 服务尚未激活。这缩小了封口事务的读取量，尚无满 65,536 项批次的延迟实测，不能把 129 项现场合成验收当作亿级负载性能证明。

落带前的分页准入又加入目标冲突栅栏。一个批次在创建头之前拒绝重复 `(parent,name)` 或 `file_id`；每个至多 128 项的页事务在**任何写入之前**核对全部原准入 intent、已有目录 parent/child/inode/head 的预期版本与副本 ID，并读取三个占用键：原请求 `p/i`、按命名空间/parent/名称编码的 `p/l`、按命名空间/file ID 的 `p/n`。全部通过后，三个占用与页、摘要同事务写入。这样另一个卷即使有合法准入请求，碰到同路径或同 file ID 也在介质 I/O 前收到冲突；页后半段请求失效不会提交前半段孤儿占用。未封口中止从原 intent 重建并验证目标，逐页原子释放三类占用；接任恢复及逐文件准备也核对目标占用。`p/l,p/n` 是在途批次状态，最终发布与安全回收尚须释放；在完成 Active 目录变更与清场协议前不得把此准入当成生产文件写入许可。现有目录校验仅覆盖导入基线，未来 Active 已发布但未归并的版本必须纳入同一读版本的冲突判断，目录删除/重命名还须处理父子路径占用。

`p/l` 和 `p/n` 的值现为同一份 81 字节、版本 1 的目标定位记录：批次 UUID、卷 UUID、目标代数、请求 epoch、operation UUID 与 file ID。`p/i` 仍保存 16 字节批次 UUID。封页时两份定位记录与原请求占用同事务写入，重试、接任、文件准备与未封口中止均逐字段核对。这样后续路径查询能从 `(namespace,parent,name)` 或 inode ID 找到对应批次及请求，再于同一 FDB 读版本读取发布标记和候选属性；目录分页也可按 `p/l` 的有序名称键与原 `C` 范围归并，直接从定位值取得 file ID。定位记录本身不代表介质已提交或文件已发布。旧实验性 16/65 字节 `p/l,p/n` 不能作为新协议的定位记录复用，正式 Active 路由尚未激活；任何残留须按原批次身份精确清理。FDB 的[事务快照与冲突规则](https://apple.github.io/foundationdb/developer-guide.html)支持同版本判定，[10 MB 事务上限与时间限制](https://apple.github.io/foundationdb/known-limitations.html)要求最终屏障只写小标记，而不复制整批文件。

批次发布标记为 `p/c/<卷><代数>`，其值必须与同版本读取的 113 字节 `p/z` 完全相同，batch ID、已观察的 `r` 历史索引摘要及原准入 intent/目标占用须一致。`resolve_active_path` 与活动命名空间的普通 `resolve_path` 在一个 FDB 读版本里选择导入基线或已标记的新收据、LTFS 属性与副本；`resolve_child`、`node`、`file_head`、`physical_copy` 同样解释目标定位与标记。`list_children` 在同一读版本从原 `C` 与有序 `p/l` 各读取至多 `limit+1` 项，按名称归并；`pending_requests` 同版本隐藏已标记请求。现在有 owner 栅栏下的 `publish_observed_active_batch` 写入口，在同一事务核对路由、卷放置、Sealed 批次、导入扫描、已观察的不可变物理索引及全部准备页摘要，要求其重新计算的证明等于 `p/z`，只写一个小型 `p/c` 可见性标记。重复调用按完整证明幂等，缺页或错误批次拒绝；它**尚未被正式 `ltfsd` 执行器调用**，调用者还必须独立复核当前介质和 PR。

可见性事务后，`finalize_published_active_batch_page` 每次至多处理 128 个请求：逐项复核原 intent、目标占用、文件准备和页证明，在一个 FDB 事务中写 `P` 请求终态、按配额分片扣减待处理计数，并写 `p/t/<卷><代数><页>` 终结标记。重复调用读取 `p/t`，不会第二次释放配额；页失败则没有部分终态。发布到页终结之间配额保守占用，文件和请求重试已可从 `p/c` 得到提交结果。原 `I` intent 仍为文件读取证明所必需，不能在终结时删除，因此请求 epoch 的最终过期、目标占用和属性键的有界归并/回收仍未完成。已发布但未归并版本的后续合法覆盖也未实现。Active `copies_on_volume` 已有发布门控的反向副本查询（见下文），`resolve_active_read` 已能按已观察代数绑定本地完整或增量 extent 缓存（见下文），但正式执行器尚未建立/使用该缓存。目录跨页快照语义、真实物理 PR/S4、故障回读和高文件量带验收同样未完成。

已发布请求在相同 owner 凭证下重试准入时，若卷代数已前进，会复用文件读取契约核对完整证明，再返回 `AlreadyApplied`；不同收据返回冲突，证明损坏则失败关闭。没有标记时仍返回代数冲突。切主后的旧 owner 凭证受栅栏拒绝，当前 owner 可按批次恢复入口接续发布/页终结。合成测试覆盖 129 文件两页、逐页重复、过期 owner、损坏 intent 的原子拒绝；这证明协议局部性质，不等于正式 `ltfsd` 已迁移。

20k 文件批次不能把全部 inode/head/copy/任务终态塞进一个 FDB 事务。当前 `p/c` 小事务提供全批可见性屏障，`p/t` 分页终结保持单页重试与配额安全；但公开的目录投影仍依赖在途 `p/l,p/n,p/o,p/v,I`，没有完成归并/回收及旧副本替换。正式执行器 PR/owner 栅栏、可信冻结、索引缓存构建和任务语义接线完成之前，不能把这些 API 当作生产文件写入许可。

目录分页读到已标记目标时，现与单文件读取一样重验准入 intent、Sealed 批次、`r` 索引摘要、活动路由与卷放置，并要求请求的 parent/name 与列表键一致。损坏准入 intent 会令两种查询同时报错，不会出现“列表可见、文件不可访问”的分歧。此逐项验证仍需在亿级目录、较大页尺寸和现场网络延迟下测量分页耗时；正式发布写入和跨页快照语义尚未实现。

Active 批次分页准入另以 `p/o/<volume><namespace><file><copy>` 写每副本卷反向定位，与 `p/i,p/l,p/n`、页清单和摘要在同一事务提交；未封口中止逐页验证并删除。值为 49 字节版本 1，含 batch、目标代数、请求 epoch 和 operation；volume、namespace、file、copy 从键取得。以 1 亿副本计算，含 `catalog/22` 前缀的键和值合计约 13.6 GB 逻辑字节，尚未计 FDB 编码、复制、LSM、日志及旧版本；它避免了查询某卷时扫描全库目录或所有批次的成本。`copies_on_volume` 在同一读版本按 `(namespace,file,copy)` 归并导入 `V` 与 `p/o`，只有完整发布证明匹配的目标才出现；未发布项隐藏，损坏项报错。分页继续使用原 `V` 形状的不透明游标，Active 单页上限为 100 项，避免大页逐项核验触发 5 秒事务超时。跨页发生发布变化时并非一致快照，维护/回收仍须在执行前重新核对最新卷索引和目标状态；高文件量带不得格式化。

增量卷读计划使用独立的本地 SQLite extent 缓存格式 2。`scan_incremental_reader` 逐条解析原始 LTFS 差分 XML，核对增量头、路径唯一性与每个条目的差分字段；`build_incremental` 只保存明确给出 UID、长度和 `extentinfo` 或 symlink 的文件，部分元数据更新与删除项不能冒充物理读取计划。构建完成前逐字节计算原始构造的 SHA-256，核对卷 UUID、代数和索引位置，缓存文件只在全部成功后原子出现。完整索引缓存仍为格式 1，二者不能互相打开。扫描内存随本次差分路径数增长，避免按整盘 1 亿文件重建内存树；极大差分批次仍须测量内存、索引写入和本地磁盘占用。

`resolve_active_read(serial,path,cache)` 在同一 FDB 读版本核对活动路由、已发布目录目标、导入基线及目标代数的不可变 `r` 索引身份。基线或后续 Full 构造打开格式 1，增量构造打开格式 2；本地缓存必须匹配精确代数、物理位置与原始 SHA，且路径解析得到的 LTFS UID/长度必须等于共享目录副本。旧代数缓存、部分差分文件和缺失缓存均失败关闭。物理设备 PR、当前装带身份、增量链和真实回读必须由执行器在 I/O 前复核；目前正式 `ltfsd` 未调用该 API，也未从已恢复介质自动构建这些本地缓存。合成索引与 FDB 测试不能替代高文件量实带验收。


## 2026-10-26：池的物理带库边界

用户明确要求池不跨物理带库。一个池在创建时绑定真实换带器序列号，此归属不可变；owner 节点切换不改变归属。一个物理库可以有多个池，池的驱动选择、挂载配额与磁带分配都限定于该库。跨库迁移与冗余副本必须使用另一物理库中的另一池；共享 FDB 的文件身份/副本索引可以跨库，并不意味着池跨库。物理带库是这里的介质调度故障域；共享 FDB 和集群控制面仍按各自 HA 方案保证可用性。

`PoolRecord.library_serial` 是必填的不可变属性；新池必须引用本命名空间已登记的物理库。分配磁带、注册卷放置、核验卷/副本及读取磁带归属时都核对池与库一致。禁止用更新池属性实现跨库迁移。池记录升级为版本 2；尚未切换的旧候选记录不能推断归属或静默升级，须显式重新导入，不修改正式 FDB 或真实磁带。此前将“没有跨库统一池”列为差距的判断由此约束取代；跨库文件身份和副本管理仍是独立目标。
