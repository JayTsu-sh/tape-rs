# Rust 运行许可发布与撤销：同步证据与候选

日期：2026-09-16；票据 29。阅读项目 `control-failure-dispatch.md` 与 `raft-rs-binding.md`，核对 Rust 官方文档及固定 Rust 1.85.0 原子源码说明。文档版本仅用于引用既有基础语义，不选择项目 Rust 版本、依赖或同步实现；未运行模型、代码或设备。

## 结论与推荐边界

推荐先采用**整体版本化门控的条件转换**作为最小验证模型：单启用/刷新者、多撤销者、多读者；每个更新明确 expected 前态、许可身份及受影响故障域。它优于无协议地逐项写多个原子字段，也避免把撤销串到 RawNode 的 S/Ready 后面。但这还是同步语义候选，不是“一个 CAS 已实现整个门控”：复合状态的原子表示、安全读取/回收、快速路径的分配与重试成本，以及期限切点仍未证明。

## Rust 官方事实

| 官方事实 | 对项目的约束或推论 |
| --- | --- |
| 原子操作是共享内存同步原语；Release/Acquire 需形成对应同步关系，Relaxed 不发布周边数据；SeqCst 给顺序一致操作增加全序。[原子模型][atomic]、[Ordering][ordering] | 多个字段各自原子不等于一次整体快照；不能混读旧许可身份、新期限与旧终止状态。SeqCst 也不会把一段检查和后续调用合成事务。 |
| CAS 只在当前值匹配 expected 时替换；weak CAS 可以伪失败；fetch_update 的闭包可能多次调用，且不自动排除 ABA。[固定官方原子说明][cas] | 重试函数只做可重复的状态计算，不派发动作、不分配新的业务轮次或重复登记事实；版本/身份不能回绕后复用。 |
| 可用的标准原子类型保证 lock-free，但不保证 wait-free；包括 fetch_or 在内的操作也可能由 CAS 循环实现。[原子进展保证][atomic] | “不用 mutex”不等于每个撤销线程有完成上界。竞争、调度暂停、平台支持和底层指令都需验证。 |
| Arc 保证共享所有权，不自动同步 T 内部可变状态；最后强引用释放时会销毁对象。[Arc][arc] | 一个 Arc 不能证明许可字段一致；分配、引用操作、最后释放与析构也不能被忽略为免费热路径。 |
| 从裸指针增加 Arc 强引用要求整个调用期间对象已有效存活。[Arc 裸指针安全前提][arc-raw] | 先 atomic load 指针、再 increment_strong_count 的间隙可能已被最后释放；单纯指针 CAS 或地址相等不解决回收/ABA。 |
| Mutex.lock 可以阻塞等待持锁者；try_lock 获取不到时返回失败。[Mutex][mutex] | 即使代码区段很短，持锁线程也可能暂停。不能把唯一撤销入口放在该锁之后；try_lock 失败也不能丢失撤销义务。 |

## 条件转换的最小候选（项目推论，未实现）

逻辑状态含实例/配置关联、不可复用修订、当前限制及其范围、准备/活动许可身份、各许可阶段与期限。证据正文可独立保存，但安全判定必须读取同一一致视图或已证明等价的验证序列，不能默认为任意结构可直接装进机器字。

1. **准备与发布。** 准备绑定 observed revision 与完整证据；发布仅能由该 expected 前态转换。失效在还没有活动许可时也必须改变对应限制/修订，从而使正在准备的发布失败，而不是仅关闭“当时的旧指针”。发布失败不能只换一个 expected 后复用全部旧证据；重新核对真实变化、范围与期限。
2. **刷新与终止。** 刷新只转换同一未终止许可，终止后不存在回到 Active 的边。撤销若先成功，旧刷新必须失败；刷新先成功，随后适用撤销仍须关闭该许可的新修订。不能因刷新造成版本变化，就把同一许可仍适用的故障扔掉。这里仅说明内存状态顺序，时间条件另见下节。
3. **多失效来源。** 每个事件携带来源/代次/作用域及具体关联，合并时保留其他尚有效限制。一个来源恢复不能清除另一个来源的故障。重复事件可幂等，失效历史不能被后来健康抹去；无法一次更新全部原因正文时，先完成足以阻止受影响派发的安全标记，正文与未处理义务不能丢。该快速安全标记和主体状态的组合协议仍须实现证明。
4. **K→G。** 成功交接是带 expected K/实例/轮次的控制转换；G 有独立身份。只针对旧 K 的迟到定时事件不能关闭 G；确实影响共同前提的存储或隔离风险仍须作用于当前相关许可，不能因事件起于 K 就忽略。只影响单卷的限制不能无依据扩大为整组停止。
5. **读者。** 安全取得受生命周期保护的描述符，核对许可身份、阶段、当前范围限制及当下期限；旧任务不能自动改绑新许可。多个故障域若分开存储，须另证联合读取与更新关系；“整体门控”不等于所有故障统一撤销全组。
6. **进展。** 启用/刷新可以条件失败并重新准备，撤销不能因一次 CAS 失败就返回成功。撤销重试必须重新判断当前许可与事件是否仍相关；不能以等 S、等存储、等慢设备锁、等无界分配或回收作为必要步骤。若选定表示做不到，维持缺口而非宣称已满足快速停发。

这个候选明确了撤销先于发布与刷新时的拒绝依据，但没有选择可对整份状态操作的标准库类型或第三方容器。尤其不能假定 `AtomicPtr<Arc<T>>` 等价于安全的原子 Arc 交换；也不建议为绕开回收问题无限保留所有旧许可而不计资源成本。

## 两个不能由 CAS/SeqCst 解决的切点

**期限跨越。** 刷新者在旧 deadline 前检查时间，随后暂停；期限已经过去而到期回调未运行，恢复后内存版本可能仍未改变，CAS 因而可能成功发布新 deadline。这说明“先读 now 再 CAS”本身不足以证明 RQ 的过期不可复活。需要另定并验证时钟检查、刷新生效和读者可使用之间的真实线性化/暂停约束；发布后复查再撤销也不能自动证明中间没有读者使用。此处不放宽 RQ，也不提出未经证明的计时算法。

**物理交付。** 读者最后一次原子检查允许之后可以暂停，撤销完成后才继续调用系统/远端。内存全序不覆盖设备受理，也不阻止线程恢复。不能把软件准备/占位当作已发，不能跨慢调用持锁以阻挡撤销；继续要求真实派发入口、未决效果与外部 fencing。源端获知至门控更新的窗口必须可观察，不能重命名“获知”来使其消失。

## 替代方案比较与成本

| 候选 | 适用性与未解决项 |
| --- | --- |
| 独立 active/deadline/pointer 等原子字段，各自覆盖 | 不能直接采用；即使全用 SeqCst，也缺整体前态检查、终止不可逆与准备中撤销的协议。若增加版本重检/单向闩锁，已是需要单独证明的新组合。 |
| 单一短 Mutex 包住全部许可操作 | 状态与生命周期容易表达，但唯一撤销等待持锁者，不符合独立快速停发要求。额外无锁 kill 路径可研究，却不能省略其与发布/恢复的竞态证明。 |
| 整体版本化条件替换 | 推荐验证语义；拒绝旧前态最直接，但状态表示、CAS 竞争、回收及期限仍有成本。不能据此宣称已有 wait-free 撤销或零开销读取。 |

建议首先验证 PP01 准备→失效→健康→迟到发布；PP02 刷新与多撤销交错；PP03 旧 K 超时与新 G；PP04 单卷/整实例范围；PP05 地址或代次复用及读者暂停；PP06 时钟检查后跨期限暂停；PP07 最后检查后跨撤销交付；PP08 持续竞争与无故障正例。全部未执行，正例必须能完成新许可启用/合法刷新及派发，不能以永久拒绝获取安全通过。
