# IBM Spectrum Archive EE V1.3.2.2：无 GPFS 架构借鉴边界

研究日期：2026-09-14。状态：来源核对完成；下文设计建议均为推论，不代表用户已接受新功能或实现方案。

## 来源、范围与结论

唯一主要来源为用户提供的 [IBM Spectrum Archive 企业版 V1.3.2.2 1.pdf](</work/jay/tape-rs/IBM Spectrum Archive 企业版 V1.3.2.2 1.pdf>)：IBM Redbooks，SG24-8333-09，Tenth Edition，**March 2022**，适用 V1 R3 M2 Fix Level 2。版本依据 PDF 第 3–4 页，不以 PDF 元数据中的 2025 年制作时间替代出版时间。共 360 页；以下“PDF 页”为从 1 开始的物理页，正文印刷页加 24。原文件 SHA-256：`642c9242c8a00d1bd4c34242de6cd4a06c3dc68f8f5ece5dcd2b3fa6fb476bcf`。

限定阅读 §1.3、§1.4、§3.7/§3.7.4、§5.1.4、§6.6–§6.7，以及与调度、失败任务有关的 §1.2.1/§6.14；第 9 章恢复流程由主地图另行核对。本报告未联网替换版本，未读取项目业务代码，未访问真实设备。

**结论：借鉴资源管理、调度和分层健康观测的职责，不复制 EE 的 GPFS/HSM 基础。** EE 原书不是“无 GPFS 的独立文件系统客户端”架构；去掉图里的 GPFS 方框并不会自动保留其共享命名空间、共享元数据或透明回迁能力。

项目已有约束由本次任务给定，不归因于 IBM：独立 Rust LTFS 核心、Native SDK → ltfsd、独立 low-level FUSE；整组 A/B active-passive，切换前外部 fencing；磁带已提交状态权威；无 A/B 暂存复制、无上传回执、无旧上传自动恢复。**不依赖 GPFS / IBM Spectrum Scale** 是用户明确要求，不是待选方案。

## 八条关键事实及其边界

1. **EE 的基础包含共享文件系统身份。** §1.3 明确要求 Spectrum Scale；同一 EE cluster 的节点可以看到同一 Scale 文件系统中的相同 inode。控制节点管理关联带库的访问请求，MMM 在每库同一时刻只运行一个实例。但这种“单个 MMM”不等于整个数据路径只有一个工作的节点。[§1.3，印刷 p9–10 / PDF 33–34](</work/jay/tape-rs/IBM Spectrum Archive 企业版 V1.3.2.2 1.pdf#page=33>)；[§1.3.3，印刷 p14 / PDF 38](</work/jay/tape-rs/IBM Spectrum Archive 企业版 V1.3.2.2 1.pdf#page=38>)。

2. **HSM、MMM、LE 的职责不同。** HSM 的一般模型是迁走数据、留 stub，并在访问时回迁；MMM 选择队列任务、磁带和驱动并启动工作；LE 通过文件系统接口访问磁带空间，处理文件对象及其命名空间元数据。原书没有把这些直接命名为本项目的 Rust 模块，也没有证明本项目必须使用 LE 的挂载接口。[§1.3.2–§1.3.4，印刷 p13–14 / PDF 37–38](</work/jay/tape-rs/IBM Spectrum Archive 企业版 V1.3.2.2 1.pdf#page=37>)。

3. **MMM 的调度不是无条件先来先服务。** 选择受 node group、格式代际兼容性、mount limit 和驱动用途约束；多块候选带时尝试使用已装载且驱动可用的磁带。控制节点还维护驱动/磁带目录、逐带剩余空间估计并分配新数据空间。书中这些职责可以启发本项目，但不直接提供本项目 DP/IP 索引收尾预算的正确公式或原子实现。[§1.3.3，印刷 p13–14 / PDF 37–38](</work/jay/tape-rs/IBM Spectrum Archive 企业版 V1.3.2.2 1.pdf#page=37>)。

4. **EE 的多节点扩展并非当前 A/B 热备设计。** §1.4 的单库多节点配置要求每个节点有自身、不与其他节点共享的驱动集合；多节点的目的包括提高存取性能。§6.7 中控制服务的切换不能被解释成“备用节点自动接管原节点的同一组驱动、暂存数据和未完成上传”。[§1.4，印刷 p15–16 / PDF 39–40](</work/jay/tape-rs/IBM Spectrum Archive 企业版 V1.3.2.2 1.pdf#page=39>)；[§6.7，印刷 p153–154 / PDF 177–178](</work/jay/tape-rs/IBM Spectrum Archive 企业版 V1.3.2.2 1.pdf#page=177>)。

5. **共享 metadata 是明确的部署前提，不是可忽略的实现细节。** EE metadata 目录所在 GPFS 文件系统必须预先创建、挂载，并能由 cluster 所有 EE 节点访问；受 HSM 管理的 GPFS 文件系统还要求 DMAPI。§6.6 将 `.global`、`.lib` 数据库置于 GPFS 下 `.ltfsee/config`，描述本地数据库备份用于重建。这些事实不等于原书规定了本项目需要同步复制 RAM/SSD 暂存，也不是“任意本地 SQLite 自动替代共享 GPFS”的证据。[§5.1.4，印刷 p104–105 / PDF 128–129](</work/jay/tape-rs/IBM Spectrum Archive 企业版 V1.3.2.2 1.pdf#page=128>)；[§6.6，印刷 p152 / PDF 176](</work/jay/tape-rs/IBM Spectrum Archive 企业版 V1.3.2.2 1.pdf#page=176>)。

6. **监控和自动恢复是按组件区分的。** §6.7 的 monitor daemon 监控 MMM、LE、其他监控进程及 GPFS/HSM 等依赖；部分组件支持自动恢复。MMM 失效时先尝试本地重启，失败后切至冗余控制节点；不是所有被监控的依赖都有自动恢复动作。**该节没有给出足以验证本项目脑裂隔离、外部 fencing、写入所有权交接或在途 SCSI 安全性的协议。** 不能用它替换本项目既有安全门槛，也不能据此新增本项目默认重启策略。[§6.7.1，印刷 p153–154 / PDF 177–178](</work/jay/tape-rs/IBM Spectrum Archive 企业版 V1.3.2.2 1.pdf#page=177>)。

7. **性能数字依赖工作负载与硬件，尤其受文件大小影响。** §3.7.4 要求实际客户硬件测量；示例基于特定 x3850、QLogic 8 Gb FC、NUMA 配置和 TS1150/LTO7。表 3-3/3-4 是多驱动合计传输率，不是单驱动保证、提交持久化吞吐或本项目 SLO；其最小测试文件为 5 MiB，不能据此代表本项目更小文件的极端归档。§3.7 的 metadata sizing 又与文件数、块大小等相关，其 GPFS 公式不能拿来计算本项目 LTFS index 大小。[§3.7，印刷 p61–62 / PDF 85–86](</work/jay/tape-rs/IBM Spectrum Archive 企业版 V1.3.2.2 1.pdf#page=85>)；[§3.7.4，印刷 p65–69 / PDF 89–93](</work/jay/tape-rs/IBM Spectrum Archive 企业版 V1.3.2.2 1.pdf#page=89>)。

8. **恢复服务不等于恢复旧任务；调度优化也有语义边界。** 书中控制节点 failover 后，原运行任务可为 aborted，需要手工重新提交；它另外提供任务历史，不应被本项目借鉴成已取消的回执功能。读回调度可按磁带和文件起始块排序，但集中到达的请求才有优化空间；RAO 还依赖支持的驱动、额外计算，不能认为地址递增就是所有布局的最优寻道。这里的历史重交和读取优先策略属于 EE 行为，不直接决定本项目的安全重传、写入公平性或接口契约。[§1.2.1，印刷 p7–8 / PDF 31–32](</work/jay/tape-rs/IBM Spectrum Archive 企业版 V1.3.2.2 1.pdf#page=31>)；[§6.14，印刷 p190 / PDF 214](</work/jay/tape-rs/IBM Spectrum Archive 企业版 V1.3.2.2 1.pdf#page=214>)；[§6.14.4，印刷 p193 / PDF 217](</work/jay/tape-rs/IBM Spectrum Archive 企业版 V1.3.2.2 1.pdf#page=217>)。

## 差异矩阵：如何用于地图

“可借鉴”仅指未来设计参考；不在本报告中冻结新模块、API、默认参数或用户语义。

| 主题 | 原书机制 | 本项目约束 / 可借鉴方向（推论） | 不能直接移植 |
| --- | --- | --- | --- |
| 应用文件入口 | Scale 命名空间、HSM stub/回迁、DMAPI（事实 1、2、5） | 既定 Native SDK → ltfsd 与独立 low-level FUSE；共享独立核心能力 | GPFS 共享 inode、HSM 文件状态自动变成本项目 POSIX 契约 |
| 带库调度 | MMM 集中选择任务/带/驱动、目录与空间估计（事实 3） | 在既定当前 owner 内统一资源安全检查，候选任务优先考虑已装载介质以减少无效换带；公平性/优先级另定 | 原书 mount limit 数值、自动多副本/跨库迁移、未经接受的永久读优先 |
| 数据路径 | 多 EE 节点各持自身驱动集合（事实 4） | 当前只在 active 节点使用整组已分配驱动；逻辑职责分开不意味着新建进程 | scale-out、多节点并发写、多份独立设备所有权 |
| HA/健康 | 监控、组件恢复、MMM 切换（事实 6） | 可借鉴按组件报告故障；保持外部 fencing、整组 ownership 及恢复安全证据门槛 | 用心跳或进程存活直接授权写带；复制 EE 的恢复操作顺序当成项目证明 |
| 目录与持久状态 | 所有 EE 节点共享 GPFS metadata，存在配置数据库（事实 5） | 已提交文件状态以磁带恢复结果为准，本地 catalog/cache 非权威；B 仍需配置、介质发现信息及密钥等既定前提 | 引入 GPFS/共享磁盘依赖，声称磁带可重建所有配置/密钥，或声称缓存可无条件代替权威状态 |
| 失败上传 | failover 后任务 aborted、人工重交（事实 8） | 与“服务恢复但不自动恢复旧上传”方向相容；无回执时应用依据可信视图和既定结果处理待定上传 | 引入任务历史数据库/回执；把人工重交解释为覆盖已有文件一定安全 |
| 性能验收 | 文件大小、驱动数、磁盘/SAN/NUMA/内存影响（事实 7） | 沿用本项目小文件专项、索引长期增长、已持久化完成量及实际硬件测量；输入继续留空 | 将 EE 实验表直接当本项目指标；假设备用节点增加吞吐；照抄 GPFS metadata 估算公式 |

## 对后续地图的有限建议

- 把“不依赖 GPFS / Spectrum Scale”写成显式边界；参考 EE 不等于实现一个删去 GPFS 的 EE。
- 在尚未解除依赖的核心职责设计中，后续再评估“应用接口适配、资源调度、LTFS 提交/恢复、设备执行”的职责边界；这只是本项目推论，不是原书模块映射，也不提前关闭接口与恢复票据。
- 同一 active 节点内可考察装载亲和性与读取定位成本，但先保持已接受的索引不可穿插、容量保护、冻结提交和有限缓冲规则。调度策略不得隐含允许中断在途设备命令或覆盖索引。
- 第 9 章提供的检查/修复流程应由主地图继续独立核对；本报告不证明“找到最大 generation 即为最新有效链”，不把可破坏性修复列为自动恢复步骤，不宣称已得到实机可安全追加的完整协议。
