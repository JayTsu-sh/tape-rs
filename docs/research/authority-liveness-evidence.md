# 持续多数派活性与执行资格时效的证据边界

日期：2026-09-15；票据 21。范围：为已授权的当前 Leader 持续设备派发门控提供证据，不设计完整租约，不选库、参数或线程布局。

## 结论

**CheckQuorum、RecentActive 或本地 Leader 状态不能直接转换为带真实期限的设备许可。** “当前上下文有效授权 + 有时效的多数派证据，过期则终止本轮执行资格”可以作为项目候选政策，但证据形成、刷新和派发竞态仍需证明；这不是 Raft 自动提供的跨节点独占租约。外部 fencing 继续必需。

## 官方事实

本次源码固定为 etcd-io/raft commit `3cbf6a74be3fa392edd8b64253fcd11c3ce5649b`，不是本项目库选型。

- `CheckQuorum` 由逻辑 tick 达到检查周期时触发，检查近期活跃多数派，不足则退位，随后清除其他节点的活跃标记；收到相应 Append/Heartbeat 响应会设置 `RecentActive=true`。这些分支本身不保存“本次活性证据发生于哪个真实时间”的设备许可字段。源码也警告租约式读取在时钟无界漂移/暂停时不安全。[固定 raft.go：Config、tickHeartbeat、stepLeader](https://github.com/etcd-io/raft/blob/3cbf6a74be3fa392edd8b64253fcd11c3ce5649b/raft.go)
- `RecentActive` 定义为近期活跃布尔标记，可在选举超时后重置；它不是一组带时间与挑战轮次的证明。[固定 tracker/progress.go](https://github.com/etcd-io/raft/blob/3cbf6a74be3fa392edd8b64253fcd11c3ce5649b/tracker/progress.go)
- `Node.Tick` 推进逻辑时钟；向内部 tick 通道提交失败时，代码报告遗漏 tick，而不是将真实经过时间自动完整折算。[固定 node.go：Tick](https://github.com/etcd-io/raft/blob/3cbf6a74be3fa392edd8b64253fcd11c3ce5649b/node.go)
- 原论文指出 Leader 可能不知道自己已被替代；读取时取得多数派回应与依赖计时假设的租约是不同方案。Raft 日志安全不依赖可靠计时，不等于建立在其上面的设备许可也自动获得这一性质。[Raft §5.6、§8](https://raft.github.io/raft.pdf)
- Linux 的 `CLOCK_MONOTONIC` 在系统 suspend 时停止，`CLOCK_BOOTTIME` 包含 suspend，`CLOCK_REALTIME` 可调整或倒退。仅写“单调时钟”不能完整说明暂停语义；这些内核说明也不能单独证明某种 VM 暂停/快照恢复的行为。[Linux timekeeping](https://docs.kernel.org/core-api/timekeeping.html)

## 反例与候选约束（项目推论）

| 反例 | 为什么旧检查不足 | 候选要求 |
| --- | --- | --- |
| 上次检查通过，此后不再收到新证据 | 检查结果只涵盖此前一段历史，不是未来持续保证 | 期限有明确证据起点，过期停止新命令，不能因再次读到同一个 bool 续期 |
| 同 term 响应在网络/队列滞留很久才送达 | 通过 term 检查不等于最近生成；到达时刻不等于证据生成时刻 | 响应须关联当前配置、Leader/执行实例、接管轮次及可核验的新鲜性上下文；不能任意旧响应到达即 `now + T` |
| 控制循环卡住，但独立 I/O 路径仍运行 | Tick/CheckQuorum 不推进，缓存 Leader 状态可能一直未变 | 派发路径不得依赖卡住的控制循环才能让旧许可过期；控制停滞不能靠旧状态续期 |
| 进程或 VM 暂停后恢复 | 旧许可、旧响应、旧计数可能一起恢复；补跑 tick 不产生新多数派证据 | 恢复后先核验时效/暂停上下文；无法证明有效则保持关闭，已失效旧轮次不复活 |
| 通过本地检查后立即暂停，恢复后才进入设备调用 | 即使刚检查时证据真实，也存在检查到实际派发的时间窗口 | 必须证明交付边界并依靠外部隔离约束陈旧执行；每命令检查仍不是单独的全局独占证明 |

“任意旧响应”并不意味着官方代码忽略 term：它有 term/成员等协议检查；问题是这些检查不等于本项目要求的真实时效证明。即使采用带 request context 的多数派交互，也须核验关联的轮次、计时起点及响应年龄，不能将其返回时刻机械转化为未来无条件许可。

可评审的最小政策：当前授权已提交应用、上下文仍有效且存在未过期的合格多数派证据时，日常设备命令做本地门控；未在期限内取得合格证据则终止该执行轮次，不等待撤权日志提交。旧响应、旧授权 apply 或时钟恢复不能自动开启已终止轮次；重新工作须按既有新轮次授权/隔离核验流程。

三成员中单个 follower 丢失不等于立即失去多数派，只要仍有当前规则认可的多数派证据且其他门控成立，不应因此自动撤权；一旦已观察到明确失效，不能等待剩余期限才停发。没有业务写入不是控制停滞：健康空闲集群可以继续交换有效控制活性证据，不能强制用户通过上传或制造文件提交来续期。

## 本地时效不是跨节点租约

本地证据有效期只规定本节点何时保守停发；如果其他节点没有参与并遵守相容的授权期限/选举约束，它不承诺“期限内不会选出其他 Leader”。不能从同一次历史 quorum 活跃推导两任执行者的许可必不重叠，也不能将 Raft 读取租约未经证明套用到磁带执行。

fencing 的定义正是让失联或不响应集群指令的节点也不能继续运行资源；它保护的是外部访问能力，不是本地 bool。[ClusterLabs：Fencing §8.1–8.3](https://clusterlabs.org/projects/pacemaker/doc/3.0/Pacemaker_Explained/html/fencing.html)

因此候选仍须保留外部隔离、新轮次核验及在途命令规则。“每条命令本地检查”可以避免逐文件/逐 CDB 共识，但不会消除时钟读取、上下文验证和同步成本；性能与失效延迟须测量。检查周期、期限、时钟来源、刷新协议、成员变更期间 quorum 规则及暂停识别均未选定。

## 待验证

AL01 无业务写入但有效活性证据持续时不误撤权；AL02 失去一个 follower 但仍满足多数派时不误撤权；AL03 证据过期或明确失效终止轮次且不等撤权提交；AL04 同 term 迟到/重复响应及旧配置响应不伪造续期；AL05 控制循环卡住而 I/O 仍可运行时门控到期关闭；AL06 进程/VM 暂停恢复及计时异常不复活旧轮次；AL07 最后检查后暂停、迟到 ioctl 与外部隔离边界可验证；AL08 刷新与到期并发不让已失效轮次重新有效。

上述仅为候选验证要求，未实现、未运行；本次无代码、现场 HA、时钟实验或真实硬件操作。研究不证明完整持续授权协议。
