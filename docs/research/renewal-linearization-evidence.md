# 两阶段续期的发布后时间证明与契约边界

日期：2026-09-16；票据 30。依据项目 `authority-refresh.md` 的已接受 RQ，审查本项目提出的 Pending/Confirmed 算法；文献并未提供该算法。仅官方资料与原始论文核对，无实现、模型运行、依赖选择或设备操作。

## 结论

**发布后采样有用，但当前候选不能直接标为已满足 RQ。** 在明确的时钟及执行顺序假设下，后采样 `t_after < oldD` 可以证明第一次 Pending 发布发生在 oldD 前，排除“先读时钟、暂停、过期后才发布”的反例。它不能自行决定 Pending 是否已经构成 RQ 的逻辑接受，也不能仅以“尚无人写 terminal”替代尚未到期。

确认晚于 oldD 的分支有两种不同规格：若 P 是期限前已经完成的逻辑接受，Confirmed 只公布其证明，可以继续研究；若 Pending 仍表示未接受、当前有效截止点仍是 oldD，那么 oldD 后确认就是原 RQ 禁止的复活。**必须先明确抽象状态与可观察结果，再证明它是既有契约的细化；不能通过线性化术语默认批准后者。** 本报告不放宽期限、不自行接受新语义。

## 文献事实与适用范围

- Herlihy/Wing 的线性化要求并发历史对应一个合法顺序历史，并尊重非重叠操作的先后；操作可以在调用与返回之间生效，但允许什么结果由对象规格决定。原论文第 1、2 节不赋予实现任意改写截止期限的权利，也不提供本候选的实时租约证明。[原论文][linear]
- Rust Instant 是单调非递减时钟测量，不承诺匀速，也没有跨平台统一的系统挂起计时语义；硬件、虚拟化或 OS 问题可能破坏单调性，部分时间差运算会饱和为零。[Instant][instant]
- Linux CLOCK_MONOTONIC 不计系统挂起，连续读取可能相等；CLOCK_BOOTTIME 计入系统挂起。这些不同语义说明“单调”不足以说明项目暂停模型已满足；本报告不选择时钟，也不据此推断所有 VM 暂停恢复行为。[Linux 时钟][clock]
- 原子 Ordering 约束内存同步；CAS 比较内存值，SeqCst 不把时间采样和 CAS 合并。标准原子不保证 wait-free。[Ordering][ordering]、[官方原子说明][atomic]

## 待证明的最小前提（项目推论）

令当前许可为 Active(r,D)，safe 请求原始证据期限为 E=`t0+T`，候选新期限为 N=`max(D,E)`。真正延長的分支可限定为 E>D；E≤D 的结果不产生延长，仍不能通过 N 掩盖已过 E 的证据。

第一次 CAS 前必须已经具备全部 safe 返回、真实 apply、身份/term/配置/轮次匹配及授权前提，P 不是“等网络或等 apply”的在途请求。相关失效与 P/确认共用已证明的版本化门控；否则即使时间正确，也可能覆盖已知风险。P 和证书绑定同一实例、原许可、原修订、D/N、ctx/t0、证据及不可复用身份。

若 `p` 是第一次 CAS 的实际生效事件，`a` 是随后时钟采样事件，需证明 `p` 确实先于 `a`，并且二者处于同一可信时间域。由非递减时钟才可推出 `time(p) ≤ t_after < D`；还需检查证据 E 未过期。不能把之前缓存的 now 或模型私有的 p 真值当作程序可获得的证据。具体编译/调用顺序、计时误差及暂停连续性尚需实现验证。

## 必须区分的交错

以下数值只表达事件先后，不是产品参数；例中 D=10、N=20。

| 轨迹 | 可得结论或反例 |
| --- | --- |
| 全部实质证据完成；P 在 8 发布；后采样 9；在 9.5 确认 | 正例候选：后采样证明 P 早于 D；读者仍需检查当前 N 及限制。 |
| 先检查 9，暂停到 11 才发布 P；后采样 11 | 必须终止。P 不提供 N，不能因定时器没运行而开门；确实排除票据 29 的简单 CAS 反例。 |
| P 在 8 发布，采样前暂停到 11 | 即使模型知道 p=8，程序没有合格后采样证明，必须保守终止；不得使用模型真值挽救本轮。这是可用性损失。 |
| P 在 8，后采样 9，随后暂停；无人观察 P；12 时才确认 | 关键分歧：只有“P 是有效逻辑接受、确认只公布证明”的规格才可能解释为未复活。若原 D 在 P 期间仍是本轮不可逆到期点，则 10 已到期，12 不能确认；无人观察不改变这一点。 |
| 同上，但读者在 11 看到 P，并成功 exact-P→terminal | 确认 CAS 必须失败；证书再好也不能覆盖 terminal。当前轮次结束，新工作走新授权。 |
| 读者在 11 看到 P，准备关闭；确认先赢 CAS | 读者不能用旧 P 直接判新状态有效或已终止。必须定义观察、关闭成功、拒绝响应各自含义并重读当前状态；若此前已向外明确宣告本轮终止，就不能再报告确认成功。只说“CAS 失败重试”不足以解决语义矛盾。 |
| 后采样 9；确认前再次检查 19；暂停至 21 才 CAS | 不允许按 Confirmed 标签永久放行。任何读者仍必须用当前时间检查 N；超过 N 的对象不是可用许可，下一刷新也不能复活。若要求确认 CAS 本身一定早于 N，单次确认前读时钟仍有相同暂停缺口。 |
| 任一阶段发生适用撤销、实例/配置变化、时间失信 | 不接受旧 P/旧证书；单一刷新者不消除多个失效来源。因别的事件改变修订而 CAS 失败时，不能无条件替换 expected 后继续确认。 |

## 原 RQ 的解释边界

现有 RQ 要求接受时旧截止点未过、不因请求在途延长、到期终止且终止不可复活，同时明确原子接受机制尚待证明。因此 P 不能只因叫作“发布”就算接受；但若全部实质确认已完成，P 也不必天然等同于原先“网络请求在途”。

可继续核对的细化方向是：把续期调用作为一个整体操作，对最终有有效证书且未被撤销的成功分支，以 P 作为经事后证据证明的逻辑接受点；证书可见之前，读者不得使用 N，必要时可保守终止。其证明必须解释所有读者返回和终止事件，不能只解释无人观察的成功轨迹。Pending 拒绝若含义是“目前无可使用的新期限”，不同于已经宣布“本轮终止”；两种结果不能混用。

**如果产品含义是“到 D 时，所有未获得公开可使用确认的 Pending 都已不可逆终止”，上述迟确认分支明确改变该规则，不能采用。** 此时后采样方案尚未给出不放宽规则的完整替代实现；简单增加一次确认前时钟检查并不能补上最终 CAS 前暂停窗口。建议把这条规格分歧保留为明确阻断，而不是将算法命名为线性化就关闭票据。

## 不可顺带推导的能力

- P 状态只按原 D 判断可派发范围；到 D 后没有可用新期限时不继续命令。条件关闭应真正提交终止状态，不能仅返回一个终止提示；失败后如何解释并发确认必须统一。
- 证书对象的可靠内存发布、生命周期、防 ABA、多读者和撤销的一致快照仍依赖票据 29；不可借事后证书抹去期间已发生的危险事实。
- 首次启用没有旧活动许可；K→G 改变权限种类、隔离阶段和前提。它们不能直接复用稳态续期的 P 生效点，必须另证对应协议，不提前使用新的设备权限。
- 本地逻辑接受不是跨节点租约，也不是物理派发点；最后检查后暂停再向设备/外部入口交付仍受 LG、未决效果和 fencing 约束。

上述轨迹全部未运行。当前得到的是有条件的时间上界论证、一个明确的契约分歧和待验证状态机；不是算法通过、工程已可实施或现场故障已被覆盖。
