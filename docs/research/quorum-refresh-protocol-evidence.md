# 多数派确认刷新与本地时效协议依据

日期：2026-09-15；票据 23。参考实现固定为 etcd-io/raft commit `3cbf6a74be3fa392edd8b64253fcd11c3ce5649b`，非库选型。本文不涉及读取 LTFS 索引、写带或现场集群操作。

## 结论

当前 Leader 本地发起、带唯一请求上下文的 **safe ReadIndex 类确认**，可以作为本项目持续资格刷新来源的候选。它能提供关联请求的多数派确认及控制状态应用位置，但不能单独提供未来独占设备的租约。`t0 + T` 是项目保守时效策略，不是官方 ReadIndex 返回的租约期限；外部 fencing、当前资格检查和设备交付边界仍需独立满足。

## 已核对的一手事实

1. 原论文允许不为每次只读请求增加日志，但要求新 Leader 先在当前 term 提交条目，并通过多数派心跳确认自己未被替代；依赖时钟的租约是另一种附加假设方案。[Raft 原论文 §8](https://raft.github.io/raft.pdf)
2. 固定实现的多成员 `MsgReadIndex` 路径在当前 term 尚无已提交条目时暂存请求；`ReadOnlySafe` 将请求加入待确认队列、记录本机确认并广播心跳。`ReadOnlyLeaseBased` 不走相同的每请求 quorum 广播；`CheckQuorum` 检查活跃标记，并非该请求的 safe 确认。[固定 raft.go：MsgReadIndex、sendMsgReadIndexResponse、MsgCheckQuorum](https://github.com/etcd-io/raft/blob/3cbf6a74be3fa392edd8b64253fcd11c3ce5649b/raft.go)
3. `ReadState` 只有 `Index`、`RequestCtx`，调用方负责用唯一上下文识别自己的请求；它不自带应用执行轮次、成员配置版本或 Leader term。该版本内部心跳 context 编码累计读位置，允许一次确认释放多个较早待确认请求；并非直接把每个应用 RequestCtx 当作独立的心跳 token。确认使用当前 Raft voter 配置。[固定 read_only.go](https://github.com/etcd-io/raft/blob/3cbf6a74be3fa392edd8b64253fcd11c3ce5649b/read_only.go)
4. 官方接口将读状态交由调用方处理，应用须应用到读位置才能据此读取一致状态；请求可能无通知丢失，重试由调用方负责。API 返回本身不是成功确认。[固定 node.go：ReadIndex 接口说明](https://github.com/etcd-io/raft/blob/3cbf6a74be3fa392edd8b64253fcd11c3ce5649b/node.go)

## 本项目候选流程与成立条件

以下均为**项目候选及推论**，不是官方业务授权协议。

1. 已在本轮正常执行状态的当前 Leader，在提交请求之前捕获本机开始时刻 `t0`、唯一 `ctx`，绑定集群/成员配置、Leader term、执行实例及接管轮次；进入库前的排队也计入年龄。起步阶段当前 term 的提交条件须满足，不把每周期检查变成新日志条目。
2. 只接受与本机待决请求匹配的 safe `ReadState(index, ctx)`；当前实例真实应用进度须 `applied >= index`，并重新检查当前控制状态没有撤权、换配置、换实例或换轮次。应用进度指本地状态机实际完成，不是仅收到 CommittedEntries 或安排 apply。
3. **先检查旧 deadline 是否已到期及轮次是否已终止，再处理新结果。** 若已到期，即使超时任务尚未获调度，也结束该轮次；不能由本次迟到结果覆盖过期事实。
4. 结果符合条件且本轮仍有效时，以该请求原始 `t0 + T` 计算候选期限；接受时必须尚未达到此期限。不能改成响应到达时刻、等待 apply 完成时刻或任务回调时刻加 `T`。已有更晚的有效期限不因旧结果缩短；重复结果不产生新的期限。
5. 初次启用或已经过期/失效，仍走新接管轮次及既定控制授权建立流程（CG），不能只凭周期 ReadIndex 恢复旧许可。当前任期新提交条件、控制授权 commit/apply、首次合格证据和隔离/恢复的完整顺序仍需在执行契约中明确。

`t0 + T` 的保守性来自：该确认覆盖的交互不早于对应请求发起，计时从更早的本地起点开始，网络、队列及 apply 等待只消耗期限，不凭迟到结果增加完整新窗口。但这依赖正确请求关联、当前控制上下文和可用的计时/暂停语义；它仅限制本地证据年龄，**不证明从 t0 到 deadline 之间其他节点不可能当选或执行**。

## 合并、乱序和配置变化

| 情形 | 候选处理 |
| --- | --- |
| 一次库内 quorum 确认覆盖多个请求 | 各返回 ctx 保留自己的原始 t0，不把较晚请求的 t0 借给较早结果；使用库返回的关联结果，不自行猜测心跳覆盖关系 |
| 结果乱序/重复、重试后旧结果返回 | 已消费或失效 ctx 不延长期限；新尝试使用独立关联或保留原尝试 t0，禁止把旧 ctx 改绑到新 t0 |
| 请求未入队、被丢弃或持续无响应 | 没有刷新；有界重试和待决资源需设计，旧 deadline 正常推进，不能因为“正在等”暂停时效 |
| 等待本地 apply 很慢 | 等待时间计入本请求期限，同时继续服从旧期限；apply 追上不代表旧轮次仍有效 |
| 当前 term、成员配置、执行实例或轮次变化 | 丢弃旧上下文结果，不沿用旧证明；适用的新配置/新轮次须重新建立合格证据及对应授权条件 |

原实现可处理成员配置并以其当前 voter 集合计算读确认，但这不替本项目证明“配置变化前发起的设备续期请求”可跨配置使用。`ReadState` 没有配置/term 字段，不能只看 index 大小判断资格；捕获、绑定、应用与接受检查的原子观察边界仍需集成设计。不得把节点物理健康候选集合当成 quorum 配置。

普通空闲不需要制造上传或周期 no-op 来证明活性；合法的周期 quorum 交互本身仍有网络、排队及 CPU 成本。普通文件/磁带命令只做本地许可检查，不因此逐条共识；控制循环停滞、系统/VM 暂停及“检查后暂停再发命令”的外部效果竞争仍未由本方案消除。
