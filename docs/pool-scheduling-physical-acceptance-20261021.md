# 池与多驱动调度 GAP 实施及现场验收

状态：本次池调度范围实施及物理验收通过；EE 全产品 GAP 尚未全部关闭。

## 本次范围

本次落实已识别的池写入调度差距：显式选池、同池多驱动并行、迁移并发配额、介质/驱动兼容检查、容量未知时的安全准入，以及同一 VIP 下的 owner 交接。GPFS HSM 生命周期、文件多磁带副本、跨池 datamigrate 等另列差距不在本次调度实现范围。

- HTTP 数据面使用 `/libraries/<真实序列号>/pools/<名称或UUID>/...`；多个池时省略目标返回 `400 pool_required`。管理操作仍使用库级 `/admin/...`。
- Rust Client、ltfsctl 和远程 FUSE 支持 `--pool`；每个 FUSE 挂载固定一个库和池。
- 一库一个设备 owner，共享池命名空间及任务表，各写入驱动独立队列、会话和容量账本。独占的设备句柄移交并行作业，所有作业返回后才允许机械操作、维护及释放预留。
- `mountlimit` 限制当前迁移写入租约；仅装载介质或执行读取不占配额。空闲写入租约可排空并让给另一个池或读取。
- 先核对驱动 REPORT DENSITY SUPPORT/WRTOK，再核对已装载介质格式；不符合池介质限制的已有内容仍可读取。排序优先已装载介质，其次缓存的物理使用比例、最后条码；这不是对 IBM 未公开排序算法的复刻声明。
- 写入预算同时要求可信 DP/IP 剩余容量，并扣除索引和事务余量。未知容量暂停新写入；不再使用虚构的 1 PiB 预算，不撤销已确认提交，周期性刷新后恢复。

接口说明见 [文件客户端](file-client.md)。模拟器通过不能替代下列物理证据。

### 验收中发现的问题

百万条真实 LTFS 目录恢复曾使控制线程长时间构造目录报告，导致其他库许可过期。最小回归先红后绿：改为事件直接移交目录所有权，控制循环按确认逐片准备，保持报告序号及原子目录提交。后续物理复验继续发现每 30ms 重提目录报告造成积压，以及最终 SQLite 合并/快照阻塞控制循环。现改为确认后立即发送下一片、在途报告有界重试；大型合并及一致快照由后台独占目录连接，目录更新按日志顺序有界批量追齐。原子合并期间仅该库数据请求返回 503，读快照本身不暂停入口；所有设备许可仍需原有多数派确认，没有延长许可或机械超时。新增写锁阻塞、持续来流追齐、快照索引及数据入口回归均通过。

R8 又发现一个许可调度错误：库目录忙时跳过候选序号的观察，Leader 把仍在线的设备 owner 判为过期，约每 90 秒重新分配轮次，15 分钟内 B 库始终未 Ready。R8 未写入本轮验收文件，控制器按预案停止测试服务、撤销 VIP、恢复原磁带池标记及 EE，清理证据见 `physical-r8/cleanup.json`。修复将候选新鲜度更新与目录报告 ACK 分开，目录忙时仍观察候选，ACK 则等待本地目录追齐；回归测试已通过。

R9 在真实 AA0000L8 的约 108 万条 LTFS 目录中完成原子恢复，许可未丢失，owner 未异常改选；两个池同一路径分别写入/读回不同 SHA，省略池返回 400，`ltfsctl --pool` 与两个真实内核 FUSE 挂载完成写入和读回。首次同池并发上传在 VIP 已返回 `100 Continue` 后遇到 `BrokenPipe`，没有可确认的提交；根因是网关把 `Expect` 透传给 owner，后者提前拒绝时关闭尚未读完的请求体。网关现剥离该头，owner 对明确拒绝的转发请求读完声明的请求体，真实 TCP 与回归测试通过。R9 清场通过，文件系统和原介质状态的复核见 `physical-r9/cleanup.json`。
