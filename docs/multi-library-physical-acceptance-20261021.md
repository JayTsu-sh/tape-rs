# 单集群多带库与 VIP 现场验收（2026-10-21）

已实现一个 ltfsd Raft 集群统一管理多个带库，并通过固定 HTTP VIP 转发请求。两个库可由同一节点持有，也可分散持有；用户无需知道设备 owner 地址。配置和路径见 [多带库说明](multi-library.md)。

## 数据面结果

主证据：[R3 acceptance](../.scratch/ltfs-ha/probes/results/multilib-physical-r3-20261021/acceptance.json)。所有用户数据请求只访问同一个 VIP URL，通过库前缀选择资源。

| 场景 | 现场结果 |
| --- | --- |
| 入口节点无 FC 权限 | 208 在 SG 全禁用时提供统一入口，任意设备 owner 均由入口内部选择 |
| 同节点持有两个库 | l9、l8 都由 207 持有；两库同名相对路径分别写入不同内容并 SHA256 读回 |
| 分散持有 | l9=207、l8=209，入口仍在 208；旧文件通过原 VIP 读回，l8 新追加成功 |
| 一个库失去唯一 owner | 停止 207 后 l9 无可用 owner；l8=209，VIP=208，l8 继续追加和读回 |
| 库恢复 | 209 获得 l9 访问权限后接管，两库均可从原 VIP 访问，l9 新追加及旧文件读回通过 |
| VIP 节点停止 | 恢复控制多数派后停止 208，VIP 接管到 209；同一地址读回之前文件并继续写 l8 |
| 原数据保留 | AA0013L8 原 64 MiB perf64m.bin 和 48 字节旧 marker SHA256 均保持一致 |

R3 追加 6 个 4 MiB 文件，合计 24 MiB，全部在接管/入口迁移后读回。此前 R2 已追加的两份 4 MiB 测试文件也保留，没有回滚介质或覆盖原测试目录。757 轮并行地址采样没有观测到双节点持有 VIP，也没有采样错误；这是采样证据，不代表对任意短时间窗口的连续测量。

接管存在预期的短暂 503：ExecutorReady 已提交之后还须取得 ReadIndex 服务许可。探针对明确只读暂态等待后重查；写操作结果未定时不自动重发。旧用户无需更换节点地址，但仍需处理短暂不可用。

[逐 CDB 审计](../.scratch/ltfs-ha/probes/results/multilib-physical-r3-20261021/hardware-command-audit.json) 确认候选数据面没有 FORMAT/ERASE；未归属的 TD8/8A0042 只有 INQUIRY、PR IN/OUT，没有 LOAD、WRITE 或文件标记。实际 MOVE 只将 RC18 从 1007 装入 l9 驱动、AA13 从 1001 装入 l8 的 HH8。清场归槽是单独记录的显式维护命令。

## 快照与迁移兼容性

[真实快照专项](../.scratch/ltfs-ha/probes/results/multilib-snapshot-physical-20261021/) 在三台物理主机上运行，全部 SG 访问关闭，不管理 VIP 地址。停掉 207 后，从 Follower 209 的 HTTP 入口向 Leader 创建 40 个临时池，等待源节点压缩日志，再重启 207。节点确实安装了控制快照并通过节点通道拉取分库目录包；日志记录报告/文件索引 41817、本地应用索引 41820。两个库的 6 个 R3 文件目录行、长度及 SHA256 完整。40 个临时池随后从全部节点删除。

分片复制、缺片拒绝、实际文件索引领先传输头的场景有纯软件边界回归。接收端按经过校验的实际快照文件索引安装，并在本地控制日志追齐前阻止执行许可。

[旧 VIP 迁移专项](../.scratch/ltfs-ha/probes/results/multilib-legacy-physical-20261021/) 是在物理主机运行的**控制面兼容性夹具**，不代表真实介质事件。它从停机的旧单库状态离线派生，追加晚于快照的旧 Takeover/Fenced/Ready/VipAcquire，全部 SG 关闭。新网关 owner=72 时仍保留旧 node=71、round=34558、token=34561 的占用屏障。仅重启 71 的真实 VIP 网络线程后，确认内核撤址/地址不存在并提交 ACK，屏障才释放。整个专项没有 SG_IO，也没有实际添加 VIP 地址。

修复前单测能稳定复现丢失该屏障：新网关 owner 状态不能用来重新验证历史设备 owner 的 Acquire。修复后先在默认库的历史状态上验证，再迁移已经验证的 VIP 记录。

## 清场与接续

[最终复核](../.scratch/ltfs-ha/probes/results/multilib-snapshot-physical-20261021/post-close.json) 确认临时单元均停止、三个节点均无 VIP、原 17421 控制集群 executor 仍为 null。EE208 available/enabled、207 disabled、没有活动 EE 任务；l9 原 drive/changer 键 0x400000000a8307d0 / 0x500000000a8307d0 为唯一注册及 type 3 holder；l8 无 PR。RC18 槽7、RC17 槽8、AA13 槽1、AA00 槽2，8A0042 仍在 TD8，HH8 空。

供后续接续的最新**真实介质目录状态**是三节点 `/root/tape-multilib-snapshot-20261021/state`。`/root/tape-multilib-legacy-20261021/{fixture,state}` 是基于旧目录派生的兼容性夹具，禁止按更新时间选作真实目录或回滚覆盖前者。最终候选二进制在各节点 `/root/tape-multilib-legacy-20261021/bin/`；尚未替换正式服务。

R1 只在设备关闭状态验证迁移，因探针过早使用 leader=0 而退出；随后补齐无设备、无 VIP 的控制多数派完成撤址。R2 完成同节点双库写读及分散持有，因探针对接管暂态 503 未等待而退出，已完整清场。两轮失败及原始证据保留，不计作整轮通过。
