部署拓扑 ltfsd × 3 · 逻辑库 TAPERS

Raft 决定谁能执行，驱动器本身不认识任期，所以靠 SCSI 持久预留把旧执行者挡在设备外面。集群里任何时刻只有执行者一个节点会给设备发命令。

模块分层 src/ · 约 1.4 万行

每层只依赖它下面的层。最关键的一道缝是 TapeTransport：上面所有代码都拿 &dyn TapeTransport，因此同一条 LTFS/ltfsd 路径既能跑在真设备上，也能跑在内存模拟库上。

ltfsd 节点内部 线程 · 通道 · 文件

设备操作可能要几分钟，所以设备只由执行线程访问，绝不放在 Raft 循环里。线程之间只通过 mpsc 通道和共享的 FileService 交互。

接管时序 round = Takeover 的日志索引

轮次不是任期，而是 Takeover 条目提交时所在的日志索引，所以它全局单调，可以直接写进预留 key。隔离要回读确认，并且由多数派记录下来，之后才允许动卷。

为什么要回读。fence 返回的 Fenced 只在回读后确认注册表恰好只有本 key、持有者就是本 key、PR 代数前进过时才成立；传输出错一律当作“未确认，不接管”。
同一发起者无法被设备拒绝。同一台机器上的旧实例共用发起者，设备分不出来，所以 LtfsVolume 在追加首字节前、提交动带前、屏障前各做一次 guard 检查。
绝不在 fence 之外抢占。IBM LTFS 把 PR 用于多路径，遇到冲突会反抢；tape-rs 只在 fence 里注册或抢占。

上传写路径 PUT → 落带 → 目录

202 只表示正文已暂存；归档成功的定义是磁带上的一次提交。目录记录在提交之后分片写进 Raft 日志，同一批只有等摘要到齐才一次性可见。

磁带上的布局 LTFS 2.4 · 按 IBM LTFS 2.4.8.3 校验

两个分区：P0 索引分区只存最新索引，每次提交整段重写；P1 数据分区只追加，数据和各代索引交替出现。恢复时先看 MAM 里的 VCR/VCI 走快速路径，不命中再从 EOD 倒着找。

尾部分类含义挂载结果怎么出去
T0 Complete最后一个有效索引的收尾 FM 之后紧接 EOD可写—
EmptyData数据分区只有标签可写—
T1 UnindexedData最后索引之后还有没被索引的数据（写到一半被接管）只读close_tail：Discard 记入 tapers.abandonedBlocks，或 Salvage 进 _ltfs_lostandfound/
T2 TruncatedIndex索引写了一半只读close_tail，前提是 guard key 已设置且持有者校验通过
T3 FakeIndex / T4 Unknown看起来像索引但自指针不对 / 无法判断只读拒绝自动处理，需人工介入

磁带状态 复制状态 TapeState

状态放在 Raft 复制状态里，校验发生在应用（apply）时，所以每个节点得出同一个结论。没有归入池的带既不装载、不探测，也不写入。reclaiming 不能成为死胡同：放弃回收时一定要写回一个出口状态。
