# FDB 原生磁带回收

原生 reclaim 由 tape-rs 的设备执行线程、FDB 管理任务和 LTFS/SCSI 实现，不调用 EE、GPFS 或挂载的 LTFS。它迁移原卷当前有效文件，并为实际源索引中的全部对象保存可验证的目的副本，最后重新初始化源带。任务完成前不能把介质当作可用空带。

本文描述当前开发实现。软件回归和真实 B 库验收分别记录；帮助中存在入口不代表已部署节点完成验收。

## CLI 与 HTTP

```sh
ltfsctl -e HOST:PORT -l LIBRARY -p POOL tape reclaim BARCODE --yes \
  --request /var/lib/tape-client/reclaim.json
```

`--yes` 明确允许在迁移、实读校验和全部安全条件满足后重新初始化源带。默认保留池归属；`-u` / `--unassign` 要求初始化后将源带正常退带、归原 home 并解除池归属。新请求可以指定多个条码，按盘保存独立请求并排队；同库串行执行。

提交只返回原 `task_id`、`request_file` 和任务回执，不等待机械操作。通过 `task show TASK_ID` / `task list -l LIBRARY` 检查原任务。逻辑文件的 inode、路径和正文保持；迁移经普通原子上传发布，新版本号递增，S3 的 opaque ETag 可能变化。恢复数据通道后，以新 HEAD/List 返回的 ETag 进行条件读取。响应丢失或客户端重启时执行：

```sh
ltfsctl -e HOST:PORT tape reclaim --request /var/lib/tape-client/reclaim.json
```

恢复时不再给条码、`--yes` 或 `-u`；这些参数已经封存在原请求中。不要为结果未知的操作生成新请求。

HTTP 提交入口为 `POST /libraries/{serial}/admin/pools/{pool}/tapes/{barcode}/reclaim`，也可通过共享管理请求入口先 prepare、保存完整请求，再提交。请求使用规范 JSON，携带与路由相同的 `x-tapers-catalog-namespace`。`change` 的字段必须完整：

```json
{"barcode":"BARCODE","confirm_format":true,"kind":"media-reclaim","pool":"POOL_UUID","revision":1,"unassign":false,"volume":"SOURCE_VOLUME_UUID"}
```

外层仍为公共管理请求的 `version/library/namespace/epoch/operation/change`；池、卷、归属修订和同一操作身份不能在重试时变化。CLI 和 HTTP 共用后端确认、归属、互斥及格式化检查。

## 持久父流程

1. 原管理任务与源卷预留在同一 FDB 事务取得同库互斥；池写入屏障和设备布局随原任务保留。
2. 核实库存、address map、home、条码、卷和驱动器身份，固定同池目的带及两个独立驱动器。已固定布局不得在错误或接管时改选。
3. 从实际源 Full/增量重放视图封存完整物理清单；随后按有界页枚举逻辑文件。每个正文先实际读源并计算摘要，使用封存的原子请求写目的，再实际读回核验，才能退休精确原副本。
4. 保存原始目录、根、链接、普通文件和 EE 内部数据节点的属性。未映射到逻辑目录的实际源正文也迁移；EE 别名解析到本卷真实数据节点，已知 SHA-256/MD5 必须匹配。来源无摘要时仍实际计算 SHA-256。节点的元数据覆盖与正文覆盖分别证明。
5. 全部物理对象和逻辑扫描完成后，按每事务最多 16 条源反向引用检查旧副本。仅在本命名空间内，有完整新版本证明或永久删除 NR/历史 H/原删除结果证明的旧副本可退休。C 保留来源墓碑，原上传和删除结果保持；不复活已删除文件。未知、同版本仍保留的副本及其他命名空间引用继续阻止初始化。
6. 重新核验实际源、全对象覆盖、全局零 V 和全部在途/恢复占用。目的带已有介质故障、要求导入或待验证时也不初始化源带。任何一项缺失均保持原任务和证明。
7. 原格式化目标先持久化，固定新 UUID、时间和空索引配方，再逐 CDB 检查当前 owner、Permission 和 PR 执行。当前使用已有两分区的快速重新初始化，不发送重新分区 FORMAT/MODE SELECT，不提供安全擦除承诺。
8. 实读确认两分区标签、精确空索引与 MAM；按原请求保留归属或实际归槽后解绑，原子完成原任务、保存独立结果并释放自己的占用。有界清理临时账本保留独立结果及永久卷 UUID 身份。

原始属性归档使用 `_reclaim_<operation>/data-<uid>`、`node-<uid>` 等内部路径；逻辑路径仍由 FDB 维护。原生链接按逻辑相对路径落带，并保留链接文本。缺失父目录按固定来源配方创建。若该路径已有普通文件且没有其他相对链接指向其旧路径，原文件只改名称保留到固定 `_reclaim_displaced_<parent-fingerprint>_<uid>` 路径，原 UID、正文 extent 和属性不变。已有目录、链接或仍被其他相对链接引用的文件冲突明确拒绝，避免改变已有链接的解释或丢弃子树。执行和结果观察也复核已封存计划；不发布破坏现有链接解析的提交结果，但仍允许以实际 NoWrite 证明结清未开写意图。

## 故障与 HA

原父任务、子请求、物理命令 issue、观察、原子回执和依赖诊断都保存在 FDB。接任先领取原任务，再核实实际介质，正常数据通道在恢复期间保持关闭。查询管理任务不需要等待全部迁移完成。

排队请求的原归属、卷或修订号已失效时，仅在同一 FDB 读版本证明原父、完成结果、库/池占用和布局都不存在，才保存原 `failed` 回执并移除其队列项；不会因此反复撤销健康 owner。已经运行、已有原占用、数据库故障或证据损坏不能按“未执行”结束。

机械命令已 issue 但结果未知时只观察原库存/TUR 后置条件；不盲重放 LOAD、UNLOAD、MOVE。原上传 Q/I 结果通过原 S4 恢复；终态已保存但监控尚未收尾时，独立书签保留原结果历史引用，收尾完成后才释放。

确认取消且无提交的子上传可建立唯一的新后继，必须重新实读、准备和取得自己的准入名额；原取消结果不改写。独立谱系与双向边限制最多三个自动后继，缺边或证据损坏拒绝推进。结果未知不能当作取消。

元数据 Writing 重入先观察。DP 提交已经观察到而 IP 尚待修复时，该精确观察随原 Checkpointing 阶段保留；它本身不发布目标卷或授权清理。原 T1/T2 尾部通过明确 Discarding/Checkpointing 意图、原来源实读和独立回执恢复；重新规划必须采用新的实际 donor 或源读证明。旧 owner 的证据不能变成新 owner 的设备许可。

任务保持 `running` 时，`progress.phase`、`progress.mechanical` 和 `progress.dependency` 分别描述父阶段、机械结果及依赖原因/观察时间。等待资源或故障不冒充成功。FDB 不可达时依赖诊断本身也可能未保存，执行端明确报错并停止依赖它的设备操作。

只有尚未开始迁移、没有未结清副作用且原占用可精确核实的父任务可安全取消。其余情况保留原任务，不能通过清锁、删除 V、改条码或重建请求强行继续。

## 当前运行边界与优化方向

- 当前每个父任务固定一盘目的带和两台独立驱动器。资源不足、目的空间不足或原布局不可用时保留原任务等待/诊断，不自动跨目的带重试，不覆盖原数据。
- 同库的正常数据通道在回收和恢复期间关闭；不同库依旧各自管理执行权。
- 来源清单与 FDB 账本按页处理；元数据提交挂载仍需物化索引树，并非全流程恒定内存。
- 原生回收使用完整 Full 历史核验。遍历深度以实际末索引所在逻辑块为有限上限，避免普通读取的默认 64 代截止阻塞正常长历史；单索引大小、磁盘暂存、尾部搜索和增量重放预算保持。超出可计数范围、链损坏或无法完成证明时保留原任务，不能接受截断历史。
- 当前按原对象逐项提交与实读核验。批量提交、复用已核验卷会话、减少重复挂载及机械定位是后续性能优化项，不能通过删除最终屏障、逐 CDB 所有权检查或目的实读来提速。

软件注入与真实带库结果必须分开报告。软件的 HA、缺证据、损坏记录和故障断点通过，不能替代真实机械、介质和固件验收。
