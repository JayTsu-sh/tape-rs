# 持续执行资格刷新协议草案

关联：[执行授权票据](issues/18-raft-execution-contract.md) · [限定研究](issues/23-quorum-refresh-protocol-evidence.md) · [决策地图](map.md)

状态：[实现方向、首次确认等待及保守暂停取舍已接受](issues/18-raft-execution-contract.md#已裁定周期多数派确认与保守期限刷新)，具体协议仍为草案，未实现或执行。沿用已接受的 CG/QG/TG/FG/SG 政策，不选择 Raft 库、计时 API、线程布局或数值。这里只讨论已提交设备执行授权的本地启用及持续时效；[H1 有限协调与 K→G 衔接](issues/18-raft-execution-contract.md#已裁定隔离协调许可与设备授权衔接)已另获接受，其具体集成仍须单独满足控制授权与安全协议，不能由本协议隐式授权。

## 选择与边界

已接受使用由当前 Leader 本机发起的 **safe ReadIndex 类多数派确认**，作为周期性刷新来源，不为每次刷新新增一条业务授权/no-op 日志。Raft 内部必要持久化、本任期首次提交及 CG 的授权建立/终止规则不省略。ReadIndex 是控制协议术语，不是读取 LTFS 磁带 index；此确认不访问磁带，不确认上传成功。

参考实现的 safe 确认与 CheckQuorum 活跃标记、lease-based 读取不同；返回结果的关联、配置语义与本地应用进度必须由集成层正确处理，具体依据见 [23](issues/23-quorum-refresh-protocol-evidence.md#answer)。不能把某个名称相似的 API 当作已经具备全部保证，也不在缺少接口时静默降级到只看 Leader 布尔值。

## 本地状态与请求关联

| 本地状态 | 含义 | 允许转换 |
| --- | --- | --- |
| 待启用 G | 新轮次授权 G 已按 CG 提交并在本机应用，现实隔离前提仍成立，但首次时效证据未完成；设备恢复 I/O 尚未开放 | 取得本轮首次合格确认才进入有效；超时/资格失效转入终止 |
| 有效 G、D | 本轮资格仍有效，D 为现有本地截止点；设备/卷能力仍按恢复状态分别检查 | 原期限未过时，合格新证据可更新 D；过期或已知失效转入终止 |
| 终止 G | 本轮已失效，停发规则生效 | 旧结果不能返回有效或待启用；重新工作需新的 CG/TG 轮次 |

G 不是单独的磁带 generation 或 Raft term，须绑定集群、节点/执行实例、接管轮次、授权记录、受管范围与配置。请求还绑定发起时的领导上下文及有效成员配置代际；配置集合后来变回同样内容，也不能把发生过的上下文变化抹掉。具体表示和持久化字段仍待实现设计。

每次确认记录唯一关联 ctx、进入协议队列前的本机发起时刻 t0、绑定上下文和所需控制应用位置。ctx 不能跨轮次/实例复用，也不能把同一个 ctx 重新绑定到更晚的 t0。参考实现可能合并多个确认，集成层使用实际返回的请求关联，不自行猜测“某个心跳代表所有请求”。

## 首次启用

1. 完成 CG 的本轮授权提交和本机应用，复核当前合法 Leader、控制存储、安全隔离及 G 的上下文；任何已知失效均不进入此分支。
2. 仅对从未被终止的这份新授权发起首次 safe 确认，保留原始 t0；所选实现须满足本任期提交等协议前提。
3. 取得匹配结果并满足下节全部证据检查后，以 `t0 + T` 建立本地截止点，再允许进入 H2 的受限设备恢复。T 为已定义但数值留空的证据最大有效期限。
4. 首次确认期限耗尽或前提失效时终止 G，不能将同一份旧授权再次标为“首次启用”。确认成功也不直接开放正常文件读写，仍须 R1—R5。

这明确增加一次首次合格确认的控制等待；本轮不以授权提交完成时间直接替代首次 t0，也不承诺该等待总能在期限内完成。

[首次与 K→G 的独立候选](activation-handoff.md)现进一步限定上述第 3 步：全部非时间证据就绪后发布 Pending，后采样证明及时才公开可核验证书，读者使用时仍核验当前 E。存在活动 K 时，G 首次证据只构成不可执行候选，必须通过统一交接才能开放 H2；不能先独立启用 G。准备封闭后首版固定已证实 Dk、不再刷新 K，失败不回开；AH01—AH06 未执行。

## 稳态刷新与接受顺序

普通文件/磁带命令只走本地资格及资源检查；周期确认由控制路径推进，不按文件数或 CDB 数触发。拟采用以下顺序，原子观察与更新机制仍须实现证明：

1. **先检查现有状态。** 若 G 已终止、现有截止点已过，或存在已知资格/安全失效，先关闭门控，不因有请求在途延长有效期。
2. **有界发起确认。** 已接受首版每个设备执行上下文最多保留一条用于资格刷新的待处理请求；重复调度合并，不堆积无限请求。保留 ctx 和 t0 后再提交给协议层，入队耗时计入年龄。这个限制只针对本组件，不限制 Raft 实现内部其他读请求。
3. **核对确认关联与真实应用进度。** 仅接收匹配 ctx 的 safe 结果；本机控制状态机实际 `applied_index >= returned_index`，返回位置不得早于 G 所要求的授权位置。只收到已提交条目或安排了应用任务还不够。再次核对当前授权、Leader、成员配置代际及执行上下文未变，隔离和控制存储前提仍成立。
4. **先判过期，再更新期限。** 网络返回、等待本机 apply 和处理回调的耗时均不重置 t0。接受时须同时满足现有 G 尚未过期、`now < t0 + T`。候选期限为 `t0 + T`，不是 `now + T`；更新为 `max(D, t0 + T)`，旧结果不缩短现有有效期限，也不凭重复消费产生额外延长。
5. **消费或丢弃关联。** 完成处理后释放该请求关联；重复、已放弃或其他上下文的结果不能再修改资格。请求被丢弃、无响应或等待 apply 超期时不刷新，现有 D 照常推进；到期终止 G。队列清理只处理本地请求记录，不声称已取消设备或外部隔离动作。

无业务写入时仍可周期确认，不要求制造上传或周期性磁带提交。确认丢失不暂停计时；首版单待处理请求策略可能导致一次迟迟未完成的确认耗尽当前有效期，此可用性代价已接受，不宣称它不会影响服务。自动重试或更深流水线优化另需证明，不能通过复用旧 ctx 并修改 t0 实现。

## 交错与计时不变量

[组合调用顺序](permit-call-sequence.md)现串联真实 apply、P/W/C 和逐动作核验，并补充必要来源时间上界：RQ 的 N=max(D,E) 不变，各层可用截止另取必要上界；同轮成功续期可用截止不倒退，稳态 Pending 只使用旧绑定，局部资源到期不误终止共同 G。它不要求 C 必须早于旧截止，也不把发布成功当作当前可执行。
[34 后的时钟契约](runtime-clock.md)现选定 Linux BOOTTIME 作为许可基线：P 成功后才发起新 W 采样，全部本地时效比较在同一受支持时间域完成，错误/溢出不回退或重置。普通 Linux 挂起与 VM 暂停/迁移/快照恢复分开，后者的活动许可延续首版未资格化；TC 未执行，不能由时钟选择推导硬实时或外部隔离保证。

[发布后时间证据分析](renewal-time-evidence.md)进一步区分证据准备 E、待核验发布 P、后取样 W 和确认可用 C。证明 P 早于旧截止不等于证明 C 及时；[31 后的接受点候选](renewal-acceptance.md)纠正“只有 C 才能接受”的后加解释，成功分支以证据证明及时的 P 接受，C 公布证明。Pending 读者只能使用保守旧截止，终止获胜不得恢复；C 已跨新期限也不提供当前权限。原 t0、证据完整、过期不得再接受新证据及已知失效规则不变；这不是预检查加 CAS 的实现，RT/RA 未执行，首次启用、K→G 和具体时效算法仍待收敛。

[许可发布 PU05 反例](permit-publication.md#不能用-cas-隐藏的过期窗口)进一步要求覆盖“旧截止前检查，暂停跨截止后才原子更新”的窗口：到期任务未运行时内存版本可以不变，普通检查后 CAS 不证明过期不复活。RQ 的接受/生效/读者可用切点仍待收敛，本文步骤不是已证明的并发算法；不默认及时调度，也不放宽既定时效。

- 超时处理任务即使尚未被调度，结果接受路径也要先检查原截止点；不能先续期、再发现旧轮次本应终止。
- 成员配置、term、执行实例、接管轮次或相关受管配置发生变化时，不沿用旧请求证据；上下文变化与撤权的关系按主协议处理，不自行修改 Raft 成员或任期。
- 正常刷新不得清除已知失效状态；并发的更新、终止与命令交付须有可检验的顺序，不仅在请求发起时检查一次。
- t0、now 与 D 必须使用已验证暂停/恢复语义的同一本地计时依据。无法信任时间连续性时保持受限；不比较未经校准的跨机墙钟，不因补跑 tick 获得新证据。
- `t0 + T` 只限制本地证据年龄，不保证期限内其他节点不会当选。最后检查后暂停再迟发、已经交付的设备命令及旧节点不能自停，仍由交付协议、可靠 fencing 与接管核验约束。

## 候选验证与剩余缺口

**RQ01—RQ08（均未实现/执行）。** RQ01：新授权未提交/未应用、首个确认未完成或已过期，不开放 H2；RQ02：safe 确认位置已返回但本机 apply 未达到，不能刷新；RQ03：首次启用成功及稳态及时刷新正例可工作，排队/网络/apply 延迟均从原 t0 消耗；RQ04：原 D 已到期而超时任务未运行，随后结果不能复活；RQ05：合并、重复、旧 ctx 和上下文变化不能借更晚 t0 续期；RQ06：确认无响应/丢失及重复调度不会冻结 D 或造成无界待处理队列；RQ07：稳定空闲集群不靠逐周期日志或上传维持活性，普通 CDB 不逐条共识；RQ08：首次失败后不把终止 G 再次作为新授权启用，本地最后检查后暂停仍由外部隔离案例验证。

仍待补齐：最终 Raft 实现/接口及固定版本映射、状态应用可见性、上下文捕获与原子门控、首个确认/成员变更与 H1 协调的完整集成、时钟/暂停能力、周期与期限、网络/CPU/锁成本及现场 fencing 证明。周期、T 和性能目标均留空；草案自洽不等于运行验证通过。
