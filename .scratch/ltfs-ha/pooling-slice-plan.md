# 池化最小切片：方案与推荐值

2026-09-17，用户指示"按照你的建议给出方案推荐"。本文把 [42](issues/42-pool-namespace-scaling.md) 的推荐定为方案，并给出具体的默认值、数据结构、流程和分阶段计划。依据：[37 资源模型](ee-resource-model.md)、[38 任务调度](ee-task-scheduling.md)、[40 卷内布局](volume-layout-interop.md)、[41 精简后的授权](authority-after-device-fencing.md)、[索引规模调研](pool-namespace-scaling.md)。所有数值都是**可配置的默认值**，附推导；真机到位后按 06 的测量契约复核。

## 0. 已裁定

1. **目录变更进 Raft 日志**（42 的方案 B）。配套规则：目录条目永远带 (条码, 索引代数)，只是"该带第 G 代索引里有这个文件"的缓存；与磁带不一致时以磁带为准修正。这修订了 37 的"放置索引不进入 Raft"。
2. **提交必须合批，每盘带的文件数有软上限。**

## 1. 推荐默认值

| 参数 | 默认值 | 推导 |
| --- | --- | --- |
| 合批：累计字节 | **8 GiB** | EE 用 20 GB。暂存区要容纳一批在写 + 一批在收，即 2 倍；取 8 GiB 使暂存区需求约 16 GiB，实验室节点放得下。真机上可调回 20 GiB |
| 合批：累计文件数 | **20,000** | 与 EE 相同。对应一个 Raft 目录批次约 6 MB |
| 合批：空闲触发 | **2 秒**没有新上传完成即提交 | 负载轻时延迟低（约 2 秒加一次提交），负载重时自然凑成大批。EE 没有这一项，因为它是策略驱动的批量迁移；我们有交互式上传 |
| 合批：最长等待 | **60 秒** | 带 `wait` 的上传延迟上界 = 60 秒 + 一次提交耗时。归档类负载可接受；需要更低延迟的池可调小，代价见下一行 |
| 每盘带文件数软上限 | **200,000** | 此时索引约 200 MB，一次提交写索引约 1.1 秒；按最坏节奏（每 60 秒提交一次）占驱动器时间 1.9%；挂载解析约 1.4 秒；按 EE 的公式占内存约 0.4 GB。50 万时分别是 2.8 秒、4.7%、3.4 秒、1 GB；100 万时是 5.6 秒、9.4%、6.8 秒、2 GB |
| 每盘带空间保留 | 容量的 **2%**，且不小于 2 × 当前索引大小 + 1 GiB | 保证任何时候都写得下收尾所需的索引（一份在 DP、一份在 IP）。到达即转 `full` |
| Raft 目录条目分片 | 每片不超过 **1 MiB**（约 3,000 个文件） | 避免单个日志条目过大拖慢复制；一批最多约 6 片 |
| 第二个驱动器的读装载空闲超时 | **300 秒** | 读请求装载的带空闲这么久后卸回原槽位，腾出驱动器 |

**文件数上限与平均文件大小的关系（必须让使用者知道）：** 20 万文件的上限只有在平均文件不小于约 64 MiB 时才能把一盘 12 TB 的 LTO-8 用满；平均 16 MiB 时只能用到 28%，平均 1 MiB 时只有 1.7%。这是 LTFS 每次提交重写整份索引的固有限制，EE 同样受它约束（它的内存公式按"每盘带的文件数（百万）"计费）。出口有三个，按池选择：

- 应用侧打包小文件（推荐，也是 EE 对小文件的建议）；
- 把该池的上限调高到 50 万甚至 100 万，接受上表的开销；
- 实现 LTFS 2.5 增量索引（后续工作，见第 6 节），届时上限可以大幅放宽。

## 2. Raft 状态与命令

在现有 `Takeover / Fenced / Abandoned` 之外增加：

| 命令 | 内容 | 谁发起 |
| --- | --- | --- |
| `PoolCreate` | 池 UUID、名称、文件数上限、合批参数覆盖（可选） | 管理接口 |
| `TapeAssign` | 条码 → 池 UUID | 管理接口。前提（37）：未归属、在库、介质受支持 |
| `TapeUnassign` | 条码 | 管理接口。前提：目录里该带没有有效文件 |
| `CatalogPart` | 条码、目标代数、片号 i/n、文件记录数组（路径、长度、sha256、fileuid；或删除标记） | Leader，卷提交**成功之后** |
| `TapeCommitted` | 条码、卷 UUID、代数、文件数、已用字节、片数 n | Leader，紧随同一批的全部 `CatalogPart`。**应用它时该批目录才可见**，保证一批原子出现 |
| `TapeState` | 条码、追加资格（appendable / data_full / full）或健康变化 | Leader，低频 |

应用规则：`CatalogPart` 先进暂存表；`TapeCommitted{代数 G, 片数 n}` 到达且 n 片齐全时一次性并入目录，并把该带的代数更新为 G；片不齐（Leader 中途失败）则丢弃暂存，该带的目录停在旧代数，由下面的对账补齐。

## 3. 每个节点的本地目录库

复用仓库已有的 `src/catalog`（SQLite），由 Raft 应用线程单写。

```
pools (uuid PK, name, file_limit, ...)
tapes (barcode PK, pool_uuid, volume_uuid, generation, files, bytes_used, append_state, health)
files (pool_uuid, path, barcode, generation, length, sha256, fileuid, PRIMARY KEY (pool_uuid, path))
staging (barcode, generation, part, payload)
```

同一路径再次上传（05 的 replace）：新记录覆盖旧记录，旧数据成为所在带的可回收空间。`stat`、`list` 只查 `files`。客户端库判定"已提交的就是我这次上传的"改为比对 `sha256`。

**对账（以磁带为准）。** 装载一盘带读到索引代数 Gt，目录里是 Gc：

- Gt = Gc：一致。
- Gt > Gc：卷提交成功、目录条目没提交完 Leader 就失败了。用该带索引与目录求差，补发 `CatalogPart` + `TapeCommitted`。补齐前对该带上的路径 `stat` 可能漏报（41 已接受的有界陈旧）。
- Gt < Gc：不应出现（磁带回退）。该带健康转 `require_validate`，不再写入，告警。

接管时新 Leader 不需要装载任何磁带就能回答 `stat`；对账只在某盘带因读写被装载时顺带做。

## 4. 执行线程的流程

**接管**（在现有"隔离 → 多数派确认 → 恢复"之后）：读换带器库存，与 Raft 里的归属比对得出每盘带的位置（37 的派生维度）；驱动器里已有的带按现有流程恢复、收尾、对账。

**选写入带**（38 的规则）：池内、健康 ok、追加资格 appendable、在库；优先已在驱动器里的；否则可用空间最大的。装载到写驱动器。标签读不出来（未格式化）且该带已归属 → 格式化，并在卷根写 `ltfs.mediaPool.uuid` 与 `ltfs.mediaPool.name`（40）。卷根的池 UUID 与归属不符 → 健康转 `label_mismatch`，不使用。未归属的带即使在库里也绝不触碰。

**换带**：准入时空间不足、或文件数到上限 → 提交 `TapeState`，当前批提交完后卸带、移回原槽位、选下一盘。没有可用带 → 上传以确定的"空间不足"拒绝（05、40），不进入结果未定。

**驱动器分工**（TAPERS 有两个）：一个固定给写入带；另一个按需装载读请求所在的带，空闲超时后卸回。只有一个驱动器可用时，读请求要等当前批提交完再换带，读完换回。

**合批**：文件服务的队列满足第 1 节任一触发条件时，执行线程取队列并冻结批次（现有的同一把锁保证两者一致）→ 一次挂载、逐个追加、一次提交 → 发布到 `VolumeState` → 提交 `CatalogPart`… + `TapeCommitted`。带 `wait` 的上传在**卷提交成功**时即返回成功（归档成功以卷提交为准，不等目录条目）。

## 5. 分阶段

| 阶段 | 内容 | 验证 |
| --- | --- | --- |
| P1 | Raft 的池与磁带归属命令、管理接口（HTTP、客户端库、`ltfsctl pool create` / `tape assign` / `pool show`）；本地目录库由 Raft 应用驱动 | 三节点状态一致；重启后从日志重放得到相同目录 |
| P2 | 合批提交（四个触发条件）；卷提交后写 `CatalogPart` + `TapeCommitted`；`stat`/`list` 改查目录；客户端库按 sha256 判定 | PN01、PN05 |
| P3 | 库存、选带、装载、首次使用时格式化并写池标记；文件数上限与写满换带；无带可用时确定拒绝 | PN02、PN03、PN04。Holo 上建两盘几百 MiB 的小带 |
| P4 | 读路径按目录定位磁带，第二个驱动器按需装载与空闲卸载；对账 | PN06、PN07 |
| P5 | Raft 快照与日志压缩：快照 = 控制状态 + 目录库文件；落后的 Follower 经节点间通道拉取目录库文件，而不是塞进 Raft 消息 | 落后节点追赶；日志大小有界 |

P1—P4 在实验室规模下不依赖 P5（日志只是一直增长）。P5 必须在任何长期运行之前完成。

## 6. 不在本切片内

多副本与副本选择、export/offline/import、reclaim（回收被替换或删除文件占用的空间）、reconcile、多逻辑库、驱动器角色位、LTFS 2.5 增量索引、重命名与删除接口、鉴权。它们在 37、38、40 里已有方向，等本切片跑通后逐项接上。其中 reclaim 会最先变得必要：replace 和放弃的尾部都在消耗带上空间。

### P1 已完成（2026-09-17）

- `state.rs`：`PoolCreate{uuid, name, file_limit}`、`TapeAssign{barcode, pool}`、`TapeUnassign{barcode}`。校验在**应用时**做（重名、UUID 重复、池不存在、已归属、未归属），所以三个节点结论必然相同；被拒绝的命令占一个日志位置但不改变状态。`pool` 可以写名称或 UUID。
- `directory.rs`：每节点一份 SQLite 目录库，只由 Raft 应用线程写。库里记录已落库的最后一个日志索引，节点重启后 raft-rs 从头重放时跳过已落库的条目，重放幂等。P2 在这里加 `files` 与暂存表。
- 管理命令的路径：HTTP 线程 → Raft 循环（`NodeInput::Admin`）→ Leader 提交，请求号放在日志条目的 context 里 → 应用后按请求号把状态机的结论回给请求方。不是 Leader 时答 503 并指出 Leader；10 秒内没有结论（例如 Leader 身份中途丢失）答 504，语义是"结论未知，请查询后决定是否重发"。
- 接口：`POST /admin/pools/<name>[?file_limit=N]`、`POST /admin/tapes/<barcode>?pool=…`、`DELETE /admin/tapes/<barcode>`、`GET /admin/pools`（任何节点都可答，来自它已应用的日志）。客户端库 `pool_create / tape_assign / tape_unassign / pools`，`ltfsctl pool create|list [--all-nodes]`、`ltfsctl tape assign|unassign`。
- P1 只做 Raft 层面的校验。37 里 `assign` 的物理前提（磁带在库、介质受支持、未格式化或可格式化）要等 P3 有了库存才能检查；`unassign` 的"目录里该带没有有效文件"要等 P2 有了文件目录。

### P2 已完成（2026-09-17）

- **合批**（`files.rs` 的 `BatchPolicy`，`ltfsd --batch-mib / --batch-files / --batch-idle-ms / --batch-max-wait-ms`）：四个触发条件任一满足即取队列并冻结。字节数与文件数是**触发阈值而不是硬上限**：`VolumeState` 的冻结一次覆盖所有已完成的上传，不能只冻结一部分，所以取队列时把已到齐的全部带走；阈值的作用是保证不会无限攒着。执行线程按"下一批到期时间"提前醒来，周期工作（持有者自检等）仍按原节奏。
- **目录进 Raft**：`CatalogPart{barcode, generation, part, files[路径, 长度, sha256]}` 与 `TapeCommitted{barcode, volume_uuid, generation, files, bytes_used, parts, full}`。分片不超过约 1 MiB。目录库收到分片先进暂存表，`TapeCommitted` 应用且片数齐全时在一个事务里并入 `files` 表，片不齐则整批丢弃。状态机只保留每盘带的摘要，且摘要的代数不回退（迟到的旧批次被忽略）；未归属的带的摘要不接受。
- **顺序**：卷提交成功之后才把目录记录提交到日志；带 `wait` 的上传在卷提交成功时即返回，不等目录。
- **对账（以磁带为准）**：执行线程每次开放一盘带时，把刚读到的索引的完整列表交给 Raft 层；若状态机里该带的代数与磁带不同，就以 `full = true` 提交，应用时先清掉该带的旧记录再并入。P4 里"装载任意一盘带时对账"用的是同一条路径。
- **查询**：`stat` 先查"当前这盘带"（开放服务时取自刚读到的索引，之后每次提交追加），再查目录库（只读连接，WAL 下不阻塞应用线程）。这样当前带的查询不受目录经 Raft 应用的延迟影响，也不受"目录记录因换届而缺失"影响；目录库负责池里不在驱动器中的其他磁带。`stat` 返回条码与 sha256。
- **客户端库**按 sha256 判定"已提交的就是我这次上传的"，不再只比长度。
- **未归属的磁带绝不触碰**：执行线程用换带器的库存加驱动器序列号认出驱动器里是哪盘带，未归属则只报告、不写入（包括不收尾）；服务期间周期重试，所以磁带被归入池之后无需重启即开始服务。
- `TapeUnassign` 在该带的摘要显示还有文件时被状态机拒绝（37 的前提）。

### P3 已完成（2026-09-17）

- **磁带状态进 Raft**：`TapeState{barcode, state}`，取值 `appendable / data_full / full / label_mismatch / check`，只对已归属的带接受。`GET /admin/pools` 返回每盘带的状态、代数、文件数、已用字节。
- **选带**（`executor.rs::ensure_write_tape`）：读换带器库存，取"已归属、状态为 appendable、在库里"的带；排序为已在驱动器里的优先，其次**已用得最多的**，再其次按条码。这里偏离了 38 写的"可用空间最大"：等容量的带按那条规则会把数据摊到所有带上、把所有带都格式化一遍，改成写满一盘再开下一盘。
- **装载与识别**：MOVE MEDIUM 到空闲驱动器，等就绪，然后只读探测带首（`ltfs::volume::probe_format`）：
  - 空白 → 格式化（卷标识取条码前 6 位）；
  - LTFS → 挂载、需要时收尾；
  - **别的数据 → 绝不覆盖**，标 `label_mismatch` 跳过。
  - 池标记（`ltfs.mediaPool.uuid` / `.name`，40 已定）：没有就写上并提交；与归属不符标 `label_mismatch` 跳过。
  - 判定不可用的带会被卸回原槽位，驱动器留给下一盘候选。
- **未归属的带绝不触碰**：不装载、不探测、不写；它若占着驱动器，就用别的驱动器。
- **容量与保留空间**：取数据分区的最大与剩余容量；保留 = max(总量 2%, 4 × 估算索引) + min(总量 5%, 1 GiB)，保证任何时候写得下收尾所需的索引。比方案文档里的"2% 且不小于 2 × 索引 + 1 GiB"多了按比例封顶，否则几百 MiB 的小带整盘都是保留空间。
- **换带**：准入时发现放不下（转 `full`）或文件数到上限（转 `data_full`）→ 置换带标记并答 503 `switching_tape`（客户端稍后重试）→ 执行线程把队列里已收到的全部落带 → 上报状态 → 卸回槽位 → 选下一盘。
- **确定的拒绝**（40、05）：文件比单盘可用容量还大 → 507 `too_large`，不触发换带；池里没有可写的带 → 507 `no_tape`。两者都不进入"结果未定"。
- **写不了不影响查**：没有可写的带时 `stat`、`list` 继续由目录库回答。

过程中发现并修复：

### P4 已完成（tape-rs 侧，2026-09-18）；跨驱动器读取受 Holo 限制

- **跨磁带读取**（`executor.rs::read_any`）：`stat` 从目录得到文件所在的条码。就在写入带或读带上就直接读；否则装载：有空闲驱动器（非写入驱动器）就用它，读带留在里面，`--read-idle-ms`（默认 5 分钟）空闲后卸回槽位，再读同一盘不重新装载。

### P4 实机读取已补齐（2026-09-18）；修复第七处 Holo 偏差

上一轮把 P4 的实机读取挂起，原因是"一盘带在驱动器 A 写入后换到驱动器 B 读不到"。这一轮定位并修复了它。

**定位过程（每一步都排除了一个假设）**

1. 盘上只有一份共享数据且完整；写它的驱动器换带往返后仍读得到 → 不是落盘缺失。
2. 给 Holo 的 `hydrate_runtime_from_layout` 加临时诊断：**驱动器 B 重建出的状态与 A 完全一致**（同一 blk_map 序号、记录数、EOD、文件标记数）→ 不是状态重建错误。
3. 驱动器 B 读出的字节**每轮完全相同、与本轮写入无关、且在盘上任何文件里都找不到** → 它在读一个已被 `unlink` 但仍被本进程持有句柄的旧 inode。
4. 查 handler 环境：**`HOLO_STORAGE_TRUST_HOT_CACHE=1`**。这个开关让按路径缓存一旦命中就直接返回，**从不按文件戳重新校验**。FORMAT MEDIUM 会 `remove_dir_all` 分区目录再重建，于是缓存里的索引与文件句柄全部指向旧 inode，且永不失效。
5. 修了读侧之后出现第二个症状：**在 A 格式化、在 B 追加**时，写入返回成功但数据段只有 1565 字节，之后读报"短读"。原因同类但在写入侧：`segment.rs` 的 `append_file_cache` 缓存了追加句柄，写入落到了旧 inode。

**修复**（`Holo.local-changes.after-claude-freshload.patch`）

磁带装入驱动器是必须丢弃该带全部进程内缓存的时刻——真实硬件上新装的带与上一盘不共享任何状态。`attach_cartridge` 现在对基布局与每个分区布局调用 `discard_cartridge_caches`，`discard_layout_caches` 补齐了三处此前漏掉的缓存：blk_map、map_lookup、以及写入侧的 `append_file_cache`（均按路径前缀清理）。热缓存在单次装载周期内的性能收益不受影响。新增回归用例 `attach_cartridge_reads_a_reformatted_medium_fresh`。数据面 285 + 7 项通过。

### P5 已完成（2026-09-18）：Raft 快照、日志压缩与日志回滚

用户在本轮追加了要求：**P5 还要包含日志回滚**。

**快照的内容。** `ControlSnapshot { control, source, directory_index }`：整份控制状态进 Raft 消息（几十 KB），目录库只放一个指针——生成方的节点号，以及它的目录库快照覆盖到的日志索引。接收方经节点间通道另行拉取那个文件。帧格式因此扩为 1 字节种类 + 4 字节长度 + 载荷：种类 0 是 Raft 消息，种类 1 是目录库拉取（应答带索引、长度和 sha256，在同一条连接上写回）。

**何时做。** 每个节点都给自己的日志做快照（不只是 Leader），触发条件是距上次快照累积 2000 条或 256 MiB（`--snapshot-entries` / `--snapshot-mib`）；另外 `ControlStorage::snapshot()` 给不出时会记下请求索引，Raft 循环下一圈现做一份。`MemStorage` 只会给出空数据的快照，所以套了一层 `ControlStorage` 把 `Storage::snapshot()` 接管过来。

**一条关键不变式：快照点不得超过目录库已落库的位置。** 收到快照的节点会把目录库整份换成配套的那个文件；若两者之间差了哪怕一条，那条的目录记录就永远补不回来——它已在快照覆盖范围内，不会再经日志送达。`take_snapshot` 取两者的最小值。这一条是实测出来的：第一版按 `applied` 做快照，落后节点追上后目录里稳定缺最后几个文件。

**等目录库期间的规矩。** 装入快照到目录库拉回来之间，节点：不接管（像冷却期一样让出领导权，否则它的 `stat`/`list` 会漏报）、不往本地目录库写（马上要被整份替换，写进去的会连基础一起丢）、也不对外发自己的快照（那份快照会把空洞传给别人）。拉取在**单独的线程**上做：几个 GB 的传输挡在 Raft 循环里会赔掉选举超时。装好之后 `replay_into` 从快照点起在一份影子 `ControlState` 上重放本地日志补齐目录（目录库需要状态机对每条命令的结论；`Directory::apply` 跳过已落库的索引，所以重叠无害）。

**日志回滚**有三种形态，都在 `store.rs`：

1. 冲突尾部被覆写——同一个事务里先删后插（`append`）；
2. 装入快照时整段日志作废（`install_snapshot`，与 `MemStorage::apply_snapshot` 在内存里做的一致）；
3. 越过快照点的回滚**直接报错拒绝**。它不可能发生（回滚只涉及未提交的尾部，而快照点不超过已应用位置），真发生就是不变式被破坏，宁可停下。

**其他。** 接管历史 `history` 原本无界增长，现在只留最近 64 条（它每换一届加一条，还要进每一份快照）。`FileService` 每次查询前 stat 一下目录库文件：文件被整份换掉后，缓存的只读连接还捏着旧 inode。

### 计划停机释放预留（2026-09-18）

P5 实机演练暴露的缺口：`kill -9` 之后设备上留着一个已经不存在的持有者，下一轮起来要靠抢占，且清不掉就得人工 `pr-release`。

**实现。** `ltfsd` 接 SIGTERM/SIGINT：信号处理函数只置一个原子标志（信号安全的事情很少，发通道不在其中），另起一个线程把它转成 `NodeInput::Shutdown`；再来一次信号直接 `_exit`，好让"按两次 Ctrl-C"可以放弃等待。Raft 循环最多等执行线程 `--shutdown-grace-s`（默认 300 秒）。

`executor.rs::shut_down` 的顺序不能换：

1. 关掉文件服务，不再收新的上传；
2. 把队列里已完成的上传落带并提交，让卷停在完整尾部（失败就记一笔继续——卷交给下一个执行者按恢复协议收尾，那条路本来就存在）；
3. 给驱动器发 UNLOAD（Holo 的 handler 不收到 UNLOAD 不落盘，真实驱动器上这也是让介质回到可取走状态的一步）；
4. **最后**才释放预留。

第 4 步为什么必须在最后：释放只是计划移交的优化，不释放同样是安全的（下一个执行者会抢占）。正因为它是优化，绝不能提前做——只有确认本线程不会再碰设备之后，放掉这层保护才是对的。

磁带**留在驱动器里**（已退带、未穿带），不移回槽位：下一次接管直接从驱动器里挂载，省一次机械动作；介质也不是穿带状态，机械手随时可以取。

### 回收（reclaim，2026-09-18）

用户指示"继续做 reclaim"。这是第 6 节"不在本切片内"里点名"会最先变得必要"的那一项：replace 和放弃的尾部一直在消耗带上空间。

#### 先修的前置件：文件版本

动手之前发现一个已经存在、reclaim 会把它放大成数据丢失的缺陷。

**现象。** 同一个路径可以同时存在于多盘带上——重写会把旧副本留在原来那盘带上。目录的并入用的是 `INSERT OR REPLACE`，谁后并入谁赢。而**每次打开一盘带都会做一次完整对账**（`full = true`），于是"为了读一个文件把旧带装进驱动器"就足以把目录指回旧内容。回收期间新旧两份并存，紧接着又要格式化源带，这条路上就是实打实的丢数据。

**判断。** 修不了合并顺序（对账本来就该发生），只能给内容一个**集群范围的全序**，让目录按版本取大者。现成的材料正好够：轮次是 `Takeover` 条目的日志索引，全局单调；一轮之内只有一个执行者在串行写入。所以 `(轮次, 序号)` 就是全序，不需要新的协调。

**实现。** 每个文件写一条 `tapers.version = 轮次.序号` 的扩展属性（`ltfs::volume::XATTR_VERSION`），`FileRec` 带上它，目录表加两列。并入规则改成：**没有旧记录、或版本严格更大、或旧记录本来就是这盘带自己的**，才覆盖。没有版本属性的文件（EE 写的、打捞出来的）记为 `(0,0)`，抢不走任何路径。

两个方向都对上了：旧带对账抢不走新版本；反过来"写 T2 的那一届没来得及记目录、目录还停在 T1"的情况（PN06 那条路），装载 T2 对账时新版本也能把它纠正过来。`the_newest_version_wins_whatever_order_the_tapes_are_reconciled_in` 把两个方向都钉住。

#### 回收本身

**入口。** `POST /admin/tapes/<条码>/reclaim`、`ltfsctl tape reclaim <条码>`、`Command::TapeReclaim`。命令**只改状态**（磁带状态转 `reclaiming`），执行者在一个工作周期内自己发现并开干。这样中途换届不用任何交接：新执行者从复制状态里看到那盘带仍在回收，重建工作现场接着搬。

**搬迁走普通上传那条路**：从源带读出 → 暂存区 → 文件服务 → 合批落带 → `CatalogPart` / `TapeCommitted`。这样目录的更新与卷提交是同一件事，不必为回收另写一条容易走偏的目录路径。客户端同时在重写同一个路径时，`VolumeState` 的路径占用就是天然的互锁：回收拿到 `PathBusy` 就让开，下一遍再看（`RECLAIM_MAX_PASSES` = 20 遍之后放弃）。**一次只搬一个批次就回主循环**，读请求和客户端上传不会被长时间的回收饿死。

**验证。** 读源带的同时重算 sha256 与索引里的对照——销毁这一份副本之前的端到端验证。对不上就整次回收作废并把带标成 `check`。

**销毁前的两道闸**（这是全系统唯一一处主动销毁数据的地方）：

1. 目录里没有任何一条记录还指向源带（`FileService::live_on`；目录经 Raft 应用有延迟，这里会等）；
2. 源带**自己的索引**里每个路径，目录给出的当前位置都不在源带上。

第一条只看目录有什么，第二条还看带上有什么——带上有、目录压根不知道的文件也拦得住。两条都过，才 `mkltfs` + 写回池标记 + 上报 `TapeReclaimed`。

**崩在 mkltfs 和上报之间是安全的**：状态还是 `reclaiming`，新执行者装上来发现源带是空的，两道闸都平凡通过，再格式化一次、重新上报。`TapeReclaimed` 是唯一允许摘要代数回退的地方（介质真的被重写了），状态机只对"确实还在回收中"的带受理它，迟到的重复上报清不掉一盘已经重新写入的带。

**要两台驱动器**（EE 也是这个要求）：一台放写入带，一台放源带。源带正好是当前写入带时，先把队列落带、换一盘写入带，再来搬它。

#### 可回收空间的口径

第一版把可回收空间算成 `bytes_used − live_bytes`，写完测试才发现这个数**恒为 0**：`bytes_used` 取自索引，而索引只列活着的文件，同一盘带上被重写掉的旧副本根本不在里面。改成在每次提交时顺带读一次 MAM 分区容量（不动磁带），把 `bytes_written = 最大容量 − 剩余容量` 一路带进 `TapeCommitted` 和摘要；**可回收空间 = bytes_written − live_bytes**，三个来源（同带重写、跨带重写、收尾放弃的块）这才都算得进来。`GET /admin/pools` 与 `ltfsctl pool list` 逐盘显示。

顺带把 `NodeStatus.tapes` 的四元组换成了 `TapeRow` 结构体——再往里塞第五个字段，调用点就没法看了。

#### 实机演练（Holo 三节点，池 rc，两盘 256 MiB 小带）

| 步骤 | 结果 |
| --- | --- |
| 建池、归两盘带 | 节点 1 当选，选中 TS1000L08 |
| 写 6 个 8 MiB 文件，再重写其中 2 个 | 全部 201；重写的旧副本留在同一盘带上成为死字节 |
| `ltfsctl tape reclaim TS1000L08`（它正是当前写入带） | 受理；执行者先把写入带换成 TS1001L08，再把源带装进第二台驱动器开搬 |
| 重复下发 | 409 拒绝（"已在回收中"）|
| 回收完成 | TS1000L08 回到 appendable、gen=1、0 个文件 |
| 6 个文件读回 | sha256 全部一致；被重写过的那两个拿到的是新版本 |
| 三节点目录 | 都不再有任何一条记录指向源带 |

演练里踩到的两点：

1. **重置脚本用 `... | tail -N` 包住会失败的命令**，管道把退出码吃掉，`set -e` 拦不住。上一轮驱动器里残留着一盘带，`move` 失败被吞掉，接着的 `mkltfs` 就打在了驱动器里那盘**别的带**上。已改成不用管道包裹这类命令，并在重置前先把两台驱动器清空。
2. **逐个停节点会在中间触发换届**：节点 1 停掉之后剩下两个还有多数派，选出新 Leader 并接管、隔离设备；等停到它时它已经因为"不再是 Leader"丢掉了 `Active`，按纪律不能再碰设备，于是预留留在了设备上。这不是缺陷——失去资格的节点去操作设备才是缺陷——但演练收尾要么三个一起停，要么记得 `pr-release`。已写进 CLAUDE.md。

#### 第八处 Holo 偏差：容量查询不看分区号

演练发现"可回收空间"恒为 0。查下来是 Holo 的问题，不是账算错了。

**事实**：对同一盘带分别问分区 0 和分区 1 的 `REMAINING/MAXIMUM CAPACITY IN PARTITION`（MAM 0x0000/0x0001），返回的是**同一个值**，而且这个值随磁头当前所在的分区变化——写完 16 MiB 之后"剩余容量"反而从 77 MiB 涨到 126 MiB，因为提交的最后一步把磁头留在了索引分区。

**根因**（`data-plane/src/iscsi/cdb_drive.rs`）：`drive_mam_attributes` 用 `active_partition_capacity_bytes(state, profile)` 和 `state.eod_position` 算容量，两者都只描述**当前定位的分区**，CDB 第 7 字节的分区号只被传给了扩展属性覆盖表，没用在容量上。SSC-5 里这两个属性是分区属性，由发起方指定的分区号决定。同一个毛病也在容量日志页 0x17 上：它逐分区报告，却只填了活动分区的已用量。

**修复**（`Holo.local-changes.after-claude-partcap.patch`）：新增 `mount_bridge::partition_eod_bytes(state, partition)`——活动分区直接用 `eod_position`，其他分区按它自己的 blk_map 与文件标记重建 EOD（与 `hydrate_runtime_from_layout` 定位进去时做的事一致，一次文件读，这类命令很少）；新增 `partition_capacity_bytes(state, profile, partition)`；`drive_mam_attributes` 多收一个分区参数；日志页 0x17 逐分区填。回归用例 `test_read_attribute_capacity_follows_the_requested_partition`。数据面 286 + 7 项通过。

**部署**：只换 TAPERS 的三个 handler（新二进制单独命名为 `holo-tcmu-handler.ssc-partcap`，按各自 `/proc/<pid>/environ` 原样重启），**EE 的六个一个没动**，EE 三节点全程 available。旧二进制备份为 `holo-tcmu-handler.before-partition-cap-read`。

修复后同一盘带：分区 0 报剩余 126 MiB（索引分区用了 2 MiB），分区 1 报剩余 61 MiB（数据分区用了 67 MiB），不再随磁头位置变。

#### 回收途中换届的实机演练（2026-09-18）

补上前面记为"尚未验证"的那一项。设备与上一节相同（Holo TAPERS 库，三节点，池 rc，TS1000L08 / TS1001L08）。

**先要能看见中间态。** 第一次演练没打中：7 个文件整批一次提交，目录从"源带 7 个"直接跳到"源带 0 个"，两次轮询之间就结束了。这本身是对的——一批搬迁就是一次卷提交、一次目录更新，中间没有可观察的半成品——但也说明要制造中间态得把批次调小。三个节点改用 `--batch-files 2` 重启，回收就分成 4 批提交，目录上看得到 7 → 5 → 3 → 1 → 0。

**窗口一：搬迁途中被杀。**

| 步骤 | 结果 |
| --- | --- |
| 写 6 个 8 MiB 文件、重写其中 2 个 | 源带 gen=10，已用 48 MiB，可回收 13 MiB |
| 下发回收，轮询到"源带还剩 5 个、目标带已有 2 个" | 命中中间态 |
| 对执行者（节点 2，轮次 2）`kill -9` | — |
| 12 秒后 | 节点 1 当选，轮次 34；三台设备都报"已隔离（原持有者 `4c02000000000002`）"——正是节点 2 轮次 2 的键，被抢占 |
| 同一秒 | 目标带挂载时发现 `UnindexedData` 尾部，**放弃块 30..63**，在 EOD 追加新索引 gen=4。这正是被杀那一刻写了一半、还没索引的那个副本 |
| 再 2 秒 | "开始回收 TS1000L08（第 11 代，带上 7 个文件）→ 搬到 TS1001L08" |
| 杀后 20 秒 | "搬走 **5** 个文件 / 40 MiB，已重新格式化" |
| 7 个文件读回 | sha256 全部一致 |
| 三节点目录（含事后拉回来的节点 2） | 完全一致，都不再指向源带 |

关键在那个 **5**：带上明明有 7 个文件，新执行者只搬了 5 个。另外 2 个已经被上一任搬过去了，目录里它们的当前版本在目标带上，于是被判为 `Superseded` 跳过。跨换届的版本全序在这里起了作用——没有它，这 2 个文件会被源带上的旧副本重新覆盖一遍。

**窗口二：搬完了、还没格式化时被杀。** 数据此时都在 TS1001L08 上，直接反向回收，轮询到"目录里源带 live=0、状态仍是 reclaiming"的瞬间杀掉执行者（节点 1，轮次 34）。

| 结果 |
| --- |
| 节点 3 当选，轮次 58，抢占 `4c01000000000022`（= 节点 1 轮次 34） |
| "开始回收 TS1001L08（第 7 代，带上 7 个文件）→ 搬到 TS1000L08" |
| 同一秒："TS1001L08 上的内容已全部有着落（搬走 **0** 个 / 0 MiB，跳过旧副本 7 个），重新格式化" |
| 10 秒内收尾，7 个文件读回 sha256 全一致 |

这一刀落在 mkltfs **之前**——源带物理上还满满当当 7 个文件，两道闸门却都判定"每个路径的当前版本都在别的带上"，于是一个字节没重搬，直接格式化。这比 CLAUDE.md 里写的"mkltfs 与 TapeReclaimed 之间崩溃"更凶险：那种情况源带已经是空的，闸门怎么写都不会出事；而这一刀，闸门写错就是直接毁数据。

顺带验到的一点：节点 1 上设备是 `/dev/sg9,10,11`，节点 3 上同样三台是 `/dev/sg6,7,8`。按 VPD 0x80 序列号找设备、不认 `/dev/sgN`，在这里是实打实用上了。

**IBM 仲裁。** 跨两次换届搬迁出来的 TS1000L08 交给 IBM LTFS 2.4.8.3：

- `ltfsck` → `LTFS16022I Volume is consistent.`，挂载成功、`Skip writing the index because the volume is not dirty`，不需要任何修复。退出码 1 不是失败：一致性检查成功那条分支返回 `LTFSCK_CORRECTED = PROG_TREAT_SUCCESS = 0x01`（`src/libltfs/ltfs_error.h:492`）。
- IBM 挂载点下 7 个文件齐全，IBM 自己读出来现算的 sha256，与预期、与索引里 `ltfs.hash.sha256sum` 记的三者逐字节相同。
- `user.tapers.version` 依次是 34.6 … 34.12——同一轮次内严格递增，跨换届不重号。

**收尾。** 三节点一起 SIGTERM 停止，sg5/sg6/sg7 预留表全空、无持有者；两盘带回槽 5/6，两台驱动器空；EE 三节点 available，TR8000–TR8003 未动。

演练脚本里踩到的一点（不是产品问题）：`wipe` 用的是 `kill -9`，预留会按设计留在设备上等下一任抢占，所以**手工重置磁带之前得先 `pr-fence` + `pr-release` 清一次**，否则 `inventory` 直接 RESERVATION CONFLICT。集群自己接管时不需要这一步——新执行者的 `fence` 就是干这个的。
