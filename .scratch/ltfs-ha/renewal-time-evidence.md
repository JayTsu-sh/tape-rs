# 续期时间证据、待核验状态与禁止迟到放行

关联：[研究 30](issues/30-renewal-linearization-evidence.md) · [RQ](authority-refresh.md) · [许可发布](permit-publication.md) · [执行授权](issues/18-raft-execution-contract.md)

状态：保留第 30 轮对 PU05 后续候选的历史分析，未实现/执行。下文以“P 只是未接受登记、C 才接受”为前提的否决，不再作为唯一实现语义；[31 审计](issues/31-renewal-contract-refinement.md#answer)指出这是助手后来固定的更强解释，而非原 QG/RQ 的明确要求。

当前采用[续期接受点细化候选](renewal-acceptance.md)：仅对证据完整、后采样证明 P 及时且无终止获胜的成功分支，允许 P 为逻辑接受点、C 为证明可见点。必须同时遵守该候选的顺序对象、保守读者返回值和失败映射，不能只改名放行。本文关于后采样不能证明 C 及时、实际终止不可逆及历史确认不代表当前许可的分析仍成立；RT02 的当前判定由 RA02/RA03 细分。所有场景未实现/执行。

## 四个时间不能合成一个接受时间

设本轮原截止为 D，候选新截止为 Dnew，仍来自原始请求的 `t0 + T` 及 RQ 的 max 规则，不取回调处理时刻加 T。

| 事件 | 明确含义 | 单独不能证明 |
| --- | --- | --- |
| E：非时间证据准备完成 | safe 结果、实际 apply、请求及上下文等必要依据已经核验 | 后续发布时仍合格，或此时已完成续期 |
| P：待核验描述发布 | 版本条件匹配后登记原许可、D/Dnew 及不可变证据，尚未允许使用 Dnew | 原许可在 D 后仍有效 |
| W：P 之后取得时间样本 | 能证明采样实际在 P 之后，且使用满足既有时钟契约的同一依据 | 后续确认或读者看到证书也发生在 D 前 |
| C：续期确认对读者可用 | 发布完整可验证结果，读者可以按统一规则决定是否使用 | 仅因发布返回成功就满足旧 D 未过或当前 Dnew 未过 |

发布与取样的因果次序、时钟信任、描述身份和证据完整性都是前提，不是调试日志中写一个时间戳便成立。W 不能换成 P 之前的时间；暂停、证据返回或重复观察均不能改变 t0。

C 指规定的确认状态已正确生效并可按协议使用，不要求每个读者都必须在 D 前实际读取它。已经合法及时续期、只是某读者晚看到结果，与续期本身仍未成立是不同情况。本节否决当前候选未经证明的追溯解释，不宣称一切有严格细化证明的线性化实现都不可能。

## 发布后取样能证明什么

在时钟连续可信且 P 严格先于 W 的假设下，若 W 的值小于 D，可为“P 发生在 D 前”提供上界证据。这样能拒绝“P 之前取样、随后暂停跨截止才发布”的原错误路径。

但是 W 到 C 之间仍可暂停。即使 P/W 都在 D 前，C 也可能落在 D 后；前态版本未变不等于时间没有过去。对 C 之前再次取样也会产生新的取样到 C 窗口；C 之后再撤销又须排除读者已经使用的窗口。因此不将这一部分时间证据当作整个 RQ 并发证明。

这里的 P 是**待核验登记**，不是既有契约中的已接受确认。若未来希望把 P 定为逻辑续期点、C 仅作为证明可见点，必须另行明确整个抽象状态机、读者结果和到期含义，并证明或明确调整它们与原契约的关系。本次不通过更换“接受”的名字自动批准该变化，也不主张原始线性化定义会自动替项目选择此语义。

## 两种读者结果分开

- **本次操作无法确认有效性。** 读者没有足够证据，当前不派发；这本身不伪造已经记录的终止，也不能被协调者当作可以延期的票据。
- **本轮许可已终止。** 依据旧截止已过或已知失效形成对精确许可的不可逆终止；迟到结果不能清除、跨实例复用或重新解释为“只是暂时看不到”。

在 Pending 状态没有已接受续期、当前时间已达到 D 时，沿用原 RQ 的终止要求；不能将其降格为第二天还可补确认的普通等待。终止标记的并发落地可能未被调度，但这不意味着获得宽限：后续路径仍要检查原截止，不能因为没有人及时写 Terminal 就认为许可一直有效。

一个旧读者在真正的、符合原契约的续期已完成后仍读到旧描述，不能仅凭旧描述的 D 去终止较新状态；须按精确版本重查。这与 Pending 尚未完成续期而跨过 D 是两个分支。版本条件失败也不能抹掉真正仍适用的失效事件。

## 必须分开的故障轨迹

以下数字/时间关系只是验证场景，不提供生产阈值；RT01—RT06 均未实现/执行。

| 场景 | 系统实际可见证据 | 保持原契约的断言 |
| --- | --- | --- |
| RT01：P 之前检查，暂停至 D 后才发布 | 旧前态仍匹配，但发布后 W 已达到 D | 不启用 Dnew，不能沿用发布前样本放行 |
| RT02：P/W 均早于 D，C 延迟至 D 后；期间没有读者 | 有 P 的及时性证明，但续期确认迟到 | 无读者写终止不提供例外；不把登记追溯解释为既成续期 |
| RT03：与 RT02 相同，但读者在 D 后见 Pending 并终止 | 原许可/版本明确终止 | 迟到确认必须失败，不得恢复原 G；健康后的新轮次是另一许可 |
| RT04：P、证据及确认均在旧 D 前完整成立 | 原上下文一致、没有失效，读者使用时当前时间仍小于 Dnew | 应允许正常合法刷新；具体实现仍须证明 C 的时间关系而非仅作输入假设 |
| RT05：C 之后暂停直到 Dnew 后才派发 | 有历史上成功续期的证据，但当前时间已经过期 | 派发仍拒绝，历史确认不是持续执行权；与最后检查后的物理交付窗口另行区分 |
| RT06：首次启用、K→G 与普通续期交错 | 首次没有旧有效许可，交接有原 K 与新 G 的独立时间条件 | 不直接复用稳态 Pending 规则来提前启用或回开 K；分别验证正例及终止 |

RT02 是本轮历史解释的关键：它不依赖是否恰有另一个线程运行到期处理。若一种实现仅在 RT03 拒绝、却在 RT02 无条件允许，仍不可放行。31 后续候选不是无条件允许，而是明确修正“P 必定未接受”的抽象映射，并增加全部读者、证书、新期限与失败分支约束；当前以该候选为准，不能沿用本表旧解释又静默改变结果。

## 下一步的实现规格要求

对拟采用的时间/同步适配，必须给出 E/P/W/C、到期终止及所有读者之间的实际生效关系。每个依赖于及时执行、暂停检测、时钟上下界或原子操作成本的前提都要写明其提供者与验证方法；不能凭空假设一段用户态代码绝不会被暂停，也不能把未选定的时钟能力当作已满足。

若最终只能通过改变续期接受语义或增加实时运行前提才能得到可实施方案，应明确报告该取舍，而不是自动将安全要求标为已完成。用户的自动接受覆盖范围内的推荐，不把本节尚未证明的算法转换为验证通过。

本轮完成了部分时间证据的适用边界、读者结果分类和明确否决路径。时效生效算法、首次启用/K→G、快速撤销及具体容器仍未收敛；18 保持 claimed，09 不解除依赖，地图尚不满足开始总 spec 的条件。没有实现、测试运行或设备操作。
