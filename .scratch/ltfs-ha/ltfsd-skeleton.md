# ltfsd 最小骨架：实现记录与演练结果

2026-09-17，依据 [41](issues/41-authority-after-device-fencing.md) 精简后的接管序列实现。代码在 `src/daemon/` 与 `src/bin/ltfsd.rs`。它是骨架：证明"Raft 选主 → 设备层隔离 → 多数派确认 → 恢复与收尾 → 服务 → 失去资格则让位"这条主线可行，不含文件服务接口、池与磁带管理、换带器调度。

## 结构

| 模块 | 职责 |
| --- | --- |
| `state.rs` | 经 Raft 复制的控制状态。命令 `Takeover{node, term}`、`Fenced{node, round}`、`Abandoned{node, round, reason}`，JSON 编码。应用过程无设备 I/O，所有节点得到相同结论 |
| `store.rs` | 任期、投票、提交位置、日志条目写穿到 SQLite（WAL、synchronous=FULL），内存里用 raft-rs 的 `MemStorage` 作读缓存。无快照与日志压缩 |
| `net.rs` | TCP，4 字节长度 + protobuf 帧。尽力而为：连不上或队列满就丢，Raft 自己重发 |
| `node.rs` | Raft 循环（raft-rs 0.7，`check_quorum` 与 `pre_vote` 打开）。应用已提交命令并指挥执行线程；写 `status.json` |
| `executor.rs` | 唯一接触设备的线程。按序列号定位设备；`Takeover` 时隔离全部设备，`Recover` 时挂载并按需收尾，服务期间周期自检持有者，可选演示写入 |

raft-rs 用 `protobuf-codec`（纯 Rust 生成，不需要 protoc）。

## 与笔记裁定的对应

- **执行轮次 = `Takeover` 条目的日志索引。** 比 41 里写的"(任期, 任期内实例序号)"更简单，性质相同且更强：全局唯一、单调、经多数派认可；同一节点重启后要再当执行者必须重新当选并提交新的 `Takeover`，自然得到更大的轮次。41 与 18 的修订表应以此为准。
- **两次多数派确认都是日志条目。** `Takeover` 提交给出轮次；隔离完成后提交 `Fenced`。应用 `Fenced{round}` 时若当前执行者已不是该轮（日志里先出现了更新的 `Takeover`），结论是 `FenceSuperseded`，该轮不进入恢复。这就是 AF02。副作用是留下完整的接管审计记录。
- **失去资格即让位（AF03）。** 执行线程发现 `ownership_lost` 或隔离失败 → 停手 → Raft 层提交 `Abandoned` 并 `transfer_leader` 给下一个节点；此后一段冷却时间内即使再次当选也不接管，直接再让位。执行线程从不自行重新预留。
- **尽早停手（I12）只是优化。** Raft 层发现自己不再是 Leader（`check_quorum` 使被隔开的 Leader 在一个选举超时后自行降级）就通知执行线程停手；安全性不依赖它。
- **设备操作不在 Raft 循环里。** 隔离、挂载、收尾可能耗时数分钟，全部在执行线程，结论经消息回到 Raft 循环。

## 验证

模拟器（`tests/ltfsd_cluster.rs`，三个节点同进程、内存通道、共享模拟带库、各用不同发起方身份；连跑 15 次稳定）：

1. 选出 Leader，成为执行者，设备上的持有者键 = (节点, 轮次)，三个节点的控制状态一致，演示写入落带。
2. Leader 被网络隔开：另外两个节点选出新 Leader，以更大的轮次接管；旧执行者停手且没有重新注册；网络恢复后旧节点追上日志，不再碰设备；两轮的文件都在卷上。
3. 预留被外来的键夺走：执行者发现、放弃、让位；另一个节点以更大轮次接管并抢占外来的键。

Holo 三节点（EE 的三台 VM，管理网 7400 端口，`--demo-write` 每 2 秒提交一个文件）：

| 步骤 | 观察 |
| --- | --- |
| 启动 | 节点 1 当选，轮次 2，隔离换带器与两个驱动器，挂载卷开始服务 |
| SIGSTOP 节点 1（卡死） | 约一个选举超时后节点 2 当选，轮次 5，抢占并接管，继续提交文件 |
| SIGCONT 节点 1 | 它的下一条设备命令得到 2A/05，执行线程停手，提交放弃，转为 Follower |
| kill -9 节点 2（写入途中） | 节点 3 当选，轮次 8；挂载发现 DP 尾部为 T1（块 424..425 未索引），**自动收尾**后继续服务 |
| 重启被杀的节点 | 从 SQLite 恢复任期与日志，作为 Follower 加入，控制状态与其他节点一致 |
| 停止集群后 | 卷上 52 个演示文件，分属轮次 2、5、8；IBM LTFS 2.4.8.3 `ltfsck`：Volume is consistent（gen 58）；EE 三节点 available |

## 过程中发现的问题

- **非法指令崩溃。** 构建机的 gcc 默认 `-march=x86-64-v3`，内置 SQLite 被编出 AVX 指令，实验室 VM 的虚拟 CPU 不支持，`sqlite3_initialize` 处 `trap invalid opcode`。此前 `tape-rs` 没暴露是因为在 VM 上没走到 SQLite。已在仓库 `.cargo/config.toml` 固定 C 代码为基线 x86-64。
- 演练脚本用 `status.json` 判断谁是 Leader，被暂停的节点的状态文件停在旧值。状态文件只能当作"该节点最后一次自述"，不能当作集群事实；以后要查集群事实应问多数派。

## 文件服务接口（2026-09-17）

`files.rs`（HTTP 线程与执行线程共享的 `FileService`）与 `http.rs`（手写的最小 HTTP/1.1，不引入新依赖）。

| 接口 | 含义 |
| --- | --- |
| `PUT /files/<path>[?wait=1]` | 上传。202 = 已暂存在本节点，不是持久化确认；带 `wait=1` 时等到落带，201 = 已提交并返回索引代数 |
| `GET /files/<path>` | 从磁带读出已提交文件的内容（骨架上限 256 MiB） |
| `GET /stat/<path>` | 已提交视图里的文件；404 = 未提交 |
| `GET /tasks/<id>[?wait=1]` | 上传任务的结论：staged / committed / failed / indeterminate。任务记录不跨节点、不跨进程保留 |
| `GET /list`、`GET /cluster` | 已提交视图的全部文件；本节点的自述 |
| 不在服务的节点 | 一律 503，JSON 里给出它所知的 Leader 编号与地址 |

**D03 的接入。** 执行者恢复卷之后，用索引建立 `core::volume_state::VolumeState`（运行实例号 = 执行轮次）。上传走 准入（预留空间）→ 接收 → 完成 → 冻结批次 → 落带提交 → 发布。"完成并入队"与"取队列并冻结"在 `FileService` 的同一把锁下完成，所以冻结批次覆盖的文件集合与实际写带的集合严格一致；否则会出现"写了带但没发布，下一批又写一遍"或"发布了但没写带"。执行线程一次挂载、逐个追加、一次提交，多个并发上传自然合批。

**执行者更换时的任务结论**（对应 05 的"结果未定与安全重试"）：仅暂存的任务 → `failed`，确定没落带，向新 Leader 重传；已进入提交批次的任务 → `indeterminate`，向新 Leader 查询该路径判定。提交失败（不论原因）后本轮到此为止：文件服务关闭，节点放弃本轮并让位，由下一次接管的恢复协议判定磁带上的事实。暂存区不复制，进程启动时清空。

**验证。** 模拟器集成测试新增两项。`upload_is_committed_to_tape_and_only_the_executor_serves`：提交前不可见、提交后 `stat` 与读回内容一致、Follower 拒绝服务、6 个并发上传合批、同一路径重复准入被拒。`committed_uploads_survive_failover_and_unconfirmed_ones_never_corrupt`：旧 Leader 被隔开后持续向它上传直到它停止服务，每次运行都有请求撞上隔离；断言**报告过已提交的文件在新 Leader 上必定可见，任何可见的文件内容必定完整正确**。连跑 6 次：每次 16—20 个确认提交全部可见，撞上隔离的那个请求得到 `indeterminate` 且不可见（设备拒绝了它），最后一个被 `not_serving` 拒绝。

Holo 三节点，真实 HTTP 客户端（`ltfsd_client.py`，从 PVE 主机发起）：

| 步骤 | 结果 |
| --- | --- |
| 上传 40 MiB 并等待 | 201，1.7 秒；`stat` 为已提交；`GET` 读回 sha256 一致 |
| 向 Follower 上传 | 503，`leader_url` 指向 Leader |
| 不带 wait 上传 | 202 staged，随后任务查询为 committed |
| 持续上传途中 kill -9 Leader | 已确认的 5 个文件在新 Leader 上全部可见，抽查内容一致；**第 6 个请求客户端只看到连接断开，而新 Leader 上该文件可见**：提交已落带、响应没送出，正是"结果未定，向新 Leader 查询"的情形 |
| 故障切换后 | 先前的大文件仍在；新上传 201；被杀的节点重启后作为 Follower 加入 |
| 停止集群后 | IBM `ltfsck` 判定一致；EE 三节点 available |

骨架的已知局限：每个带 `wait` 的上传在 Holo 上约 1 秒（每批一次挂载加一次提交），串行客户端吞吐很低，并发客户端靠合批改善；没有合批的延迟上限与大小上限（04 的检查点策略）；读接口把整个文件读进内存；没有鉴权；元数据读是有界陈旧（41 已裁定）。

## Rust 客户端库（2026-09-17，用户提问"为什么要通过 HTTP 上传，是不是可以通过 Rust API"之后补上）

结论：应用应当只面对 Rust API。进程内本来就有（`FileService`，集成测试直接调用）；但 ltfsd 是三台节点上的守护进程，应用在另一个进程或另一台机器上，两者之间必须有线上协议。按用户最初给的架构（Python Client API → 自研 Rust LIB API → ltfsd），正确形态是一个**客户端库**，把线上协议和下面三件事都包在里面；HTTP 降为库内部可替换的传输细节。

`src/client.rs`（`tape_rs::client::Client`）与基于它的命令行 `ltfsctl`：

- **找 Leader**：给出全部节点地址即可；503 里的 `leader_url` 自动跟随，上次成功的节点优先。
- **故障切换期间的等待**：没有节点在服务时在 `retry_for` 之内重试。
- **结果未定的判定与安全重试**：`put` 返回即表示已随卷提交。服务端明确答 `failed`（仅暂存、确定没落带）则直接重传；连接在请求可能已到达服务端之后断开、或服务端答 `indeterminate`，则先到当前 Leader 查询该路径，已提交且长度相符视为成功（`resolved_by_query`），否则重传。带内容的请求一旦可能已到达服务端，库不会换个节点悄悄重发。连接根本没建立起来（节点已死）不算结果未定，直接换节点。
- 局限：判定"已提交的就是我这次上传的"只比长度。更强的保证需要调用方在路径里带版本标识，或服务端按内容哈希判定（`ltfs.hash.sha256sum` 已经在写，接上即可），后者是后续工作。

验证：

- 模拟器加真实本机 HTTP（`client_library_hides_failover_from_the_application`）：应用线程只管连续 `put`，中途 Leader 被隔开。4 次运行各 24—49 个上传，应用线程没有看到一次错误，事后逐个 `stat` 全部已提交、抽查内容正确，执行轮次 2 → 5。
- Holo 三节点，`ltfsctl` 从 tsclient 连续上传 30 个文件，第 8 个之后 kill -9 Leader：应用侧 30/30 成功；第 9 个请求次数为 2，它第一次上传留下的两个未索引数据块被新 Leader 自动收尾放弃，随后重传成功；抽查 7 个文件内容一致；磁带上 `/ctl/` 下正好 30 个文件。

## 压力下发现并修复的接管竞态

带负载并行跑集成测试（6 份同时）时约四成失败，节点永远停在"正在恢复卷"。原因链：第一条 `Takeover` 提交慢，Leader 重复提交，同一节点有了轮次 N 与 N+1；轮次 N 的隔离结果被判过时并回以**不指明轮次的停手**；该停手在执行线程已完成轮次 N+1 的隔离之后才到，把 N+1 的状态清掉；随后 N+1 的恢复请求被执行线程**悄悄忽略**。修复：停手指明轮次，执行线程已在处理更新的轮次时忽略它；没有对应状态的恢复请求上报为放弃而不是忽略；每个任期只提交一次 `Takeover`。另修一处隐患：用"当前时刻减一小时"表示很久以前，在开机不足一小时的机器上单调时钟会下溢 panic，守护进程在刚重启的节点上会起不来。修复后同样压力下 30 次全过，并加了两个确定性的执行线程消息次序用例。

教训：这类缺陷只在时序被拉开时出现，单跑永远是绿的。集成测试应当定期在加压条件下跑。
