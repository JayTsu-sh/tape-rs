## 搜索状态模型

对每个分区维护按逻辑块号的区间集合，取值互斥：`verified`（已读且已解析核验）、`excluded`（由规范关系可靠排除，不影响当前性结论）、`unread`、`ambiguous`（读错、短记录或无法分类）。搜索结论只能由这些区间推出，不能由循环结束或命令返回推出。

设备原语（SSC-5 语义，均由唯一执行流程串行调度）：

- `POS`：READ POSITION，取当前分区与逻辑块号，用于每次跳转后核对实际位置。
- `EOD`：SPACE 到 End-Of-Data；成功后 `POS` 得到 EOD 块号 `E`。
- `BackFM(n)`：SPACE 反向 n 个文件标记；用于从 `E` 回到最后一个构造边界。
- `LOC(b)`：LOCATE(16) 到块 b；跳转后必须 `POS` 核对。
- `READ`：按标签块大小读记录；短记录、文件标记、BLANK CHECK 分别记录为不同结果。

## 快速路径

按 F8：读介质 VCR 与两分区 VCI。全部 VCI 的 VCR 与介质 VCR 相等且有效 → 取最高 generation 的 VCI 位置为候选，`LOC` 并读取索引构造，按“候选核验”通过后，把该位置之后到 `E` 之间标 `unread` 并执行尾部分类；若尾部为 T0，则整卷当前视图成立，搜索结束。任一条件不满足则不使用 VCI 结论，进入标准路径；不写回 VCI。

**实机修正（2026-09-17）**：VCI 新鲜不足以采信提示。必须同时满足"提示索引的结束文件标记紧接 EOD"，否则退回标准路径。依据：Holo-VTL 的 VCR 曾不随写入变化；更一般地，DP 索引已写完但 VCI 未及更新（屏障或 VCI 阶段失败）时，即使 VCR 行为正确的设备也会出现"旧 VCI 的 VCR 与当前值不同"——那种情形本来就走标准路径；而 VCR 行为不正确的设备只有靠这条附加条件才不会漏掉更新的已提交索引。

## 标准路径：末构造定位与停止证明

**定理（停止条件）。** 若某分区 `E` 可靠取得，且从 `E` 反向找到的最后一个构造 `C_last` 经核验是有效索引构造，则该分区上所有位置早于 `C_last` 的索引都不影响当前状态判定：由 F2、F3，`C_last` 是该分区代数最高的索引；由 F5/F6，它的回指链完整确定其依赖的 Full 与增量序列；早于 `C_last` 且不在链上的索引是历史快照，其内容已被链上更晚索引覆盖。因此搜索可以在 `C_last` 及其链核验完成后成功停止，无需遍历分区。

**推论。** 大范围扫描只在两种情况需要：`E` 不可靠取得（T4），或 `C_last` 不是有效索引构造（T1/T2/T3），此时目标退化为“找到最后一个有效索引构造”，搜索用有界反向步进完成。

步骤：

1. `EOD` → `E`；失败或 `POS` 与预期分区不符 → 该分区标 T4，转受限出口。
2. `BackFM(1)` → 位于最后一个文件标记之前；`POS` 得 `p1`。若 `p1` 不存在（分区仅有标签构造）→ 分区为空内容区，按“无索引”处理（新卷或异常，交由 R1 身份核验决定）。
3. `BackFM(1)` 再退一个文件标记 → `POS` 得 `p0`；正向 `READ` 从 `p0+1` 到 `p1` 之间的记录，尝试解析为索引：
   - 解析成功且自指针（卷 UUID、分区、startblock=`p0+1`）匹配、读到的记录末尾紧接文件标记 → `C_last` 有效，位置区间 `[p0, p1]` 标 `verified`。
   - 自指针不匹配或非索引 XML → 按 F4 视为数据 extent；本构造标 `excluded`，继续第 4 步反向找上一个索引。
   - 记录短读/读错 → 标 `ambiguous`，继续第 4 步，但最终只能得出“受限”而非“成功”。
4. 反向步进：`BackFM(1)` 后重复第 3 步；每次跨过的区域按第 3 步结果标记。步进次数与读取字节受预算约束；预算耗尽 → 受限出口，未标记区域保持 `unread`。
5. 得到有效 `C_last` 后核验回指链：沿 F9 顺序读取 `previousincrementallocation`/`previousgenerationlocation` 指向的索引，每个都做候选核验；链上出现环、指向更高代数、指向不同卷、位置在 `C_last` 之后、或指向的构造无效 → 链断，按 RE08 拒绝发布，结论为受限。链完整到某个 Full（该 Full 无回指或回指再往前不需要）→ 链核验完成。链上索引之间的区域标 `excluded`（由定理）。
6. 对另一分区重复 1–5。IP 上 `C_last` 必须是 Full（F2/F5）。IP 的 `C_last` 代数高于 DP 时分两种情形（2026-09-17 反向校准后修订）：IP 的回指针正好指向 DP 的 `C_last`，这是规范定义的一致卷（IBM LTFS 只改元数据或挂载时补写 IP 后留下此状态），视图取 IP；回指针不符才是冲突（RE03 变体），结论受限。实现为 `RecoveryReport::ip_ahead()`。
7. 当前视图 = DP 的 `C_last` 及其链正序应用（15 的重放规则）。两分区都得到有效 `C_last` 且 DP 链完整 → 搜索成功停止；IP 落后只记为“IP 维护债务”，不阻止读取开放。 追加放行另有两条（同日修订）：视图里任何文件的 extent 位于 IP 时一律只读，因为本实现的提交会从内容区首块整段重写 IP；视图里没有 IP 数据且 DP 尾部完整时，IP 自身的尾部状态不阻止追加（典型情形是上次提交在 IP 阶段失败，IP 只剩开头文件标记）。此外索引含未知元素或 `volumelockstate` 非 unlocked 时只读，见[卷内布局与外来卷兼容](volume-layout-interop.md)。

**候选核验**（每个索引构造）：前后文件标记存在；记录解析为 `ltfsindex` 或 `ltfsincrementalindex`；`volumeuuid` 与标签一致；`location` 等于实际位置；`generationnumber` 满足 F3 相对已核验邻居的单调性；回指元素存在性符合 F6（增量必有 `previousgenerationlocation`）；不含超出规范的顶层元素时保留未知子元素。

## 尾部分类

对 DP 与 IP 分别在 `C_last` 之后到 `E` 的区域分类；分类只读，不改介质：

| 类型 | 观察 | 含义 | 首版处理 |
| --- | --- | --- | --- |
| T0 完整尾部 | `C_last` 的结束文件标记紧接 `E` | 分区完整（F2） | 可进入追加放行检查（AP01/AP02） |
| T1 未索引数据尾 | `C_last` 之后有一个或多个记录/文件标记，但不存在完整索引构造 | 上次写入的数据落带但未提交，或构造被打断 | 不自动追加、不发布为文件、不截断（AP03）；该分区只读 |
| T2 残缺索引构造 | `C_last` 之后有文件标记 + 若干可解析为索引前缀的记录，缺结束文件标记或 XML 不闭合 | 索引写入途中中断 | 同 T1；额外记录“存在候选索引前缀”供诊断，不据此更新视图 |
| T3 假索引 | 结构像索引构造但自指针不匹配 | 按 F4 为数据 extent | 同 T1 |
| T4 未知 | `E` 不可靠、读错、位置核对失败 | 无法分类 | 恢复受限；不开放该卷写入；读取按 RV 规则单独判定 |

“看似完整”的 T1（例如数据后紧跟 `E`）在首版仍不追加：追加会让这些块永久处于 F2 意义上的合法但无索引引用状态，对账/回收语义与容量记账尚未为此定义。后续放开需要单独裁定。

## 安全追加位置

仅当 DP 为 T0 且 IP 为 T0（IP 的 `C_last` 为有效 Full）时进入；IP 为 T1–T4 时，即使 DP 完整，首版也不开放写入，因为 IP 收尾会要求在 IP 上追加或覆写，属于修复范畴。

放行检查（在 R5 已有六项之上给出可执行判定）：

1. 追加位置 `A` = DP 的 `E`。核对 `A` = `C_last.startblock + C_last 记录数 + 1`（结束文件标记占一个逻辑对象）；不等则回到尾部分类（结果视为 T4）。
2. `LOC(A)` 后 `POS` 必须返回 `A`；不一致不放行。
3. 介质写保护、容量账本按 R5 第 5 条重建、DP/IP 收尾预算成立。
4. 资格绑定：卷 UUID、装载实例、当前运行许可轮次、`C_last` 位置与代数共同构成写资格上下文；任一变化即失效。正常读取改变位置后，写前重新执行第 2 步，不重扫。
5. 首次新写入产生的索引的 `previousgenerationlocation` 指向链核验得到的最新 Full，`previousincrementallocation` 指向 `C_last`（若 `C_last` 为增量）；代数取 `C_last.generation + 1`，允许更大但不采用。

不做试写；不用写文件标记探测位置；不在放行前更新 VCI/MAM。

## VCI 与 MAM 的项目用法

- VCI 只作快速路径输入与提交后的可选提示；按 F8 顺序在索引落带且屏障成立（S4）后更新，失败不影响 S4 事实。恢复阶段不写 VCI。
- F10 的 MEDIA POOL 属性是 LTFS 规范认可的可选主机属性，可承载 37 提出的池标识；作为 import 提示与一致性检查，不作为归属权威。是否写入由 37 的“磁带自描述标记”实施时决定。

## 预算与受限出口

- 每分区反向步进次数上限、累计读取字节上限、单次恢复总时长上限：留空，由 08 的 RTO 与 06 的测量共同确定。
- 受限出口输出：每分区的区间集合、`C_last` 候选（若有）、链核验进度、尾部类型、失败原因；供 39 的事件与 07 的 Recovery 模块。
- 受限结论下的读取开放按 RV 规则：仅当 DP 链完整且视图可信而只是尾部非 T0 时可开放读取。

## 接管后的自动收尾（2026-09-17，用户裁定）

用户接受建议：**新 Leader 在确认隔离后自动收尾**，保留"只报告不修复"的开关。这修订了 04 的"不自动截断修复"：仍然不截断、不覆盖，但允许在证明独占后**追加**一份索引使卷恢复一致。动机是三节点演练的实际观察：写入途中发生接管后卷为 T1、只读，每次这类切换都会留下一盘需要人工处理的磁带。

**做法。** 在 EOD 追加 Index Construct（FM + 索引 + FM），回指最后一个有效的 DP 索引，代数 +1，随后照常重写 IP、刷缓冲、写两分区 VCI。实现上就是一次不带新文件的提交，写入位置取恢复报告里的 EOD。不覆盖任何已有块，未索引的数据块物理上仍在带上。与 IBM ltfsck 的做法一致。

**前提（全部满足才做，否则保持只读并说明原因）。**

1. 已设置预留自检键，且设备回读确认持有者就是该键（证明独占；没有这一条，收尾就可能与还在写的旧执行者交错）。
2. DP 尾部是 T1 UnindexedData 或 T2 TruncatedIndex。T3 FakeIndex（结构完整但自指针不符，来历不明）与 T4 Unknown 不自动处理。
3. 恢复报告没有其他受限原因：回指链通过、两分区不冲突、视图不是来自 IP。
4. 索引不含未知元素、卷未锁、视图里没有位于 IP 的文件数据。
5. LOCATE 到 EOD 后 READ POSITION 一致。

**未索引数据的处置。** 默认放弃：数据块不被任何文件引用，块范围追加记录在卷根扩展属性 `tapers.abandonedBlocks`（形如 `b:11-252`，多次收尾用分号相接）。可选打捞：从末索引之后读到第一个文件标记或 EOD，登记为 `_ltfs_lostandfound/tail-gen<G>-block<N>` 只读文件，按"extent 内只有最后一块可以不满"切分 extent；耗时与数据量成正比。打捞不等于恢复了那个文件：它只是旧执行者写到一半的前缀，是否有用由应用判断，05 的"结果未定"语义不变。

**实现与验证。** `LtfsVolume::close_tail(TailPolicy)`、CLI `ltfs-takeover --node --round [--salvage] [--report-only]`（隔离 → 挂载 → 需要时收尾）。`tests/sim_close_tail.rs` 5 项：T1 放弃、T1 打捞（内容等于旧执行者写入的字节）、T2（打捞只取文件标记之前的数据）、缺自检键或键陈旧时拒绝且介质未被触碰、T0/T3 拒绝。三节点 Holo 演练：节点 3 写 1 GiB 途中被暂停，节点 1 接管并打捞，得到 242 块 126,877,696 字节，与源文件同长度前缀 sha256 相同；节点 3 恢复后第一条命令被拒；IBM LTFS 2.4.8.3 `ltfsck` 判定一致，回滚点链完整包含收尾追加的那份索引。
