# 性能验收框架草案

关联：[性能票据](issues/06-performance.md) · [决策地图](map.md)

状态：依用户自动接受授权，测量口径、场景、观测与参数化判定作为规划基线已接受；尚未实现或运行。未知输入与阈值继续留空，空白不表示零、无限或采用默认值。[06](issues/06-performance.md#answer)已完成规划裁定，不代表性能达标；提交/文件/HA 的未决算法仍由对应票据处理。

## 范围与边界

- 大文件连续归档和恢复作为基线；小文件归档作为用户明确的极端场景。两者均保留独立 LTFS 文件身份，不引入私有打包容器。
- 区分应用接收、磁带持久化和应用收到确认；暂存速度不代表归档完成速度。
- 保持现有容量保护、所有权检查、提交屏障及有界接收政策。未知输入留空不意味着新增自适应流控功能。
- 本文只规划测试，不实现测试程序，不访问设备，也不授权故障注入、写带或清除缓存。

## 计量口径

受控归档测试使用互不覆盖的文件身份，记录测试端任务清单、预期内容及终态。清单是测试证据，不是产品上传回执，不要求新增持久化上传 ID、回执属性或请求历史查询。

| 指标 | 草案口径 |
| --- | --- |
| 接收吞吐 | 客户端被确认已接收的逻辑字节 / 接收阶段耗时；明确其不具备归档成功含义 |
| 可靠完成文件率 | 测量任务中，完整内容及相关可恢复索引达到既定持久化条件的文件数 / 完整测量窗口；每个文件只计一次，部分文件不计 |
| 完整归档有效吞吐 | 上述完整文件的逻辑大小总和 / 同一窗口；与压缩后物理写入量、索引开销分开。已提交前缀可另报，但不得重复计入完整文件吞吐 |
| 应用确认完成率 | 应用实际收到归档成功的文件数 / 同一窗口；与可靠完成文件率分开，响应丢失不能伪装成已确认 |
| 文件端到端延迟 | 从应用计划发起该文件任务到收到归档成功；包括任务排队、准入、传输及提交，报告 P50/P99 和未完成数量，避免只统计快速成功样本 |
| 就绪后持久化延迟 | 从完整文件就绪到覆盖该文件的提交屏障成功；与应用收到确认的时间分开。设备和客户端计时分别使用单调时钟，不直接相减未校准的跨机时间戳 |
| 准入成本 | 正常快速路径与校准慢路径分别报告延迟分位数、CPU、锁等待及附加设备查询次数 |
| 索引成本 | 分别记录增量、DP Full、IP Full 的 XML 大小、构建 CPU、队列等待及设备执行时间；不得只报告增量索引的小样本 |
| 资源占用 | CPU 时间/完成文件、元数据内存及每文件增量、峰值 RSS、SSD 占用、数据与控制队列深度、背压等待、设备空等时间 |

逐项拆分主动合批等待、设备排队、数据排出、索引写入和屏障耗时。并行阶段允许重叠，不把重叠耗时简单相加当作总延迟。暂时无法观测的指标留空并说明缺少证据。

故障场景中，跨节点恢复不能凭产品回执确认历史请求。仅在隔离、卷恢复和受控内容校验提供足够证据时核对该测试文件的恢复状态；证据不足则保留结果未定。恢复出的完整内容也不等于应用此前已经收到确认。

## 测量窗口与可复现性

1. 记录版本、设备/介质身份、初始卷状态、已有文件数、索引链状态、缓存状态及全部测试参数。已有索引可以属于预置背景，但不能把窗口前积累的待写数据计为本轮工作。
2. 完整批次窗口从首个任务计划发起前开始，到全部任务取得明确终态且相关在途工作排空结束；成功、拒绝、失败、取消和结果未定分别报告。异常或未排空的运行不能冒充完整成功基线。
3. 仅 size-based 的有限批次可能不足阈值；由测试端在批次末显式提交尾批，并把这段耗时纳入窗口。记录该操作，不能暗中启用 time-based 或改变产品默认策略。
4. 同时报告完整批次结果和单独标注的稳态窗口。稳态起止缓存占用、积压量及积压趋势一并记录，缓存持续增长的窗口不能证明可持续吞吐。
5. 长跑覆盖实际触发的增量提交、DP Full 及 IP 维护，报告各类次数和时间。未覆盖某类维护时注明覆盖不足；短时无检查点窗口不作为总体性能结论。
6. 冷读带与热缓存读分开；启动/装载/定位是否计入读取窗口明确记录。写入基准后的内容校验单独计时；若采用端到端含校验指标，必须单独命名。
7. 重复次数、运行时长、预热方法和统计要求待选定。保留每次运行及离散程度，不只挑选最好结果。

## 场景矩阵

以下为需要覆盖的维度，不要求盲目运行所有笛卡尔组合。优先建立单驱动基线，再扩展索引规模和并发。

| 场景 | 主要观察 | 正确性约束 |
| --- | --- | --- |
| 大文件连续归档 | 持续有效吞吐、设备空等、提交暂停 | 流式写带，不依赖整文件先暂存 |
| 小文件连续与突发归档 | 可靠完成文件率、逐文件 CPU/延迟、队列积压 | 独立文件身份；合批不等于逐文件强制 sync |
| 空目录基线与已有大量文件的卷 | 元数据内存、增量和 Full 构建/写入成本 | 明确目录结构、文件数、extent 和标准属性规模，不添加回执属性制造负载 |
| time-only、size-only、OR | 触发原因、合批程度、最早未提交变更年龄 | time 不被后续变更重置；size 只计完整就绪文件；尾批显式提交可见 |
| 持续运行与检查点维护 | 完整周期吞吐、资源增长、IP 滞后 | 不能跳过应执行的维护来改善成绩 |
| 已接受的缓冲上限触达 | 背压时长、内存上限、控制请求进展 | 数据队列饱和不得阻塞必要提交/取消控制，不新增流控政策 |
| 正常容量与接近容量边界 | 准入开销、拒绝和校准等待、收尾成本 | DP/IP 收尾预算不可挪用，状态不明时不强行继续写 |
| 冷读、热读及读写混合 | 读延迟、读写公平性、排队 | 分开报告缓存命中与真实读带，不预设混合比例 |
| 单驱动与多驱动 | 每驱动及全库吞吐、共享 CPU/网络竞争 | 不用理论线性倍数代替实测；配置和资源边界明确 |

另外以独立正确性用例覆盖：提交中取消、失败后仅有已提交前缀、提交成功但响应丢失、主节点失效后由备节点恢复。核对不误报成功、不自动删除已提交部分、不自动重传结果未定任务、不在隔离前接管。具体故障点与验收步骤由提交及恢复票据继续细化；本框架不假定它们已完成。

## 测试步骤草案

以下是供后续测试实现绑定的逻辑步骤，不是现有 CLI/API 使用说明。时间阈值用 T、完整文件大小阈值用 S、缓冲预算用 B 表示；它们没有预填数值。确定性触发和交错测试优先使用可控时钟与设备替身，真实设备只在协议及环境就绪、另获授权后执行。

### P01：完整文件计数与尾批排空

1. 由测试端生成独立文件清单，记录预期大小与内容校验依据；初始无属于本轮的待写任务。
2. 在 size-only 模式下，先使完整就绪文件的累计逻辑大小小于 S，再增加一个完整文件使累计值达到或超过 S；设备替身暂不完成本次提交屏障。
3. 检查已接收、已就绪可增长，但本批可靠完成文件数和应用归档成功数不能提前增长。屏障成功后，只把快照覆盖的完整文件计入一次。
4. 再提交一个不足 S 的尾批，由测试端显式请求提交并等到结果。最终核对完整文件数和逻辑字节总量；尾批等待和提交时间纳入完整窗口。

判定重点：不把创建、接收、文件就绪或仅数据写入完成当作归档成功，不遗漏尾批，也不重复统计一次文件的多个提交事件。

### P02：时间触发与完整文件大小触发

1. time-only：记录首个未提交变更时刻 t0，在 t0 + T 前继续产生变更；检查首个截止点仍为 t0 + T。单独覆盖仅元数据变更和无变更空闲，不将其计为新归档文件。
2. size-only：让一个尚未完成的文件持续写入，即使已写字节超过 S，也不能仅据此产生 size 触发；文件完整就绪后按完整逻辑大小纳入一次计量。
3. 跨提交前缀：先在时间模式提交文件前缀，再使该文件完整就绪；检查完整文件大小口径未变为仅剩尾部大小，既有前缀数据也不为计数再次写带。
4. OR：分别安排时间先满足、大小先满足和两者同时满足。每种满足条件均使相关变更具备提交资格，不额外等待另一条件；同时满足不能重复确认同一文件。
5. 时间到达只检查触发和调度行为；设备排队、数据排出及屏障完成单独计时，不要求在 t0 + T 时已经持久化完成。

### P03：提交快照与有界接收

1. 使文件甲完整就绪并冻结当前提交快照；在设备替身暂停该提交期间，继续接收快照外的文件乙。
2. 让下一批缓冲达到 B，观察既有背压策略；统计所有相关缓冲和在途资源，不能仅把占用转移到未计量队列来宣称有界。
3. 检查必要控制请求仍可被处理；“可被处理”不代表可绕过串行设备操作或强行中断在途命令。
4. 完成甲所在的提交，核对不能因此确认乙，乙的未提交变更年龄也不能被清零。继续推进后续提交，检查背压能随可用资源恢复而解除，无数据遗漏或重复确认。

判定重点：快照隔离、预算约束和控制进展；B 的单位、覆盖范围及具体限额需由后续实现规格明确，不能借本用例隐式选定。

### P04：索引规模增长与完整维护周期

1. 分别在空目录基线和预置文件系统背景下执行相同的新文件负载，记录初始文件/目录/extent/标准属性规模及增量链状态。
2. 保持每轮数据、可靠性和调度配置可比；逐轮扩大背景规模，分别记录元数据构建、XML 序列化、设备索引写入、RSS 和单位完成文件 CPU 成本。
3. 长跑记录实际增量、DP Full、IP Full 事件，包含维护期间的吞吐、积压及最早未反映到 IP 的提交年龄。维护触发阈值继续留空。
4. 若测试窗口内未触发某类维护，结果标记“覆盖不足”。可另用明确标注的合成配置触发维护验证行为，但不能将其性能替代未来生产配置结果。

判定重点：区分随已存文件规模合理增长的元数据与未释放的工作状态；仅凭 RSS 增长不直接诊断内存泄漏，也不以缓存增长掩盖不可持续吞吐。

### P05：容量边界与结果分类

1. 在设备替身中分别提供可信充足、可信不足和需要校准的容量证据，观察相同文件准入的路径、等待原因与结果；不通过真实写满介质构造首轮测试。
2. 可信不足时应拒绝当前准入；校准分支按未来配置的有界等待退出或继续，超时数值和错误码不在本用例中决定。
3. 模拟在途消耗使收尾预算受威胁，检查停止扩大写入义务且容量安全优先于 time/size；设备状态不明时，不以强行提交替代恢复门控。
4. 分别报告容量充足路径的附加查询/等待成本与边界路径成本。拒绝或等待属于预期分支时，可以验证行为正确，但不能把拒绝掉的工作计作高吞吐。

本用例只检查既定准入政策及观测能力，不假定容量估算算法或真实 EOM 恢复协议已经完成。

### P06：读取与多驱动扩展

1. 使用内容已经校验的独立文件集，先分别测冷读带与热缓存读；记录缓存证据、定位和装载成本是否纳入，不能仅把某次读取命名为“冷读”。
2. 在实际资源允许时扩展到多驱动，保留每驱动数据与库级汇总；分别测独立工作集，之后再加入读写混合负载。
3. 记录应用计划发起速率、实际发起速率、完成速率和等待；没有输入的并发、读写比例及公平性目标不填默认值。

无多驱动环境或未定义冷缓存构造方法时，对应覆盖保持未运行，不外推结果。测试准备不得隐式清除共享缓存、改动非测试介质或部署远程服务。

## 最小观测点草案

这是后续实现应提供的证据需求，不规定接口类型、遥测库、线程模型或持久化格式。

| 位置 | 需要关联的事件/字段 | 用途 |
| --- | --- | --- |
| 测试客户端 | 运行标识、文件清单项、计划/实际发起、接收完成、成功响应或其他结果 | 分开计算供给、接收、应用确认，识别负载发生器瓶颈 |
| 准入与缓冲 | 快/慢路径原因、等待起止、预留变化、缓冲占用、背压起止 | 检验正常路径成本、边界分支与资源上限 |
| 提交调度 | 卷身份、进程实例、测试内提交关联标识、触发原因集合、最早未提交变更时刻、快照覆盖的文件状态 | 解释触发、归属和不能提前确认的文件；不把索引 generation 当请求 ID |
| 数据与索引执行 | 操作开始/结束、实际结果、索引类型/代际/大小、屏障结果 | 区分排队、构建、传输与持久化完成；数据 WRITE 返回不单独构成完成证据 |
| 资源与维护 | CPU、内存、SSD、队列曲线，Full/IP 事件及覆盖范围 | 判断积压趋势、维护覆盖和共享资源竞争 |

关联标识与逐文件映射只用于受控测试或诊断，不写入磁带回执，不要求跨节点延续，也不参与产品权威状态判断。索引 generation 的关联须带卷身份；跨进程事件还须区分实例，不能把重启后的局部计数器当全局身份。

观测本身不能成为小文件瓶颈：建议高频指标聚合、详细轨迹按测试需要受控启用；输出缓冲有界，不引入每文件同步刷诊断日志、设备查询或 A/B 同步。避免按每个文件创建永久保留的指标标签。具体采样率和缓冲额度留空。

正确性用例需要足够完整的关联证据；若关键事件丢失，标记证据不足，不用采样结果证明“从未提前确认”。性能运行记录观测模式及事件丢弃量，对比不同观测强度时保持相同安全保证，并报告测量开销，不能通过关闭可靠性检查来抵消开销。

## 结果判定与实施前置条件

每个用例分别记录“行为检查结果”和“性能结论”，不要合并成一个通过标志：

- 行为检查可以是通过、失败、证据不足或未运行；发现误报成功、计数重复、越过隔离/容量保护等问题时，即使吞吐高也不能判通过。
- 没有数值目标时，性能结论只能是已测基线或尚未测量，不能标为性能达标。运行不完整或维护覆盖不足时单独注明。
- 模型中的逻辑步骤可以先实现；涉及真实完成条件的断言须绑定 04 最终提交协议，客户端具体调用须绑定 05 文件操作契约。06 不提前代替这些票据选定接口和错误码。
- 取消、部分文件、响应丢失及 A/B 接管仍作为前述独立正确性场景，详细故障注入协议由 04/08 继续收敛；本轮不启动有未解决依赖的 05/08 票据。

## 验收证据与未完成项

### 已接受的优化次序与比较方法

在相同可靠性与容量保护下，以大文件持续归档/恢复吞吐为基础优化方向，以小文件可靠完成文件率及逐文件成本作为必须单列的极端场景；同时保留端到端延迟、积压与多驱动公平性指标，不通过逐文件强制提交换取单个延迟样本，也不隐式新增混合负载 SLA。

准入不能成为写入瓶颈：正常可信预算快速路径不额外按每文件发起容量 SCSI 查询或 Raft 共识，后台校准与真正需要的慢路径另计。已有设备数据操作不算“新增容量查询”；不能把查询移到未统计队列来满足该断言。该约束不承诺零 CPU/内存开销，实际增量开销仍以同等保证的可比试验衡量。

硬件连续流基线可作为设备能力参考，但若缺少文件索引/提交屏障，则不作为具有同等归档语义的直接胜负基线。软件回归对照须记录相同初始卷、文件集、压缩及持久化/维护配置；不同配置的结果另列，不从实验中倒选最有利基线。

### 已接受的参数化判定与留空处理

每次用于宣称性能达标的实验，在运行前固定一份测试配置记录：工作负载与环境、启用场景、完整/稳态窗口、参考基线及其适用保证、各指标目标和统计规则。配置记录是测试资产，不是上传回执或生产持久化协议。

可用符号定义判定，但本轮不赋数值：吞吐/文件率至少达到对应目标，延迟/资源/准入开销不超过对应上限；若采用硬件或软件基线比例，明确分母含义、配置一致性和待测比例。目标不得在结果出来后修改以把本次运行改成通过。

| 条件 | 允许的结论 |
| --- | --- |
| 目标或必要输入未填，尚未运行 | 未配置/未测量，不是失败也不是达标 |
| 只有明确标注的合成配置，业务目标仍未知 | 可报告该配置基线和行为结果，不能外推实际业务达标 |
| 已有目标，但窗口不完整、维护未覆盖或关键证据缺失 | 该目标覆盖不足，不以最好稳态片段替代 |
| 正确性失败，即使吞吐超过目标 | 行为失败；不宣称整体验收通过 |
| 目标事先固定、行为/证据合格、所有适用指标满足 | 仅对该版本、配置及覆盖范围报告达标 |

用户明确允许未知业务输入留空，因此它们是后续测量/验收配置，不再作为本票据无限等待补问的理由。具体数据集、参数、统计置信要求、测试程序和实际结果仍待实施/测量；此处只确定如何填入、如何判定以及禁止怎样外推。产品 time/size 默认模式、缓冲/链长算法、文件 API 和 HA 规则不由 06 代定。

- 性能对比保持硬件、数据、压缩、初始状态和持久化保证可比。配置有差异时逐项列出，不能将更弱的确认语义当作等价基线；也不关闭容量保护来证明准入低开销。
