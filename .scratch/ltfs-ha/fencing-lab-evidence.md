# 设备层隔离的实验室证据：SCSI 持久预留

来源票据：[09 隔离设施选型与部署前提](issues/09-fencing-deployment.md)。本文只提供"已观察事实"，不替用户回答现场环境问题，也不改变 [03](issues/03-ownership-fencing.md) 的裁定：外部隔离是安全基线，SCSI 持久预留（PR）是待验证的可选加强。证据三类：**[源码]** 参考实现 LinearTapeFileSystem/ltfs `v2.4.8.3-10521`（与 EE 集群的 LE 同版本号）；**[只读]** 2026-09-17 对实验室设备发 PERSISTENT RESERVE IN；**[实验]** 同日在 TAPERS 专属驱动器上用两个发起方做的抢占实验。

先澄清一层关系：Raft 决定谁有资格执行（任期只存在于软件里，驱动器不认识）；隔离保证没资格的节点确实动不了设备。两者不能互相替代（[17](issues/17-raft-ha-direction.md) 已写明）。PR 属于后者里"让设备拒绝旧节点"的那一种手段。

## 1. IBM LE 怎么用 PR [源码]

| 事实 | 位置 |
| --- | --- |
| 类型固定为 Exclusive Access（0x03），作用域 LU | `tape_drivers/ibm_tape.h:136`，`sg_tape.c::sg_reserve` |
| 8 字节键 = 1 字节前缀 + 节点标识：0x40 + IPv4 地址，0x60 + IPv6 后 7 字节，取不到地址时 0x10 + 主机名 | `ibm_tape.c:1280–1335`，`ibm_tape.h:187–189` |
| 打开设备时先读预留：无人持有则可用；持有者是自己的键则尝试重新预留；是别人的键则跳过该设备 | `sg_tape.c:1375–1420` |
| **TUR 得到 RESERVATION CONFLICT 时，LE 用自己的键重新注册并 PREEMPT AND ABORT 抢回预留**，日志称"选择另一条路径，恢复预留"，然后返回 NEED_FAILOVER | `sg_tape.c:823–850` |
| 读不到任何持有者时视为驱动器真的上电复位过，重新注册并预留 | `sg_tape.c:857–866` |
| `ltfs -o release_device` 只做释放介质与设备后退出，用于异常终止后解锁 | `main.c:1010–1014`；对应指南 §9.6.4 |
| 只对驱动器做预留；换带器不预留 | 源码无换带器预留路径；下节只读查询吻合 |

第四行是关键：**LE 的 PR 用法是为多路径切换设计的，不是为隔离设计的。** 被别的键抢占后它会主动抢回。所以"EE 用了 PR"不等于"EE 靠 PR 隔离旧节点"，不能照搬。

## 2. 实验室设备上的现状 [只读]

- EE 驱动器 `IBMlisa42299`（从 ee1 查询）：一个注册键 `0x400000000a830948`，预留类型 Exclusive Access。键 = 0x40 + `0a 83 09 48` = 10.131.9.72，即 ee2。与源码的键构造逐字节吻合。
- TAPERS 的驱动器与换带器：无注册、无预留。
- 能力报告（驱动器与换带器相同）：六种预留类型全部支持，PTPL_C=1（可跨断电保持）但 PTPL_A=0（当前未启用），ATP_C=1，SIP_C=1，CRH=1。
- 这些能力来自 Linux 内核的 LIO 目标而不是 Holo：Holo 的 backstore 上 `emulate_pr=1`，PR 命令由内核按真实的发起方-目标端口关系处理，Holo 数据面里的 PR 代码在这条路径上不生效。所以实验室里的 PR 语义可信，但它代表的是 LIO，不代表 TS4300 与 LTO-8 的固件。

## 3. 抢占实验 [实验]

环境：tsclient 上给 open-iscsi 建第二个 iface（发起方名 `iqn.2026-09.lab.claude:tsclient-path-b`），Holo 侧给 `drive-tapers-drv-01` 临时加该发起方的 ACL，得到同一驱动器的两条独立路径 A（`/dev/sg6`）与 B（`/dev/sg8`）。实验后已登出、删除 iface 与 ACL，预留已清除。脚本 `ts_fence.sh`。

| 步骤 | 观察 |
| --- | --- |
| A 注册键并取得 Exclusive Access | 成功 |
| B 未注册时经 tape-rs 列目录 | 第一条介质命令即 `RESERVATION CONFLICT`，tape-rs 报 `TapeError::ReservationConflict`。B 仍可用 PR IN 读到持有者的键 |
| B 注册自己的键，PREEMPT AND ABORT 抢占 A | 成功；注册表里只剩 B 的键，A 的注册被移除 |
| A 的下一条命令 | 先得到 UNIT ATTENTION「Registrations preempted」（2A/03），之后一律 `RESERVATION CONFLICT` |
| A 上 tape-rs 写文件 | 被设备拒绝，没有任何数据落带 |
| A 用旧键重新预留 | `RESERVATION CONFLICT`（键已被移除） |
| B 挂载该卷 | 只看到抢占前已提交的文件，快速路径命中，可写；B 追加成功 |
| A 模仿 LE：REGISTER AND IGNORE 重新注册，再 PREEMPT AND ABORT 抢回 | **成功，预留回到 A** |

## 4. 由此得到的结论与边界

1. **PR 能挡住"不知道自己已下台"的旧 Leader**：抢占之后旧路径的读写、定位全部被设备拒绝，已提交内容不受影响。这正是 Raft 任期做不到的那一段。
2. **PR 挡不住"主动抢回"的节点**。任何能到达设备的发起方都可以重新注册并抢占。所以 PR 只对守纪律的软件有效：本系统必须把 2A/03 和 `RESERVATION CONFLICT` 当作"已失去执行资格"的权威信号，立即冻结，绝不自动恢复预留。IBM LE 的做法相反，不能沿用。对卡死、失控或被入侵的节点，仍需要 03 裁定的外部隔离。
3. tape-rs 现状：已能识别 `RESERVATION CONFLICT` 并给出专门错误；`retry_unit_attention` 会重试 2A/03，但重试得到的是冲突，仍然上报，不会误判成功。尚无注册、预留、抢占的实现。
4. 键应取什么：LE 用节点 IP。本系统若启用 PR，键里应带 Raft 任期或执行授权的代数，使"旧键"在语义上就是陈旧的；具体编码留给 18。
5. 换带器：LE 不预留换带器。本系统的 Leader 独占整组设备（17），换带器是否也预留取决于真实 TS4300 的支持情况，未验证。

## 4a. 怎样才算"确认旧 Leader 已被隔离"

原则（03 已裁定，这里配上实验证据）：确认必须是**不需要旧 Leader 配合的一方给出的肯定回读**，而不是"命令已发出"或"等够了时间"。

| 手段 | 什么算确认 | 什么不算 |
| --- | --- | --- |
| 断电/复位（BMC、PDU、虚拟化平台） | 管理面执行后回读到电源状态为关，或实例状态为已停止 | 请求已受理；旧节点 SSH 上停服务成功；旧节点自报已下台 |
| 路径隔离（FC zoning、带库主机访问控制、iSCSI 目标 ACL） | 配置变更后回读生效，且目标侧看到旧发起方的会话已断开 | 只改了配置没回读；只断了其中一条路径 |
| 设备层 PR | 抢占后对**每个**受管设备发 PR IN 回读：注册表里没有旧键，持有者是新键，PR generation 已变化。这是设备自己的回答，实验第 3 步即如此 | 只看到自己 PREEMPT 返回 GOOD 而不回读；只处理了驱动器没处理同组其他设备 |

三条共同的否定项：心跳超时、租约过期、Raft 任期增长都只说明"它该停了"，不说明"它停了"。无法得到肯定回读时，按 03 不接管，报告不可用。

确认之后还有两件事不能省：一是 18 的交错情形，后来当选的节点不能直接沿用前一轮的"已隔离"结论，要重新回读；二是接管后一律走 D02 恢复协议，因为被中止的写入有没有落带目前没有证据（见下节）。

## 5. 仍未验证，且实验室验证不了的

- 真实 TS4300 换带器与 LTO-8 驱动器固件的 PR 支持、类型与 PTPL 行为。实验室是 iSCSI + LIO，生产是 FC + 驱动器固件（CLAUDE.md 记录的目标硬件）。
- 多路径（同一节点经两条 FC 路径）下注册与抢占的语义；ATP_C/SIP_C 在真实设备上的取值。
- PREEMPT AND ABORT 对在途写入与驱动器缓冲区的影响：被中止的 WRITE 之前已进缓冲、未刷带的数据是否会落带。本次实验 A 在被抢占时没有在途命令。这一点决定新 Leader 是否必须无条件走 D02 的完整尾部核验；在得到证据前按"可能落带"处理，即接管后一律走恢复协议，不信任旧的 VCI 之外的任何内存状态（现有设计已如此）。
- 驱动器断电或复位后预留是否保持（PTPL 未启用时会丢失；LE 把"读不到持有者"当作真的上电复位）。

## 6. 实验室拓扑的已观察事实（供 09 使用）

- holo-vtl、ee1、ee2、ee3、tsclient 五台都是同一台 PVE 主机（10.131.9.20）上的 VM：计算、电源、网络是同一个故障域，不能用来演示独立故障域或外部断电隔离。PVE 可以对单个 VM 执行停止/重置，这在实验室里可充当"外部隔离"的替身，但生产环境是否有等价物（BMC、受控 PDU、虚拟化平台 API）需要用户提供。
- 设备经 iSCSI（10.10.1.0/24）而不是 FC 到达；发起方访问靠目标侧 ACL 控制。ACL 本身也是一种隔离手段（目标侧摘除旧节点的 ACL 即断开其会话），在真实 FC 环境里对应交换机 zoning 或带库的主机访问控制，是否可由软件自动操作同样需要用户提供。
