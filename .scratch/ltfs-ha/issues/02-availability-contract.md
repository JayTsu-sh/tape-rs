## Question

如何精确定义已接受的 60 秒控制面和 5 分钟数据服务目标？从节点实际失效还是检测完成开始计时，设备核对时间是否计入总预算，哪些节点故障必须覆盖？对断电、网络分区、写带过程中断、已暂存未提交、提交成功但响应丢失分别规定 RPO、可见错误和恢复终点。保留已提交数据零丢失的底线；磁带定位可能使固定时限无法无条件保证。

讨论后拆分范围：本票据解决数据权威、上传恢复责任与 A/B 同步必要性；计时起终点、覆盖卷范围和完整故障验收留给[接管时间与故障验收范围](08-recovery-acceptance.md)，不视为已决。

## Comments

### 首轮讨论草案（待用户裁定）

用户已接受主备接管、严格 commit 零丢失与同步暂存保护。本轮补充可检验语义，不重新征求这些方向的授权。

- 建议验收从注入节点故障的时刻计时，60 秒控制面、300 秒数据面共享同一起点；故障检测、隔离、身份核对、恢复和定位均计入。生产观测只有检测时间时，单独说明检测误差。此建议比原“设备核对后五分钟”更严格，尚未确认。
- 控制面完成建议定义为确定唯一有效所有者、验证旧主隔离、服务端点可响应恢复状态；不能以启动新进程即视为成功。
- 数据面完成建议以校验后的目录可用及真实磁带读取探针成功为证据，写入可用性单独记录；不能以请求进入队列作为恢复完成。五分钟读写均恢复是否必需，取决于下述降级选择。
- 计划覆盖进程崩溃、节点断电、节点间网络分区，以及写数据/索引提交期间中断。无法证明旧主隔离时禁止备节点发设备命令，报告安全停机和超时，不能为达成 RTO 跳过隔离。
- 返回严格 commit 成功的数据在单节点故障后零丢失；返回同步暂存持久化成功的数据也应可恢复。普通 write 返回、缓存接收和持久化确认的区别由文件接口与提交票据细化。尚未确认的操作可以要求重试；已完成但响应丢失的操作必须能查询/去重，不能把超时视为未执行。

### 当前需裁定的取舍

两节点同步复制中一节点失效后，存活副本保住了此前确认的数据，但新的暂存写入无法继续获得跨节点同步确认。见证只参与仲裁，不能充当数据副本。保持相同保护级别时，应暂停新的暂存持久化成功确认；如果要求五分钟恢复同等保护的新写入，则拓扑须提供在单节点故障后仍可用的冗余存储能力。

建议默认保持数据保护：恢复读取与已确认任务的恢复处理；冗余不足时背压/拒绝新写入，不静默降级为单副本成功。用户需裁定是否接受该降级服务范围，然后才能确定五分钟目标覆盖读取还是完整读写。

### 第二轮：同步一致性与磁带权威

用户明确 A/B 为主备模式，并提出：若不能实时一致，应以带库数据为 single source of truth。这里记录该条件性偏好，尚未视为撤销此前同步暂存保证。

事实澄清：主备可在写入确认点实现同步持久化，例如 [DRBD Protocol C](https://linbit.com/drbd-user-guide/drbd-guide-9_0-en/) 等待本地和远端磁盘确认；这不是两台机器每个瞬间完全相同。文件内容、命名元数据与恢复日志的应用事务一致性仍需协议保证，不能靠块复制自动推出。

建议进一步区分两个权威：已提交文件状态以具体 LTFS 卷上的有效数据与可恢复索引为准；同步暂存只保护尚未提交的工作。若外部存储先返回了持久化成功，就产生了不能仅凭旧磁带索引丢弃的义务。反之，若唯一持久化确认点是磁带提交，暂存可重建，未提交操作可由调用方重试。

对首轮草案的补充：节点故障后暂停新写入并非唯一可行路线。若采用磁带提交才返回持久化成功的契约，在旧主已隔离、卷恢复成功且磁带可写的前提下，备节点可继续写带并延后确认至提交完成，无需等待另一暂存副本恢复。代价是提交延迟和暂存级别保证变化；不能静默变更此前给出的同步暂存成功承诺。

待裁定：磁带是“已提交文件状态的权威”还是“所有已确认持久化状态的唯一权威”；普通 write 接收、可选同步暂存确认与严格 fsync/commit 的语义分别是什么。此项选定后继续确定 RTO 及故障覆盖范围。

### 第三轮：主节点未同步暂存即掉电

用户提出 B 的暂存可能不等于 A，要求明确处理方法。当前讨论不构成接受未提交数据丢失。

恢复建议：先隔离 A，再验证卷身份与可恢复索引，重建已提交视图。B 的缓存未经卷身份、已恢复版本与内容对应关系验证不得提供为最新文件；B 的 dirty staging 先隔离保留，不自动提交或覆盖磁带状态。A 恢复上线后也必须经过重新对账与授权，不能沿用旧写头继续写。

- 已完成磁带提交：依据磁带恢复，即使 B 的 catalog 落后也不回退到 B 的版本。
- 数据部分落带而尚无完整恢复证据：视为未完成/结果未定，保留现场并验证；不按物理尾部字节数推算可续传偏移，不直接覆盖未验证尾部。
- 数据仅在 A 的内存或本地 SSD：B 无法重建不存在的字节。A 存储可取回时再恢复；否则由保留源文件的应用重传。若所有源副本均丢失，未提交内容无法保证找回。
- 磁带提交已完成但响应丢失：应能凭可恢复的操作标识/版本证据查询结果或安全重试；具体去重信息如何持久化由提交/接口票据决定。

因此“磁带是已提交状态权威”解决分歧判定，不补足未复制且未落带的数据。若需求包含不依赖源应用重传、不中断续接所有已接收写入，就必须增加受保护共享暂存、同步复制，或在对应确认前完成磁带持久化。主备接管可用性与未提交任务连续性须分别验收。

### 第四轮：已确认范围与上传对账方案

用户已明确：A 掉电后的未提交上传不要求自动续传。此前关于无条件接续全部暂存任务的假设不再作为接管要求。用户进一步要求说明 B 如何读磁带、与应用交互以及决定重传范围；以下为接口与协议草案，不提前裁定整张票据。

建议以一个完整文件版本作为首版上传提交单位，多个完整文件可批量进入同一 LTFS generation。应用在开始前持久保存 upload_id、目标卷身份/可恢复的卷路由、文件版本、源文件位置与长度，直到收到或查询到匹配的提交回执。重试保持同一 upload_id 与同一内容，改变内容必须使用新版本/新任务。

B 在旧主隔离后读取卷 label，验证身份；检查索引分区与数据分区可用的完整索引、必要的增量链及恢复证据，不能单读固定 P0 block 或取最大的未验证 generation。根据恢复后的文件元数据、extent 和上传提交记录重建 catalog。仅恢复元数据与索引不要求逐文件读回全部内容；记录的内容摘要不等于已在接管时读回校验全卷。

LTFS 索引已有文件身份、长度与 extent，但应用 upload_id 与完成回执是本项目需要额外设计的语义。建议将 upload_id、文件版本、长度/内容摘要等完成证据纳入与文件相同的磁带提交；可通过标准 xattr 或卷内清单表达，编码选择由持久化票据裁定。仅存在节点 SQLite 的回执不能满足磁带权威目标。覆盖/删除后回执的保留范围也必须定义；否则查询缺失只能表示 UNKNOWN，不能证明从未提交。

原生客户端重连新主后，批量查询尚未确认的 upload_id。候选结果：

- COMMITTED：有与卷、文件版本、长度/内容标识匹配的完整提交证据，返回回执，无须重传；涵盖响应丢失。
- RETRY_REQUIRED：已完成相关卷恢复、查询历史覆盖范围充分，确认没有完整上传提交；应用可重传整个文件，从 0 开始。部分落带字节或旧暂存均不构成可跳过的上传偏移。
- RECOVERING / UNKNOWN：恢复未完成、卷离线、介质读错或历史证据不足；稍后查询或排障，不自动判定缺失后覆盖。
- CONFLICT：同一 upload_id 对应不同版本/内容或不同目标，拒绝复用，交由应用处理。

B 无法从磁带列举 A 从未落带的所有上传任务，因此待对账任务集合必须来自应用的持久任务清单。若一个文件未整体完成提交，首版建议整文件重传；独立文件已提交则不重传整批。保留未验证尾部直至恢复策略判定，不直接截断或覆盖。

FUSE 的普通 POSIX 应用没有 upload_id 查询协议：SDK 主导此精细对账；挂载路径的中断上传须向应用报告失败，由其重开/重传并通过严格 fsync 判断持久化。自动对账不能被描述为所有 POSIX 应用的透明能力。

当前代码证据：src/ltfs/volume.rs 的 mount 固定读取 P0 block 4，再定位 P1 EOD；src/catalog/sync.rs 能从读取到的卷索引重建文件/extent 数据。完整索引恢复、上传回执与跨节点查询均需后续设计实施。

### 第五轮：是否必须进行 A/B 同步

用户询问在上述方案下的数据与元数据同步必要性。条件性结论：若只有磁带提交确认持久化成功、应用保留未确认任务和源数据、全部已提交文件与上传结果可从卷恢复，则 A/B 的文件暂存、读缓存、catalog 和磁带位置缓存均不必同步。已提交元数据仍必须可靠落带，而不是不需要持久化元数据。

节点拥有权、fencing 和接管资格仍需一个可验证的协调机制；这不要求同步大块数据，也不等同于 A/B 异步互抄 owner 文件。控制面具体实现由设备所有权票据裁定。服务配置、卷发现/路由以及实际启用的访问凭据或加密密钥须在备节点可用，不得只有 A 能解释或解密磁带。

可选同步已提交索引快照/提交回执缓存以加速接管，但快照需绑定卷 UUID、已提交版本及完整性证据；落后时从磁带补齐，不能因缓存宣称更新就覆盖磁带。多卷恢复若缺少可用卷路由/索引缓存，可能需要装载多个卷，五分钟目标不能由无需同步的可行性推出。

当前建议为“数据暂存无需同步；已提交元数据缓存可异步复制作性能优化；所有权须可靠协调”。尚未视为用户已选择具体缓存或协调技术。

## Answer

后续范围调整：[暂不引入上传回执](04-durability.md#已裁定暂不引入上传回执)。本节的磁带权威、暂存不复制与所有权约束仍生效；上传回执、按上传 ID 查询/去重和历史保留已移出当前范围。响应丢失后的文件系统状态仍须恢复，但应用的单次请求结果可能保持未定。

用户在第五轮建议后明确回复“按照适合当前的方向”，确认以下架构方向。本节为生效决策；Comments 中同步暂存和降级只读的早期建议仅保留讨论历史。

1. **数据权威与确认点**：磁带保存已提交文件状态及恢复所需的标准文件系统元数据，不额外保存上传回执历史。只有满足磁带可恢复提交条件，才能确认归档持久化成功；暂存接收、普通 write 返回不得等同于该确认。严格 fsync/commit 的具体协议由后续票据设计。
2. **节点暂存无需复制**：A/B 各自的上传暂存、读缓存和设备位置缓存不要求同步。未提交上传不承诺自动续传；应用保留未确认任务清单与源数据，故障后核验恢复的文件状态，仅在满足安全重试条件时重传；不能确定的请求保留结果未定。
3. **元数据缓存可异步复制**：catalog 和已提交索引快照属于可重建数据。允许异步复制作为接管加速手段，但不作为正确性的必要条件。恢复时核对卷 UUID、提交版本和完整性证据，以磁带有效状态为准，不以节点间哪个缓存更新来裁定。
4. **所有权需要可靠协调**：主备必须确保同一目标设备只有一个有效所有者；无法证明旧主隔离时不能接管写入。仲裁、fencing、所有权粒度及目标硬件能力由设备所有权票据裁定，不预设 A/B 之间复制 owner 文件就足够。
5. **接管后可以继续写带**：隔离旧主、恢复卷并确认可写后，B 不因缺少第二份暂存副本而必然只读；新的持久化成功仍须等待磁带提交。此前建议的“失去暂存冗余则等待副本恢复才开放写入”不适用于本契约。
6. **区分未提交与未确定**：B 无法从磁带发现从未落带的上传任务，应用负责保留未确认工作。证据不足或恢复未完成时不得把查不到视为确认未提交；当前文件状态也不保证能证明某次历史请求结果。暂不设计回执或按上传 ID 的持久结果查询；核验、重传单位与安全重试条件仍待文件语义票据裁定。
7. **备节点的基础能力**：恢复所需配置、卷发现与路由、访问凭据以及启用加密时的密钥须在 B 可用；不能仅存在于 A 的不可访问状态中。磁带库/介质共同故障域不因该节点接管设计而消失。
