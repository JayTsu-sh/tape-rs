## Question

根据实际目标环境，选用哪一种外部 fencing 设施与适配组件，并如何验证它覆盖整个受管设备组？记录 A/B/C 是物理机还是 VM、三个节点的管理面/电源/FC 路径及共享故障域、稳定 drive/changer 身份、逻辑带库划分与外部软件访问范围。说明所选隔离在节点卡死、心跳网断开、节点断电、管理面失联时能否可靠执行和确认，以及无法确认时的行为。

核对三个 Raft 投票节点的独立故障域、控制存储及通信条件；按 18 的授权协议验证单节点失联、网络分区、旧 Leader 恢复、启动时只有单节点可达等场景的行动资格。不再配置独立 qdevice/qnetd 见证。选择计划切换/停止失败时的现场隔离处理、是否增加经验证的 SCSI PR、相应预留类型和三节点全路径验证前提；同时明确部署配置与凭据如何在任一接管节点可用。

## 已观察事实（2026-09-17，claude）

票据仍 open：现场环境约束要由用户提供，本节只登记实验室能给出的证据，详见[设备层隔离的实验室证据](../fencing-lab-evidence.md)。

- IBM LE（参考实现源码，与 EE 集群同版本号）对驱动器用 Exclusive Access 持久预留，键 = 前缀 + 节点 IP；实验室 EE 驱动器上读到的键正是 ee2 的 IP。但 LE 遇到预留冲突会**主动抢回**，它的 PR 是为多路径切换设计的，不是隔离手段，不能照搬。
- 两个发起方的抢占实验：新持有者抢占后，旧路径的全部介质命令被设备拒绝（先 2A/03 Registrations preempted，后 RESERVATION CONFLICT），旧路径上 tape-rs 的写入没有落带，新持有者看到的卷完整可写。旧路径若重新注册并抢占，可以把预留抢回。
- 结论：PR 能覆盖"旧 Leader 不知道自己已下台"这一段，前提是本系统把 2A/03 与预留冲突当作失去执行资格的权威信号并立即冻结、绝不自动恢复预留；对卡死、失控的节点仍需要 03 的外部隔离。
- 实验室的 PR 由 Linux LIO 内核目标实现，不代表 TS4300 与 LTO-8 固件；换带器的 PR、多路径语义、抢占对在途写入与缓冲数据的影响、断电后预留是否保持，均未验证。
- 实验室五台 VM 同在一台 PVE 主机上，是同一个故障域；设备经 iSCSI 而非 FC 到达。

## 仍需用户提供

1. 生产环境的三个节点是物理机还是 VM？各自有没有可由软件调用的断电/复位手段（BMC/IPMI、受控 PDU、虚拟化平台 API）？
2. 节点到 TS4300 的 FC 路径数、是否经交换机、交换机 zoning 或带库主机访问控制能否由软件操作？
3. 带库是否划分逻辑库，是否有本系统之外的软件访问同一逻辑库？
4. 是否接受"外部隔离为主、PR 为设备层第二道"的组合；若生产环境拿不到任何外部隔离手段，是否接受仅靠 PR + 软件纪律，并接受它挡不住失控节点这一已知缺口？

## 用户已提供（2026-09-17）

- **问题 1**：生产环境没有可由软件调用的断电或复位手段。后果：03 列举的三类外部隔离里，"电源/PDU"与"虚拟化管理面关停"两类不可用，只剩"覆盖全部设备路径的 fabric 隔离"；若 fabric 也不能由软件操作，则没有任何符合 03 原文的外部隔离手段，自动接管的前置条件需要重新裁定（见问题 4）。
- **问题 3**：带库需要支持划分逻辑库。记为产品要求：受管设备组 = 一个逻辑库（其换带器控制路径 + 分配给它的驱动器）；同一物理带库的其他逻辑库可能由别的软件使用，不在本系统控制范围内。推论：隔离与预留的"全部受管设备"以逻辑库为边界；本逻辑库的驱动器不得同时对外部主机可见，否则外部主机的访问不受 Raft 与隔离约束。是否像 EE 那样同时管理多个逻辑库未裁定。
- 问题 2、4 用户要求先详细说明，尚未回答。说明要点见下。

## 问题 2、4 的说明要点（2026-09-17，claude）

**问题 2 为什么重要。** 没有电源类手段后，FC fabric 是唯一可能满足 03 的外部隔离位置。需要知道的事实：

1. 节点到驱动器是直连还是经 FC 交换机。17 要求三个节点都能到达全部驱动器；LTO FC 驱动器端口数有限（常见 1–2 个），三节点全可达在物理上基本要求有交换机。TS4300 的换带器没有自己的 FC 端口，控制路径经某个驱动器的 LUN 1 到达（EE 指南称"控制路径驱动器"），所以切断一个节点到驱动器的全部路径也就切断了它到换带器的路径。
2. 交换机能否由软件管理（Brocade FOS 的 SSH CLI / REST，Cisco MDS 的 SSH / NX-API）。可以的话，隔离动作 = 禁用旧节点 HBA 所连的交换机端口，或把旧节点 WWPN 从 zone 里移除并激活；确认 = 回读端口状态为禁用、name server 里旧 WWPN 已无登录。它不需要旧节点配合，节点卡死也有效，属于 03 认可的 fabric 隔离。
3. 前提：旧节点的每一条路径、每一个 fabric 都要处理；交换机管理网要独立于故障节点且三个节点都可达；凭据三个节点都要有；解除隔离按 18 的裁定由运维显式触发。
4. 带库侧按主机限制访问（LUN masking 一类）：TS4300 是否提供、能否由软件操作，未核实，不作假设。

**问题 4 的实质。** 若交换机不可由软件管理（或根本是直连/SAS），就没有任何外部隔离，03 的"外部 fencing 是自动接管的前置条件"无法满足。三个选项：

| 选项 | 内容 | 覆盖 | 不覆盖 |
| --- | --- | --- | --- |
| A | fabric 隔离为主 + PR 为第二道 | 节点卡死、失控、网络分区后恢复，全部覆盖 | 依赖可管理的交换机 |
| B | 仅 PR + 软件纪律：新 Leader 对逻辑库内全部驱动器抢占并回读确认后才接管；本系统把 2A/03、预留冲突、29/00 复位一律当作失去资格并冻结，绝不自动恢复预留 | 旧 Leader 不知道自己已下台（分区、暂停、卡死后恢复）：它恢复后的第一条命令就被设备拒绝 | 旧节点上有软件主动重新注册并抢占（本系统不会；IBM LE、ITDT、运维手工 sg_persist 会）；驱动器断电或复位且未启用 PTPL 时预留丢失（此时旧 Leader 会先收到 29/00，靠软件纪律冻结）；换带器若不支持 PR，旧节点仍可移动磁带（不损坏数据，但扰乱库存） |
| C | 不自动接管：故障后由运维确认旧节点已停，再显式授权新 Leader | 全部，代价是恢复时间取决于人 | — |

B 需要修订 03 的原文，把"设备层 PR 抢占 + 逐设备回读"认定为合格的隔离确认。B 的残余风险范围：抢占到回读之间已进入驱动器缓冲的旧写入可能落带，由接管后必走的 D02 恢复协议处理；不会出现"旧节点在新 Leader 写入期间继续写同一盘带"，除非旧节点上有别的软件主动抢回预留。真实 LTO-8 的 PR 行为未在本项目验证，但 IBM LE 在真实驱动器上依赖同一套 PR 命令，是其可用的间接证据；TS4300 换带器的 PR 支持未知。

推荐：有可管理交换机则 A；没有则 B 作为自动接管的条件，并把 C 作为 B 的任何一步无法确认时的出口。待用户裁定。

## 已裁定：持久预留 + 软件纪律（2026-09-17）

用户补充：**没有外部隔离；没有本系统之外的软件访问同一逻辑库。** 选项 A 因此不成立；选项 B 的主要缺口（旧节点上有别的软件主动抢回预留）由该运维前提覆盖。按推荐与自动接受授权记为已接受方向，用户可推翻：

- 自动接管的隔离条件 = 对逻辑库内每个支持持久预留的设备完成抢占并逐设备回读确认；任何设备无法确认则不自动接管，转人工确认（选项 C）。
- 这修订了 [03](03-ownership-fencing.md) 的"外部 fencing 是自动接管的前置条件"：合格手段增加"经设备回读确认的持久预留抢占"一类。03 其余内容不变。
- 本系统把 2A/03、2A/04、2A/05、RESERVATION CONFLICT、29/xx 一律当作失去执行资格的信号并冻结，绝不自动恢复预留；每次卷提交的屏障前自检持有者。
- 具体步骤、键的编码、换带器处理、人工出口与 PF01—PF10 见[设备层隔离协议候选](../pr-fencing-protocol.md)。

用户补充（2026-09-17）：**目前没有真实的 IBM 带库，只有 Holo-VTL。** 因此 FC/SAS 与交换机的问题暂不需要回答，移入[待真机验证清单](../real-hardware-checklist.md)的拓扑一节，将来选购真机时重新提出；PF08—PF10 同样移入该清单。三节点全可达在 Holo 上由 iSCSI ACL 实现，没有端口数限制。

票据保持 open 的原因只剩：是否同时管理多个逻辑库未裁定；三节点实验环境（三个发起方）尚未搭建，PF04 的上层整组冻结与 18 的 K→G 对接未实现。
