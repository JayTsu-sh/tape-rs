## Question

共享文件语义应如何表达 staged write、读自己尚未提交的写入、文件替换、rename/unlink、打开后删除、offset 写入限制与严格 fsync？为每个支持/不支持操作定义返回结果和原生接口对应关系，明确句柄在断连接管后的处理、结果未定及安全重试边界；不预设跨节点幂等重试。首版接受功能子集不等于可假装所有普通 POSIX 应用都兼容。

## Context

用户已裁定[暂不引入上传回执](04-durability.md#已裁定暂不引入上传回执)。接口保留正常成功/失败响应及严格持久化语义，但不增加回执文件、上传专用回执属性或持久上传查询接口。标准 index 恢复文件系统状态，不保证将该状态对应到某次响应丢失的请求。

根据[接管研究](01-ha-evidence.md)，分别裁定“客户端/FUSE 节点存活而后端切换”和“应用所在节点同时故障”时的重连、重新挂载与任务恢复；不默认迁移内核 fd。

此前[恢复与数据承诺的第四轮讨论](02-availability-contract.md)中基于 upload_id/回执的自动对账草案不再是实现前提。当前须定义：应用保留源数据和未确认工作，重连后如何核验文件状态，何时可安全重传，何时只能报告结果未定。不能将超时当作从未执行，也不能默认重放具有创建、替换或追加副作用的请求。

删除、覆盖、唯一命名和只创建等策略继续单独裁定，不因移除回执而默认禁止删除或强制只追加。回执历史保留与期限暂移出范围；业务文件保留策略是另一问题，不能被一并删除。

[首版恢复与跨卷范围](04-durability.md#已裁定首版恢复与跨卷范围)已获用户接受：不自动截断修复、不自动跨卷续传，证据充分才恢复写入。[容量策略草案](04-durability.md#异常尾部恢复与容量收尾策略草案)的预算及收尾算法仍待细化。本票据后续须明确已知空间不足与结果未定的不同返回、部分文件的可见性和显式清理授权、重选卷与新上传意图，不因范围确认而提前选定这些接口或解除依赖。

[部分文件保留策略](04-durability.md#已裁定部分文件保留策略)已获用户接受：保留已可靠提交的部分文件，不自动删除，不误报整文件上传成功。B 恢复后的上传完整性判定仍需应用源数据与任务信息，不新增完成标记/回执。最终路径发布、替换原子性、显式删除、重试与错误码仍由本票据裁定。

[准入慢路径等待政策](04-durability.md#已裁定准入慢路径等待政策)已获用户接受：可信预算确定不足直接拒绝，仅校准场景允许有界等待。接口仍须区分预算不足、校准等待超时和设备恢复中，不把网络超时或已有文件副作用等同于可安全重试。原生会话/预留取消与响应丢失、FUSE 已创建或修改文件后的返回语义、具体错误码及等待期限仍待定义，不因本次确认授权自动重放。

[取消不回滚与安全释放预留](04-durability.md#已裁定取消不回滚与安全释放预留)已获用户接受：取消停止后续工作而非回滚，已提交状态保留，只有确定未消耗且无在途/收尾引用的预留可释放。文件契约仍须明确取消与完成竞争、返回时机、缓存清理及 FUSE 调用中断与原生上传取消的区别；网络超时不代表服务端已取消或未执行，不提前选择会话过期及自动重试政策。

## Comments

### 依自动接受授权采用：文件契约首版候选（2026-09-17）

04 已裁定的无回执、部分文件保留、准入慢路径、取消不回滚、会话续期、有界接收、恢复时分开开放读写，加上 37/38 的任务身份与“已终止轮次、结果未知”回答方式，已足以形成可实施的接口语义草案。依自动接受授权采用[文件接口契约候选](../file-contract.md)，要点：

- 五个文件状态 in_progress / ready / committed / partial / unknown 对两个入口一致可见；读取只服务 committed 当前版本，ready 与恢复中返回“尚未提交/恢复中”而不是不存在。
- 创建默认 create_only（EEXIST），替换为新版本、在索引提交发布时原子切换，失败保留旧版本为当前、新版本为 partial。
- 只支持顺序追加写；已完成文件不可再追加，只能替换。
- 原生 `commit/wait` 与 FUSE `fsync` 是唯一归档确认点；`close` 只标 ready。`fsync(dirfd)` 提交命名空间变化。
- rename/unlink 对 in_progress/ready 拒绝 EBUSY；unlink 已提交文件允许并保留打开读句柄。
- 换 Leader 或执行实例重启后写任务一律 aborted（ESTALE / TerminatedRound），读在恢复完成后可继续；不承诺 fd 迁移。
- 安全重试四条规则：committed 且一致→不重传；不一致→replace；partial/不存在→重传从 0 开始；unknown→等待。create_only 是唯一服务端重放保护，不提供任务 ID 持久查询或去重。
- 错误类别与 errno 映射表固定；RecoveryInProgress 不得映射为 ENOENT。

**仍待 04 收敛后补齐**：会话期限与校准等待数值、partial 可读范围（D02）、fsync 与 time/size 交错（D03/PC）、恢复期间可信视图判定（RV01—RV05）。FC01—FC10 未实现/执行。本票据保持 claimed，不解除 07/08 依赖；Python Client API 只封装原生接口，不新增语义。

## Answer

**结论（2026-09-23）：05 resolved。** 用户在两轮提问里回答了 8 项（下表），合同全文改写在[文件接口契约](../file-contract.md)。9-17 的候选是在 ltfsd 实现之前写的，按流式写入设计；实现采用"整文件暂存 → 合批落带"，与之冲突的部分以实现为准并在契约开头说明。

| 问题 | 用户裁定 |
| --- | --- |
| 同一路径再次上传 | 默认替换；`If-None-Match: *` 为只创建（412 / `EEXIST`） |
| 删除与重命名 | 支持删除，写带版本号的墓碑（`.tapers/tombstones/<路径>`，目录按版本取大者）；不支持 rename |
| 已暂存未落带的 `stat` | 区分状态：200 + `state: uploading/staged`，附已提交旧版本；404 只表示视图可信且不存在 |
| FUSE 的地位 | 首版就实现 |
| FUSE `close` / `fsync` | `close` = 已暂存（被拒绝时返回错误）；`fsync` = 上传当前内容并等落带 |
| 读暂存中的文件 | 不能读：有旧版本读旧版本，否则 `EBUSY` |
| 目录 | 隐式目录；`mkdir` 只在挂载内存里生效，`rmdir` 只对空目录 |
| FUSE 放在哪里 | 独立进程，基于客户端库，可装在任何主机 |

**以实现为准的修订**（向用户说明过，未反对）：整文件暂存、上传需已知长度；单个文件不会"部分已提交"，`partial` 状态删除，04 的部分文件保留只剩接管收尾的 salvage；不提供持久任务查询，结果未定按"路径 + 长度 + sha256"判定。

**按推荐自行决定、用户可推翻的细节**：FUSE `rename` 返回 `EXDEV` 而不是 `EOPNOTSUPP`，让 `mv` 自动退回复制 + 删除（rsync 默认的临时文件改名因此不可用）；墓碑在回收时按活对象搬走，清理留到后续；`chmod/chown/utimens` 返回 `EOPNOTSUPP`；`GET /files` 支持单段 `Range`；`list?dir=` 按目录列举。

**与 EE 的对照**：EE 删除 GPFS 文件不改磁带，要等 `reconcile` 装带改写索引（与写入互斥）；未对账的带导出再导入会出现已删除文件。tape-rs 的墓碑不需要装旧带，单独导入旧带时同样会"复活"。删除切片实施前在实验室实际观察 EE 的删除、覆盖写和 migrated 文件读取（契约末节）。

**实施切片**（按"EE 观察 → Holo 偏差核对 → 实现与模拟器测试 → Holo 演练"）：

1. F1 语义补齐：只创建（412）、`stat` 在途状态、`list?dir=`/`pending=1`、`Range` 读、`not_committed`。FC01/02/09/10/11。
2. F2 删除：墓碑写带、目录按版本应用墓碑、回收搬墓碑、客户端与 ltfsctl。FC06/07/08。
3. F3 FUSE 适配器 `tape-fuse`：本地缓存写、close/fsync、错误映射、xattr。FC03/04/05/12。

未定的只有数值（合批时长、`retry_for`、暂存额度），沿用配置项。本票据不再阻塞 07/08。
