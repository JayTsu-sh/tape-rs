## Question

根据已确认的磁带权威与暂存不复制方向，磁带上需要保存哪些文件数据与标准索引，按何种顺序落带才能回应严格 fsync/commit 成功？定义单文件/批量提交边界、本地暂存和 journal 的非权威角色、缓存失效、generation 恢复与容量不足行为；处理数据已写但 index 未提交、索引副本分歧及响应丢失时的结果不确定性。节点丢失后必须能从磁带重建已提交文件系统状态，不能依赖遗失的节点 journal 或将 SSD 暂存视为归档成功。上传回执、其保留期及基于回执的跨节点自动去重暂不属于当前范围。

## Comments

### 首轮产品契约草案（待用户裁定）

已定方向不变：只有磁带持久化才确认归档成功，A/B 暂存不复制。当前要裁定完成条件、批量提交和历史凭据的取舍；以下不是现有实现能力。

**提交单位与批处理。** 原生上传以一个完整文件版本为完成单位；只收到部分文件不能返回上传完成。允许多个已完成上传共用一个卷 generation，以摊薄写索引开销；未完成上传不能阻挡已完成上传的提交，等待合批须有上限，显式提交可触发当前可提交内容。此处不把多文件批次定义为跨卷事务，也不把原生 finish 与普通 POSIX fsync 等同；FUSE 打开文件上的 fsync 必须覆盖该调用要求持久化的已有修改，不能要求应用先 close，具体可见性由文件语义票据细化。

**成功条件。** 推荐选择“可恢复的磁带持久化”：文件数据、文件映射与对应上传完成凭据已按可靠顺序落带，恢复流程不依赖节点缓存即可确认结果，才返回成功。允许索引分区快照稍后补齐，在清洁卸载/导出前达到规范要求的一致卷状态；MAM 更新失败不单独推翻已有持久化证据，但必须使提示状态失效并保留诊断。需要对延迟索引分区更新设置检查点策略，以平衡吞吐与接管耗时。

依据：[LTFS 2.5.1 §4.1.4、Annex C.4](https://www.snia.org/sites/default/files/technical-work/ltfs/release/SNIA-LTFS-Format-2-5-1-Standard.pdf)区分一致卷和 sync 后可无损恢复状态；§2 要求交换/存放介质时为一致状态。以上允许更高性能的契约，但不代表任意一次 P1 WRITE 返回成功就满足持久化。确切 SCSI 刷缓冲/文件标记/索引顺序必须有规范与故障测试证明，设计未证明前不能按该草案提前确认。

**上传凭据。** 建议将稳定 upload_id、卷身份、文件版本、长度与内容摘要等恢复证据同文件一起纳入提交。SSD/catalog 只存可重建副本。同一 id/内容重试应返回原结果；id 与内容冲突应拒绝。数据结构和标准兼容编码（例如卷内清单或扩展属性）仍待细化，不能靠路径或文件长度去重。

**历史保留（期限待定）。** 初始建议为保留上传完成凭据至卷重新格式化；后续讨论了有限期历史查询。用户明确三个月只是举例，具体期限尚未选定。回执证明的是该上传曾完成，不表示文件当前仍存在。删除文件是否需覆盖旧数据属于其他语义，不能通过删除去重凭据隐式实现。外部软件若不保留本项目凭据，则不能继续承诺完整的历史对账。

**中断处理。** 在提交证据齐全前中断，不确认成功；恢复后确定未提交的完整上传可由应用重传。提交已持久化但响应丢失，B 查询凭据返回成功。证据不足、卷离线或损坏返回结果未定/恢复中，不把“查不到”当作可安全覆盖。任何提交 I/O 结果不确定后，停止在当前会话中盲目重试写带，核对设备和磁带状态再决定后续动作；节点内存 generation 不能作为已提交凭据。

**空间与错误。** 必须为提交所需索引/凭据及收尾预留可证明的空间预算，设备报告早期告警或无法满足预算时停止接收超出可提交能力的新写入；实际短写、EOM、延迟错误都需纳入恢复。缓存、数据块或元数据任一写入失败均不能宣称整次归档成功。性能验收区分暂存吞吐、磁带持久化吞吐和索引检查点耗时。

首轮提出时，完整上传合批与成功确认政策均待裁定；成功确认政策现已接受，见下方“已裁定：归档成功确认点”。完整上传合批、提交记录编码、具体屏障协议及检查点策略仍需细化，历史查询原则已接受但具体保留期限待定。

### 回执保留原则与期限澄清

用户接受回执历史查询及其与文件保留独立的原则，随后明确“三个月回执记录只是一个举例”。此前将三个月记录为已确定期限是助手误解，现已修正。具体期限和是否可配置尚未选定，也不代表首轮中其他提交取舍已获确认。

- Index 表达当前文件状态及其数据映射，上传回执记录上传完成历史。两者逻辑职责分开，具体物理存放格式仍待设计，不能预设必须有两套独立文件。
- 历史回执从磁带提交成功起，在约定的保留期内提供查询依据，即使文件随后改名、覆盖或删除。回执依赖的必要信息随提交可靠落带，节点查询库仅为可重建缓存。三个月仅是讨论示例，不是默认值或固定要求。
- 回执候选字段为 upload_id、volume_uuid、文件身份/版本、长度、内容摘要、提交 generation、committed_at 和 expires_at；具体编码、保留期计算与时钟处理在协议中明确。
- 到期后不再承诺完整历史查询；若有效的当前 index 仍能证明对应上传成功，可以返回成功，否则返回历史过期或结果未知，不得据此断言从未提交或触发不受控覆盖。
- 回执保留期与文件保留期独立。回执到期不会删除文件，也不意味着物理擦除或立即回收旧磁带记录空间；后续索引/清单整理须保留文件和所有尚在保留期内的完成证据。
- 保留期内的查询仍须有可访问且可恢复的卷；卷离线、损坏或恢复未完成时返回相应状态，不误报为记录不存在。

当前票据继续保持 claimed：合批和两类检查点调度原则已接受，具体边界参数仍需细化；尚需裁定具体回执保留策略，并明确回执落带和中断恢复协议。已明确的成功确认政策、调度原则、回执用途及其与文件保留独立的原则不再重复征求同意。

### 本轮裁定草案：有限合批与两阶段索引维护

1. 原生上传按完整文件版本确认完成，同一卷内已就绪的多个文件可合批。每次提交截取有限的修改集合，后续新任务不无限延长该批。显式 commit 结束主动合批等待并排入设备队列，不代表磁带操作立即完成；合批等待上限和公平调度参数另行确定。FUSE 的 fsync 是已有修改的持久化要求，不因文件尚未 close 而拒绝，也不能被等同于原生完整上传完成。
2. 建议确认条件为：数据分区中的文件数据、回执所需内容，以及能完整定位并恢复该批文件和回执的有效 LTFS 索引记录已可靠落带，满足经验证的介质持久化屏障，且短写和延迟错误均已处理。满足该条件才返回本批上传成功；单纯数据写完或存在孤立回执片段均不足。
3. 数据分区也可以承载 LTFS index。上述方案推迟的是索引分区中的维护副本，不是推迟所有索引落带。两分区按 label 映射识别，协议不得预设物理分区编号恒为 P0/P1。
4. 索引分区按后续确定的有界检查点策略补齐，在清洁卸载/导出完成前达到一致卷条件。后续检查点失败单独报告维护/恢复状态，不把此前已可靠提交的数据误报成从未成功；不能继续信任已失效的快速挂载提示。
5. 崩溃发生在可靠提交前：从前序有效状态恢复，确认未提交的上传由应用重传；提交已可靠完成而回应未送达：恢复数据分区有效索引与回执后返回成功。任何恢复尚未完成或证据不足的情形继续返回未知，不仅依靠索引分区中的旧快照判定未提交。

取舍：摊薄索引写入并减少分区切换有利于顺序吞吐；接管时可能需要额外索引恢复。两项是否满足性能和 RTO 仍需后续测量。当前请求用户裁定的是合批与上述成功确认政策；其接受不会自动选定回执编码、SCSI 屏障序列或检查点参数，也不会视为协议已经实现/验证。

### 提交状态与验收案例草案

介质持久化前提已由[磁带提交屏障与中断恢复证据](10-commit-durability-evidence.md)完成文档研究。当前票据仍由 codex 持有，具体提交顺序须结合研究细化并验证；本段记录可评审的结果要求，不锁定底层命令。

候选状态区分：待提交、正在写入、已可靠提交、索引分区已更新、需要恢复。前三者不能仅由内存变量推断，尤其设备调用返回结果不明确后要进入需要恢复状态。已提交后的检查点维护失败与提交前的数据失败必须分别报告。

| 故障注入点 | 期望结果 |
| --- | --- |
| 只写入部分文件数据 | 不返回归档成功；恢复后确认未提交才要求重传，证据不足仍返回未知 |
| 数据完成、上传回执或索引尚未完整 | 不返回归档成功；不能靠文件长度认定提交 |
| 请求看似执行、介质持久化尚未确认 | 结果未定；经恢复核查后才能查询出最终结果 |
| 提交可靠完成、成功响应丢失 | B 从磁带恢复并返回同一上传的成功结果，不重复写带 |
| 可靠提交后、索引分区更新前 | 按已选政策可以确认成功；B 必须能从磁带找回全部已确认上传，不能只读旧索引分区快照 |

### 数据分区采用标准增量索引

用户提出数据分区 index 采用增量方式。本项目据此将标准 LTFS Incremental Index 作为常态提交方向，不将其解释为私有 journal，也不要求每次提交都写完整索引。规范依据由[LTFS 数据分区增量索引与完整检查点约束](11-incremental-index-evidence.md)核实；当前票据保留认领，本节不代表其他提交问题已解决。

- LTFS 2.5.1 §9.2.13、Annex H 区分完整快照与相对前一索引的变化；增量索引只写数据分区，索引分区保持完整索引。采用标准增量格式及变更规则，而非仅把完整 XML 改名。
- 先前成功确认条件中的“有效数据分区索引”可以由完整基线和必要增量链共同满足，不要求单个增量记录独立描述整卷。数据、回执及整个依赖链必须已可靠持久化并可验证；链缺失或中断时不得跳过缺口宣称最新状态完整。
- §5.4.3 的 `previousgenerationlocation` 仍指向前序完整索引；`previousincrementallocation` 用于必要的增量回链。恢复先找到正确完整基线，再按顺序应用变更，不以 generation 数值必须连续作为有效性条件。
- 推荐周期性在数据分区写完整检查点，限制恢复链长度；触发阈值仍待裁定，规范示例次数不是本项目默认值。完整检查点频率、索引分区更新频率和上传合批窗口是不同参数，不能混为一个提交周期。
- 清洁卸载/导出时，不仅补齐索引分区，还须确保数据分区末尾为完整索引，并满足两分区的一致卷及回指针要求。仅有增量尾部加旧索引分区快照不满足正常卸载条件。
- 原生增量索引不会自动提供上传回执或历史保留策略；回执仍需通过标准允许的承载方式设计。尤其不能只依赖被后续完整快照省略的旧增量来承诺当前恢复后的回执查询。
- 旧客户端可能正常挂载已收尾的一致卷，但不能假定它能恢复增量尾部的异常卷；故障接管工具必须理解增量索引。兼容版本与互操作验收另行明确。

CodeGraph 核对：当前 `src/ltfs/index.rs:70` 的模型只有单一 previous_location，`:156` 的序列化写 `ltfsindex` 完整树；现有追加完整索引不等于实现了标准增量索引。此轮仅规划，未改业务代码。

### 合批与两类检查点的调度边界（原则已接受，参数待定）

本轮沿已接受的标准增量方向，讨论三个相互独立的调度选择。提出时以下均为建议；随后用户先接受 Q1 小文件合批的澄清，再回复“全部接受”，确认 Q2 数据分区完整检查点及 Q3 索引分区更新的推荐原则，见下方裁定。具体参数尚未选定，本票据保持 claimed。

| 调度对象 | 推荐政策 | 主要取舍 |
| --- | --- | --- |
| 上传提交批次 | 原生上传以完整文件版本确认；同卷已就绪任务有限合批，冻结批次后新任务进入后续批次；合批等待到期或显式 commit 时停止主动等待 | 摊薄索引和同步开销，但单个任务可能等待同批数据落带 |
| 数据分区完整检查点 | 增量链条数或累计增量索引字节预算将超限时，下一次索引改写完整索引；不为保持吞吐无限追加增量 | 增加完整索引写入，换取受控的恢复重放量 |
| 索引分区更新 | 与每次 DP 完整检查点解耦，优先在合适空档维护；自首次未反映提交起计算滞后时间，到期在安全边界优先维护 | 减少分区切换，但不让持续写入无限推迟维护 |

边界与验收草案：

- 合批等待上限只限制主动等待，不是从应用请求到磁带确认的总时限。正在执行的设备命令不强行抢占；设备排队、公平性与超时另外约束。原生提交规则不要求 FUSE 的 fsync 先 close。
- 例如同卷上传甲、乙已就绪而丙仍在上传，甲乙可进入一个有限批次，丙不能因尚未上传完而阻止该批提交；同批共享一次提交不意味着向应用新增任意多文件事务或跨卷原子性承诺。
- 完整检查点应冻结在选定提交状态，包含该状态全部文件映射及必要回执引用；不能直接把随后仍在变化的内存视图序列化为检查点。检查点中断保留旧基线和有效链，结果不明则先恢复，不能边报错边盲目续写。
- 条数和索引字节上限不直接保证 RTO。验收还须覆盖索引之间的数据跨度、磁带定位、完整基线读取及回执查询成本；大文件或大目录造成的超大单次增量应触发完整索引选择，而非突破预算后仍当作普通增量。
- 索引分区滞后计时不被每次新提交重置，也不因卷空闲而虚构待更新状态；到期表示应停止扩张普通写入队列并在安全边界优先维护，不承诺计时到点即可完成机械操作。维护无法完成时报告降级/错误，不无限继续积累滞后，也不撤销既有可靠提交。
- 清洁卸载/导出要求仍然成立：必要时补数据分区完整索引，更新索引分区并达到一致卷状态。数据分区完整检查点和索引分区维护都不是重新定义归档成功点。

标准依据：[LTFS 2.5.1 §9.2.13](https://www.snia.org/sites/default/files/technical-work/ltfs/release/SNIA-LTFS-Format-2-5-1-Standard.pdf#page=53)建议限制完整索引之间的增量数量。上述字节预算、滞后调度和公平性是项目设计建议，不是标准新增要求。

本轮仅请求裁定三项调度原则，不锁定等待秒数、批量字节数、增量次数、检查点间隔或回执保留期限。参数需结合[磁带吞吐目标与可测工作负载](06-performance.md)及[接管时间与故障验收范围](08-recovery-acceptance.md)收敛，不能以未定参数声称已达到恢复目标。

- 常态通过数据分区增量索引记录变化，完整基线与必要增量链共同恢复上传完成信息；数据与这些元数据满足经验证的介质持久化条件后才确认。属性内容写着“完成”或单个 XML 已写出，都不能绕过真实持久化屏障。
- B 隔离旧主、核实介质并恢复有效 index 后，可从其中的完成信息重建按上传身份查询的本地缓存；对这些已保留记录，不再需要额外读取回执正文文件。装载、索引定位及增量重放仍有成本，不据此承诺整个带库立即可查。
- 取舍：去掉独立文件读取和段生命周期管理，代价是完成信息计入 index 大小和重写成本。更新对象扩展属性须遵守完整集合记录规则，不能假定增量索引只写新增单个键。格式与成本依据见[回执承载研究](12-receipt-storage-evidence.md)。

后续范围：上传元数据字段与身份冲突规则、删除/覆盖后的查询承诺及保留策略、应用对账与卷路由凭据、错误恢复与验收参数。独立回执文件布局不再作为未决选项；本票据整体保持 claimed，未实施源码或硬件变更。

### 已裁定：暂不引入上传回执

用户提出“没有回执会影响整个主备 HA 设计么？如果不影响，暂时不要回执”。结论是回执不是仲裁、fencing、设备接管或标准 LTFS 文件系统恢复的必要条件；它提供的是跨节点请求级结果查询与去重。按此区分，当前移除回执机制，明确不再承诺响应丢失后的每次上传都能自动判定或去重。

**保留的保证：** 设备组单主及可靠隔离后接管；B 从磁带有效完整索引和增量链恢复已提交文件系统；只有数据和必要索引满足可靠介质持久化条件才返回严格提交成功；无 A/B 暂存复制要求。已可靠提交的数据在约定节点故障范围内必须可恢复，不因客户端没收到响应而回退或丢弃。后续主动删除/修改、介质或整站故障不与节点故障承诺混淆。

**当前移出的能力：** 独立回执文件、回执段管理、为回执新增的 upload_id/版本/摘要/完成标记属性、按上传 ID 的持久结果查询、回执保留期与历史账本，以及依赖这些记录的自动去重。此调整替代此前已接受的回执历史查询方向，不限制标准 xattr 支持，也不取消独立的数据完整性校验设计；不得以“HA 必需”为由再隐式加入上传回执字段。

**正常返回仍存在：** write 的接收结果与 fsync/commit 的持久化结果仍须明确；“不要回执”不是不返回成功/失败，也不是允许缓存接收即报告归档成功。原生完整上传完成与 FUSE 对打开文件的 fsync 继续区分。

| 故障时点 | 当前契约 |
| --- | --- |
| 持久化条件未满足 | 不确认提交成功；恢复可能暴露此前状态或可验证的新状态，不能凭未收到响应推断磁带毫无变化 |
| 可靠提交完成，成功响应已送达 | B 必须恢复相应已提交文件系统状态 |
| 可靠提交完成，成功响应丢失 | 数据仍须恢复；不保证 B 能把状态准确对应到某次旧请求，应用可得到结果未定 |
| 应用重试结果未定的写入 | 不自动重放、覆盖或以同路径同长度当作同一次上传；由后续接口契约定义核验和安全重试条件 |

应用继续保留未确认工作与源数据，重连后可查询、读取恢复后的文件状态并核验。回执机制不再负责提供“哪些任务必定要重传”的完整清单；无法证明重试安全时保留未知结果，由应用按明确策略处理。可以另行设计仅创建、唯一命名或版本前置条件等重试保护，但本次未默认选择任何一种。

所有权协调、B 的配置/介质发现/访问密钥可用性、恢复测试与 RTO 度量依旧必要。本次不引入 A/B 数据复制，不承诺应用句柄跨节点连续，也不等于当前代码已实现 HA。

后续仅收敛提交/恢复状态机、短写/EOM/延迟错误、空间预留、无回执的应用错误与安全重试语义、调度参数及验收。回执相关讨论暂移出当前地图范围，不作为未完成的实现前提；提交契约其余部分仍保持 claimed。

### 已裁定：无回执的增量索引与逐文件确认

用户在讨论 IBM LE sync、逐文件同步以及增量 index 能否表征回执段后回复“按照建议保持”，确认继续采用以下方向，不恢复此前的回执方案。

- **不做回执子系统。** 不创建独立回执文件或回执段，不增加回执专用扩展属性，也不把增量 index 另作上传历史账本。标准索引表达文件系统状态；按上传 ID 的历史查询和基于回执的自动去重继续在当前范围之外。
- **常态 sync 使用数据分区增量索引。** 沿用完整基线与必要增量链恢复机制、定期完整索引和正常卸载/导出时的一致卷要求；索引分区只写完整索引，其维护时机与数据分区提交分开。规范允许该设计不等于 IBM LE 提供增量写入配置或已验证与具体 IBM 版本的故障恢复兼容性，依据见[增量索引研究](11-incremental-index-evidence.md)。
- **逐文件确认与同卷合批并存。** 原生完整文件可以请求并等待持久化确认，服务端允许同卷已就绪文件共享一次卷提交，在成功后分别返回结果；保留独立文件身份，不产生私有文件容器。应用串行逐文件等待时不能假定一定存在合批机会，也不为等待未来文件无限拖延当前提交。
- **不默认每次 write 强制 sync。** write 接收、原生完整上传结束、FUSE fsync 与设备介质持久化屏障分别定义。显式 commit 结束主动合批等待，但仍受设备队列与安全操作边界约束；FUSE 对打开文件的 fsync 不以 close 或原生上传结束为前提。
- **确认点不放宽。** 文件数据和可恢复的必要索引可靠落带、满足经验证的介质持久化条件并处理相关短写/延迟错误后，才返回严格提交成功；索引写调用返回成功或暂存接收完成均不足以确认。底层命令顺序仍须细化与验证，不能将应用 sync 和设备刷缓冲命令直接等同。
- **保持无回执的故障边界。** B 恢复已可靠提交的文件系统状态；成功响应丢失时，单次请求结果可能未定。不能因超时或索引中缺少某路径而盲目重传、覆盖，应用核验与安全重试条件仍由文件接口票据裁定。

本次确认政策，不选择合批时间、文件数/字节数阈值、完整索引频率或索引分区最大滞后，也不新增整批跨文件原子事务保证。提交/恢复状态机、容量与错误处理、参数及验收尚未收敛，本票据保持 claimed；未修改业务代码或访问真实设备。

### 已裁定：流式写入与两类索引提交触发

用户先提出沿用 LE 式数据写入与索引同步分离、周期性写增量 index，随后明确要求同时提供 time-based 和 size-based 索引下刷能力。本轮确认的是这两类触发能力；组合配置、计量细节和数值阈值尚未由用户具体选定。

**共同写入模型。** 数据在设备可用并满足缓冲/调度条件时持续流式写带，不等待索引周期，也不以整个文件先在 SSD 暂存完成为前提。合批主要共享索引写入和介质持久化开销；原生完整文件的完成确认不成为开放文件状态同步的前置条件。索引提交可覆盖开放文件截至所选快照的有效长度和映射，但不意味着整文件上传完成或跨节点自动续传。

**两类触发能力。** time-based 按时间触发待提交变化的索引同步；size-based 在累计数据量达到门槛时触发，将该范围的索引变化合批提交。两者触发相同的卷提交流程，常态写增量索引，需要完整检查点时写完整索引；不另建私有 journal 或回执机制。严格 fsync/commit 继续可以提前触发，正常卸载必须收尾，不能因时间或大小尚未达标而跳过这些要求。

**建议口径（待定，不作为已选配置）：**

- 允许分别启用，也允许组合；推荐组合使用，时间到期或大小达标任一满足即触发（OR），不是同时满足（AND）。无变化时不为定时器写空索引。
- time-based 建议以该卷最早尚未提交的变化开始计时，新增写入不重置倒计时；这用于限制主动等待，不是保证设备排队、刷带和故障处理必在该时长内完成。若要求严格固定节拍而非未提交变化年龄，需另行确认。
- size-based 原建议按未被可靠索引覆盖的流式写入字节累计；用户随后明确要求文件粒度，该建议已被[完整文件粒度决策](#已裁定size-based-以完整文件为粒度)替代，不作为当前实施口径。
- 本 size 门槛用于决定“何时提交”，不同于既有增量链累计索引字节预算；后者决定“本次写增量还是完整索引”，不能合并为同一参数。
- 只启用 size-based 时，不足门槛的尾批及零数据字节的 rename/delete 等变化可能长期未提交；不能宣称具有时间上界。显式提交或正常卸载负责收尾，若另需自动时间兜底，应明确启用 time-based，不隐式声称纯 size 模式有时间保证。

**提交边界不变。** 达标只请求在安全边界执行提交，不打断不安全的设备命令；提交截取有限变化集合，后续写入不无限延长该集合。计数和时间状态仅在对应范围可靠提交后推进，提交期间产生且未覆盖的新变化继续保留；失败不清除 dirty 状态，不提前确认持久化成功。具体并发快照、错误恢复与背压协议仍待细化。

后续验收应覆盖：时间先到、大小先到、二者同时到达、无变化、纯元数据变化、不足门槛尾批、单个未关闭大文件跨多次提交、提交期间新写入及提交失败。测试用于确认不丢待提交变化、不重复触发不受控写带、不将部分文件状态误报整文件完成。当前只更新规划，不选定周期/字节数，不实施源码或硬件操作，票据保持 claimed。

### 已裁定：size-based 以完整文件为粒度

用户明确“size based 要以文件粒度”。据此替代此前按流式写入片段累计的建议：当前按完整文件累计逻辑大小解释 size-based，而不是文件数量阈值；具体数值仍未选定。

- 只有完整文件就绪、其本次完成状态尚未被可靠索引提交覆盖时，才将该文件逻辑大小计入候选批次并判断大小门槛。文件正在写入时不逐块累加到 size-based 计数，不能仅因部分文件已超过门槛就触发此策略。
- 达到或超过门槛即请求提交已就绪批次；不为精确凑齐阈值拆分文件。单个文件大于门槛时，在该文件完整就绪后即可触发，不必等待另一个文件。其他未完成文件不阻挡已就绪批次。
- 数据仍流式写带，不要求先把整文件缓存在 SSD；完整就绪只是 size-based 的触发资格，不代表已经持久化。确认成功继续等待相关数据与必要索引满足可靠提交条件。
- time-based 和显式 fsync/commit 不受该完整文件触发门槛限制，仍可同步打开文件截至所选快照的有效状态。由这两类触发产生的开放文件快照不是 size-based 提前触发，也不是原生上传完成。
- 该门槛是完整文件批次的逻辑大小，不是精确未提交物理字节数：若文件前缀此前已被周期同步，文件后来完整就绪时仍按完整文件大小衡量待提交完成状态；其完成状态已可靠提交后不重复累计。它不改变实际增量索引的变更范围，不要求重复写入已有数据。
- 本轮只约束触发计量粒度，不禁止同一卷索引包含其他必要文件系统变化，也不承诺多文件事务原子性。原生接口就绪事件、FUSE 关闭/多句柄/重开写入如何对应新的就绪状态仍由文件契约细化；close 不自动等于归档持久化成功。

补充验收：多个完整文件累计越过门槛、单个超大完整文件、部分大文件越过门槛但不触发 size-based、完整批次不被另一未完成文件拖延、time-based/显式提交与文件完成相交时不重复累计，以及提交失败后保留待提交状态。纯 size 模式下未完成文件和不足门槛尾批仍无时间保证。未实施源码或设备操作，票据保持 claimed。

### 驱动器串行执行与提交状态草案

用户询问数据写入与数据分区 index 写入是否需要互斥，随后要求“继续”。本段推进可评审的设计草案，不把继续讨论视为全部实现细节获批，也不关闭本票据。

**执行职责。** 建议每个驱动器由单一执行模块统一管理数据、索引、文件标记、介质同步及会改变位置的操作。互斥覆盖整个索引提交序列，不能只覆盖每个单独 WRITE 调用；同驱动器的读取、定位、分区切换与卸载也不得插入该序列。不同驱动器可并行，带库机械手操作另行协调，不使用全库数据写锁。

格式依据：[LTFS 2.5.1 §5.2.3、§9.1](https://www.snia.org/sites/default/files/technical-work/ltfs/release/SNIA-LTFS-Format-2-5-1-Standard.pdf)规定索引构造由文件标记、索引 XML 和文件标记组成。单执行模块是本项目的实现建议，不是标准要求采用某种线程模型；具体底层命令及屏障仍依赖[提交证据研究](10-commit-durability-evidence.md)和设备验证。

**建议的提交阶段：**

| 阶段 | 设备与元数据约束 | 返回及失败处理 |
| --- | --- | --- |
| 流式写入 | 持续顺序写数据，积累尚未提交的变化 | 普通接收/写入结果不等同于归档成功 |
| 建立提交切点 | time/size/显式请求选取有限变化集合，完成集合所需的数据写入，在合法块/extent 边界暂停后续数据写带 | 不以等待全部未来上传完成为前提，不中断在途命令 |
| 固定索引快照 | 所引用数据及其实际位置已确定；固定长度、extent、目录与必要属性，隔离后续修改 | 数据传输失败或位置不明时不生成宣称完整的新映射 |
| 写索引并持久化 | 连续完成索引构造及经验证的介质屏障、结果检查，不允许其他改变介质位置/内容的操作插入 | 索引或屏障失败、超时及结果不明时停止追加，进入需要恢复 |
| 发布已提交状态 | 只有可靠持久化条件满足才推进已提交版本，并清理本快照覆盖的 dirty 变化和计数 | 仅满足本次快照覆盖要求的等待者可收到成功；后续变化仍保留 |
| 恢复流式写入 | 按已确认位置处理下一批；索引分区维护使用既定独立策略 | 索引分区维护失败单独报告，不撤销此前已可靠提交的事实 |

**并行与资源控制。** 写索引期间，允许在有界内存/SSD 缓冲中继续接收后续数据，也允许后续元数据变更形成下一批，但不得修改正在提交的快照或提前写入本次索引的未完成映射。快照隔离不预设复制整棵目录树，可在模块实现阶段比较版本化状态与变更集合等方案。缓冲耗尽须背压或明确返回接收失败，不丢弃已经接收的数据来腾空间，也不将接收确认升级为跨节点持久化保证。

**触发合并。** 建议同卷已有提交在途时合并 time/size 触发，避免并发生成索引。显式 fsync/commit 须记录其要求覆盖的变化范围：当前快照已覆盖才可共享结果，否则安排下一次提交，不因“刚完成一次 sync”就误报后来的请求成功。新变化不得被旧提交的 dirty 清理或计时重置吞掉。

**故障门控。** 需要恢复时不得沿用旧内存写头盲重试；介质访问只在当前所有权有效、旧主隔离条件满足后进行。恢复核实卷身份、有效完整基线/增量链和可安全追加状态，再恢复写入。失去所有权后停止发出新设备命令，排队任务不能绕过门控；本地互斥不能替代跨节点 fencing。已可靠提交而响应丢失仍恢复数据，但没有回执时不保证判定每个历史请求结果。

**候选验收：** 将索引拆为多个 WRITE 时穿插并发上传、读取与定位请求，确认序列不被插入；time 与 size 同时达标只产生受控提交；提交期间新写入及新 fsync 不被旧快照错误确认；短写、索引中断和屏障超时后停止追加；缓冲满时背压；不同驱动器仍可独立推进；索引分区维护失败不抹除已有提交；所有权失效后不再发新设备命令。

下一步仍需裁定恢复后尾部处理、空间预留与 EOM 行为、错误返回/重试契约，以及上述建议中的并发和调度细节。未选择具体 Rust 同步原语或线程模型，未修改业务代码、运行硬件测试或承诺性能/RTO 已达标。

### 异常尾部恢复与容量收尾策略草案

用户继续推进地图。本轮给出首版策略建议和可验证条件，不视为截断、介质修复、自动跨卷续传或真实设备操作的授权。

**事实依据。** [IBM LTO SCSI Reference GA32-0928-08 §4.12.2 表 17](https://www.ibm.com/support/pages/system/files/inline-files/LTO%20SCSI%20Reference%20GA32-0928-08%20%28EXTERNAL%29.pdf#page=80)分别列出 Write in Early Warning 与 Write at EOM：前者可能已写入数据，后者可能未执行写入；应综合状态、sense 和实际传输信息判断，不按单一 EOM 标志或 NO SENSE 判成功/失败。完整索引与增量链、数据映射及实际位置须按[既有提交研究](10-commit-durability-evidence.md)和[增量索引研究](11-incremental-index-evidence.md)验证；以下恢复/容量政策是本项目建议，不是已实现能力。

**恢复建议：自动核验，条件满足才自动续写。**

1. 在隔离旧主、取得有效所有权后，B 自动执行不修改介质的身份与索引恢复核验。定位、读取仍由独占设备执行流程管理，不与正常写入并行；禁止以恢复为名无条件写索引、补文件标记或截断尾部。
2. 确认最新可验证的恢复状态：卷身份、完整基线、必要增量链、索引结构与数据引用须相符；不能只取最大 generation、固定 IP 位置或缓存宣称的最新版。恢复核验不等于全卷数据读回校验。
3. 对最新有效索引之后的尾部单独分类。无有效索引映射的字节不能自动变成业务文件；数据看似完整也不能猜路径、长度或上传身份。文件开放前缀已被有效同步时则按其已提交状态恢复，不能因上传未完成而丢弃该前缀。
4. 只有卷可写、尾部与可安全追加位置已由经过验证的协议确定、空间足够且所有权仍有效，才恢复正常追加。有效文件状态可恢复与允许继续写带是两个不同判断；本段未规定仅凭 EOD 就足以放行。
5. 尾部残缺、链断裂、位置未知或读错误不能消除时，保留介质，阻止业务写入并报告恢复受限。可独立验证的文件可受限读取；若无法证明恢复视图是最新，不冒充最新完整目录，也不将缺失对象判为从未提交。覆写或舍弃尾部的修复另需明确方案及授权。

**容量建议：同时保护本次提交和最终收尾。**

- 数据分区预算覆盖：尚需排出的已接收数据、本次所需增量或完整索引、正常收尾的完整索引与文件标记，以及设备/格式相关安全余量。重合步骤可合并计算，但不能只预留一份很小的增量索引就宣称能正常卸载。
- 索引分区另核算完整索引可写空间；不能用数据分区剩余容量替代。预算随文件数、extent 和属性增长重新评估，包含排队/在途工作；压缩收益与设备容量提示不能单独充当确定保证。具体估计方法、余量和设备误差须研究与测量，不预先写死 MB/GB 值。
- 进入收尾空间预算或收到容量预警时，暂停扩大该卷的新数据负担，优先处理受保护的提交与收尾。容量压力是 time/size 之外的安全触发条件；不等待批次凑够门槛，不为了 size-based 的完整文件要求耗尽收尾空间。
- 若当前大文件无法完整写完，在满足安全条件时保存可验证的已写前缀及已就绪文件状态，并明确报告该上传未完成；此时同步前缀不改变 size-based 的完整文件计数规则，也不引入自动续传承诺。故障导致实际状态不明时报告未定，不能直接当作干净的空间不足。
- 若真实 EOM、短写、延迟错误或索引写失败使提交条件不明，停止当前追加并进入恢复，不盲补剩余字节、不循环重试写 index。当前未确认批次不得报告成功；此前已可靠提交状态仍须保留。无法形成一致卷时报告收尾未完成，而不是正常卸载成功。

**跨卷与应用建议（待用户裁定）。** 首版建议不在文件中途自动换卷拼接，也不因结果未定就把同一请求自动投向新卷。已知文件大小时可在开始前用保守预算拒绝不适合的目标卷；未知大小的流仍允许按现有流式方向处理，但不能承诺一定写完。未完成工作保留源数据，由应用在核验后选择新卷发起明确的新上传意图；路径冲突、部分文件清理和安全重试条件由文件契约细化。大小声明、卷选择机制和产品默认值未在此自动定案。

**候选验收。** 预警但当前数据已写入、真实 EOM 未写入、索引写到一半、有效索引后的孤立数据、增量链缺失、IP 空间不足、单个未知大小文件耗尽数据预算、提交成功后收尾失败，以及故障时完全丢失 A 缓存。验证预警分类正确、保留已提交前缀、不盲目修复/跨卷重放、不误报正常收尾，且不因旧缓存覆盖磁带事实。

待裁定的首版产品政策：自动无介质修改的恢复核验；证据充分才放行续写；歧义尾部隔离且修复另授权；容量压力提前收尾；不自动跨卷续传。具体算法、错误映射及空间数值尚待细化，本票据保持 claimed；没有执行设备命令或修改源码。

### 已裁定：首版恢复与跨卷范围

针对“是否接受首版不自动截断修复、不自动跨卷续传，证据充分才恢复写入的范围”，用户明确回复“接受”。据此将上方草案中的以下范围固化为已接受约束，其余细节不因本次回答自动获批。

1. **不自动截断修复。** 歧义尾部保留并阻止业务写入，不能自动覆写、舍弃或猜测补齐。任何可能改变或丢弃介质内容的修复均需另行明确方案及授权；该限制不禁止受所有权门控的不修改介质的恢复核验。
2. **不自动跨卷续传。** 首版不将中途未完成文件自动跨卷拼接，也不将结果未定的写请求静默重投另一卷。应用核验后重新选择目标并发起新上传的具体接口、部分文件处理与冲突规则由文件契约另行定义，不隐式禁止正常的新任务卷分配。
3. **证据充分才恢复写入。** 有效所有权、卷身份、可恢复索引状态、安全追加位置、可写性及空间条件须得到核实；可读不等于可写，仅找到 EOD 或仅恢复旧缓存不足以放行。证据不充分时报告恢复受限，不用猜测换取接管时限。

上方容量预算、预警收尾、部分文件处理及验收表保留为后续细化依据；具体算法、计量阈值、错误接口与测试尚未定案。本票据仍为 claimed，不将这项范围确认描述为整个提交协议完成、设备验证通过或真实修复操作授权。

### 待裁定：容量压力下的部分文件处理

本轮继续当前提交票据，将容量草案收敛为一个产品选择：容量压力下提前收尾，保留可恢复的部分文件，不自动清理或跨卷续传。以下待用户回答；既有“不自动截断修复”针对介质异常尾部，不能据此直接推出应用文件删除策略已获同意。

**推荐行为：**

- 收尾预算将不足时，停止扩大该卷的数据与元数据写入负担；有序处理在途工作和已接收缓存，不等 time/size 门槛。此安全触发可以同步开放文件前缀，不改变 size-based 只按完整文件累计的定义。
- 在所有权、设备状态与容量均允许时，优先可靠提交可验证的已写状态，并完成正常收尾所需完整索引。若缓冲中仍有未能落带的数据，明确报告对应写入/提交未完成，不静默丢弃并宣称全部成功；缓存的后续释放/清理协议另行定义。
- 已完整持久化的文件不因同批另一个大文件未完成而被撤销；未完整上传的文件只保留可恢复长度和映射，不返回原生整文件归档成功。不新增完成标记属性或上传历史回执。
- 不自动 unlink 部分文件，不自动移到隐藏目录，也不默认覆盖已有目标。应用核验后决定保留、显式删除或重新上传；删除本身是新的元数据变更，仍受所有权、剩余索引空间及持久化规则约束，不能保证满卷可立即执行。

| 可验证情况 | 对应用的结果边界 |
| --- | --- |
| 写入开始前已知目标卷预算不足，尚未修改目标 | 拒绝本次写入；应用可以重新选择目标，不把此情况报告成提交结果未定 |
| 文件仅部分写入，但已可靠提交其前缀 | 报告上传未完成、空间不足；恢复视图保留已提交前缀，不报告整文件成功 |
| 数据/索引/屏障结果不明 | 报告需要恢复或结果未定，不凭估算承诺准确持久化长度 |
| 文件已完整可靠提交，后续索引分区维护失败 | 文件提交事实与维护失败分开报告，不把文件误判为需要重传 |

表中“上传未完成”是服务对当前请求的返回语义，不是新的磁带回执。A 丢失后，B 可恢复当前文件长度和内容，却未必知道应用原本要上传多长；该判断继续依赖应用保存的源数据与任务信息。路径存在、长度较短或当前内容相同都不单独赋予覆盖/重传许可。

用于裁定的例子（不是阈值）：应用要上传 100 GiB，写入 40 GiB 后需停止增长；若这 40 GiB 和映射已可靠提交，则保留这 40 GiB 文件状态，报告整个上传未完成，不自动删除或把余下 60 GiB 拼到另一卷。若 40 GiB 的提交本身不确定，则先恢复核验，不能承诺全部 40 GiB 已持久化。

本轮只请求确认“容量压力优先收尾，保留可靠提交的部分文件且不自动删除”的政策。不选择具体容量估计、errno、路径发布/替换原子性、缓存清理或时间/大小阈值。验收需覆盖上述四类结果及同批完整/部分文件并存；票据保持 claimed，未实施源码或访问设备。

后续回到本问题时的范围澄清：上传前容量检查与性能保护已经另行讨论，但不能据此将本策略记为接受。这里仅针对准入后因估算偏差、未知最终长度或设备异常触及容量边界的兜底；正常已知不够的上传应在准入阶段拒绝。建议只确认“保留已可靠提交状态、不自动删除、不误报整文件成功”，不默认将部分文件发布到最终业务路径，也不授权覆盖已有文件或把所有未索引尾部强行纳入索引。是否主动追加一次安全的前缀提交，仍取决于设备状态与收尾预算；不能将保留策略解释为对实际 EOM 后写入成功的保证。

### 准入检查的性能约束与快速路径草案

用户在讨论上传前容量检查后明确要求：“准入检查还要注意写入性能，不能以牺牲写入性能为代价”。将准入不得成为持续写带瓶颈记为产品约束；下面是满足该约束的实现建议，尚无性能实测，不宣称绝对零开销或预留等同于可靠持久化。

**正常路径建议只做本地预算检查与预留。** 活动节点维护绑定卷身份及本次所有权会话的保守容量账本，分开核算数据分区、索引分区、收尾余量与已有任务预留。文件大小已知时按整文件预计成本准入；检查和预留在同卷内原子完成，防止并发重复占用空间。不为每个文件同步查询驱动器、读回索引、序列化完整索引、等待另一节点复制或新增日志落盘；具体同步原语和持久任务调度机制另行设计。元数据开销须用可增量维护且经过验证的保守预算，不能为降低开销忽略它。

**连续写入路径不重复整文件准入。** 文件完成准入后按已预留范围流式写带；实际写入、取消及完成只推进对应账本状态。尚未消耗的预留与已消耗的空间分开，不能在设备容量快照更新时重复扣减，也不能在取消任务时把已经写到介质的部分退还成空闲空间。未知大小流建议按有界额度补充预算，不逐个小 write 发设备查询；未获预算的数据不能无限接收。超过声明大小时重新申请预算，不默认越界继续。

**低频校准建议复用安全时机。** 装载/接管且恢复完成后建立可信基线；正常运行按成本可控的周期、容量低水位或状态异常触发校准。涉及驱动器的查询仍由统一执行流程在安全时机安排，不能以“后台”为由与索引提交或定位并发乱序。刷新结果须与在途消耗和预留对齐，不用旧容量快照覆盖更新的账本，也不因盲信压缩收益而放大可用额度。

**慢路径不能绕过安全。** 预算充分且基线有效时不等待校准；预算不足、失效或设备/所有权变化后，等待校准、背压或明确拒绝新增负担，不超卖容量以维持吞吐。已有预算内工作是否继续取决于所有权、设备及提交状态，不能笼统保证任何校准期间都可写。保护收尾空间的优先级不因性能目标降低。

本地准入预留不要求引入回执或 A/B 暂存复制；接管后旧会话预留不能直接视为新主的有效承诺。B 从磁带恢复已提交状态并建立新预算，新上传重新准入；不会据此承诺自动续接 A 的未提交任务。该账本是运行时调度数据，不是新的已提交数据权威。

**验收要求传递给性能票据。** 正常容量充足时，比较相同安全提交策略下准入路径的 CPU、P50/P99 延迟、锁/队列等待、每文件附加设备查询次数、设备因准入等待的空闲时间和真实已提交吞吐。覆盖大量小文件、并发同卷、多驱动器及未知大小流，并单独测量容量低水位、基线失效和接管慢路径。允许退化幅度及阈值由测量裁定；无硬件测试不能声称未牺牲吞吐。

本轮确认性能约束，不默认接受此前部分文件清理策略，也不选定校准周期、预留粒度、缓存清理、错误接口或容量数值。提交票据保持 claimed，未修改源码或访问真实设备。

### 待裁定：time-size 组合与计时语义

用户要求继续推进地图。本轮收敛此前已提供的两类触发能力，不新增索引格式或回执机制；组合配置和时间起点此前仅为建议，本段等待用户明确选择。

**推荐配置能力。** 允许仅 time-based、仅 size-based，或两者组合；推荐组合使用，任一条件满足即请求一次提交（OR），不要求同时满足（AND）。size-based 继续按完整就绪文件累计逻辑大小，不以半写文件或 XML 大小代替。

**推荐时间定义。** time-based 从当前卷最早尚未可靠提交的变更出现时开始计算固定时长 T。后续数据写入、文件完成或元数据变更不把该起点向后移动。这是未提交变更的等待时长策略，不是固定墙钟节拍，也不是“最后一笔写入之后空闲 T 才提交”；用户此前提到周期性下刷，本轮明确提出这一细化选择，不将其假称为先前已经确认。

- 无变更时不产生空索引。纯 rename/delete 等元数据变化也开始计时，不能因没有新增文件字节而永久忽略。
- 若 size 先达标，则提前提交；本次覆盖的变更可靠持久化后，从剩余未覆盖变更中保留最早起点。若没有剩余变化，计时器停止，下一笔变化重新开始。
- 提交期间的新变化不修改当前快照，也不在完成时被清除或重置年龄。若下一批已经到期，在设备安全条件允许时安排下一次提交，不重复等待完整 T。
- 到期表示请求在安全边界执行提交，不是保证磁带在 T 内完成落带；不得中断在途命令。需要恢复或失去所有权时，保留未提交状态并遵守禁止继续写入的约束，而不是让定时器反复强制写带。

仅 size 模式仍不提供时间上界，不足门槛的尾批及纯元数据变化须靠显式提交、正常卸载等处理；选择组合模式用于避免这种长期等待，但不改变已讨论的容量压力安全收尾问题，部分文件处理仍另待裁定。

### 待裁定：索引提交期间的接收与背压

本轮收敛既有驱动器执行草案中的并行接收政策，不新增整文件 SSD 暂存或 A/B 复制要求。建议以“有界缓冲下一批、缓冲满后背压”作为正常索引提交期间的行为，等待用户确认。

- 在所有权有效、容量预算足够且设备未进入恢复状态时，当前批写 index 和执行持久化屏障期间，可以继续接收后续数据到有界内存/SSD 缓冲；同一驱动器的后续数据不能插入正在执行的索引提交序列。
- 当前提交使用固定快照，后续数据和修改归下一批。当前批成功只能确认其覆盖范围，不能顺便确认下一批；提交完成后仅推进已覆盖的 dirty 状态、计数和等待者。具体快照表示不预设整树复制或固定两个物理缓冲区。
- 达到缓冲额度后暂停继续接收，通过等待容量释放向应用施加背压；不无限增大缓冲，不丢弃已经接收但尚未完成的数据来伪造成功。错误、取消及等待期限如何映射为部分接收/失败，由文件接口细化，不能将普通接收确认当作跨节点持久化承诺。
- 数据缓冲额度、目标卷介质预留与索引收尾空间是不同资源，需要分别约束；缓冲尚有空间不等于可以绕过磁带容量准入。某个卷的背压不应占住全库锁，导致其他驱动器无关请求无法推进。
- 数据队列满时仍须让必要的提交、取消、所有权变化和错误通知得到处理，防止“等待提交释放缓冲、提交却排在满队列之后”的死锁。此处要求调度能力，不预设某种 Rust channel、锁或线程数量。
- 一旦所有权失效或设备需恢复，不继续沿正常缓冲流程扩大该卷的未提交负担；已接收数据与排队等待者按错误/恢复契约处理，不能仅因接收仍快就继续报告提交成功。

例：批次 A 正在写增量索引时，应用可继续发送批次 B 到缓存。A 完成后只确认 A；B 必须等覆盖自身修改的后续提交。B 缓冲满则暂停接收，不阻止 A 完成；若 A 提交失败且结果不明，不能把 B 从缓存直接接着写带。

候选验收包括：缓冲满但当前提交仍能完成、后续 fsync 不被前一快照误确认、取消/所有权变化不被队列堵住、提交失败停止后续追加、每卷限额与全局缓冲上限同时有效，以及其他驱动器可独立推进。大小阈值、等待期限、内存/SSD 分层、回收策略和实现方式仍待细化；本次只请求接受接收与背压原则，不关闭提交票据或声称性能达标。

本轮细化已讨论的容量账本生命周期，建议将原生上传取消定义为停止后续工作，而非回滚磁带数据。以下产品政策等待确认，不选择取消接口签名、会话超时或磁带命令。

| 取消到达时的状态 | 建议处理 |
| --- | --- |

**预留释放的不变量。** 只释放确定未消耗、且已不再被在途数据、固定快照、必要收尾工作使用的额度。已经写入介质的空间不能因取消变回可用容量；任务取消也不能释放其他任务或卷级必要的索引收尾预算。内存/SSD 缓冲释放与磁带空间释放分开核算，避免缓存清理导致虚增介质容量。

**取消不是立即停止一切 I/O。** 停止接收该任务的新数据和尚未承诺进入执行范围的后续工作；为安全结束已经开始的提交或处理设备状态，可能仍须完成必要操作。具体切点、返回时机和“已取消/已完成/需要恢复”的接口映射仍待设计，不保证一次取消到达后磁带立刻不再移动。

**超时与断连不等于确认取消。** 应用停止等待不能证明服务端已停写或释放额度；连接丢失、准入响应丢失及会话过期的自动清理政策另行裁定。既有 A/B 故障后不承诺未提交上传自动续接的范围不变，本次不增加回执、跨节点任务查询或自动重放。

本轮请求确认“取消不回滚、保留已提交状态、仅释放已确认安全的未消耗预留”。缓存自动清理条件、会话期限、部分文件发布/删除、错误码和自动重试均不在此选定；FUSE 调用中断不能直接等同于原生整个上传取消。验收覆盖取消与准入、在途写入、提交完成和所有权切换的竞争，以及重复取消不重复释放额度。票据保持 claimed，未修改源码或访问设备。
