## Question

双节点失联时谁有资格接管，如何证明旧节点无法继续操作驱动器、机械手和持久化状态？选择仲裁/见证与 fencing 策略、所有权粒度、过期 owner 的排除方式、设备身份和多路径约束。物理双节点 FC/SAN 与驱动器和机械手能力须有可核实证据；尚无现场资料时记录明确部署前提而不认定成立。

范围说明：本票据裁定所有权架构及生产接管约束；依赖现场信息的具体隔离设施、quorum 配置与验证证据要求，由[隔离设施选型与部署前提](09-fencing-deployment.md)继续裁定。

## Comments

### 首轮方案（待用户裁定）

建议首版采用一个受管逻辑带库及分配给它的驱动器作为接管资源组，由一个节点独占运行。主节点内部可并行使用多台驱动器；备用节点不对这些设备执行定位、流式读取或写入，避免读操作改变磁带位置。其他逻辑带库或外部备份软件不自动纳入本资源组，但须核实与本组的设备隔离。

建议生产 HA 采用成熟的 Pacemaker/Corosync 加独立 qdevice/qnetd 见证，由它管理唯一活动 ltfsd 及服务入口。见证只参与仲裁，不保存上传数据或作为文件状态权威；部署位置避免与 A/B 同时失效。不在本轮决定见证规格或部署到真实环境。

外部 fencing 是自动接管的前置条件，使用经验证的电源/PDU、虚拟化管理面关停或覆盖全部设备路径的 fabric 隔离。最终方式依据部署环境选择，要求旧节点失去集群通信甚至操作系统卡死时仍可执行和确认。不得用普通 SSH 停服务作为生产隔离证明；本地锁或 lease 过期也不能证明旧主停止发命令。

依据：[Pacemaker Fencing 文档](https://clusterlabs.org/projects/pacemaker/doc/3.0/Pacemaker_Explained/html/fencing.html)指出隔离要能约束不响应集群命令的节点，且管理网络和电源故障域必须评估；[Red Hat quorum device 文档](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/8/html/configuring_and_managing_high_availability_clusters/assembly_configuring-quorum-devices-configuring-and-managing-high-availability-clusters)说明独立见证在双节点分区时参与选择存活方。二者分别解决资格与执行隔离，不能互相替代。

接管顺序建议：获得有效仲裁 → 验证旧主隔离 → 获得受管设备访问权 → 核对稳定设备身份与卷 UUID → 等待/核实在途设备命令结束并恢复卷 → 宣告对应数据服务可用。关掉旧节点不等于机械动作立即停止，不能跳过设备恢复。IP/SDK 服务入口切换不应被视为数据面已经可用。

运行与异常建议：

- 主节点失去有效资格，停止接受新设备任务并进入受控停机；如果不能确认旧主停下，由 fencing 阻止其继续访问。
- 备节点没有有效仲裁或无法确认隔离完成时，不发起设备操作；允许报告不可用/恢复状态，不以超时强行接管。
- 见证失联不自动等于整个集群停机：A/B 仍保持有效仲裁时可继续；单节点既失去对端又无法获得有效资格时不强升主。具体 quorum 策略须经实现与故障验证。
- A 恢复后作为备用重新加入，不自动抢回资源；计划回切通过受控切换完成。
- Embedded/运维 CLI 与集群设备所有者互斥。直接访问设备的其他进程须纳入运维和权限约束，否则本集群的唯一主承诺不覆盖它们。

SCSI PR 仅列为可选设备层保护：先验证每个 drive/changer LUN、所有 FC 路径、预留类型及抢占后的在途命令行为，再决定是否启用；当前不能把仅有 reservation-conflict 错误处理当作实现了 PR fencing。

待用户决定：是否接受整组资源单主、独立轻量见证及外部 fencing 作为生产自动接管前提，以及旧主恢复后不自动回切。具体硬件适配与 quorum/fence 配置在前提接受后继续细化；若无法提供这些设施，自动接管方案需重画，不能静默删除隔离要求。

## Answer

用户明确回复“接受”，确认以下生产架构。本节为有效决策，前面的方案与核对记录保留为依据。

1. **整组单主**：一个受管逻辑带库及分配给它的驱动器构成接管资源组，由一个活动节点持有。主节点内部可并行使用多台驱动器；备节点不独立对这些设备进行定位、流式读写或介质搬运。设备归组须与其他逻辑带库和外部软件使用范围核对。
2. **成熟集群管理**：采用 Pacemaker/Corosync 管理活动 ltfsd 和服务入口，配置独立轻量 qdevice/qnetd 见证辅助仲裁。见证不保存上传数据，不改变磁带作为已提交状态权威的决策。
3. **外部隔离前置**：自动接管必须具有可执行、可验证的外部 fencing。根据实际环境选择电源/PDU、虚拟化管理面或覆盖全部设备路径的 fabric 隔离；不能以心跳超时、SSH 停服务、本地锁或 lease 过期代替隔离证据。
4. **接管顺序**：获得有效资格 → 确认旧主隔离 → 获得受管设备访问权 → 核对稳定设备身份与卷 UUID → 核实设备在途操作并恢复卷 → 宣告对应数据服务可用。获得服务 IP 不等于磁带已经就绪。旧主断电也不能代替对仍在进行的机械操作和设备状态的核查。
5. **不强制冒险接管**：资格不足或隔离无法确认时不发起受管设备操作，返回不可用/恢复状态；主节点失去有效资格时停止接受新设备任务并受控停机，必要时由外部 fencing 阻止其继续操作。见证单独失效时是否继续运行取决于集群是否仍有有效仲裁，具体策略和组合故障由后续票据确定。
6. **不自动回切**：旧主恢复后以备用身份重新加入，校验身份和清理旧会话后接受调度；回切通过计划操作完成，避免恢复时再次打断写带。
7. **配套约束**：Embedded 模式、维护 CLI 和其他直接设备访问必须与活动所有者互斥。SCSI PR 仅是待设备验证的可选加强机制，未选定预留类型，也未确认 TS4300 changer/LTO-8 的支持与多路径隔离行为。

此确认是架构和部署前提的接受，不是实际部署、故障演练或设备隔离操作的授权。仓库目前仍没有已验证的双节点、见证和 fencing 环境证据。

## 修订（2026-09-17，来自 09）

用户确认生产环境没有可由软件调用的断电/复位手段，也没有可用的外部隔离；没有本系统之外的软件访问同一逻辑库。"外部 fencing 是自动接管的前置条件"据此修订为"经设备回读确认的隔离是自动接管的前置条件"，合格手段增加"对逻辑库内每个设备完成持久预留抢占并逐设备回读确认"。已接受的缺口：持久预留挡不住在旧节点上主动抢回预留的软件，由运维前提覆盖。详见 [09 的裁定](09-fencing-deployment.md#已裁定持久预留--软件纪律2026-09-17)与[协议候选](../pr-fencing-protocol.md)。本票据其余裁定不变。
