# 控制存储完成、观察与写者退出契约

关联：[存储恢复](control-storage-recovery.md) · [故障出口](control-failure-dispatch.md) · [Ready 绑定](raft-rs-binding.md) · [接口事件](control-interface-events.md) · [执行授权](issues/18-raft-execution-contract.md)

状态：依自动推进授权采用的存储适配语义基线，未实现/执行。不定义 Rust 公共 API 或模块归属，不越过 07 的依赖；引擎与锁现由 [SQLite 基线](control-store-sqlite.md)具体化。本节约束未来实现必须能回答什么，不声称已有这些接口。

## 完成不是一个布尔值

对一次保存分别表达三件事：**指定内容是否可靠、当前 Storage 视图是否已反映它、该写者是否还可能继续修改存储**。第一件成立不证明第二件或第三件；回调是否送达是观察结果，不是第四种持久化方式。

例如：批次已经可靠保存，进程更新内存 Storage 视图时失败。重启可使用该批次，但当前 Ready 不能伪报 P2 完成。又如：一个批次成功后仍有旧快照构建任务在写对象，不能因此允许新实例接管同一写入口。

## 操作关联与不可变输入

每次操作携带：存储/集群/成员身份、存储写者实例、实例内操作序号、操作种类、对应 Ready/LightReady 或快照构建关联、预期存储修订、不可变内容及依赖关联。存储修订只排序本地发布，不是 Raft term、log index、磁带 generation 或外部 fencing token。

- 同一关联不重新绑定不同内容、不同阶段或新实例；重复观察不是重新提交。接收了同关联不同内容应明确报冲突，不按最新参数覆盖旧请求。
- 单 Ready 也可能有 P2 和 LightReady commit 两个保存阶段，不能用一个“本轮完成”覆盖二者。无新持久状态则没有虚构的空保存操作。
- 大对象可由受控任务准备，但影响权威恢复视图的更新仍经单一有序写入口；准备时取得的旧 HardState 不在发布时覆盖更新的任期/投票。
- 这些关联用于本机控制适配与恢复，不新增上传回执、跨节点请求历史服务或逐 CDB 日志。旧操作的历史结果不要求永久查询，但未决任务及唯一恢复依据不能先丢。

## 六类语义操作

| 操作 | 必需输入及成功结果 | 成功仍不表示 |
| --- | --- | --- |
| 准备不可变快照/依赖对象 | 固定切点及内容关联；返回该对象与依赖已可靠保存的证据 | 已成为当前恢复基线，或配置/状态机已安装 |
| 保存协议批次 | 预期前态、日志追加/合法后缀替换、必要 HardState 更新及依赖；返回配套的可靠后态修订 | 已多数派提交、实际 apply，或旧写者已退出 |
| 发布本机快照基线 | 已可靠对象、切点/配置/边界任期及前态条件；在当前有序写入口保留更新的协议历史 | 可删除所有旧对象/后续日志，或可回退运行状态到快照切点 |
| 读取配套恢复视图 | 固定已发布修订、完整必要日志/协议状态和对象引用；所得组合有一致读取保护 | 仅凭内部自洽就排除整目录回滚，或读取本身可以恢复权限 |
| 封闭并收束写者 | 原写者身份及全部任务归属；分别报告新任务入口已封闭、底层在途修改已收束 | 任务成功、设备已隔离、存储历史必然可信 |
| 回收特定历史对象 | 精确对象/范围、替代恢复依据、当前引用检查；返回实际回收结果 | “允许回收”已等于实际回收，或不在当前目录中的对象必定没有读者 |

接收快照的权威切换属于配套协议批次，不直接套用“发布本机快照”并保留旧后缀。正文准备、权威发布、Storage 视图切换、实际状态机安装各自有完成点，仍按 P2 的保守顺序汇合。读取视图需保护必要对象直到使用结束；回收与旧读者/快照发送任务的生命周期保护由具体引擎证明，不能凭元数据中没有引用就删除。

## 操作结果与观察结果分开

| 结果类别 | 必须成立的证据 | 调用方处理 |
| --- | --- | --- |
| 未受理 | 该提交确定未进入任何可继续修改目标的队列或底层任务 | 不把它当提交成功；若业务重新发起，按当前授权及前态创建操作 |
| 条件不成立且未修改 | 前态检查拒绝，保证该操作不会再有后续修改 | 过时本机快照可安全放弃；必要 Ready 批次不能假 advance，须核对集成顺序并按故障出口处理 |
| 可靠完成 | 明确内容、后态修订及适用故障模型已满足保存契约；必要依赖全部可恢复 | 原周期仍有效且 Storage 视图已匹配时才确认该阶段；已停止实例只核对事实 |
| 明确失败 | 必要阶段无法完成；另报是否已无后续修改、哪些可靠前态仍能证明 | 不默认完全回滚，按影响分类；必要故障停止并核对，原周期不盲重试 |
| 仍在途或观察未定 | 已知任务未完成，或观察主体尚不能区分实际结果 | 等待/查询原关联，不重新提交；超时、断开、取消观察不转为“未受理” |

“可靠完成”通知必须带适用的准确操作身份与修订，不能仅凭较大序号替另一操作确认；旧实例通知不能直接推进新实例 A/Cd 或 Ready。同一原操作的重复成功可以合并观察，但失败通知与后续恢复事实须保留因果关系：历史已证实可靠，不意味着可以复活因失败已被停止的原实例。

观察端找不到某个结果记录，不证明该操作没发生。若已无精确结果，只能在旧写者收束后读取完整配套恢复组合，判定当前可恢复状态；不能借空查询结果重新执行旧操作。允许回收结果缓存不允许回收安全恢复必需的状态或未决任务归属。

## 写者退出的两个关口

[SQLite 具体退出顺序](control-store-sqlite.md#持有数据库的独占运行实例)采用稳定锁文件的进程期 flock、单数据库入口/连接及对象显式收束；锁最后释放，close_v2 或 interrupt 不单独构成完成。正文/引用可按 [DB3/DB4](control-store-transactions.md#四类权威事务)同事务保存，但可靠、RAM 可见及真正安装的三层结果仍不合并。
1. **封闭新任务。** 在同一接纳边界停止全部新修改：协议批次、快照对象写入/发布、后台回收及适配器内部重试。已排队但尚未开始的任务须明确不会再启动；仅关闭上层发送句柄不够。
2. **证明旧修改已收束。** 观察所有已交付底层任务达到不会再修改目标的终态；包含异步文件/数据库操作和后台工作，不以回调丢弃或进程退出通知替代该证明。具体实现若只能确认“当前不知道”，就保持未知。
3. 两个关口均成立、旧入口不会重开且存储排他接续有证据，才可创建新写者并读取可信恢复组合后启动。存储写者排他与旧成员身份不并存都要满足；新实例编号不提供物理排他。

收束不要求所有操作成功，失败但确定不会再改也可以收束；反过来，某批成功不代表整个写者已收束。进程崩溃/机器重启后的排他与底层残留写入，由实际存储设施的恢复语义另行证明，不能借“旧代码不在运行”直接跳过。这里不授权停止宿主、杀进程、卸载磁盘或变更设备配置。

## 验证切点

SCM01—SCM06 均未实现/执行，复用 SR/FD 而非新增已通过结果。

- SCM01：可靠保存成功、Storage 可读性切换失败、回调丢失分别注入；不假 P2，可信重启能恢复实际保存结果。
- SCM02：P2 与 LightReady 保存、旧实例/重复/冲突通知交错；不相互代替完成，正常两阶段有进展。
- SCM03：慢本机快照、最新协议保存与发布前态冲突；旧 term/vote 不覆盖新值，过时优化可以放弃后重新准备。
- SCM04：封闭入口后仍有后台对象写入/回收或底层未决任务；新写者不得抢先，全部收束后能安全接续。
- SCM05：未知结果查询为空、取消观察、旧结果缓存被回收；不推断未执行，不盲重试，可信恢复组合仍可恢复控制状态。
- SCM06：读者/发送任务固定旧视图与回收竞争；引用保护期间对象可用，释放且替代依据成立后可回收，不用永久保留一切作为唯一正例。
