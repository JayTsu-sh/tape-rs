# SQLite 控制库的可靠性与运行基线

关联：[研究 36](issues/36-control-store-sqlite-evidence.md) · [对象及事务映射](control-store-transactions.md) · [恢复组合](control-storage-recovery.md) · [停止并核对](control-failure-dispatch.md)

状态：依本轮自动接受授权采用、经 [36 限定研究](issues/36-control-store-sqlite-evidence.md#answer)核对的首版运行基线。仅规划，不安装 SQLite/Rust 绑定、不创建或迁移数据库、不修改 catalog。Rust 原生文件接口的要求保持；采用 SQLite 不代表全部内部依赖都是纯 Rust，也不把数据库加入每文件/每条 CDB 热路径。

## 引擎与事务政策

首版候选使用每节点本地的 SQLite 单库，`journal_mode=DELETE`、`synchronous=EXTRA`。SQLite 官方说明 DELETE 模式仅 FULL 在某些文件系统掉电后仍可能丢失最近已提交事务，EXTRA 另同步删除回滚日志后的目录；该配置仍依赖真实 VFS/存储正确履行同步。[SQLite 同步政策](https://www.sqlite.org/pragma.html#pragma_synchronous)

不选 NORMAL/OFF/MEMORY 日志来获得未证明的速度。WAL+FULL 是可另行验证的替代，当前单连接、RAM 协议读路径没有已测并发收益，首版不承担额外 WAL 检查点/回收职责。DELETE 的额外同步、完整快照事务耗时和恢复等待是明确接受的控制面成本，不宣称满足尚未填写的性能目标。

配置不是只执行一段初始化 SQL：每次实际打开连接均核验真实 journal_mode、synchronous、SQLite 版本/source-id、构建选项及运行限制。未知或不符时不开协议服务，不静默降级；历史库模式不符也不在正常启动中擅自转换。变更模式/版本属于受控维护与兼容性验收，不混入保存 Ready。

首个验证候选固定上游 SQLite 3.53.4，准确 source-id 与构建核对项保留在 36 报告；不是运行时接受任意“版本更高”的库。实施时重新核对安全公告并锁定实际链接产物，不能用命令行工具版本替代进程内版本，也不声称仓库现有构建已满足。[SQLite 3.53.4 发布记录](https://www.sqlite.org/releaselog/3_53_4.html)

首版单连接由唯一数据库工作入口持有，事务从 `BEGIN IMMEDIATE` 开始，检查准确前态、执行配套变更并显式 COMMIT。无变化不发空事务。禁止插件/运维连接、ATTACH、共享缓存、外部修改及自动维护写者；准备语句只能执行固定内部操作，外部输入绑定参数而非拼接 SQL。

## 持有数据库的独占运行实例

SQLite 的事务锁不能证明只有一个 Raft 实例使用该身份。首版在打开数据库及触发恢复前，取得稳定独立锁文件的 `flock(LOCK_EX|LOCK_NB)` 并持有至全部数据库工作收束；不能只在每次事务期间持锁。该锁是本机合作式互斥，不是磁带 fencing，也不是跨机器同身份克隆检测。[Linux flock](https://man7.org/linux/man-pages/man2/flock.2.html)

部署须提供本机受支持文件系统上的唯一控制目录/锁文件映射；不允许别名另锁、活跃目录替换、删除重建锁文件、复制同身份目录同时启动，或将其放到共享/网络文件系统。所有正常工具遵守同一入口；特权绕过或整个 VM 回滚不在本地 advisory lock 能排除的范围内，继续遵守 SG/09。锁不授予操作设备的权力。

锁描述符不向子进程泄露或被无关任务关闭。正常退出顺序为：封闭全部新任务和重试 → 使排队未启动项不再启动 → 等待活动数据库调用结束 → 结束事务、释放语句/BLOB/备份等对象 → 确认连接确实关闭 → 最后释放锁。实例重建不得以换一个锁文件规避旧任务尚未收束。

`sqlite3_close_v2` 返回成功可能只是延迟销毁的 zombie 连接，不能单独充当写者退出证明。适配需明确跟踪所有对象；常规关闭必须能证明没有遗留对象/活动调用，关闭失败继续持锁并受限，不靠 Drop 忽略错误。[SQLite 关闭语义](https://www.sqlite.org/c3ref/close.html)

## 提交错误与结果未知

| 可观察情况 | 首版处理 |
| --- | --- |
| BEGIN 因锁冲突返回 BUSY，尚未执行修改 | 保留未修改事实并调查非预期连接/所有权；必要阶段不能假完成，候选期限继续走时 |
| COMMIT 返回 BUSY | 可能仍有活动事务；不释放连接给下一项，也不当成未执行自动重做；按必要故障出口停权、封闭并在原工作入口核对/结束事务 |
| FULL、IOERR、NOMEM、INTERRUPT 等错误 | 结合阶段及事务状态判断；不由错误码断言所有修改已回滚，恢复前收束旧调用 |
| COMMIT 成功、通知丢失或 RAM 发布失败 | 已可靠历史不回滚；原周期不假推进，停止后按持久事实恢复 |
| 调用未返回、观察超时或取消 future | 仍在途/未知；不投递第二次旧批次，不提前释放终身锁 |
| 必要历史损坏或恢复组合不可信 | SG 受限；不删 journal、清库或回退整个目录继续旧 voter |

SQLite 某些错误只影响语句，某些会回滚整个事务；COMMIT BUSY 也不必结束事务。适配可以检查 autocommit 等实际连接状态来完成清理，但连接状态不证明底层掉电可靠性，清理成功也不复活已停止的原实例。[SQLite 事务及错误处理](https://www.sqlite.org/lang_transaction.html)

这里禁止的是盲重做业务/协议批次，不是禁止在原串行工作入口执行必要的显式 ROLLBACK 或资源清理。清理失败、底层仍可能修改时继续保持未知；不能仅发 interrupt 就宣布收束。无新入口/无活动修改/可信恢复组合全部成立后，正常故障恢复才可重建控制实例。

## 打开、恢复与物理假设

“只读核对恢复组合”指不修改应用层控制历史，不是承诺启动时以只读文件描述符打开 SQLite。崩溃遗留的 hot journal 由已取得独占运行权的 SQLite 正常恢复；不能人工删除它以消除报错。恢复阶段没有 Raft 输入/tick/竞选或设备副作用，恢复后再校验身份、格式、根/日志/快照及协议不变量。[SQLite 原子提交与恢复](https://www.sqlite.org/atomiccommit.html)

SQLite 结构完整性检查不能证明 Raft 业务闭包、正确成员身份或未发生整机回滚。内存状态只从可信根及连续必要日志重建，未提交后缀不提前应用；实际 A、Cd 及配置配套仍遵守原启动屏障。

目录初建/存储初始化的文件及命名空间可靠性必须在受控初始化流程落实，正常打开不能偷偷补造身份。数据文件与其恢复日志作为同一恢复集合管理；运行中不直接拷贝单个数据库文件作为可恢复备份，首版不隐含提供在线备份/还原能力。禁止自动 VACUUM、在线改 PRAGMA 或擅自删除辅助文件来腾空间。

真实持久化保证要求目标文件系统、VFS、块设备、控制器及虚拟化链路正确执行同步和写序；锁能否覆盖全部访问路径也须核验。PVE/EE3 的现有信息不足以证明这些条件，未进行宿主掉电、虚拟磁盘缓存或生命周期资格化；不将软件事务测试等同实机掉电验收。

## 容量与性能支持边界

完整快照正文采用同库 BLOB，受实际 SQLite 长度限制及进程内存预算约束；不得按理论数据库总大小推导单个快照无限大。编码、SQLite 绑定/复制、Raft Snapshot、旧读者引用及新 RAM 视图的峰值共同预算。[SQLite 限制](https://www.sqlite.org/limits.html)

日志压缩须在上限之前准备，不截断安全闭包。物理磁盘可用空间、数据库内部可复用页和 RAM 额度分开计量；删除行不承诺立即把文件空间还给操作系统。阈值留空，部署配置须提供并由后续测试核验，不能先承诺任意数量未决控制动作。

控制库变慢可以增加接管延迟，也可能让 RQ 过期导致安全停权，必须测量这些间接影响；“不逐文件入库”不等于对数据服务毫无影响。正常数据/索引 I/O 不新增数据库事务，不以削弱 EXTRA 换取未测吞吐。
