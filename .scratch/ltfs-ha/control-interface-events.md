# 控制故障验证的接口事件与证据契约

关联：[四条故障轨迹](control-fault-traces.md) · [控制转换](control-transitions.md) · [维护交接](maintenance-handoff.md) · [执行授权票据](issues/18-raft-execution-contract.md)

状态：既有协议的语义观察契约，未绑定实现、未执行验证。下列事件名是设计标识，不代表仓库已有 API，也不要求部署事件总线、永久审计服务或逐文件同步日志。本文不选择 Raft 库、存储引擎、线程模型及现场隔离设施。

## 事件由什么证明

每条观察须关联其适用的集群/配置、节点及实例、接管或维护过程、权限种类和动作/请求身份；有日志位置或快照切点时同时携带对应身份域。并非每种事件都包含全部字段；首次维护参选前不要求未来 term 或未来提交位置。请求关联不能代替具体日志条目身份，同一业务请求的重复提案须能分别追踪。

区分三种来源：负责该边界的组件实际状态、系统通过获准接口取得的证据、测试模型私有真值。测试观察钩子不是产品授权来源；组件打印事件也不独立证明它正确完成了持久化或物理隔离。模型可以知道效果已发生，但只在产品确能获取相应证据时交付给恢复逻辑。

按本机顺序和明确的发送/接收、提交/应用依赖建立因果关系。响应回调、事件采集和实际动作可能分离，须分别记录，不能按跨机墙钟或日志到达顺序重排已提交日志。

## 控制与存储边界

| 语义事件 | 成立条件及需要的证据 | 不能据此推导 |
| --- | --- | --- |
| `proposal.accepted` | 提案入口已接收指定请求，能关联其内容及后续处理；入队、拒绝与返回丢失分别观察 | 已持久化、已提交或已授予权限 |
| `control.persisted` | 明确哪些日志/协议状态及版本已达到所选存储约定的可靠保存条件；记录适用故障模型 | 本地保存等于多数派提交；普通 write 返回等于断电可靠 |
| `control.committed` | 所选 Raft 集成确认对应条目已提交，能核对条目身份、位置及协议所需持久化依据 | 提案成功回调等于提交；所有副本都已应用 |
| `control.applied` | 指定副本已按顺序完成确定性转换并推进实际应用位置；保存成功、条件拒绝或重复处理的结果分类 | 已投递 apply 队列等于已应用；条件拒绝可以跳过条目；历史 G 自动成为本机运行许可 |
| `snapshot.captured` | 快照状态及安全引用属于同一实际应用切点 S，可与配套协议元数据关联 | 构建开始位置等于完成内容切点；内容已经可靠保存 |
| `snapshot.durable` | 指定快照正文及声明覆盖的依赖达到明确可靠保存条件，未覆盖元数据须单列 | 单有正文就能被恢复程序可靠选中 |
| `snapshot.published` | 完整配套恢复组合已可靠发布，重启后可识别其身份、切点及所需日志/协议状态；外部必要证据依赖仍可核验 | 一次 rename、发布回调或最新文件名本身证明全部条件 |
| `history.reclaim_allowed` / `history.reclaimed` | 前者表明指定范围满足协议及证据保留条件；后者明确实际回收范围及替代恢复依据；区分允许、请求、实际不可用和回调 | 发布即允许删除所有旧状态，或回调未到表示旧状态仍可用 |

`control.applied` 的运行时状态生效与它是否另行落盘分别表达，不强制每条 apply 独立 fsync。恢复可依赖可信快照加所需日志，但不能把已丢失的运行时事件记录当成控制状态仍然存在。快照发布与日志回收是否持久、其崩溃窗口如何表现，须由后续存储绑定明确，不能由事件命名赋予保证。

## 资格、外部交付与维护边界

| 语义事件 | 成立条件及需要的证据 | 不能据此推导 |
| --- | --- | --- |
| `qualification.checked` / `gate.closed` | 记录当前实例检查所用轮次、K/G 种类、实际应用位置及安全依据；关闭须观察到派发入口实际受限 | 某次检查通过永久有效；本地停发等于旧命令完成或物理隔离 |
| `quorum.result` / `quorum.usable` | 前者仅表示收到关联 safe 确认结果；后者还须满足 RQ 的实际应用、原 t0 期限、当前上下文及旧期限未失效等条件 | 收到迟到确认可以复活旧许可，或需逐文件发起确认 |
| `dispatch.attempted` | 已进入指定外部边界的调用/交付尝试，关联单条设备命令或管理动作；标明具体边界层次 | 调用已进入等于远端已受理，也不能再直接宣称肯定未发出 |
| `dispatch.accepted` / `dispatch.not_accepted` / `dispatch.unknown` | 分别有该边界受理、确定未受理且不会被隐藏重试交付的证据，或无法区分；不同层分别报告 | SDK 入队等于设备执行；超时、连接断开或缺日志等于未受理 |
| `effect.observed` / `effect.settled` | 前者保存获准渠道取得的事实与来源；后者须证明指定动作不会再产生未约束的后续影响，保留其结果与范围 | 管理任务成功码等于持续隔离；取消被受理等于取消完成；动作收束等于目标已可重新准入 |
| `evidence.assessed` / `risk.recognized` | 记录来源及原动作关联的核验、对当前上下文的适用性结论；危险已被当前流程识别须与随后实际停发分别观察 | 收到原始响应等于完成核验；保存事实必须等到控制提交后才能停发 |
| `response.observed` | 指定观察主体实际收到结果，关联原动作与内容；发送、到达客户端及客户端丢失本地资料分别记录 | 未收到响应等于无效果，或旧结果可以直接开启新权限 |
| `maintenance.sealed` | 原维护上下文新派发确受约束；入口、排队/传输重试与服务端未决效果分别核验 | 工具退出或本地阶段值证明封闭；封闭允许撤掉物理隔离 |
| `handoff.verified` | 当前协调路径已核对必要控制转换的实际应用、维护封闭及相关效果安全证据，关联双方实例和范围 | 控制提交单独完成跨系统原子交接；旧工具必须继续在线才能维持新 G |

外部实际效果是独立事实，不必存在一个能即时返回它的产品接口。模型的 `effect.actual` 只供断言；现场若只能看到部分效果，保持相应未知范围，不虚构可查询的终态接口。一次动作已经结束但隔离仍失败，与动作还可能迟到生效是不同结果；安全结论需要逐项核对相关动作和持续屏障。

最后资格检查与外部交付之间的暂停窗口仍存在。语义事件不能将软件调用包装成物理原子操作；本地门控机制和外部隔离分别证明。已交付的单条命令按 LG 处理，迟到完成不授权后续命令。K 可以在 HK 条件满足后进行限定隔离协调，不要求先证明设备执行隔离全部完成；G 仍须自己的全部条件。

`handoff.verified` 是对组合条件的核验结果，不是唯一权威布尔值或一次永久资格。交接核验成功与响应送达可分别丢失；恢复须从仍可核验的控制记录和外部事实重建结论。已独立有效的新 G 不因旧观察工具缺记录而自动撤销，但任何当前必要安全条件失效仍按既有规则停发。

## FT01—FT04 的切点绑定

| 轨迹 | 必须独立控制或观察的事件 | 切点与断言要求 |
| --- | --- | --- |
| FT01 快照中断 | `control.applied`、`snapshot.captured/durable/published`、`history.reclaimed` 与重启实际读取的恢复组合 | 在可靠保存前、正文保存后发布前、发布后回收前/后分别崩溃；独立核对留下的对象和协议状态，不能只延迟回调冒充未持久化；旧运行资格不恢复 |
| FT02 旧授权重放 | `proposal.accepted`、`control.committed/applied`、`gate.closed`、资格检查及快照/结果回收 | 延迟实际 apply 与延迟 apply 通知是不同分支；严格保持固定日志顺序。条件拒绝仍推进位置，旧 apply 或响应均不得开放门控；有效新轮次可前进 |
| FT03 迟到隔离结果 | 动作原关联、`dispatch.*`、模型实际效果、`effect.observed/settled`、`gate.closed` 和当前派发 | 分别延迟外部效果、产品可见观察和回调；未知动作不重发，冲突不覆盖。识别危险后不等控制补录即停发；独立充分安全证据成立时允许正常推进 |
| FT04 维护交接丢响应 | `maintenance.sealed`、效果安全证据、所需 `control.applied`、`handoff.verified`、当前 K/G 及 `response.observed` | 已交接仅丢工具响应与交接未完成分别注入；起始超时外观相同，系统只用可见证据区分。不恢复旧维护权限；已有效服务与显式接续成功分别有正例 |

## 缺失观察如何判定

[DB/SB 场景](control-store-transactions.md#验证目标与剩余边界)增加 SQLite 实际版本/PRAGMA、锁取得/释放、原事务开始/提交结果、autocommit 状态、RAM 候选/发布、对象释放及恢复所选根。语句成功不当 COMMIT 成功，close_v2 返回不当写者收束，SQLite 自动恢复不当应用主动修改控制历史；失败或丢观察不盲重做原批次。DB/SB 均未实现/执行。
[竞选重叠 EA](election-overlap.md#事件与状态展示)分开记录 F/X/I/O/M/A/N：内部角色变化不能隐藏，但不等于被接受的可服务资格；输出来源、领取 Ready 与退回的合法切点分别核验。[组合 CSQ](permit-call-sequence.md#组合验证清单)另记录原 t0、真实 apply、P/W/C、旧/新来源上界与实际可用截止，以及当前检查和真实交付。Pending 使用旧绑定须保持保守，局部证据到期不得被观测器误标为共同 G 终止；EA/CSQ 均未实现/执行。
[故障源 SI 场景](fault-source-integration.md#验证目标)增加来源注册/交接、epoch 分配、事件正文可用、连续处理 H 与 Reviewed 发布；e+1 已处理不证明缺失的 e 无害。[TC 场景](runtime-clock.md#验证目标与环境证据)记录实际时钟调用/采样关系、时间域和环境生命周期，区分 Linux 挂起、VM 暂停/恢复及旧内存复活。没有独立生命周期证据不把来宾自检通过当作未发生回滚；均未实现/执行。

[RP/FS 场景](permit-representation.md#验证与完成边界)增加描述锁获得/忙/毒化、描述替换、token CAS 成败、锁内恢复、整轮 STOP、gate epoch 前进、Reviewed 审查起始/发布及实际引用释放。源端已获知、epoch 已前进、详细原因已处理、健康重新合格分别记录；缺失事件不假报已审查，诊断写入不成为关闭前提。RP/FS 均未实现/执行。

[首次与交接 AH 场景](activation-handoff.md#待验证的完整历史)另记录准备期入口实际封闭、固定 Dk、相关旧效果约束、G 首次证据、交接 P/W/C、K 退出及失败结果。一次队列空或一个 sealed 布尔值不证明持续封闭；交接失败不抹掉 K 退出。Pending 受限不作为精确抽象阶段查询，旧 K 到期与真实共同风险分别观察；AH01—AH06 未实现/执行。

[续期时间事件 E/P/W/C](renewal-time-evidence.md#四个时间不能合成一个接受时间)要求分开观察非时间证据准备、待核验发布、发布后取样和确认可用。[接受点细化候选](renewal-acceptance.md)另外记录精确 P 的证书、原/新截止、关闭竞争结果和实际读者返回：及时 P 不证明 C 及时，但完整成功历史可把 P 映射为接受；C 晚于新期限仅是历史确认。读者暂不派发、保守可用截止与真正终止分别记录，不伪报精确最新截止或终止完成。RT/RA 均未实现/执行，终止未被调度本身仍不赋予续期权。

[存储完成契约](storage-completion-contract.md)要求分别观察可靠保存、Storage 视图匹配、入口封闭和底层修改收束。[许可发布候选](permit-publication.md)要求记录当前修订、证据核验时刻、条件替换及读者实际使用；尤其核验时间与更新之间暂停跨截止的情况，不用一条“刷新成功”事件隐藏时间窗口。SCM/PU 尚未执行。

[故障与派发基线](control-failure-dispatch.md)要求另关联存储正常在途/明确失败/未知结果、原写任务收束、运行许可准备/发布/终止及恢复实例。诊断回调不是写者已停止的证据；上层入队或软件准备通过不称为底层已发出，旧观察未保存时也不冒充已持久化。FD01—FD08 均未实现/执行。

[资格同步候选](raft-rs-binding.md#资格发布失效代次与同步边界)要求另分源端发现、资格发布开始/完成、内核检查/完成和门控实际关闭。资格恢复不抹去失效代次，通知被合并不能让测试漏掉中间失效；按 EA 明确的可发布资格边界验证重叠，不能把未证明的内部瞬时保证写成通过。

“失效后没有新命令”需要覆盖指定实例、范围和观察区间内全部实际外部派发入口，包括适配器内部队列及重试；仅检查上层没有调用或诊断日志为空不够。无法证明观察完整时，该否定断言标为覆盖不足；若已观察到违规派发，则明确失败，不能因其他日志缺失改为未覆盖。最后检查后暂停再交付的分支须另查外部隔离保证，不隐含瞬时检测或不可实现的调用原子性。

测试记录丢失与必要控制持久化失败分别注入。前者影响验证证据完整性，不凭空新增生产日志满即全组停服策略；后者仍按 SG 和当前资格规则处理。验证结果同时保留安全断言、正例进展、实际命中切点、可见证据及未满足前提，不以一直拒绝所有动作算通过。

## 下一步的绑定清单

后续实现规格须对每个选定边界填写：实际负责组件/API、事件精确发生点、回调与完成关系、适用故障模型、恢复后查询方式、无法确定时的既有处理规则、故障注入及独立观察方法。不能观测的受理/终态保留未知；不能证明的可靠发布标为缺口，不补造接口。

优先绑定控制存储的保存/发布/恢复边界和 Raft 的提交/实际应用可见性，再绑定本地门控及外部交付；库和存储选择仍需独立证据。外部命令与管理任务的真实隔离能力、维护封闭机制由后续 09 的现场验证负责。上述绑定未完成，18 保持 claimed，09 不解除依赖。

[24 的固定版本研究](issues/24-rust-raft-binding-evidence.md)现已提供 raft-rs/OpenRaft 的具体接口对照，并明确两者全竞选门控的剩余责任；[优先验证 raft-rs 的顺序](issues/18-raft-execution-contract.md#已接受raft-rs-优先验证候选)已获用户接受。研究报告的 API 映射不是已实现绑定，存储产品和物理可靠性仍未选择或证明。

[25 的推进依据](issues/25-raft-rs-ready-election-evidence.md)及[单 Ready 绑定规格](raft-rs-binding.md)进一步对应了 Ready/LightReady、真实保存/应用和参选门控。事件字段仍是验证语义，不以规格形成代替实际同步机制、存储恢复或全入口测试。

[控制存储恢复草案](control-storage-recovery.md)进一步要求观察可靠恢复 commit Cd、完整快照 S、实际 A，以及启动中真实使用的 ConfState 和日志序列。SR01—SR08 将可靠保存、发布、实际安装、应用和回收拆开注入；原子批次、实际屏障及防整目录回滚能力均不能由事件名赋予。

本轮仅补验证契约，不新增产品裁定、不实现注入器或 Rust 接口，不运行模型及硬件测试；细粒度观察仅服务验证，正常性能路径不增加逐文件共识或同步诊断持久化。
