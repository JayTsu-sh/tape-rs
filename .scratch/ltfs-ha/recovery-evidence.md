# D02：卷发现、索引核验与安全追加的证据流程

关联：[提交契约](issues/04-durability.md) · [提交状态机](commit-state-machine.md) · [IBM EE 参考研究](issues/14-ibm-ee-architecture.md) · [地图](map.md)

状态：六步恢复逻辑流程及 IBM 参考适用边界已获用户接受，见[裁定记录](issues/04-durability.md#已裁定ibm-参考边界与恢复六步流程)；尚非完整 LTFS 恢复算法或实现。遵守不依赖 GPFS、磁带已提交状态权威、整组独占及外部隔离、无回执、不自动修复和读写分开开放的已定约束。这里的读取可能改变驱动器位置，仍须统一调度；“只读核验”仅指不修改介质内容，不表示可绕过设备所有权。

## 从指定 IBM 文档借鉴什么

参考用户提供的[EE V1.3.2.2 指南](</work/jay/tape-rs/IBM Spectrum Archive 企业版 V1.3.2.2 1.pdf>)，版本为 SG24-8333-09、March 2022；以下是原文事实，不是本项目已实现功能：

- §6.18（印刷页 201–202 / PDF 页 225–226）区分装卸/带库、元数据不一致、密钥服务及读写故障等状态，并提供 validate/replace 操作。可借鉴按原因限制能力，但不照搬状态名、自动清除条件或命令。
- §9.6.1、§9.6.3（印刷页 312–313 / PDF 页 336–337）分别处理掉电后的不一致介质和条码识别失败；其 LE 目录消失行为不能成为本项目返回普通“文件不存在”的依据。
- §9.3–9.4（印刷页 301–302 / PDF 页 325–326）的坏带处理涉及换带；其中 safe-remove 还依赖召回到有足够空间的 Spectrum Scale。这不是本项目无共享暂存的节点接管算法。
- §9.6.4（印刷页 313 / PDF 页 337）描述异常退出后释放设备的运维入口；不能把执行类似释放操作当作已经完成旧主 fencing。

这份指南没有在上述章节给出本项目所需的 LTFS 2.5.1 增量链发现、尾部分类及安全追加充分性证明。其“validate 后可用”不能被当作恢复算法；规范证据仍沿用[增量索引研究](issues/11-incremental-index-evidence.md)与[屏障研究](issues/13-final-barrier-evidence.md)，缺口须继续补齐。

## 已接受的恢复逻辑流程

每一步都输出可核验的事实和仍未知的条件，而不是只输出一个 ready 标志。后续步骤不能用缓存、目录可解析或某条命令成功替代前一步的证明。

| 步骤 | 输入与应形成的证据 | 不足时的处理 |
| --- | --- | --- |
| R0 获得安全执行资格 | 当前所有权及旧主隔离成立；目标驱动器/机械手身份与受管组一致；在途操作影响已经受控 | 不发正常读写任务，不以释放设备锁替代外部隔离 |
| R1 区分库存与卷身份 | 库存位置、条码和缓存只用于发现候选；实际读取卷标识及分区信息，核对卷 UUID 与预期目标 | 未装载、识别失败、介质身份冲突分别报告；不当成空卷、缺失文件或可自动格式化的介质 |
| R2 发现索引候选 | 从可信格式入口和经核对的定位线索发现 Full/增量候选，记录位置、类型、generation、依赖关系及读取结果 | 候选发现未完成时不声称视图最新；旧 IP 或本地 cache 不能直接成为最终恢复结论 |
| R3 验证完整依赖与恢复覆盖 | 验证索引构造、卷身份/指针、Full 基线及必要增量链；区分可恢复提交与未完成构造，确定依赖完整的恢复目标 | 缺链、冲突或无法排除遗漏有效提交时保持受限；不拼接不相容候选，不跳过缺口后宣称完整 |
| R4 建立可信已提交视图 | 由验证结果重建目录/文件映射及可重建 catalog；新视图与尚未验证数据隔离，覆盖范围可说明 | 只在当前视图与安全读取条件都成立时开放相应读取；不以旧目录给出误导性的不存在，不沿用 A 的执行队列 |
| R5 独立判定追加资格 | 进一步验证未索引尾部、实际位置、可写性、DP/IP 预算及本地执行状态 | 不满足则维持可证明的只读能力或恢复受限；若必须截断、补标记、覆写或其他修复，停止自动推进并报告所缺条件 |

R2/R3 不是“从头扫描全卷”或“只读最后一份 XML”的算法选择。具体入口、候选搜索范围、回指针处理、重复/损坏索引选择、停止条件和读错策略必须另有规范依据；这些未完成前不能将表格当成可执行恢复协议。R5 不因找到 EOD 或新主执行空同步成功而通过。

当前通过[索引链与安全尾部研究](issues/15-recovery-chain-evidence.md)补齐 R2/R3/R5 的资料依据。研究发现的具体候选步骤须分别标记规范要求、参考算法及本项目取舍，不因六步框架已接受就自动接受写入修复或更改故障范围。

## D02 细化：条件式快速定位与独立验证

本节快速定位前提、两类回指与正序重放方向已获用户接受，见[裁定记录](issues/04-durability.md#已裁定条件式定位与依赖核验方向)；尚未实现或实机验证。该接受不表示完整异常卷搜索或安全追加算法已完成。

### R2：VCI 只在前提成立时加速定位

LTFS 2.5.1 §10.3 给出通过介质辅助信息进行快速一致性检查的条件：所有分区 VCI 中的 VCR 都与当前有效 cartridge VCR 一致时，可利用最高 generation 的 VCI 定位当前索引；任一过期时，不能仅凭 VCI 判断整卷一致，需读取两分区索引比较。全零或全一的 VCR 不作为有效值。VCI、VCR 与文件请求身份不是同一概念。[SNIA LTFS 2.5.1 §10.3](https://www.snia.org/sites/default/files/technical-work/ltfs/release/SNIA-LTFS-Format-2-5-1-Standard.pdf#page=59)

据此提出以下项目处理：

- 恢复阶段核验身份、读取结果和全部必需分区的条件，不仅检查 IP 的一份 VCI，也不默认缺失字段等于零且有效。
- 满足快速路径前提只减少候选定位工作；仍须读取实际索引并验证结构、身份、引用及必要依赖。最高 generation 的 VCI 不是跳过索引验证的许可。
- VCI 缺失、过期或无法可靠取得时，放弃这个快捷判断，进入索引核验；不自动判卷损坏，不发布旧目录，也不为使 VCI 看起来匹配而写回 MAM。
- 这种核对在恢复/必要校验阶段执行，不为普通每文件准入新增设备查询。既有 MAM 后续维护策略不变，不新增每批提交必须更新 MAM 的成功条件。

VCI 更新本身也有先持久化索引与挂起写、再读取 VCR 并更新相应信息的顺序前提；不能先更新提示再把提示当作数据已经落带的证明。具体维护协议不在本节提前定案。

### R2/R3：发现范围与目标索引分别证明

定位到一份可解析索引，仅证明获得了候选。要称为当前已提交视图，还须说明该候选为何覆盖应恢复的状态，以及为何可以结束候选搜索。快速一致性条件不成立时，不能简单退回“最高数字”“第一次成功解析”或“固定 IP 位置”。

本项目候选校验应记录卷/分区与实际位置、索引类型和 generation、Full 与增量依赖、构造完整性以及尚未排除的候选/读错。相同 generation 的副本也须按格式关系核验，不能只用数字相等判定等价或随意混用。

### R3：分清两种回指，先核验再正序重放

| 信息 | 规范含义及候选处理 |
| --- | --- |
| `previousgenerationlocation` | 指向 Full，而非通用“上一份索引”；IP/DP 同代 Full 等特殊关系仍按格式规则核验 |
| `previousincrementallocation` | 指向最近 Full 之后的前一份增量；存在该前驱时应记录，历史遍历优先沿此指针，不能直接跳到 Full 而漏掉中间变化 |
| generation | 同分区随位置前进不得下降，但不要求每次恰好加一；合法代数跳跃不能直接被判为缺链，数字最大也不单独证明有效或当前 |
| 自指针与实际位置 | 不匹配的 XML 不能仅凭内容可解析被当作有效索引；构造边界、类型、卷身份及引用也须同时验证 |

格式规则依据 [LTFS 2.5.1 §5.4、§9.2.4](https://www.snia.org/sites/default/files/technical-work/ltfs/release/SNIA-LTFS-Format-2-5-1-Standard.pdf#page=26)；正序应用增量的说明见[资料性 Annex H](https://www.snia.org/sites/default/files/technical-work/ltfs/release/SNIA-LTFS-Format-2-5-1-Standard.pdf#page=99)。表格不替代这些章节的完整约束。

据此形成具体的候选处理顺序：

1. 先对目标候选及实际指向的依赖检查完整构造、读取结果、版本/UUID、分区位置、目标类型和代数规则；记录异常位置，不把读错当作正常链终点。
2. 目标为增量时，沿真实依赖收集至对应 Full，检测环、非法重复位置、方向异常及基线不一致；不得跨缺口拼接另一条链。具体合法指针关系由格式校验器决定，不用代数连续性代替。
3. 从 Full 开始，按最早依赖增量到目标增量的顺序构建隔离的候选视图；目标为有效 Full 时，其自身文件系统快照不因单纯存在历史而强制重放所有旧代。
4. 应用删除、替换、目录导航、重命名及属性/extent 更新时遵守增量文件系统语义，不采用通用 XML 合并。完成后验证对象及引用关系，再结合 R2 搜索覆盖证据判断是否可以发布当前视图。

以上只把依赖核验与重放顺序具体化，不证明候选发现已经覆盖所有更晚提交，也不证明任何尾部都能安全追加。Annex D 是完整卷示例，不能作为恢复算法；Annex H 的资料性高层流程也不能替代设备搜索与修复协议。

当搜索限额或等待预算耗尽而覆盖仍不明确时，结果只能是恢复尚未完成/受限；不能把截止时间变成“现有候选就是最新”的证据。预算和续检调度方式留空，不强行中断在途设备命令，也不默认无限扫描。

### R5：尾部检查不是自动修复

有效目录与安全追加位置独立判定。缺少结束标记、残缺索引、无法解释的尾部/读错或不能验证的 EOD 均不得由“再写一个标记试试”转成正常恢复；遇到必须改写介质的条件，停止自动推进并报告恢复受限。此处沿用既定不自动修复政策，不声称这些现象都能用同一办法修复。

即便设备能定位某个 EOD，也仍需证明追加不会破坏既有已提交状态及格式关系；书中运维工具或参考实现的修复步骤不是本项目自动执行授权。若当前视图及安全读取已验证而追加证据不足，继续按已接受原则只开放可证明安全的读取。

官方产品资料提供了需要特别避开的反例：IBM `ltfsck` 的 full recovery 会将未索引块恢复为介质上的文件，erase-history 可能使较新数据不可恢复，deep recovery 面向缺少 EOD 等异常情况。因此这些不是本项目“只读核验”的同义词，也不能作为自动 fallback。[IBM SDE：ltfsck](https://www.ibm.com/docs/en/storage-archive-sde/2.4.6?topic=ltfsck-checking-media-by-using-command)

**仍未完成的算法项。** 快速路径失败后的候选搜索范围与终止证明、完整依赖链重放的全部语义校验，以及目标设备上尾部分类/定位/追加的具体协议仍须进一步设计与验证。本轮已落实定位前提、两类指针及重放顺序，不把格式条款和资料性示例描述成覆盖任意损坏介质的恢复程序。

## 已裁定：快速路径失效后的有界只读搜索

用户回复“接受，继续推进地图”，确认本节有界只读搜索策略，见[裁定记录](issues/04-durability.md#已裁定有界只读搜索与停止条件)。算法和 SC01—SC05 验证仍未完成。

本节是本项目已接受的策略，不声称 LTFS 标准规定了这种调度。它细化 R2/R3 的工作选择与退出条件，不增加介质修复、持久回执、GPFS 或共享恢复数据库。

### 搜索顺序与覆盖记录

1. **固定本轮核验上下文。** 绑定有效所有权、卷 UUID、装载实例及可验证的介质状态。库存/缓存指向的位置仅成为待验证线索，不直接生成“已覆盖”范围；设备定位仍由唯一执行流程调度。
2. **优先核验已有线索。** 在位置及访问安全可判断时，先验证已知索引候选及其直接依赖，尽早得到可能可用的基线。找到候选不是停止理由；仅有向旧代回溯的完整链，也不能单独证明后面没有新提交。
3. **列出尚未排除的范围。** 分别记录 DP/IP 的已核验范围、可证明不影响目标选择的范围、未检查范围和读错/歧义范围。读取两个位置或找到一个 EOD 不代表其间所有潜在索引已经检查；一次跳转不能将跨过的区域自动标成已覆盖。
4. **补查影响当前性结论的区域。** 在安全和预算允许时继续获取证据。若无法证明可跳过某段，就不能用缓存或性能目标略过；缺少可信线索时，搜索可能需要扩大到更大范围，最坏接近分区遍历。具体从何处开始、如何识别与跨越记录/标记、如何验证边界，仍须设备协议与格式算法证明；这里不预选 CDB 或默认逐字节读取全部文件内容。
5. **评估结论或结束本轮。** 每次新证据到来都重新核对候选有效性、依赖完整性及尚未排除范围。达到以下完成判据才发布当前视图；否则受搜索预算与安全条件约束，保留未完成结果。

不要求读取每一份历史索引或全卷文件内容才能完成，但任何排除搜索范围的优化都必须有依据。例如已验证完整快照可以减少重放历史的工作，不代表它之后的区域可以不查。排除规则与候选比较器属于仍待实现/验证的算法，不靠“看起来更晚”或没有收到错误来证明覆盖。

### 区分成功停止与受限停止

| 停止原因 | 本轮可以得出的结论 | 服务及后续动作 |
| --- | --- | --- |
| 目标索引及全部必要依赖有效，所有可能改变当前性判断的范围均已核验或有可靠排除依据，且无未解决冲突 | 已形成当前已提交视图的恢复证据 | 再经过本地发布及读安全检查开放读取；追加写入仍单独经过 R5 |
| 搜索预算耗尽，仍有未排除区域或未完成依赖 | 本轮核验未完成，不是找到最新状态 | 报告进度与限制原因；不以候选旧目录回答正常文件查询，不因为达到时间目标就宣告恢复成功 |
| 读错、范围边界不明或互相冲突的候选无法解释 | 恢复受限，相关范围仍未知 | 保存可用诊断，不把读错转成正常终点，不自动补标记、改索引或调用修复命令 |
| 所有权或介质上下文失效 | 原上下文不能继续授权核验或服务 | 停止发出新设备任务；旧结果不得更新新主的视图、进度或预算 |

“搜索已完成”必须是可检查的结论，不能只用遍历循环结束或请求返回表示。单独的搜索完成也不证明所有文件数据都已读回校验，更不证明追加安全。

### 预算、进度与性能边界

- 候选数量、解析/重放内存、读取工作量和等待预算需要有界管理；具体数值、默认值和跨轮调度留空。达到边界时报告未完成，不删掉尚未核验的候选来挤出一次假成功。
- 在同一有效恢复上下文内，可复用已验证且仍然可信的证据，避免因短暂让出执行机会就从头重扫。后续核验必须重新验证上下文和实际设备位置；只有进度游标不足以证明前面已经安全完成。
- 跨进程/跨节点续用搜索进度不作为正确性要求，也不默认实现；不把局部进度变成需要复制的共享权威。即使保留诊断资料，新主也须重新验证其适用性，不恢复旧上传权限。
- 预算到期不缩短在途机械命令超时或授权强行中断。命令已经发出时，其结束/未知结果仍须按设备门控处理，不能同时启动冲突的下一轮。
- 广范围扫描只用于无法依靠可信证据收敛的恢复分支，不成为普通每文件上传或正常准入的工作。它可能显著延长接管，不能保证在固定 RTO 内完成；恢复验收应分别报告快速定位、补查和受限退出，不把它们混成一个平均值。

“线索优先、按覆盖补查、每轮有界且未完成不伪装成功”的策略已接受。搜索位置算法、范围排除规则、代数/分区候选冲突判定、设备终止状态和安全追加充分性仍待完成。该策略不承诺异常卷都能自动恢复到可写。

**新增候选验证 SC01—SC05。** SC01：旧缓存候选可读但后方存在有效新索引，不能提前成功停止；SC02：两个已读位置中间存在未查区域，跳转不能虚增覆盖；SC03：在任一预算点退出，未完成依赖/区域仍被标识；SC04：同一有效上下文继续核验可复用证据，换卷/换 owner 后旧进度不能放行；SC05：搜索结论成立而尾部追加条件不成立，只开放已验证读取。以上未实现或执行。

## 已裁定：首版自动恢复写入的尾部范围

用户回复“接受，继续推进地图”，确认首版支持范围及原卷可能不能立即恢复写入的可用性取舍，见[裁定记录](issues/04-durability.md#已裁定首版自动恢复写入的尾部范围)。首版只对已具备完整证据的尾部类型自动恢复新写入，不实现面向任意残留尾部的通用追加恢复器。这是项目范围选择，不是声称 LTFS 标准禁止在所有未索引数据之后追加；以后可凭新的协议及验证证据扩展类型，但不能靠现场试写来决定是否安全。

### 尾部类型与放行条件

| 恢复核验后的情形 | 首版处理范围 | 仍须满足的条件 |
| --- | --- | --- |
| DP 尾部为完整有效 Full，当前视图已验证，无未解释后续内容 | 可进入新写入放行检查 | 全部执行资格、索引/分区关系、真实追加位置、设备可写性、容量及本地状态检查通过；仅 Full 可读不够 |
| DP 尾部为完整有效增量，Full 基线及必要依赖已验证，IP 允许落后且无未解释后续内容 | 同样可进入放行检查，不仅因 IP 落后就永久只读 | 完整依赖及最新性证明、实际追加路径、必要 Full/IP 维护义务和预算均成立；不强制每次恢复先达到清洁卸载状态 |
| 最新有效索引之后存在尚未索引的数据，即使看似完整 | 首版不自动在该尾部后继续写，保留介质和可证明的读取能力 | 后续若要支持，须另行证明保留这些字节仍可合法追加、保持恢复语义及正确记账；本轮不默认删除、发布为文件或生成 lost-and-found |
| 索引或文件标记残缺，尾部结构/位置/EOD 无法确认 | 不自动恢复该卷写入；仅在独立读安全证据成立时提供读取，否则恢复受限 | 不自动截断、补标记或覆写；需要修复时明确报告，不以新写入掩盖修复动作 |
| 尾部类型在支持范围内，但容量、设备可写性或所有权等其他门控失败 | 仍不得放行写入 | 分别报告容量不足、设备限制或执行资格失效；不能将其统一解释成索引损坏或必须修复 |

“完整索引尾部”包括构造、实际位置及后续内容的核验，不是只看 XML 闭合或缓存的末尾标记。DP 尾部被认定可接受不代表 IP 的未知状态可以忽略；两分区的所需格式、维护与预算检查仍有效。识别算法与实际定位/追加命令顺序尚未验证，因此本表目前没有任何“已经实测可写”的行。

### 从只读恢复到新写入

按以下一致的顺序开放，不能在仅恢复目录后立即把全卷标成 writable：

1. 将已验证当前视图、尾部类型及位置证据绑定到同一卷和有效所有权上下文，确认没有未结束或结果不明的冲突操作。
2. 根据实际介质状态重建/校准容量保护和执行状态，保留必要 DP/IP 索引收尾义务，不继承 A 的授权额度或旧写头。
3. 在设备实际准备执行前，再核对当前所有权、卷身份、读操作后的位置及尾部证据是否仍适用。检查通过与新任务准入保持一致，不能让旧回调抢先把卷重新开放。
4. 仅接受新的授权工作，后续仍按通常容量准入、流式写入及合批持久化流程处理。恢复写资格本身不生成用户文件、不重放旧上传、不通过“试写一块”证明资格。

资格有效期取决于上下文与证据，而不是一个永久 ready 位。换卷、重置、所有权变化或无法解释的执行结果须使相关资格失效；正常读取引起的位置变化须由统一执行流程跟踪并在写前正确定位，不据此要求每次读取后都重扫整卷。具体一致更新方式仍留给实现设计。

### 可用性代价与范围

若 A 在文件数据流式写入途中掉电，即使 B 能恢复全部此前已提交文件，失败卷仍可能因未索引尾部进入只读/受限状态。已接受的首版范围因此不承诺“每次节点故障都在原卷立即恢复新写入”。这不推翻已提交状态恢复要求，也不意味着只要节点恢复就必须永久禁写。

其他已独立通过安全门控的卷可按既有规则继续工作；本节不新增自动选带、跨卷续传或故障任务重投策略。原卷重新开放需证据满足首版支持条件，或后续有明确授权的处置及重新核验；不默认引入修复能力，也不将 GPFS/共享暂存作为解决办法。

**候选验证 AP01—AP05。** AP01：完整 Full 尾部与全部门控成立时只开放新授权工作；AP02：完整增量尾部及旧 IP 的可恢复组合不因“非清洁卸载状态”被一概禁止，仍检查维护义务；AP03：当前视图有效但存在未索引尾部，首版不自动追加、不篡改旧提交；AP04：检查后换卷/换 owner 或收到旧完成通知，不能用旧资格放行；AP05：同一完整尾部下分别注入容量不足、写保护、位置未知，验证这些门控分别生效且不发试写。均未实现或运行。

首版自动恢复写入的支持范围及上述可用性取舍已接受。这个范围声明不替代每种尾部的充分性证明、目标设备命令协议、掉电验证或完整恢复验收；AP01—AP05 未执行，04 仍未完成。

## 恢复信息的权威与生命周期

- 当前恢复过程可保存来源位置、原始执行结果、已验证关系和未决原因，供核验与诊断；不因此向磁带写新日志、回执或私有索引，也不要求 A/B 同步这份运行记录。
- catalog 是从磁带已提交状态重建的副本，不变成 GPFS 元数据或共享数据库权威。已存在的缓存可作定位线索，但接受它之前仍须验证身份、覆盖和完整性；不默认全量删库或清理原数据。
- 所有权变化、换带、设备重置或新发现的证据使原结论不再可信时，相关证据不得继续放行操作。失效范围应由可证明的影响决定，不默认整个带库每次重扫。
- 文件系统状态恢复与旧上传请求结果分别处理。B 不凭恢复记录自动续接旧会话、恢复旧额度或重放未提交数据；应用安全重试接口仍由文件契约裁定。
- 配置、卷发现线索、访问权限及启用加密时的密钥仍须在 B 可用。“不依赖 GPFS”不意味着这些前提可以只存在于 A。

## 待验证情形

| 用例 | 检查重点 |
| --- | --- |
| RE01 库存/条码异常但存在旧 catalog 条目 | 明确识别/可用性未知，不返回空目录、无文件或自动覆盖许可 |
| RE02 缓存卷 UUID 与实际装载卷不符 | 拒绝混用缓存/索引与设备，不向错误卷写入 |
| RE03 有旧 Full 和更晚残缺构造 | 由算法区分未完成尾部与可能遗漏的有效提交；无证据时不静默回退，也不仅凭残片永久禁读 |
| RE04 当前已提交视图已验证，但尾部或容量未定 | 可以通过已接受条件开放读，不能因此开放追加写入 |
| RE05 恢复推进需要修复或出现旧主迟到事件 | 不自动修改介质；旧事件不能改变新主授权、账本或恢复视图 |
| RE06 合法 generation 跳跃，或较大 generation 的 XML 自指针错误 | 前者不因差值大于一判缺链，后者不成为有效最新索引 |
| RE07 仅一分区 VCI 新鲜，或 VCR 无效/缺失 | 不走全卷快速一致性捷径，也不把介质当无数据；转入进一步索引核验 |
| RE08 增量回指成环、缺失依赖或指向不相容 Full | 拒绝发布候选视图，不跳过缺口或混用基线 |
| RE09 多份依赖增量含删除/替换及属性变化 | 正序按文件系统语义应用，不以通用 XML 合并或只读最新增量代替 |
| RE10 搜索遇到读错、预算耗尽或未验证的更晚区域 | 不当正常终点，不发布“已恢复最新”的假成功，不自动补标记或调用修复命令 |

RE01—RE10 只是待实现验证要求，未执行模型测试或硬件操作。R2/R3 的完整搜索/链验证算法、R5 的安全尾部协议、时间预算及资源上限继续待定；不补填数值，不把 IBM 示例耗时或配置当本项目指标。
