# 控制存储的可靠发布与重启恢复草案

关联：[执行授权](issues/18-raft-execution-contract.md) · [控制转换与保留](control-transitions.md) · [单 Ready 绑定](raft-rs-binding.md) · [存储恢复研究](issues/28-raft-rs-storage-recovery-evidence.md) · [故障轨迹](control-fault-traces.md)

状态：依用户自动推进授权采用的恢复基线，未实现/执行。仅细化控制存储，不改变磁带格式、归档成功点或三节点成员规则；早期保持存储无关，现由 [36 后的 SQLite 基线](control-store-sqlite.md)与[具体事务映射](control-store-transactions.md)补齐引擎选择。不把文件缓存、上传暂存或磁带 index 当作 Raft 恢复依据。

## 一个持久业务基线，而非两套独立应用进度

首版候选采用：Raft 必需的日志和协议状态可靠保存；业务控制状态平时在内存中按顺序应用，仅通过同一实际应用切点的完整控制快照持久化；重启重放快照之后的已提交日志。暂不另建逐条持久化的业务数据库/applied 标记。这里的“业务”只指配置、接管、隔离和授权控制，不是逐文件元数据。

接受的成本是重启须重放必要日志、构建完整控制快照需要资源；不声称这是生产吞吐最优方案。SQLite 控制库已选为首版验证基线，快照频率、重放预算和空间额度仍待配置/测量，不能用任意固定保留期删除未决动作。控制快照与 LTFS Full/Incremental Index 是不同对象；选用完整控制快照不改变磁带数据分区增量索引方向。

这一选择消除“独立业务数据库已前进但协议历史没保存”的一类组合，不消除日志、HardState、快照及配置之间的一致性责任。以后若引入增量持久业务状态，必须重新证明其与 commit、applied、配置和恢复组合的原子关系。

## 配套恢复组合

| 组成或位置 | 本文限定含义 | 不能替代它的东西 |
| --- | --- | --- |
| 节点持久身份与历史关联 | 合法集群/成员及其存储历史；同一身份不得并存于两个活动实例 | 目录名称、网络地址或新进程 ID |
| 最新可靠 HardState | 按协议可靠保存的当前 term、vote、commit 等状态；后续保存必须继承未改变的必要字段 | 较旧快照携带的日志任期；发送者的投票 |
| S 与完整控制快照 | 同一实际应用切点的业务状态、位置/任期、完整 ConfState 及必要安全证据闭包 | 只有摘要、只有位置，或来自不同切点的配置 |
| 连续必要日志与边界任期 | 支持快照后恢复、复制与匹配；覆盖已提交部分，保留协议仍需的未提交后缀 | 将 last_index 当成全部已提交；直接拼接不同日志分支 |
| C、Cd、A | C 为内核已知 commit，Cd 为本节点可靠恢复组合证明的 commit，A 为当前实际应用位置 | 入队位置、快照正在构建的位置或 tape generation |
| 可靠发布关联 | 重启能识别当前快照与协议记录的合法组合，并知道哪些旧对象已被安全替代 | 最大文件名、最后修改时间或发布回调 |

正常运行的稳定切点采用 `S <= A <= Cd <= C`；日志后缀还可能包含 `C` 之后的未提交条目。此关系是本项目“提交依据可靠后再应用”的保守基线，不能当作任意 raft-rs 集成的强制规则。构建新快照时的目标切点与已发布 S 分开；接收快照切换中的临时状态不暴露为稳定视图，不能通过修改数字强行满足不变量。

ConfState 必须保留所选库需要的完整成员关系，包括可能出现的联合配置等协议字段，不能只存三节点地址表。重放业务状态与重放配置转换使用同一位置序列；当前运行配置不能任意混配较旧快照的 applied。`ConfState_S` 是本次从 S 重放的启动视图，不是要求运行中永久返回旧配置；运行配置随实际配置应用更新，对外生成的新快照仍须携带其自身切点的完整配置。Storage 不得直接套用假设 commit 全已应用且没有业务正文的内存示例来生成生产快照，依据见 [28](issues/28-raft-rs-storage-recovery-evidence.md#answer)。

## 可靠保存的最低契约

当前具体映射为[同库四类事务](control-store-transactions.md#四类权威事务)：日志/HardState/完整快照及引用不跨库，DELETE＋EXTRA 下的 COMMIT、RAM Storage 发布和实际安装仍分别完成。下述先保存正文再发布是一般顺序约束；首版同事务插入正文并发布引用时，两者可在一次提交共同可靠，不额外要求第二次快照 fsync。物理可靠性按 [SQLite 运行前提](control-store-sqlite.md#打开恢复与物理假设)验证。
[存储完成契约](storage-completion-contract.md)现分别定义可靠内容、Storage 视图、操作观察和写者收束的结果，以及准备/批次/发布/恢复读取/退出/回收的前态要求；本节的逻辑原子批次仍需由具体引擎证明。

要求未来存储适配器提供**可恢复的逻辑原子批次**：崩溃后只观察到满足前态及引用约束的完整记录序列，未完成批次不能只显现其中的 commit、后缀替换或快照指针。它可以由受支持的事务或经过验证的日志协议实现；本文没有宣称现有组件已经提供这种保证，也不批准自行实现一套 WAL。

- 批次所需日志内容与对应协议状态必须配套；冲突后缀替换遵循 Raft 已决定的范围，不回退已提交历史，不在恢复时拼接旧后缀与新分支。
- 大快照及其必要正文依赖可以先作为不可变对象可靠保存，再由原子批次发布引用；保存正文失败或发布失败都不能提前回收唯一恢复依据。
- 快照发布与普通协议保存由同一个有序存储写入口协调。慢速构建使用 S 时刻视图，但发布时不得把构建开始时的旧 term/vote/commit 写回覆盖更近的协议保存；过时快照构建结果不能覆盖更新的已发布基线。
- 只有达到声明故障模型下的可靠完成，才通知相应 Ready/提交/发布阶段。成功回调丢失与根本没有可靠保存必须分开；结果未知不伪报成功，不盲重做整批并复用已经失效的运行上下文。
- 若采用文件实现，必须另行给出文件内容、命名空间、引用发布及回收的可靠顺序和错误处理证据；单次 write、rename 或 CRC 不足以完成这份契约。进程崩溃与机器掉电分别验证，底层虚拟磁盘/宿主缓存也在故障假设内。

存储 API、记录格式/校验、具体屏障与故障模型是仍须补齐的实现规格，不能凭“原子批次”四字视为已完成。检测到必要控制历史失信时沿用 SG；未提交新工作的准入不足与已有可靠历史损坏不混为同一故障。

## Ready 与 LightReady 的持久化顺序

1. 按 P1 捕获完整 Ready 及其关联。P2 可靠保存本周期必要日志、HardState、接收快照及其配套发布；Storage 可读内容须与这份完成一致。没有变化不凭空写空批次。
2. 接收快照按下节完成实际安装后才满足 P2；随后 P3 调用 `advance_append`，保留全部 LightReady 输出。
3. 若 LightReady 给出新的 commit，在 P4 应用任何超过 Cd 的条目前，可靠保存该 commit 及其已有日志/快照依据，并维护当前 term/vote；不等待下一 Ready 再猜是否重报。这个保存属于当前控制周期，不插入 step/tick，也不抢用旧 HardState 整体覆盖新状态。
4. Ready 与 LightReady 条目按顺序实际应用，配置转换、空条目和条件拒绝都正确推进 A；然后按 P5 确认。没有新 commit/条目时不为周期性 RQ 确认增加业务日志或固定 fsync。
5. 快照捕获只选择已实际应用且 commit 依据可靠的切点。实际 apply 失败不推进 A；必要保存失败不确认完成，独立失效停发不等待存储恢复。

第 3 步可能增加控制提交的可靠保存等待，作为简化恢复证明的明确成本接受；不将其加入逐文件/逐 CDB 路径，不承诺可用一个 fsync 包含所有 advance 后才出现的工作。

## 本机生成与接收快照分开

**本机生成。** 从同一实际应用切点 Snew 取得业务状态、该点配置、日志任期及安全引用，构建时可让后续应用继续，但须证明视图不串点。先可靠保存完整新对象，再在有序存储入口发布其与最新协议状态、必要日志的配套关系。发布不是把运行中状态机回退到 Snew；也不是给 RawNode 注入一条远端 MsgSnapshot。仅在发布可靠且恢复依赖完整后才允许回收覆盖范围，后续必要日志与未决动作证据不得一起删掉。

**接收快照。** 由正常 Raft 输入路径判断是否接受，不由文件年龄或业务代码擅自替换。固定版可能拒绝过旧快照，或因本地日志匹配而仅快进 commit；这两种分支不能因为收到 MsgSnapshot 就安装正文。真正恢复并产生非空 Ready 快照时，日志视图重置到其切点；P2 将该快照、Ready 的日志/协议更新组成合法恢复组合，随后实际安装匹配的控制状态机和配置视图。旧本地后缀不能默认保留，只保留/追加恢复后内核认可的后缀。接收快照的边界任期不是本节点当前投票任期，不能借安装清空或回滚本节点 term/vote，也不泛化为“安装快照就清空整个控制目录”。

若发布已可靠但安装前崩溃，重启可以从完整新组合安装；若只完成正文而未发布，只使用仍完整可信的已发布组合。发布成功、实际安装失败时不假报 Ready 完成，也不能回退投票历史继续工作。重放或安装均只恢复历史，旧 K/G、截止点、ready、网络待发队列和维护派发许可不恢复。

## 启动顺序与故障出口

1. **关闭运行入口。** 新实例开始时禁止竞选、业务提案及外部副作用；不以旧 active G/维护状态开门。启动校验完成前不向网络承诺已能投票或处理复制。
2. **只读核对恢复组合。** 读取可证明的已发布基线及有序可靠记录，检查身份、完整性、引用、边界任期、日志连续性和 commit 覆盖。截断边界不能超过 S，`(S, Cd]` 不得缺日志；可靠后缀末位置不能小于 Cd。不能只挑最大的有效校验文件；更高位置未完成产物和已可靠发布后出现的数据损坏须分别判断。
3. **装入快照切点。** 安装同一 S 的业务状态和完整配置；准备最新可靠 HardState、必要日志及边界。持久投票不得退回 S 时刻的值。未知编码/缺失依赖不能静默丢字段继续。
4. **按匹配位置构建并重放。** 候选以 `Config.applied=S`、S 的 ConfState 和最新可靠协议状态构建 RawNode，再通过正常 Ready/配置接口按序重放 `(S, Cd]`，分批时连续推进实际 A。先不开放网络内核输入/tick/campaign，使启动不在中间旧配置上参与共识；空条目及已拒绝业务照常推进，不提前设置 applied=Cd。完整消费本阶段所有 Ready/LightReady、完成必要保存及实际应用，不预设恢复必无新输出。该顺序有 [28 的固定源码依据](issues/28-raft-rs-storage-recovery-evidence.md#answer)，具体适配仍待验证。
5. **恢复控制参与。** 到达启动时可靠 commit 切点且配置/状态一致后，才开放当前合法成员的正常投票/复制及后续追赶；未提交后缀保留为未提交，不自动应用。被合法移出的身份不得因磁盘里还有本机 ID 自动成为 voter。参选仍受 EG，运行 K/G 按新实例、新轮次及现实证据另建。

本地重放期间不开网络内核入口，是有界恢复工作的保守候选，不是控制健康但设备禁选的 Follower 长期停止投票。需测量重放时间及内存/调度成本；未知上限留空。可信历史正常恢复不要求人工，不能把所有旧快照重放都误判为 SG。

**允许回退的是快照选择，不是投票历史。** 仅当更旧快照加所需日志仍与最新可靠协议历史配套、能完整恢复时才可使用。较新已发布组合损坏后，不能随便回滚整个目录到旧组合“修好”；无法证明连续性则限制该身份并走显式受控恢复/替换。

**检查无法证明所有回滚。** 整目录/VM 快照整体回滚可能连同本地校验与代际一起倒退；同一身份被克隆也不是校验和可排除的。这里没有选择外部防回滚锚点或克隆检测设施，部署约束及证据仍待补齐。不能宣称启动检查已涵盖不可区分的整历史回滚，不能从磁带重建控制身份。

## 故障切点与进展验证

[存储故障与派发基线](control-failure-dispatch.md)进一步区分正常等待、未发布本机快照失败、必要保存/应用失败与历史失信；必要故障采用先停止并核对、排除旧写者后重建的出口，不在原 Ready 盲重试，也不将一次可恢复写失败等同于 SG。SR06/SR08 与其中 FD 场景合并核验，具体存储错误映射仍待适配。

SR01—SR08 均未实现/执行；复用 CS/FT01/SG/RB，不表示已有独立故障注入器。

| 用例 | 切点与安全断言 | 进展正例 |
| --- | --- | --- |
| SR01：正常重启跨配置重放 | S 后包含配置、空条目和业务拒绝，逐点崩溃；不混配新 ConfState/旧 applied，不重放外部动作 | 完整重放后当前成员可投票/复制，新授权按正常门控推进 |
| SR02：LightReady 新 commit | 在获得 commit、保存、实际应用之间崩溃；A 不先于可靠依据，恢复不 max 修补 | 保存成功后 Ready/LightReady 两组条目都应用，不丢后续输出 |
| SR03：本机快照发布 | 正文前后、发布前后、回收前后崩溃；后续 term/vote 更新不被慢快照覆盖 | 完整新或配套旧组合均可恢复，安全依赖无引用断裂 |
| SR04：接收快照 | 拒绝过旧、匹配日志仅快进 commit、真正安装分别注入；可靠发布、实际安装及 advance 分离，不回滚 term/vote，不保留未经内核认可的旧后缀 | 新组合可靠而安装前崩溃，重启仍能安装并继续追赶 |
| SR05：日志后缀替换 | 替换与协议记录中途故障；不拼接分支、不丢已提交依据、不应用未提交尾部 | 合法替换后复制与连续应用可以推进 |
| SR06：保存失败或完成未知 | I/O 错误、无结果、回调丢失、旧实例通知分别注入；不伪报完成，失效停发不等磁盘 | 可信恢复按已保存事实继续，不重发旧管理动作 |
| SR07：损坏与整体回滚 | 缺日志/证据、错身份/编码、校验失败、整体回滚和克隆分开；仅按系统可见证据判断 | 可信旧快照加完整日志可正常恢复；不可区分回滚记检测缺口 |
| SR08：容量和持续快照竞争 | 慢快照遇到新发布、空间紧张或旧读者引用；不逆向发布，不删除唯一依据 | 空间及替代依据充足时可回收并继续，不靠永久拒绝通过 |

测试须记录实际可靠批次、发布选择、恢复读取对象、配置序列、A/Cd/C、真实外部派发及可见证据，不只采集成功回调。具体存储格式、事务/屏障、日志回收与读者引用保护、启动恢复 API 对接及故障分类仍待实现规格；身份失信后的运维步骤仍按 SG/09 后续定义。18 保持 claimed，09 不解除依赖，本轮不操作实验室或真实控制目录。
